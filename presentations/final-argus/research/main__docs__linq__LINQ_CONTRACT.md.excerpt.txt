95: ## 5. Точность и потеря от квантования
96: 
97: - int8-квантование YOLOv8n даёт ощутимую потерю относительно FP32: лучший вариант 640 — recall 0.91, IoU 0.93, средняя разница скоров 0.05; потери — в основном объекты со скором у порога 0.25 (маленькие/частично видимые люди в толпе: на 000000000564.jpg 28 CPU-рамок против ~15 TPU).
98: - **Fake-quant на CPU (SDK `as_torch_graph` + `rescale`) совпадает с TPU практически точно** (recall 0.856 = 0.856, 0.907 = 0.907, 0.9375 = 0.9375). Подбирать квантование можно офлайн, без TPU.
99: - Что помогло: разрез перед decode (IoU 0.85 → 0.92), `activation_percentile=99.99` (recall 0.86 → 0.91). Хуже: 99.9, 99.999, `samplewise_percentile=99`.
100: - 960 даёт лучшие рамки (IoU 0.94) — важно для мелких объектов, — ценой ×2.5 времени.

102: ## 6. Рекомендация для адаптера `linq` в baseline
103: 
104: 1. **Обработка видео — внутри Jupyter**, схема «загрузка файла → удалённый скрипт → опрос → JSONL»: `tools/linq/run_video.py` + `remote/video_worker.py`. Это соответствует «не стримить», а пересылка тензоров до TPU идёт внутри площадки (162 мс против 3.7 с с ноутбука). 21 кадр/с — с большим запасом против «хоть 1 FPS».
105: 2. Прямой вызов API с бэкенда (через туннель) — только для отладки/одиночных кадров.
106: 3. Постоянный воркер в Jupyter — следующий шаг, если нужны частые короткие ролики (сейчас накладные расходы на запуск воркера и опрос — ≈2.5 с на ролик). Не проверяли, переживает ли detached-процесс рестарт пользовательского сервера Jupyter.
107: 4. Данность для baseline: программы `mosprom_det640_cut_ap9999_b1_o1_h1m.tpu`, `mosprom_pose640_cut_ap9999_b1_o1_h1m.tpu`, `mosprom_det960_cut_ap9999_b1_o1_h1m.tpu` лежат в `/auto/cache/hackathon70007/`; хвосты `*_tail.onnx` загружаются рядом с воркером (`mosprom_work/tails/`); формат JSONL: `{frame_idx, ts_ms, detections:[{cls, name, score, bbox_xyxy[, kpts:[[x,y,conf]×17]]}]}`.
108: 5. В воркере обязательно `OMP_NUM_THREADS=1`, `cv2.setNumThreads(1)`, onnxruntime intra/inter = 1, 4 запроса в полёте.
