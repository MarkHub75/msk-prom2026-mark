Дата исследования: 2026-10-23, около 06:51–06:56 Europe/Moscow (03:51–03:56 UTC). Роль: вторая волна, исследование первичных документов. Прочитаны исходные договоры, K001, W1_10/11/12/15 и handoff. DOC означает опубликованную документацию; OBS — фактически выполненное чтение/получение источника; INFERENCE — наш ограниченный вывод; PROPOSAL — будущий договор измерения; UNKNOWN — отсутствующий вход. ## Решение

**W2-01-F01 — DOC + INFERENCE.** Публичный путь завершённого локального inference существует: перечисление устройств → открытие выбранного устройства → загрузка `.tpu` → создание inference session → `inference.sync(...)` → полученный словарь выходов. Руководство прямо называет последний вызов блокирующим. Это уточняет W1-11-F02: неизвестен не сам факт публично описанного completion primitive, а его соответствие будущему пакету/устройству/удалённому сервису. Документ не даёт оснований называть TLM estimate измеренным аппаратным временем. [W2-01-S01, printed pp20–21 / PDF indices19–20]

Возможная будущая формулировка после реального выполнения: «Для указанного пакета и выбранного устройства получен результат блокирующего `sync` на сохранённых входах; длительность завершённого вызова измерена хостом». Она требует журналов фактического прогона и не равна утверждениям о чистом времени TPU, о выполнении всей видеоцепочки на TPU или о конкретной производительности. Сейчас подтверждено только наличие описанного пути.

## Timing и placement: допустимые величины будущего прогона

**W2-01-P01 — PROPOSAL, повторно использует W1_11/12.** Названия столбцов ниже — измерительные поля команды, не придуманный LinQ API.

| Величина | Единица / population / empty case | Что требуется и что остаётся за границей |
|---|---|---|
| TLM execution estimate | µs / отдельно для exact compiled model+input+simulation config; это не sample hardware distribution | Сохранить estimate как estimate. Перевод µs→ms арифметичен, но не превращает его в measured device latency. |
| Host completed sync duration | ms = same-host monotonic return−entry; N завершённых вызовов, raw samples; N=0→NA | Соответствующий API должен реально совпасть с S01. Внутренние copy/queue/runtime costs внутри call включены; pre-call work исключено. Ошибки/timeouts/unresolved имеют отдельные counts, не нулевые latency. |
| Remote completed request duration | ms = client output-ready−client submit; успешные unique logical requests, N и outcome ledger | Может включать transport/remote queue/host work. Job accepted не равно done. Remote SDK semantics пока неизвестны; public local sync не переносится на RPC. |
| Device execution interval | µs или ms по documented device timer, exact begin/end и measured workload | UNKNOWN. В S01 не найдено callable hardware timer/profiler API или границ аппаратного счётчика. Называемое в W1_15-S08 Performance Tools не заменяет такую инструкцию. |
| Advertised classifier latency | ms / vendor classifier claim | S04 имеет ≈2.3ms, optimization possibility1.5ms для ResNet50; это не наша модель, нагрузка, measurement protocol или event latency. |
| Event→delivered alert | ms или s / независимые GT episodes, matching и compatible clocks W1_11 | Требует video/evidence/temporal policy/delivery endpoint; вообще не измеряется простым `sync`. Misses/censoring сохраняются. |

Публичный manual различает compile target и реальную загрузку на выбранное локальное устройство. Это первичное основание для будущего **model-core** placement claim при actual matching SDK/device logs. Он не перечисляет per-op fallback/partition inspection, disable-fallback mode, signed device attestation или device profiler contract в inspected pp4–25. Не утверждаем отсутствие этих возможностей у производителя. Host pre/postprocessing прямо присутствует в примере, поэтому blanket claim «всё на LinQ» не следует даже из успешного sample.
