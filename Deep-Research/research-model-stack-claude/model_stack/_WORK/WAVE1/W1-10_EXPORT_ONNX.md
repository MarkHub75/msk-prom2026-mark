## Резюме для оркестратора

- Exporter Ultralytics 8.4.184 прочитан по коду и проверен экспериментом: ONNX строится **TorchScript-экспортёром** (`torch.onnx.export(..., dynamo=False)`), хотя у torch 2.14 по умолчанию `dynamo=True`; opset по умолчанию = **18** (маппинг `best_onnx_opset`, cap введён PR #25915 2026-08-24), минимально 9 (11 с `nms=True`); `onnxslim` по умолчанию включён; metadata_props содержит `names/stride/imgsz/task/end2end/args`.
- Реально получены 23 графа для YOLO11n / YOLOv8n / YOLOv5nu / YOLOv5su / YOLO26n при opset 9/11/12/13/17/18, simplify on/off, dynamic, 384x640, batch 4, nms True/None/False. **Все прошли** (`onnx.checker` full_check ok) и исполнились ORT CPU; сырые выходы совпали с PyTorch на одном кадре `bus.jpg` (max|Δ| box ≤ 8.4e-3 px, score ≤ 1e-5).
- Карта «что в графе / что снаружи» установлена для каждого режима (раздел 6.3). Сильнейшая цепочка для LinQ-первого шага: «статический вход 1×3×H×W, без NMS, opset 11–13» — либо дефолтный граф, либо (вероятнее нужен) граф **без decode** с 6 выходами, где DFL/anchors/stride/NMS уходят на CPU (это прецедент Hailo-экспорта в самом Ultralytics и NPU-форков).
- opset влияет на граф мало: при opset <13 Softmax получает axis=3 и лишние Transpose; при opset 9 Resize → устаревший `Upsample`, Split хранит `split` как атрибут. Всё прочее (88 Conv, 3 MaxPool, 2 Resize nearest/asymmetric/floor) идентично.
- `dynamic=True` добавляет Shape/Gather/Range/ConstantOfShape/Expand (анкоры строятся в графе) — плохой кандидат для фиксированного NPU-компилятора (inference). `batch=4` статический — граф тот же, батч просто в форме.
- Найдена важная разница пред-обработки: `.pt` predict использует «rect» letterbox (минимальный паддинг), статический ONNX — полный 640×640; это даёт разные детекции на одном фото (IoU до 0.84, иногда ±1 объект) при совпадающих сырых тензорах на одном входе. → W1-11/evaluation.
- YOLOX (`tools/export_onnx.py`, commit `6ddff482`): opset 11 по умолчанию, `--decode_in_inference` выключен по умолчанию → ONNX выдаёт сырые `[1,N,85]` (reg raw, obj/cls sigmoid), decode на CPU. YOLOv5 v7.0: opset 12, simplify off, decode (grid/anchor_grid) в графе, NMS для ONNX нет. torchvision SSDLite: полный граф экспортируется (opset 11/17) и исполняется ORT, но содержит 90 TopK, 180 NonZero, `If` с NMS-подграфом, динамические выходы и встроенный resize/normalize; «ядро» backbone+head экспортируется чисто (Conv/HardSigmoid/Relu/Clip/GAP/Reshape/Transpose/Concat).

### 6.3 Где что лежит в графе (YOLO11n default, opset 18)

- **Resize** ×2 (`/model.11`, `/model.14`): `nearest`, `asymmetric`, `floor`, scales `[1,1,2,2]` константа. Для int8-NPU nearest ×2 обычно самый лёгкий вариант (inference по общему опыту; для LinQ unknown).
- **Concat** ×21: каналовые в C3k2/C2f, в neck (FPN/PAN), плюс в голове: 3 по anchors (axis −1), `Concat_2` (xy‖wh), `Concat_3` (box‖cls) — **последний склеивает величины 0..640 и 0..1**.
- **Split** ×10: C2f/C3k2 `forward_split` (опция exporter: `m.forward = m.forward_split`, иначе получаются пары Slice — проверено в rawhead до правки: 16 Slice вместо 10 Split); в attention Split [32,32,64].
- **Slice** ×2: только в decode (box на lt/rb).
- **Reshape/Transpose**: 3 Reshape в голове на уровень (view(bs, C, −1)), DFL Reshape+Transpose, attention Reshape/Transpose.
- **Softmax+Conv DFL**: `/model.23/dfl/Softmax (axis=1)` + `Conv 1×1` с фиксированными весами `0..15` (`requires_grad=False` — ожидание дискретного распределения).
- **Sigmoid**: 78 штук — 77 в SiLU (`x·sigmoid(x)` = Sigmoid+Mul) + 1 на class-logits. Отдельного op SiLU/Swish нет.
- **Sub/Add/Div/Mul decode**: константы `anchors [1,2,8400]` (0.5…79.5) и `strides [1,8400]` (8/16/32) — зашиты как initializer'ы под конкретный imgsz (поэтому статический граф нельзя кормить другим размером).
- **MatMul/Softmax attention (C2PSA)**: на 20×20 (stride 32) → матрица `[1,2,400,400]`; при imgsz 1280 станет `[1,2,1600,1600]` (inference: квадратичный рост).
- **MaxPool SPPF**: 3× k5 s1 p2.
- **NMS-ветка** (`nms=True`): см. F17; **TopK/GatherElements/Mod** (YOLO26 `nms=False`): см. F09.

### 6.4 «Граф без decode» и что обязан делать CPU

- Прецеденты в самом Ultralytics 8.4.184 (source_code S03): Hailo — режет ONNX на 6 `cv*.{i}.2/Conv` и декодирует на хосте (+ `nms_postprocess` на CPU); RKNN — оставляет decode, но нормализует box на `[w,h,w,h]` для per-tensor INT8; ONNX INT8 — не квантует decode (только Conv/Gemm/MatMul); end2end отключён для форматов «without top-k support» (rknn, ncnn, executorch, paddle, imx, edgetpu, qnn). Форки (airockchip и т.п.) — у W1-02 (в его файле на момент проверки упоминаний не нашёл; не выдумываю).
- Наш raw-head граф (F20) делает то же, что Hailo-разрез, но на уровне PyTorch-обёртки (Sigmoid cls оставлен в графе; можно убрать). CPU обязан: (1) DFL softmax по 16 бинам × 4 стороны × 8400 анкоров (YOLO26 — не нужен), (2) ожидание, (3) anchors+stride, (4) порог по max-prob, (5) class-wise NMS (или для YOLO26 one-to-one — только top-k/порог, но тогда сам head one-to-one должен остаться в графе — это `nms=False` + `rawhead` по one2one-ветке, мы не делали). Объём на CPU: 8400×(64+80) float — тривиально.
- Почему опасна склейка в int8 (гипотеза для LinQ; известная проблема других NPU): при одной per-tensor шкале на `[0..~660]` шаг квантования ≈ 2.6 (uint8) / 5.2 (int8 симметр.), т.е. все вероятности 0..1 квантуются в 0 или одно значение — arithmetic inference; это ровно то, что пишут авторы Ultralytics (F18, F19). Кроме того DFL-логиты (−7..18) и YOLO26 ltrb (−0.5..12) имеют разный диапазон с cls (0..1), поэтому даже в raw-варианте **box и cls должны быть разными выходами** (так и сделано: 6 отдельных тензоров). Для YOLO26 Hailo-экспорт сам ставит 16-битные выходы — если LinQ строго int8 на выходах, для YOLO26 это повышенный риск (hypothesis).

### 6.5 Влияние параметров (local_observation, op_matrix.md)

- `opset` 11/12/13/17/18: графы почти идентичны; отличия — Softmax axis/Transpose при <13, Split атрибут vs вход (<13), Resize с пустым roi при 11; opset 9 → `Upsample`. Все проходят; min 9 без NMS.
- `simplify=False`: +29 Constant, +Shape/Gather, +Div — onnxslim сворачивает; размер почти тот же. Без slim граф всё равно валиден.
- `dynamic=True`: +Shape(11)/Gather(12)/Unsqueeze(17)/Range(6)/Cast(6)/Expand(6)/ConstantOfShape(3) — анкоры строятся в рантайме.
- `nms=True` + `dynamic` + `batch=4`: NMS разворачивается **по батчу** (4× NonMaxSuppression, 4× NonZero), т.е. батч в графе фиксирован (комментарий кода: «batch size needs to always be same due to loop unroll»).

## 7. Противоречия

1. **YOLO26 «NMS-free по умолчанию» vs 8.4.184.** Маркетинг/старые доки YOLO26 (релиз v8.4.0) — end2end; код ≥8.4.142 и docs сейчас — one-to-many+NMS по умолчанию (F07, F08, F09). Меняет: контракт графа и, вероятно, метрики (PR #26066 упоминает разные floor-метрики голов на COCO8-pose). Разрешение: всегда фиксировать версию и явный `nms=` в команде экспорта; → evaluation: метрики YOLO26 из таблиц сравнивать с указанием головы.
2. **Docs «opset: latest supported» vs код**: фактически 18 при onnx, поддерживающем 28 (cap PR #25915). Не ошибка, а определение «supported»; для нас важно: дефолт 18 ≠ «последний ONNX».
3. **torch docs (`dynamo=True` default) vs Ultralytics (`dynamo=False`)**: собственные экспорты (raw-head и т.п.) надо делать тоже с `dynamo=False`, иначе граф может отличаться от того, что даёт `yolo export` (не проверял dynamo-вариант — открытый вопрос Q6).
5. **W1-03: «YOLO26 uses end2end=True»** — верно для чекпойнта/архитектуры (есть one2one-голова) и для Ultralytics ≤8.4.141, но в 8.4.184 при экспорте по умолчанию (`nms=None`) голова one-to-many, end2end=False (metadata `end2end: False`, выход [1,84,8400]) — F09. Разрешение: фиксировать версию + явный `nms=`. Про разные размеры yolov8n.pt HF vs GitHub: я экспортировал только GitHub-assets, sha256 в S15 (yolov8n.pt 6 549 796 B, f59b3d83…).
6. **YOLOv5 v7.0 «просто запустить export.py»** не работает на свежем torch (F28) — нужен pin torch<2.9 или `dynamo=False`-обход; графы при обходе — TorchScript-экспортёр, как в эпоху v7.0.
4. **.pt predict vs ONNX predict различаются** на одном фото из-за letterbox (F21) — не ошибка экспорта; разрешение — сравнивать на одинаковом тензоре.
