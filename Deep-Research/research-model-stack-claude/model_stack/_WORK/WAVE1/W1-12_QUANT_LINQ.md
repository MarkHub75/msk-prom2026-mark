## FLASH

1. **Найден публичный операторский мануал фреймворка LinQ** — `https://files.lin-q.ru/tpu/docs/Framework_manual_H1.pdf` («ФРЕЙМВОРК IVA H1. Руководство оператора», RU.РМДВ.04.06.014-03 34 01, 2025, 27 стр.; ссылка «Руководство оператора. Фреймворк» на https://lin-q.ru/docs). Он описывает реальный Python API: `onnx_direct.onnx_to_tf` (ONNX → TF GraphDef) → `dnn_quant.QuantizedModel.quantize(original_graph_def, input_shapes, output_nodes, calibration_dict, percentile=100.0, …)` → `.qm` → `Network.from_quantized_model` → `compiler.compile_(…)` с пресетами `DEFAULT`/`STAGING`, `TPU_128x128_PARAMS` → `TpuProgram` → файл `.tpu` → `pytpu`: `tpu.Device.list_devices()/open()/load()/inference().sync(dict)`. Текст: `W1-12_files/Framework_manual_H1.txt`. (primary_documentation; → linq_platform — это их главный документ.)
2. **Следствие для квантования (primary_documentation + inference):** LinQ ожидает **fp32 модель (TF GraphDef или ONNX) + калибровочные тензоры** и квантует сам (DNN Quant, PTQ по калибровке, порог по `percentile`). ONNX сначала **конвертируется в TensorFlow** собственным конвертером. Путь «принести готовый QDQ/int8 ONNX» в документации **не описан** → готовить заранее QDQ-граф для LinQ не нужно; нужно готовить **fp32 ONNX (статический shape, batch=1) + ~100 калибровочных изображений с точно тем же preprocessing** (мануал: «Рекомендуемое количество образцов – 100», «предварительно обработанных так же, как и для обучения»).
3. **Квантованная модель batch-чувствительна** (фиксированный batch в графе), `input_shapes` в примере NHWC `(1, 224, 224, 3)` — после конвертации в TF раскладка NHWC (для YOLO из ONNX NCHW — что ожидает `input_shapes`, не установлено).
4. **Есть программный симулятор TLM** (`model_execute(executable, tensor_descriptions, input_data)` → `execution_time_us`, `output_data`) и «квантованная модель» исполняется в TF на CPU (`as_graph` + `rescale`) — т.е. при получении wheel `tpu_framework` можно проверять int8-точность и оценивать время **без устройства**. Спросить у организаторов wheel/доступ.
5. **Опубликованное измерение YOLO на LinQ** (презентация `https://files.lin-q.ru/tpu/pr/2026_linq_presentation.pdf`, стр. 4, «по методике MLPerf», i7-10700K, Ubuntu 24.04, **TPU Runtime 16.18.6, TPU Framework 2026.8.43**): LinQ HP batch 1: `yolo5s` 106,1 FPS / 23,71 ms; `yolov8n_pose` 104,8 FPS / 21,51 ms; `ssd_mobilenet_v2` 556,7 FPS / 3,54 ms; resnet50 432,9 FPS / 2,99 ms. Размер входа, классы, где делается decode/NMS — **не указаны**. Это первое публичное свидетельство, что YOLOv8-семейство (C2f + DFL-голова, pose) проходит компилятор LinQ (reported_measurement, детали unknown).
6. **LinQ HX содержит RK3588 (собственный NPU 6 TOPS, RKNN)** рядом с LinQ H — если выдадут HX, легко случайно запустить на RKNN; инференс по условию должен быть на LinQ TPU.
7. **Сторонний публичный репозиторий с реальной работой на LinQ HP1M/HPD1M**: `github.com/sherstpasha/linq-cv-bench@3ad1b7aa92a6b2fe057e60c36c6e03039ccaa140` (2026-02..04). Показывает **более новый API**, чем мануал: `from tpu_framework import onnx_to_tf, RegularModel, QuantizedModel, Network, TPU_128x128_PARAMS, TpuProgram, compiler`; `RegularModel(original_graph_def, input_shapes={in: (1,3,H,W)}, output_nodes=[out], anchors_mapping=mapping)` → `.calibrate(calibration_data=..., percentile=100.0)` → `.quantize(thresholds)` → `.save(...)`; `Network.from_quantized_model(q)` → `network.set_batch(b)` → `compiler.compile_(hardware_parameters=TPU_128x128_PARAMS, network=..., parameters=O1|O5|DEFAULT)` (`from tpu_compiler.compiler import O1, O5`). Автор отметил как «done» self-build ResNet-50 (O1, O5) и FCN-ResNet50 (O1) на HP1M/HPD1M; **детекцию** в финальный набор взял только **vendor-программу** `tiny_yolo3_b8_o5_128x128_asic.tpu` (вход `input_1:0`, `(8,416,416,3)`, NHWC, float32 0..1). Скрипты self-build YOLOv8s (`scr/detection/build_yolov8_program.py`, 500 калибровочных COCO, NCHW 0..1, один выход `output0`) есть, но в финальный план не вошли и не обновлялись с 2026-03-12 — **успех YOLOv8 через этот путь не подтверждён** (author_statement/source_code; inference об отказе — не установлено, почему).
8. **`.tpu` = ZIP с `metadata.json`**, где для каждого входа/выхода есть `user_shape/user_order/user_dtype`, `tpu_shape/tpu_order/tpu_dtype`, `scales`, `padding`; `pytpu` `Inference.sync(inputs, mode=ProcessingMode.FULL)` по умолчанию сам переводит пользовательский float32 → tpu int8 и обратно (режимы `RAW/PRE_PROCESS/POST_PROCESS/FULL`) (source_code, PyPI `pytpu==15.0.24`, 2023 — старше Runtime 16.18.6). Т.е. **вход/выход для пользователя — float32**, квантование входа делается рантаймом по `scales` из программы.
9. **Вендорский прецедент для YOLO2/3/4**: в `iva_applications` (PyPI 11.0.1, 2021) decode (`sigmoid`, `exp`·anchors, grid) и NMS делаются **на хосте** по raw-выходам свёрточных голов; препроцессинг YOLO4 — letterbox с заливкой 128, деление на 255 (float 0..1). Для старого IVA TPU (MLPerf v0.7, FPGA) вендор писал: «Matrix operations are performed in INT8, vector and element-wise operations are performed in FP16» — для LinQ H не подтверждено (HX datasheet: «int8 и векторные вычислители»).

## Резюме для оркестратора

- Главный сдвиг: вопрос «fp32 ONNX + калибровка внутри или готовый QDQ?» **закрыт публичной документацией вендора**: официальный операторский мануал фреймворка (W1-12-S04) описывает путь fp32 ONNX/TF → `onnx_to_tf` → DNN Quant (PTQ по калибровочным тензорам, параметр `percentile`) → компилятор → `.tpu` → `pytpu`. Квантование делает **сам фреймворк LinQ**; внешнего QDQ/int8 ONNX нигде не требуется и не описано. Команде не нужно заранее строить QDQ-граф под LinQ; нужно: fp32 ONNX со статическим входом, калибровочный набор (вендор рекомендует ~100 образцов, сторонний пользователь брал 500) с **точно тем же** preprocessing, и решение о том, где резать голову.
- ONNX внутри **переводится в TensorFlow** (`onnx_direct`/`tpu_framework.onnx_to_tf`) — значит реальный фильтр совместимости операторов = «что умеет конвертер ONNX→TF + DNN Quant + компилятор», а не ONNX opset сам по себе. Список поддерживаемых операторов публично не найден (unknown).
- Публичные свидетельства YOLO на LinQ: (а) вендорская таблица 2026 г.: `yolo5s` 106 FPS / 23,7 ms и `yolov8n_pose` 105 FPS / 21,5 ms на LinQ HP (batch 1, TPU Framework 2026.8.43) — вход и место decode не указаны; (б) мануал 2025 тестировал yolo2/3/tiny/yolo5s, но не v8/11; (в) сторонний бенчмарк linq-cv-bench (весна 2026) сделал self-build ResNet-50/FCN, а для детекции взял **готовую вендорскую** программу tiny_yolo3; его скрипт self-build YOLOv8s существует, но не доведён (не установлено, почему). → **YOLOv8/11 detect self-build на LinQ публично не подтверждён**, только yolov8n_pose вендором.
- Контракт ввода/вывода (pytpu, source_code): пользователь подаёт float32 и получает float32; квантование входа/деквантование выхода по `scales` из `metadata.json` программы делает рантайм (`ProcessingMode.FULL`). У вендорской tiny_yolo3: NHWC `(8,416,416,3)` float32 0..1. Self-build из PyTorch ONNX у стороннего автора: `input_shapes` NCHW `(1,3,H,W)`, 0..1.
- Чувствительность YOLOv8/11 к int8 (по первичным источникам других вендоров, **другое устройство**): общий выход `[1,4+nc,8400]` = concat боксов (пиксели 0..~640) и sigmoid-скоров (0..1) под один scale — Ultralytics прямо пишет, что это «rounds every score to 0» и поэтому исключает из квантования всё кроме Conv/Gemm/MatMul; Rockchip выносит DFL+decode на CPU и режет выходы на свёртках; Hailo тоже режет на 6 свёрточных выходах, sigmoid на устройстве, DFL/decode/NMS на CPU. Для LinQ нет механизма `nodes_to_exclude` в публичном API (есть только `percentile`), поэтому **самый надёжный вариант для LinQ — экспортировать «raw-head» граф (выходы свёрток box/cls по 3 масштабам) и делать DFL/decode/NMS на CPU**, как вендор делал для YOLO2/3/4 (`iva_applications`). Это гипотеза для проверки, а не установленный факт о LinQ.
- Локально (сторонний runtime ORT, не LinQ) — см. раздел «Локальный эксперимент».
- Главные разрывы: список операторов LinQ; поддержка multi-output; per-channel/per-tensor и симметрия в DNN Quant; где выполняются SiLU/Sigmoid/Softmax (int8 или fp16-векторный блок); есть ли смешанная точность/исключение слоёв; доступен ли wheel `tpu_framework` для локальной (TLM/CPU) проверки до доступа к устройству; на каком модуле (HP/HPD/HPQ/HX) и какой версии рантайма будет стенд.

| Место | Почему чувствительно | Источник | Что делать для LinQ |
|---|---|---|---|
| Concat box (px 0..640) + cls (0..1) в `output0` | один scale → скоры обнуляются | F21 (Ultralytics), F27 (наблюдение ORT) | raw-head (F28) или хотя бы два выхода (box и cls отдельно); проверить, сохраняет ли DNN Quant `output0` в float — unknown |
| DFL (Softmax по 16 бинам + Conv 1×16 с фиксированными весами 0..15) | softmax в int8, «unfriendly for quantization», медленно на NPU | F24 (Rockchip), F22 (Ultralytics QAT оставляет DFL в float), F25 (Hailo — на CPU) | выносить на CPU вместе с decode |
| Decode `dist2bbox`·strides, anchors (константы) | большие абсолютные значения, Sub/Add/Mul | F23, F24 | на CPU |
| Sigmoid скоров | маленькие значения у границы порога conf → дискретизация; при int8 выходе с scale ~1/127 шаг ≈0,008 | inference | cls-логиты отдавать до sigmoid, sigmoid на CPU (Hailo делает sigmoid на устройстве — F25) |
| SiLU (Sigmoid·Mul, 77–78 пар) | на старом IVA TPU поэлементные операции были в FP16 (F19) | F19, F10 | спросить вендора; если int8 — следить за ошибкой по слоям |
| C2PSA attention (MatMul ×2, Softmax) в YOLO11 | matmul активация×активация, softmax | F26 (наличие в графе); ORT-комментарий о крахе на uncalibrated attention Softmax (S14 `onnx.py` стр. 60–62) | если компилятор/квантователь не примет — YOLOv8 (без C2PSA) как запасной; вендор публиковал yolov8n_pose, не yolo11 (F09) |
| Маленькие объекты (каска/сигарета) | в 80×80 (stride 8) ячейках; ошибка в 1–2 px заметна относительно бокса 10–20 px; низкие скоры теряются при грубом шаге | inference; F28 (средняя ошибка 0,4–1 px на 2 картинках) | калибровка с кадрами, где много мелких объектов; оценивать recall по размерам (→ evaluation); не завышать `percentile`-клип для активаций, если он к ним относится |
| Вход 0..1 vs 0..255 | вход квантуется рантаймом по `scales` (F17); 0..255 с mean-subtraction (F07) или 0..1 (F16) — оба встречаются | F07, F16, F17 | брать ровно тот, что в `input_shapes`/калибровке; uint8-вход (как у Hailo) — unknown для LinQ |

### Сторонние инструменты: что дают и что ожидает следующий шаг

- **ORT static (QDQ/QOperator)** — даёт QDQ-ONNX для ORT CPU/TRT/QNN EP; калибровка через `CalibrationDataReader`; гибкие исключения узлов (F20). Для LinQ — только как **дешёвая локальная модель ошибок** int8 (какие слои ломаются, стоит ли raw-head), не как артефакт сдачи.
- **Ultralytics `quantize=8`** (v8.4.184) — ONNX: ORT static только Conv/Gemm/MatMul (F21); OpenVINO: NNCF (`nncf.Dataset(get_int8_calibration_dataloader)`, `int8_detect`/ignored scope для головы — exporter.py стр. 1290–1302); TensorRT/TFLite/IMX и др. — свои калибраторы по `data`/`fraction`. Ни один из этих форматов не является входом LinQ.
- **QAT (Ultralytics+ModelOpt, torch.ao/PT2E, Brevitas)** — дают Q/DQ-граф или fake-quant модель; LinQ принимает fp32 и считает свои пороги, поэтому QAT может помочь только косвенно (веса устойчивее к int8). Стоимость: дополнительное дообучение (≥ несколько эпох) + отдельный экспорт + повторная проверка на LinQ; в 45 часов оправдано только если PTQ на LinQ даёт измеримую потерю recall, которую не лечит raw-head/калибровка. Ultralytics QAT требует ModelOpt (NVIDIA) — на RTX 4070 возможно, не проверял.
- **Distillation/pruning** — в 45 часов не окупаются для int8-совместимости: размер модели и так мал (yolo11n 2,6M параметров), скорость LinQ по вендору ~105 FPS для v8n-pose (F09); pruning меняет граф и требует перекалибровки. Не рекомендую (inference).
- **MCT (Sony, Ultralytics IMX)**, Hailo DFC, RKNN Toolkit, TensorRT — не изучались подробно: это пути для другого железа; полезны только как прецеденты (F24, F25).

## Противоречия

1. **Python 3.8 vs 3.11**: сайт (S02) — «API языка Python 3.8»; мануал (S04) — «Python 3.11», лог в мануале — `python3.8`; S07 — venv311. Влияет на окружение, которое команда готовит. Разрешение: спросить у организаторов точную версию wheel/Python; не ставить заранее.
2. **API**: мануал — `dnn_quant.QuantizedModel.quantize(...)`; S07 (2026) — `tpu_framework.RegularModel(...).calibrate().quantize()`, пресеты O1/O5 вместо DEFAULT/STAGING. Разрешение: использовать документацию, выданную на хакатоне; держать оба шаблона.
3. **YOLO8/YOLO11 «поддерживаются»** (S01, S05) vs мануал 2025 (нет v8/11) vs S07 (self-build YOLOv8s не доведён, детекция — только вендорская tiny_yolo3). Вендорская таблица содержит yolov8n_**pose**, не detect. Разрешение: спросить, есть ли готовая/референсная программа или пример для yolov8/yolo11 detect, и в каком виде голова (полный `output0` или raw).
4. **Формат входа**: NHWC `(1,224,224,3)` в мануале (TF-модель) и вендорская tiny_yolo3 NHWC, но S07 для PyTorch-ONNX — NCHW `(1,3,H,W)`. Разрешение: в первом же тесте вывести `metadata.json` программы (`user_order`) — это прямой ответ.
5. **Платформа по умолчанию**: `as_graph(..., platform='64x64_fpga')` vs «128x128_asic по умолчанию» (S04 стр. 7). Для ASIC LinQ H указывать `TPU_128x128_PARAMS` явно.
6. **Latency в таблице S05**: единицы для anti_spoof_mn3/lenet5 явно не ms. Не использовать эти числа как latency без уточнения.
