# W2-E — TinyYOLO3: provenance, three-path parity and exact I/O

Assigned questions: K007 (main), K006 (TinyYOLO adapter boundary), K019 (artifact-specific rights). Historical team context: five experienced developers, 45-hour hackathon, mandatory LinQ inference. Actual investigation: 2026-10-23, approximately 04:52–05:03 Europe/Moscow (UTC+03). Network timestamps are in `_WORK/W2_E/FETCH_LOG.JSON`, `FETCH_EXTRA_LOG.JSON`, `PIN_VERIFY.JSON`, UTC. No account/access grant, LinQ SDK, compilation or device inference was obtained/performed. This is research plus small CPU-only artifact probes, not a submission prototype.

## Decision

**The three paths are not interchangeable as supplied.** Vendor `.tpu` remains an unprovided binary with an unverified original checkpoint/pre/post contract. It is a good candidate for an early hardware smoke test **only when supplied with its own known-good input/output/reference recipe**. Running the third-party RGB runner without that reference proves neither semantic correctness nor parity with Darknet.

W2 adds a materially stronger answer for the two public CPU paths: the real ONNX Model Zoo binary and the currently downloadable pjreddie checkpoint share **all 13 convolution kernels bit-for-bit and both final convolution biases**. However, Model Zoo embeds a different fine-head anchor mask, geometry correction, and NMS. Its actual graph also does not support batch2 in the tested evaluator despite symbolic `N`. Thus it is possible to prepare a controlled raw-head comparison using the downloaded checkpoint and the head-only boundary of Model Zoo, but **the original Model Zoo final boxes are not a strict Darknet baseline**. We did not generate/run the strict TensorFlow→ONNX export, so complete numerical parity of that actual export remains untested.

The most consequential new finding is not merely RGB/BGR: **the pinned Model Zoo binary uses fine anchors `(23,27),(37,58),(81,82)` = indices1,2,3, while pjreddie cfg, strict export metadata, the TPU runner and the old MIT TinyYOLO helper use indices0,1,2.** This originates in the linked `qqwweee/keras-yolo3` decoder source. [W2-E-F03/F04]

## Detailed facts and evidence status

### W2-E-F01 — What the vendor path actually proves

Type: source_code + unknown. Checked: pinned local source and new exact-name network searches, no vendor execution.

Repository commit `3ad1b7aa92a6b2fe057e60c36c6e03039ccaa140` (sherstpasha, 2026-04-03) provides `scr/detection/run_tiny_yolo3_vendor.py`, `run_tiny_yolo3_accuracy.py`, and `RUN_SCENARIO.txt` §§3.4/5. The code references an external `.tpu`, not a download endpoint or bundled artifact. The filename’s `128x128` must **not** be interpreted as image resolution: runner explicitly defaults416. Its compiler/hardware meaning is not established here. The filename `b8` is also weaker evidence than actual program metadata.

The runner’s discovery logic tries input aliases, missing-input exception text and auxiliary descriptors. For output decode it first tries rank3 tensors; if no candidate succeeds it takes the first two rank4 tensors and sorts their spatial height. These are heuristics, not a schema. Rank3 combined mode presumes pixel xywh and raw object/class logits, applying sigmoid to both; raw-head mode presumes actual raw logits and standard anchors. A supplied graph may already have sigmoid/decode/another coordinate convention. API success or plausible boxes do not validate those presumptions. It also always maps class indices through COCO80→91 even though `--num-classes` is configurable. This TinyYOLO seam reinforces K006; it does not resolve the separate Ultralytics runner investigation. [S01]

### W2-E-F03 — Checkpoint lineage established; not full numerical graph equivalence

Type: local_observation + inference. Checked: all13 conv kernel arrays and final biases compared directly, not model-name inference.

Model Zoo Conv initializers `conv2d_1/kernel:0` through `conv2d_13/kernel:0` are OIHW and exactly equal the corresponding contiguous kernel arrays read from the hashed pjreddie checkpoint. Both output biases `conv2d_10/bias:0`, `conv2d_13/bias:0` also exactly equal. Thus the alternative “these public branches use entirely unrelated learned conv checkpoints” is falsified for these downloaded bytes. This evidence does **not** extend to vendor `.tpu`.

The11 BN layers in binary have means0/variances1, transformed scales/offsets, epsilon≈1e−6. Strict exporter sets original gamma/beta/mean/variance on Keras BatchNormalization without explicit epsilon. A host algebra probe using source variance+`.001` gives maximum absolute effective-scale difference `9.5367431640625e-06`, offset difference≤`9.5367431640625e-07` across all layers. This supports transformed BN lineage, but `.001` was a tested hypothesis, not a pinned installed TensorFlow runtime contract. No claim of all-parameter byte equality or actual strict export numerical equality is made. BN epsilon/default version and exact execution still belong in the future parity test. Detailed per-layer measurements: `PARAMETER_COMPARISON.JSON`; code: `COMPARE.py`.

### W2-E-F04 — Fine anchors differ, with direct source provenance

Type: source_code + local_observation. Checked: real protobuf initializer values, graph connections, pinned upstream decoder.

Model Zoo initializer `TFNodes/yolo_evaluation_layer_1/Const:0` contains coarse anchors `[[81,82],[135,169],[344,319]]`. `.../Const_2:0` contains fine `[[23,27],[37,58],[81,82]]`, then Reshape_6 and Mul_7 multiply fine `Exp_1` outputs. This is not a documentation typo: it changes decoded sizes. For zero wh logits, e.g. first fine anchor width is23 instead of10 and height27 instead of14. The same raw predictions therefore yield different boxes before NMS.

`qqwweee/keras-yolo3` commit `e6598d13c703029b2686bc2eb8d5c09badf42992` (Phillip K.S. Chu,2018-07-30), `yolo3/model.py:196`, uses two-layer mask `[[3,4,5],[1,2,3]]`; cfg instead explicitly uses3,4,5 then0,1,2. Upstream source explains the binary’s decoder lineage. It is safer to call this **a proven recipe difference from the Darknet checkpoint cfg**, not claim an independently benchmarked accuracy defect. Model Zoo headline mAP0.331 is a card claim based on original Darknet model; it was not remeasured here and is not proof of this exact full-graph recipe’s AP. [S03/S04/S05]

### W2-E-F05 — Actual binary I/O, embedded limits and batch failure

Type: local_observation. Checked: protobuf plus CPUExecutionProvider ONNX Runtime1.31.0, tiny synthetic input, no timing benchmark.

The actual inputs use symbolic batch and unspecified H/W, despite card’s inference example `(1,3,416,416)`. Output annotations are `[1,?,4]`, `[1,80,?]`, `[1,?,3]`; third output is **int32**, after graph Cast of NMS indices. At416,b1 actual outputs are `yolonms_layer_1 (1,2535,4)`, `yolonms_layer_1:1 (1,80,2535)`, `yolonms_layer_1:2 (1,0,3)` on the chosen constant image.2535 =3×13²+3×26². No detections at embedded .6 on a synthetic image is not an accuracy result.

The original binary accepts b1 with float `image_shape=[[321,641]]`. b2 with `(2,3,416,416)` and `(2,2)` shape input fails at `TFNodes/yolo_evaluation_layer_1/Squeeze`: dimension0 must equal1 instead of2. Therefore **do not batch this full graph by trusting symbolic N**. Only the tested b2/geometry combination is an actual observed failure; it is not a general statement that every derivative/raw backbone is batch1-only.

Embedded NMS receives scalar initializers `max_output_size=20`, `iou_threshold=.5`, `layer.score_threshold=.6000000238418579`. The repo decoder can apply a second score threshold and global max300 afterward, but changing CLI `--iou-thres` never changes this node. Per-class cap20 also differs from global top300. Outputs boxes/scores remain dense candidates; NMS indices choose entries. Do not feed these output tensors to a raw-head decoder or apply sigmoid again. [S02/S06]

`HOST_PROBE.py` writes `HOST_PROBE_RESULT.JSON` and `GOLDEN_SYNTHETIC_RAW.NPZ`. It also creates an **in-memory head-only derivative** by retaining ancestors of two raw conv outputs, dropping image_shape input and exposing coarse/fine outputs. That derivative succeeded with finite `(1,255,13,13)` and `(1,255,26,26)` outputs. It is a diagnostic reference, not the original full graph and not an exported strict model. Initial shell command reported exit1 because native stderr for the intentionally caught b2 failure was redirected by PowerShell; the script completed and recorded both cases. A repeat with Python subprocess capture established actual process returncode0 (`HOST_PROCESS_RESULT.JSON`), preserving native stderr separately (`HOST_PROBE_STDERR_NATIVE.TXT`). No success claim for b2; it remains a caught/recorded runtime failure.

### W2-E-F06 — Color and geometry need separate contracts

Type: source_code + primary_documentation + inference. Checked: official upstream sources and inspected helpers; no vendor color test.

Darknet’s `image.c`/`image_opencv.cpp` load RGB: OpenCV path calls `rgbgr_image` after cv2-style loading, and stb path deinterleaves native RGB; unit range. The strict exporter loads the same kernel channels and never implements a color permutation. Thus its BGR sidecar is not supported by the primary checkpoint recipe. Model Zoo’s PIL recipe creates RGB padding and OpenVINO’s own model description explicitly calls original ONNX input RGB, while its **converted OpenVINO** variant is BGR. This is concrete evidence that color order is artifact-specific; quoting the converted OpenVINO setting for the ONNX input would be wrong. [S04/S07]

Repo vendor runner reverses cv2 channels; repo ORT helper does not, and does not read/use its `image_color_order` field in preprocessing. Both strict and downloader sidecars say BGR. For original Model Zoo bytes the ORT recipe therefore conflicts with its primary RGB recipe. **For vendor binary we cannot choose RGB over BGR**: it could be separately transformed, exported from another source, or require different calibration/input handling. Need the vendor manifest/golden tensor or a known-good reference output; a photograph looking plausible under RGB is insufficient.

Geometry also differs independently. Repo: OpenCV linear, rounded new dimensions, fill114. Model Zoo card: PIL bicubic, truncated new dimensions, fill128. Original Darknet letterbox: its own resize and fill`.5` in float, not exactly128/255. Do not call all these the same “letterbox”. Model Zoo graph’s inverse correction uses rounded new shape and floating half-offset like its linked Keras source. For original H321,W641 at416, floor pre yields H208 while rounded inverse geometry yields H208 too; other noninteger cases can differ by a pixel, and odd padding can differ by a half pixel from integer paste. Tests must log actual new shape and pad, not just `scale`.

The old MIT `yolo_correct_boxes` is yet another geometry: builds **xyxy**, then scales directly by the supplied tuple twice; it has **no letterbox offset/scale inverse**. Caller must supply dimensions in the matching xy order for that formula; we did not find a TinyYOLO-specific preprocessor proving the vendor caller’s intended order. This helper is not interchangeable with Model Zoo yxyx/original-image boxes or the new runner’s letterbox inverse. [S08]

### W2-E-F07 — Old MIT helper cannot be used unchanged as b8/custom-N decoder

Type: source_code. Checked: actual archive source and LICENSE, not installed/executed with TensorFlow.

`iva_applications-11.0.1/src/iva_applications/tiny_yolo3/postprocess.py:55–56` asserts first dictionary value shape `(1,13,13,255)`, second `(1,26,26,255)`; it relies on dictionary insertion order instead of explicit known output names. The wrapper accepts `num_classes`, but255 forces80 classes with3 anchors if reshape is to be valid. Removing asserts alone is insufficient: shared `yolo_boxes_and_scores` flattens boxes to `[-1,4]` and scores to `[-1,num_classes]`, and NMS operates per class with no separate batch identity. b8 could merge detections from different images. Source uses coarse anchors3:6 and fine0:3, xy sigmoid, wh exp, sigmoid object/classes, product scores. Defaults score.5,IoU.5,max20 per class. This is a versioned host-code reference only. The archive has no TinyYOLO-specific preprocess module; generic yolo2 RGB resize is a different module, not evidence of this `.tpu` contract. [S08]

## Golden tensors and future parity protocol

1. **Freeze provenance:** hash `.tpu`, original cfg/checkpoint, intermediate ONNX and compiler output; record version, target SKU, compiler/quantizer options and any input-channel/BN transforms. For vendor ask explicit source checkpoint hash, all user input/output names/dtypes/shapes, color/range, calibration preprocessor, output boundary and exact postprocessor. Do not infer these from filename or choose first rank4 outputs.
2. **Canonical image bytes:** include one legal non-square color image (red/blue distinguishable), a square control, and a synthetic ramp/checkerboard with odd dimensions. Hash decoded RGB array independently from encoded image bytes. Save original H/W, interpolation implementation/version, rounding, resized H/W, all four integer pads, fill value, normalization and dtype. Save both RGB/BGR alternatives as explicitly named probes when vendor contract is unknown; do not select winner by visual plausibility.
3. **Same numeric input:** construct one canonical unit-float NHWC RGB tensor; save `.npy` and byte hash. Derive contiguous NCHW with exact transpose for Model Zoo. For b8 vendor, repeat the same b1 tensor into eight slots initially and save each slot hash. Then test different images in slots to detect cross-batch decode mistakes. Padding the final batch requires recording duplicate slots and excluding them from quality/timing sample counts.
4. **Raw boundary:** compare strict NHWC coarse/fine heads against Model Zoo raw conv outputs transposed NCHW→NHWC. At416 expected `(B,13,13,3*(N+5))` and `(B,26,26,3*(N+5))`; exact names must come from artifact, not assumed. Record before-sigmoid logits, batch slot, head/anchor/cell/channel, min/max/finite; per-tensor max absolute, mean absolute and relative errors. Set justified tolerance per FP/quantized boundary; hashes identify bytes, not cross-provider numerical tolerance. The supplied NPZ is a CPU diagnostic seed, **not expected vendor output**.
5. **Decode once with shared specification:** sigmoid xy/object/classes, exp wh, standard coarse3,4,5/fine0,1,2 for the strict cfg; score product; explicitly choose xyxy pixels and one inverse geometry. Use the same class-aware NMS and limits for compared raw heads. To preserve original Model Zoo semantics instead, choose its fine1,2,3 and embedded .6/.5/max20 and compare a separately labelled recipe. Never silently mix these two baselines.
6. **Locate differences:** first same prepared tensor→raw logits; then raw→decoded boxes before NMS; then selected indices/boxes; only then a fixed licensed evaluation subset and timing boundaries. An AP/FPS delta between original Model Zoo full graph and current vendor runner mixes pre/decode/NMS/batch/checkpoint effects, so cannot be attributed to quantization/LinQ. A vendor smoke success still does not validate custom PPE training/import.

Host-only reproduction already done: run `python _WORK/W2_E/COMPARE.py` for checkpoint kernels and BN algebra; `python _WORK/W2_E/HOST_PROBE.py` for CPU b1/b2 and head NPZ, from research folder. Dependencies: numpy, protobuf, onnxruntime1.31.0; protobuf definition extracted from public onnx1.17.0 wheel via `GET_ONNX_PROTO.py`. A separate target-local pip onnx1.17.0 installation also finished, but scripts deliberately use the standalone saved protobuf definition, so no reliance on a vendor SDK or global onnx install. Re-execution can produce provider/version-dependent floating byte hashes; use numerical tolerances to assess, retain environment record.
