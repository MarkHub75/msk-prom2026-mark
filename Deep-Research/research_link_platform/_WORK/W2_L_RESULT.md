# W2-L — online control/data plane и граница видеосервиса

**K014, K017, K001, K020.** Исторический контекст: подготовка ночью 23.10.2026 к 45-часовому хакатону. Фактическая проверка этой ветки: 23.10.2026 приблизительно 05:05–05:11 MSK (02:05–02:11 UTC); точное время CLI GET 02:08:35–36 UTC сохранено. Это targeted research, без регистрации, отправки форм/сообщений, credentials, установки SDK, аренды, compiler job или LinQ inference. Пользователь не сообщил actual signup/SDK outcome. Общие файлы не менялись, делегирования не было.

## Решение

**Не выбирать SSH как обязательную архитектуру.** Обещание организатора устанавливает online-доступ к LinQ, но не его control plane или data plane. Публичный runtime API — локальный, а не спецификация сети соревнования. Облачный сервис у производителя имеет первичное публичное основание, однако endpoint/schema/custom upload/quota/session/persistence contract по новому поиску не установлен. Service-only способен закрыть задачу, если допускает собственную модель или согласованный `.tpu`, возвращает нужные outputs и имеет достаточный бюджет передачи/очереди. Это условное инженерное доказательство возможности, **не подтверждение наличия такого сервиса**.

И обратное: shell сам по себе не закрывает задачу. Он может не давать install/compiler, `/dev` permissions, long-running jobs, открытие портов, исходящую сеть или маршрутизацию к камерам. При shell без inbound-портов рабочий вариант — наш локальный UI/backend плюс worker, который инициирует разрешённый исходящий канал или получает задания через выданный job mechanism. Поддержка этих каналов должна быть отдельно выдана, мы не утверждаем их наличие.

**Что изменилось относительно W1:** повторно проверены official case/demo/software/cloud страницы; отсутствующие поля online contract локализованы в пять вопросов с развилками и минимальный единый эксперимент. Нового доказательства фактического режима конкурса не найдено. K014/K017 остаются открыты по actual limits; K001 не повышен до access granted; K020 получает владельцев/решающий gate. IVA CV API и deployment остаются отдельным продуктом.

## Confirmed versus conditional control/data plane

`Подтверждено` ниже означает документ/заявление; ни один remote route не исполнен. Артефакт команды, worker и backend не следует автоматически размещать на одном хосте.

| Route | Control plane: модель/compile/update | Data plane: кадры/результаты | Где worker и сервис команды | Status / решающее условие |
|---|---|---|---|---|
| R-L0: public promise | Не раскрыт | Не раскрыт | Не установлено | **Подтверждено только обещание** online LinQ inference, S01. До выдачи ничего не именовать endpoint/SSH. |
| R-L1: service custom model | Документированный upload исходного graph+weights и server compile **либо** upload matching `.tpu`; immutable model version, update readiness/rollback | Tensor/image calls с известными dtype/layout/limits и raw outputs; decode/pre/post согласно фактической схеме | Vendor runtime worker; наш backend/decoder/tracker/UI локально или на своей разрешённой машине | **Условно достаточно без shell.** Нужны Q1–Q4 и evidence Q5. Отсутствие compiler у клиента не blocker, если его функцию разрешённо выполняет vendor. |
| R-L2: service ready models only | Только catalog, custom update запрещён/не предоставлен | Готовые detections/events; tensor access может отсутствовать | Vendor model/video worker; наши правила/UI снаружи | **Условный ограниченный route.** Если нужные classes/outputs и правила конкурса допускают — интеграция возможна. Если нужен свой PPE graph и его нельзя загрузить, access формально есть, custom-model route блокирован; спросить альтернативную выдачу. Не объявлять generic detector эквивалентом PPE. |
| R-L3: shell/container + compiler/runtime | Graph/weights и compile на remote host при наличии поставки; либо перенос `.tpu` с другого совместимого compiler host; права записи/update отдельно | Local tensors через supplied runtime; video decode на host или доступном codec hardware | Worker remote; backend/UI remote только при подтверждённых lifecycle/ports; иначе backend локально | **Условно**, local API documented S06; факт shell/permissions конкурса неизвестен. Shell не гарантирует compiler, root, Docker, device permission или server lifecycle. |
| R-L4: job-only batch/file | Upload artifact/config и submit job по supplied documented procedure; persistence между jobs отдельно | Файл/набор tensor inputs → output artifact/log; deadline, queue и max payload определяют практичность | Worker lifecycle vendor job; local backend формирует/получает jobs | **Условно подходит для smoke/offline**, real-time только если bounded turnaround реально удовлетворяет задаче. Нельзя назвать upload whole video real-time автоматически. |
| R-L5: managed video service | Проектная model/config update, если разрешена | Camera/stream ingest и events; decode/tracking могут входить в service | Vendor video/runtime worker; наш UI/event adapter | **Условно**, нужен реальный supplied video contract. IVA CV S08 — пример отдельного продукта, не доказательство этой выдачи. Проверить camera reachability и timestamps, не дублировать decode без нужды. |

Все неподтверждённые limits: authentication scope/expiry; upload/file/model size и storage; per-team/device sessions; max in-flight, QPS и batch; queue timeout/cancel/retry/idempotency; compile queue и продолжительность; warm/cold lifetime, disconnect/restart; CPU/RAM/disk quota; persistent volumes/retention; inbound/outbound networking/proxy/VPN; codecs/camera count; logs/model-to-device correlation. **Ни одного численного лимита источники не дают.** Значения типа QPS/ports/session TTL не придумывать.

Service-only особенно рискует на передаче raw tensors, если API не принимает compressed frames/video. Пример исключительно нашей арифметики: один `1×3×640×640` float32 tensor = 4,915,200 bytes, восемь камер по10fps =393,216,000 bytes/s без protocol overhead. Для uint8 при том же shape:98,304,000 bytes/s. Это **не shape/model/fps требования и не измерение LinQ**; иллюстрирует необходимость Q2/Q3. JPEG/video уменьшают передачу, но только при поддержанном codec/decode, с отдельным влиянием на качество. Shell при decode на remote host не решает сетевую недостижимость камеры.

## Наш queue/timestamp/frame identity contract — рекомендация, не функция LinQ SDK

Назначить **одного владельца video/control adapter**. Он потребляет общий model manifest и golden input/output спецификацию от model/runtime владельцев, а не делает второй exporter/inventory. На границах сохранить:

- `camera_id`, уникальный `stream_epoch` после reconnect и монотонный внутри epoch `frame_seq`; tuple — frame identity. Отдельно `request_id/job_id`, `model_version/artifact_sha256`, preprocess/config hash. Это наша schema; vendor поля могут называться иначе и связываются adapter mapping.
- Source PTS + time base, если источник их даёт; local receive/decode-ready/enqueue/submit/result/event monotonic times; UTC wall time для журнала с отметкой clock source. Не вычитать часы разных host без known offset/synchronization. Capture-to-event нельзя заявлять, если capture timestamp неизвестен; тогда честно receive-to-event.
- Геометрия: original size, resize/letterbox scale/padding, crop/rotation; mapping outputs обратно к source frame. Tracking получает source timestamp и реальный gap после drop, а не считает каждый результат соседним кадром.
- Очередь finite по count/bytes и age budget; значения выбираются после Q3 и измерения. Для live alert при перегрузе предпочтителен свежий кадр: заменить устаревший unsent кадр той же камеры, записать reason/count. Для offline evaluation отдельный no-drop режим; не смешивать его FPS/quality с live sampling.
- Глобальный in-flight ≤ supplied quota; bounded per-camera pending и fair dispatch, чтобы активная камера не вытеснила остальные. Batch formation имеет deadline, padding/real-count по model manifest; не ждать медленную камеру бесконечно. Это policy команды, не характеристика vendor scheduler.
- Начать с одного владельца runtime session и serial submission допустимо как консервативную политику команды до ответа о concurrency. Это не аппаратное требование one-process-per-device: исторический код S09/S10 содержит параллельные descriptors. Повышение concurrency проверять на actual release по correctness/isolation и разрешённой quota, не по старому TODO.
- При timeout результат может появиться позже: сопоставлять по identity, не добавлять старую detection к новому кадру; discard stale outputs с журналом. Retry только по documented semantics и лимиту, дедуплицировать event delivery локальным event key; не считать HTTP timeout доказательством отмены compute.
- Reconnect создаёт новый epoch; после model activation новый version boundary. Не смешивать old/new output в одном tracker state без явного перехода. При несовместимом class/geometry contract reset/перепривязка state — решение владельца модели/правил.

Метрики по каждой камере: ingress/source cadence, sampled/dropped/processed count, queue wait, network/serialization, vendor call (включает неизвестный internal queue если нет timestamps), inference только при отдельном trustworthy timer, postprocess, frame age и event delay; p50/p95/p99 и cold/warm отдельно. Суммарный accelerator throughput не подтверждает freshness/fairness видео.

## Один решающий будущий эксперимент, владельцы и stop conditions

**W2-L-E01: custom model update + correlated frame roundtrip без обязательного shell.** State сейчас: нужен ответ постановщика и actual service/device grant; SDK нужен только для выбранного route. Сейчас можно подготовить manifest/schema/checklist; нельзя выполнить integration probe.

Prerequisites: Q1–Q5, supplied documented client/job command (не наши invented endpoints), поддержанный artifact или matching compiler+custom example, общий golden tensor/frame с CPU reference и expected raw-output contract, разрешённая сеть, model/version/device evidence mechanism. Известный vendor binary — полезный optional smoke, **не обязательный**, если старт возможен с compiler+custom example и reproducible reference.

Владелец control/video adapter выполняет только transport/lifecycle часть; environment владелец выдаёт release manifest, model владелец — immutable artifact+golden, runtime/observability — подтверждение LinQ; video владелец сопоставляет identity/latency. Не дублировать их numerical validation/компиляцию.

1. По supplied процедуре зарегистрировать/загрузить V1 с hash и дождаться explicit readiness; один и тот же golden input передать с identity, сохранить raw outputs/request correlation и runtimes/logs.
2. По официальной update процедуре активировать V2: это иной известный artifact/weights hash с ожидаемым reference output либо документированно новая model version. Проверить фактическую привязку результата к версии; изменение случайного request label не доказательство update.
3. Отправить короткий конечный replay из двух источников с разной cadence в пределах разрешённого лимита; проверить frame association, bounded queue, stale/drop журнал, максимум in-flight. Эскалация нагрузки и длинный multi-camera soak — следующий video/performance gate, не часть минимального доступа.

**Success:** собственный разрешённый artifact реально исполняется, raw outputs совпадают с согласованным tolerance, V1/V2 различимы по model lineage и device-backed evidence; timestamps/identity не теряются. Если service-only проходит, необходимость SSH для этой архитектуры **опровергнута**. Не доказаны full PPE quality, устойчивый8-camera throughput, допустимость всех host stages или arbitrary model compatibility.

**Альтернативы/stop:** catalog-only без нужных outputs → R-L2 либо другой официальный grant; compilation unsupported/queue не укладывается в принятый командой бюджет → обратиться к согласованному compatible example/route, не менять вслепую exporter. Shell есть, но network/lifecycle нет → external backend + permitted job/pull route; если ни один путь своевременных кадров/результатов не разрешён, real-time branch заблокирован данным доступом. Не назначаем «30–60 минут» измеренным свойством: срок остановки задаёт команда с учётом45часов и фактически измеренной очереди. Успешный generic vendor smoke без custom update не закрывает K014.
