# W1-12 — Vast.ai: RTX 3090, наблюдаемые офферы и полная стоимость

Дата исследования: **2026-10-23**. Контроль времени инструмента: 17:02:29 UTC, то есть 20:02:29 Europe/Moscow; публичные API-снимки получены 17:04:35–17:04:37 UTC / 20:04:35–20:04:37 МСК. Это реальное наблюдение read-only интерфейса, без входа, токена, аренды, платежей и изменений аккаунта. Обучение, экспорт, GPU benchmark и LinQ inference не выполнялись.

## Решение прежде деталей

**Vast.ai остаётся практическим кандидатом для обучения, но закупочная единица — конкретный оффер с диском, сетью и сроком, а не «3090 по фиксированной цене».** Публичный endpoint реально вернул 1× и 2× RTX 3090 с `gpu_ram=24576`, `rentable=true`, `rented=false`. Это наблюдаемая доступность в момент ответа, не резерв и не гарантия будущей цены. Для команды разумна первая проверка **одной on-demand GPU**, затем решение о второй по измеренному time-to-result и стоимости. Это рекомендация исследователя, не уже выполненная закупка [W1-12-F01–F04].

Не выбирать автоматически минимум: предварительный поиск без reliability-порога показывал verified-хосты около 75% исторической надёжности и ограниченную мощность GPU. Формальная верификация не равна надёжному выполнению именно нашей задачи. Цены ниже относятся только к повторяемой выборке reliability ≥99%, 100 GB и on-demand. Финальная нейросетевая обработка по условиям команды должна работать на LinQ; успешная тренировка на CUDA ничего не доказывает о CPU/TPU LinQ [W1-12-F05].

## Как считать до покупки

**W1-12-F04. Формула для конкретного оффера (собственная бухгалтерская модель).** Пусть `G` — ставка compute за **весь оффер**, `D` — выбранный размер, `Srun(D)`/`Sstop(D)` — почасовой storage в соответствующем состоянии, `Trun`/`Tstop` — часы, `Vin`/`Vout` — оплачиваемые единицы TB, `Bin`/`Bout` — сетевые ставки. Тогда:

```text
C_vast = G*Trun + Srun(D)*Trun + Sstop(D)*Tstop
       + Bin*Vin + Bout*Vout
       + Σ(volume_hourly_i * volume_billable_hours_i)
C_project = C_vast + external_storage + external_egress + payment/FX/tax_if_applicable
```

Не умножать `G` ещё раз на число GPU, если взят `dph_base` multi-GPU оффера. Не добавлять storage повторно к `dph_total`: у снимков `dph_total = dph_base + storage_total_cost = search.totalHour`. В ответах `search.diskHour` и `instance.diskHour` совпали; `instance.gpuCostPerHour=0` — это структура расчёта оффера, **не доказательство состоявшегося stopped-инвойса**.

`storage_cost` имеет подпись CLI `$/Gb/Month`. Для 100 GB во всех шести строках наблюдается `storage_total_cost = storage_cost * 100 / 720`. 720 — восстановленный из этих ответов расчётный месяц, не календарное обещание и не основание игнорировать разные stopped-тарифы. Для точного расчёта предпочтителен готовый `diskHour` для нужного D. Код CLI фиксирован: [vast.py, commit 42c3a47…, строки 774 и 4369–4448](https://github.com/vast-ai/vast-python/blob/42c3a47b44603775a5e31f54de0fce3994bd3f11/vast.py#L774); он задаёт `allocated_storage=args.storage`. Локальная выдержка: [vast_cli_units_excerpt.txt](W1_12_MATERIALS/vast_cli_units_excerpt.txt).

**Арифметическая иллюстрация, не прогноз времени обучения:** оффер 55729405, условные 10 running hours, 14 stopped hours, 0.1 тарифицируемой TB ingress и 0.02 TB egress, без volumes, при допущении одинакового diskHour: `10*0.218148148 + 14*0.031481481 + 0.12*0.666666667 = $2.702222`. Эти часы/объёмы выбраны только для проверки формулы. Допущение stopped-rate должно быть подтверждено перед оплатой; цена не включает неизвестные внешние налоги/FX/сервисы.

| Статья / риск | Что включить | Как ограничить до покупки |
|---|---|---|

## Lifecycle и противоречия документации

**W1-12-F05.** Compute не тарифицируется «по проценту GPU utilization»: активный экземпляр оплачивается по времени, даже когда dataloader/декодирование ждёт CPU. GPU exclusive, stopped не резервирует GPU; CPU/RAM baseline выделяются пропорционально доле GPU машины, burst сверх baseline не гарантирован. Память выше allocation может закончиться OOM. Поэтому таблица offer должна учитывать выделенные CPU/RAM, а не полный сервер [W1-12-S07].

**W1-12-F06.** Stop сохраняет container data, но оставляет storage charges; restart может ждать GPU неопределённо. Destroy уничтожает container data. Локальный volume переживает destroy экземпляра, но остаётся платным и привязан к физической машине — это не offsite backup. Размер container allocation фиксируется при создании. Перед destroy требуется проверенная выгрузка результатов [W1-12-S05, S06].

**W1-12-F07.** On-demand имеет фиксированные условия данного контракта и высокий приоритет, однако не иммунитет от отказа хоста. Interruptible уступает on-demand/более высокой ставке и требует checkpoint/resume. По завершении max duration экземпляр останавливается; текущая документация допускает удаление expired через 48 часов, не гарантирует 48-часовой safe backup window. Reserved credits привязаны к instance/host; ранняя отмена включает clawback скидки и 5% fee по разделу Refunds. Скидка «до 50%» — предел маркетингового описания, не применённая к нашим офферам скидка [W1-12-S04, S10].

**W1-12-F08. Существенные расхождения, не скрывать:**

- Current Billing, Pricing, строки 195–196: storage начисляется в online-состояниях, **offline исключён**. Legacy `console.vast.ai/faq/`, Billing → How does pricing work?, прямо включает offline/broken. Для планирования использовать консервативный резерв storage до destroy; актуальное исключение offline не является способом гарантированно уменьшить бюджет [W1-12-S02, S11].
- Current Billing → Loading, строки 339–341 говорит об отсутствии charge; общий Pricing там же описывает storage во всех online states. Managing Instances также говорит «not charged during loading». Поэтому не утверждаю точную state-by-state бесплатность storage/bandwidth loading без сверки Charges; до покупки запросить уточнение [W1-12-S02, S05].
- Security FAQ описывает ISO 27001 и Tier 3/4; Find & Rent → Machine Tiers — TIER 2/3 **или** ISO 27001. Нельзя превращать общий secure badge в подтверждение конкретного стандарта конкретной площадки [W1-12-S03, S08].
- Billing Refunds сначала допускает возврат unspent credits «в большинстве случаев», далее отдельно исключает crypto; решение о возврате не закладывать в budget как гарантированное [W1-12-S02].

## Community / verified / secure и доступ без аккаунта

Unverified не прошёл внутреннее тестирование; verified прошёл тесты Vast. Это классификация машины, не независимый SLA и не право передавать любые промышленные видео. Community-среда может принадлежать частному хосту. Secure Cloud означает проверенный datacenter и отдельный фильтр; точное подтверждение сертификата/региональной политики нужно по выбранной площадке. Docker isolation защищает от соседних клиентов, но документация признаёт технический доступ владельца машины к файлам. Для данных с ограничениями нужен отдельный ответ владельца данных; бюджетный community training допустим только с разрешёнными материалами [W1-12-S03, S05, S08].

**W1-12-F09.** Без аккаунта реально проверены документация, официальный CLI source, описанный GET offers. Поисковик показывал индексированные карточки cloud.vast.ai, однако прямое открытие выдачи через web либо возвращало пустой JS-shell, либо ошибку доступа инструмента. Эти индексированные цены не использованы как live-offer. Документированный API пример содержит Bearer token, но наш GET оказался публично доступен; это наблюдение, не обещание бессрочного anonymous API. Аккаунтные Balance, Charges, Invoice, финальные условия оплаты и реальная возможность rent не проверялись. Отдельного auth gate для offers в нашем опыте нет; для остального не выдаём отсутствие проверки за отказ авторизации [W1-12-S09, S12].

## Предлагаемый различающий эксперимент (не выполнен)

Вопрос: оправдывает ли 2×3090 доплату по отношению к 1× для выбранного CV-training recipe, и безопасен ли resume? Предпосылки: отдельное разрешение аренды/лимит, разрешённые данные, pinned image digest и code commit, dataset manifest, training owner, внешний backup. **В этой работе только публичные read-only проверки; эксперимент не запускается.**

Входы: одинаковый model/checkpoint, train split и validation, preprocessing, seed, сопоставимый budget оптимизационных шагов; 1-GPU baseline и корректная DDP-конфигурация 2-GPU. Сначала короткий representative batch/epoch smoke-test: VRAM peak, CPU/RAM, GPU utilization, data wait, samples/s, checkpoint save/load, bytes transfers. После сохранения проверить восстановление состояния, hashes, отсутствие повторной загрузки всего датасета. Оценить `cost per completed comparable run` и time-to-result по фактическому ledger; отдельно влияние batch/world-size на convergence, не путать throughput с accuracy.

Метрики/артефакты: elapsed/setup/training/backup time, peak memory, utilization trace, failures/retries, validation metric, exact steps/examples processed, manifest, configs, logs, checkpoint hashes, счета compute/disk/bandwidth, offer snapshots. Success: воспроизводимый run и resume с согласованной стоимостью; затем выбрать 1 GPU, 2 GPU для DDP либо две независимые задачи по наблюдениям. Failure: OOM, dataloader starvation, плохое масштабирование, budget overrun, нестабильный host, несовместимый driver — изменить recipe/offer и повторно оценить, а не объявлять модель непригодной.

Успех не докажет качество на других камерах, готовность industrial deployment или скорость LinQ. Lockbox не загружается для подбора batch/threshold/checkpoint; train/validation/optional SELECT/lockbox разделяются по сценам/камерам/соседним кадрам согласно общему протоколу. GPU benchmark использует train-only/синтетические репрезентативные формы, не lockbox. При выборе победителя по validation многократные попытки фиксируются.

## Передача и открытые вопросы

- Training strategy: сформировать размер D из реальных manifests/cache/checkpoint policy; определить, нужен DDP или независимые runs. Hardware minima, VRAM-fit и длительность пока неизвестны.
- Dataset/privacy owner: разрешение на перенос промышленных видео/лиц на конкретный host/регион; public marketplace не решает права/конфиденциальность.
- Evaluation owner: удержать independence splits; определить cost-to-validation-target без использования lockbox для выбора.
- LinQ/export owner: CUDA training artifact → поддерживаемый формат/операторы/quantization и **реальный** CPU/TPU latency benchmark. Конфигурация LinQ неизвестна.
- Финансовому владельцу: перед отдельным разрешением оплаты сверить stopped storage, loading metering, TB divisor, конкретные secure credentials, taxes/FX и account autobilling. Неизвестные не заполнены вымышленными числами. Офферы необходимо перечитать непосредственно перед решением.
