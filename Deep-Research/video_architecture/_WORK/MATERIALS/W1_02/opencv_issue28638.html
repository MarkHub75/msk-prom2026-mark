System Information

System Information

OpenCV version: 4.8.0+
Operating System: macOS Darwin 25.2.0
Python version: 3.9+
Backend: CAP_FFMPEG

Persistent cv2.VideoCapture connections to RTSP streams (H.264) produce corrupted frames after 15-30 seconds of continuous operation. The corruption is silent - cap.read() returns ret=True but delivers corrupted frames.

Detailed description

IMPACT

  • Makes persistent connections unreliable for production systems
  • Forces expensive reconnection overhead every 10-15 seconds
  • Silent failure mode (no error/warning) makes detection difficult

Steps to reproduce

We created minimal test script

#!/usr/bin/env python3
import cv2
import time
import os
from datetime import datetime

RTSP_URL = "rtsp://127.0.0.1:8554/leftcam"
OUTPUT_DIR = "frames_tcp"
os.environ["OPENCV_FFMPEG_CAPTURE_OPTIONS"] = "rtsp_transport;tcp"

os.makedirs(OUTPUT_DIR, exist_ok=True)

cap = cv2.VideoCapture(RTSP_URL, cv2.CAP_FFMPEG)
cap.set(cv2.CAP_PROP_BUFFERSIZE, 1)

for i in range(900):  # 15 minutes at 1fps
    # Flush buffer
    for _ in range(5):
        cap.grab()
    
    ret, frame = cap.read()
    
    if ret and frame is not None:
        frame_mean = frame.mean()
        timestamp = datetime.now().strftime("%H%M%S")
        filename = f"tcp_frame_{i:04d}_{timestamp}.jpg"
        cv2.imwrite(os.path.join(OUTPUT_DIR, filename), frame)
        
        status = "OK"
        if frame_mean < 10:
            status = "BLACK/CORRUPT"
        elif frame_mean > 250:
            status = "WHITE/CORRUPT"
        
        print(f"Frame {i}: mean={frame_mean:.2f} - {status}")
    
    time.sleep(1)

cap.release()

Behaviour

  • Frames 0-14: Normal (mean ~50-200)
  • Frames 15+: Corrupted (persistent bottom-left artifact, mean < 10)

Timing is non-deterministic:

Run 1: TCP corrupts at 15s
Run 2: TCP corrupts at 35s

Comparison: Continuous ffmpeg (works perfectly)

We tested native ffmpeg as a control:

ffmpeg -rtsp_transport tcp -i rtsp://127.0.0.1:8554/leftcam \
  -q:v 1 -vf fps=fps=1 -strftime 1 \
  frames_ffmpeg/frame_%Y%m%d_%H%M%S.jpg \
  -t 300

Result: 0 corrupted frames in 5-minute test

This proves:

  • RTSP stream is stable
  • Issue is specific to OpenCV's VideoCapture
  • ffmpeg's RTSP handling doesn't have this corruption

Expected behavior

Persistent connections should either:

  • Continue delivering valid frames indefinitely, OR
  • Return ret=False to signal failure (allowing graceful reconnection)

Current behavior:

  • Returns ret=True (claiming success)
  • Delivers corrupted frames
  • No error/warning raised
  • Silent failure mode

Questions

  1. Is this a known limitation of persistent RTSP connections in OpenCV?
  2. Could this be H.264 decoder state accumulation?
  3. Are there VideoCapture properties to prevent this?
  4. Why does ffmpeg handle the same stream perfectly?
  5. Should cap.read() return ret=False when frames are corrupted?

Additional context

  • Using MediaMTX RTSP server streaming looped MP4 files on local system
  • CAP_PROP_BUFFERSIZE setting has no effect (returns False in Python)

Issue submission checklist

  • I report the issue, it's not a question
  • I checked the problem with documentation, FAQ, open issues, forum.opencv.org, Stack Overflow, etc and have not found any solution
  • I updated to the latest OpenCV version and the issue is still there
