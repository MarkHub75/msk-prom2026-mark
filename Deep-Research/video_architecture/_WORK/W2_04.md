## Решение для автора

**W2-04-F01 [INFERENCE].** Простого сочетания «PTS в envelope + один inflight на камеру + latest-frame» недостаточно для корректной временной модели. У проверенного ByteTrack фиксированный `dt=1` на update, возраст tracks в update count, `frame_rate` регулирует только lost buffer. Для minimum45ч: один actor/camera, один parent frame в обработке, timestamps/coverage в собственном state; opaque tracker **не обязателен**. Включать этот reference tracker только после отдельного допуска фиксированного source cadence и reset при нарушении cadence/наблюдаемости. Если методы требуют устойчивый ID, а gate не пройден, соответствующий сценарий остаётся unsupported/degraded, а не становится методом без ID. Основания F02–F07 и W1-04-F16–F18.

**W2-04-F02 [CODE].** В pinned ByteTrack `KalmanFilter.__init__` задаёт `ndim, dt = 4, 1.` и один раз строит motion matrix. `predict`/`multi_predict` используют её; elapsed seconds/PTS параметра нет. `BYTETracker.update(output_results,img_info,img_size)` также не принимает время, делает `self.frame_id += 1`, затем один `STrack.multi_predict` для tracked+lost pool. Следовательно, два вызова после source delta 0.2s и 2s оба дают один шаг модели. Порядок применения по PTS сохраняет причинность, но не меняет этот dt. Проверено чтением S01/S02, не прогоном. Временной шум/covariance также обновляется на шаг; просто заменить значение в motion matrix недостаточно, чтобы доказать корректный variable-dt tracker.

**W2-04-F03 [CODE].** `BYTETracker.__init__`: `buffer_size=int(frame_rate/30.0*args.track_buffer)`; `max_time_lost=buffer_size`. Удаление проверяется как `self.frame_id-track.end_frame > self.max_time_lost`, где BaseTrack.end_frame возвращает последний frame_id track. Никакого wall-clock таймера нет. `frame_rate=5, track_buffer=30` даёт 5 update steps, не универсальную секунду: примерно 1s только при фактических 5 update/s без gaps. При 2 update/s те же 5 шагов соответствуют примерно 2.5s; strict `>` и порядок стадий добавляют границы. В update association/re-activation идёт **раньше** удаления old lost tracks: expiry не следует использовать как строгий запрет re-association через заданное число физических секунд. Изменение frame_rate не меняет KF dt. Основание S01 L146–160, L270–288; S03 L30–37.

**W2-04-F04 [CODE/INFERENCE].** Valid empty observation отличается от отсутствия наблюдения. Ветка `output_results.shape[1]==5` допускает NumPy массив `(0,5)`; empty detections проходят predict/association, unmatched confirmed tracks становятся Lost, unconfirmed — Removed, frame counter растёт, существующие lost проверяются на expiry. Matching явно обрабатывает пустую cost matrix. Это вывод по коду S01/S04, **не smoke test API**; shape `(0,)`, `None` или error response не эквивалентны `(0,5)` и не подходят этому API. Пустой выход detector означает «в обработанном кадре не осталось подходящих детекций», а не физическое доказательство отсутствия человека/нарушения. Threshold filtering может также превратить непустые raw outputs в пустые detections.

**W2-04-F05 [CODE/INFERENCE].** Если при timeout/gap вообще не вызывать update, frame_id, predict и lost aging не продвигаются в этот промежуток. Следующий valid result будет одним шагом, даже после минуты outage. Если вместо этого подать empty detection на каждом отсутствующем tick, библиотека воспримет отсутствие измерения как unmatched observation и изменит жизненный цикл tracks. Это не нейтральный способ передать Gap. У проверенного публичного API нет `gap(dt)`, `predict_only(dt)` или аргумента source frame_id. Собственный wrapper обязан сохранить отдельный Gap/coverage и явно reset либо использовать проверенную другую реализацию; synthetic empty updates не объявлять отрицательными наблюдениями.

**W2-04-F06 [CODE].** В прочитанных BYTETracker/STrack/BaseTrack нет публичного `reset()`. Новый BYTETracker очищает собственные lists/frame_id/KF; глобальный `BaseTrack._count` продолжает расти. Безопасный minimum reset — заменить instance только в последовательном actor, поднять собственный `tracking_generation`, обнулить temporal candidates согласно domain contract, старые результаты отвергать. Не сбрасывать class-wide ID counter из actor одной камеры: он общий для instances в процессе. Subject identity: `(camera_id,stream_epoch,tracking_generation,local_track_id)`, поскольку tracking reset может случиться без source reconnect. S01/S03. Это проектный wrapper contract, не существующий ByteTrack API.

**W2-04-F07 [CODE/INFERENCE].** Reference не является автоматически лёгкой готовой dependency для нашего окружения: tracker импортирует torch, matching — scipy/lap/cython_bbox/OpenCV, используются старые `np.float`; полный README содержит detector/training dependencies. «Лёгкий» относится к рассматриваемой классической tracking схеме, не доказанному footprint/installability. Новая библиотека/порт только ради этого сравнения не нужны. README Any detector показывает integration boundary с detections; это не выбор detector. License прочитан MIT с исходным copyright, но dependencies/weights имеют отдельный scope. S01/S04/S05; установка не производилась.

## Проверка популярных обходов и минимальный cadence gate

**W2-04-F08 [INFERENCE, попытка опровержения].** Проверены три возможных опровержения fixed-dt риска: (1) передать actual FPS constructor — он меняет buffer, dt остаётся 1; (2) передать source frame_id — update такого аргумента не имеет; (3) не обновлять на dropped frames — это сохраняет state в памяти, но останавливает aging/predict, не учитывает физическую паузу. Следовательно, эти обходы не дают variable-time semantics. Равномерная задержка ответа сама по себе не меняет source cadence, если применяются все результаты по source order; **нерегулярный sampling, timeout/drop или source discontinuity меняют**. Поэтому нужно измерять source deltas и application freshness отдельно.

Предлагаемый контракт допуска opaque reference tracker:

1. Метод согласовал `f_track`, допустимую погрешность интервала `eps_cadence`, `max_gap_media_s`, `max_live_age_s`, минимальный coverage, warmup и reset/interruption semantics. Числа сейчас UNKNOWN; 5fps — сценарный target W1, не требование кейса.
2. Source media_time известен и монотонен в epoch. Равномерный sampler выбирает реальный кадр на tick; duplicate/held frame не подменяет новое наблюдение. Измеряются `delta_media=t_current-t_last_observation`, deviation от `1/f_track`; если нужно bound ошибки выбора кадра, фиксируется source FPS/PTS uncertainty.
3. В tracker поступают success observations, включая **реальные** empty detections, последовательно с заданным cadence по source time. Late arrival допустим только в live deadline и пределах reorder budget. Между ними нет unresolved missing tick. Эквивалентность фиксированного cadence реальному видео остаётся проверяемым допущением, не обещанием ID quality.
4. При missed tick/cadence violation/unknown timestamps/слишком длинном gap wrapper делает explicit tracking reset **до** следующего accepted observation, отмечает coverage interruption. Нельзя продолжить прошлый dwell только потому, что новый track визуально похож. Не требуется новый source epoch при обычном inference drop: отдельная tracking_generation сохраняет честную source identity.
5. Если reset происходит так часто, что downstream метод не может набрать required coverage/ID lifetime, включается degraded/unsupported для этого метода. На minimum без tracker допускаются только методы, которым он не требуется, после согласования violation_methods; универсальная замена трекинга per-frame boxes не заявляется.

Это строгая минимальная политика, которая может терять эпизоды/часто сбрасываться. Более мягкая «перенести tracker через короткий gap» требует отдельной validation с подходящим gap-aware tracker/адаптацией динамики и noise; ни PTS envelope, ни rename аргументов её не доказывают. Dwell и coverage в собственном state измеряются media seconds, не update count; неизвестное время не засчитывается как доказанное наблюдение нарушения или безопасности.

## Per-camera ceiling и исправление sizing/admission

**W2-04-F09 [INFERENCE/arithmetic].** Пусть `L_i` — measured steady parent-frame cycle камеры от занятия её slot до возможности admit следующего: local encode/preprocess, transport, remote queue/infer, return, **client postprocess/NMS**, необходимый cascade, ordered application; плюс локальные ожидания, если slot удерживается ими. Для максимум одного такого slot на камеру средний throughput `f_i <= 1/E[L_i]` в насыщенном renewal-like режиме. Если между release и следующим admission есть scheduling delay, реальный FPS ниже. Это ceiling по среднему, а не worst-case max gap или доказательство p95. Если прежнее L означало только RPC, его нельзя подставлять в формулу полного cycle. Источник арифметики — W1-03-F17, W1-06-F15 с уточнением K005 и handoff W2_01.

| Условный постоянный полный L, ms | Ceiling при p_i=1, fps | Target 5fps: sequential | Идеальный нижний p_i для 5fps | Что разрешает переход к p_i>1 |
|---:|---:|---|---:|---|
| 50 | 20 | арифметически возможен, проверить load/gaps | 1 | не нужен ради target |
| 100 | 10 | возможен при запасе и fairness | 1 | не нужен ради target |
| 160 | 6.25 | возможен, но небольшой tail может сорвать tick | 1 | только после measured necessity |
| 200 | 5 | нулевой запас, не admission guarantee | 1 | запас/variance gate всё равно нужен |
| 300 | 3.33 | невозможен при одном slot | 2 | endpoint stateless/concurrent, bounded ordered buffer, credits, deadline |
| 500 | 2 | невозможен | 3 | те же prerequisites, measured throughput растёт |
| 1000 | 1 | невозможен | 5 | те же; freshness/gap могут уже исключить live |

Числа — **не LinQ измерения**, `p_min=ceil(f_target*L)` только детерминированная нижняя оценка occupancy. Несколько inflight помогают заполнить путь только при backend capacity/concurrency; remote queue может увеличить L при росте p. Для arbitrary-delay backend нет finite p, который гарантирует live age/max gap. Нельзя вычислять tail guarantee как `1/p95(L)` или складывать stage p95.

**W2-04-F10 [INFERENCE].** В W1-06-F15 перед `floor(min(...))` добавить отдельный **per-camera feasibility gate**: для каждой admit камеры `f_req_i <= p_i/E[L_i]` как necessary mean check, затем measured fresh ordered FPS, max media gap, wall inter-result gap и age в целевом workload. При p=1,L=300ms target5fps не допускается даже для N=1; глобальное K=100 эту камеру не исправляет. Уменьшить target можно только если это проходит методический min-FPS/max-gap contract, иначе reduce camera count не решит single-camera latency. Потолок по bandwidth/compute также остаётся.

Для однородного пути без каскада к W1 Nmax terms можно оставить `K_a/(f_req*E[L_a])` для app parent slots **при определённом lifecycle L_a**, но отдельно проверить `p_i`, queue/reorder bytes, remote credits. С W2_01 нельзя считать live Gap/reset доказанным remote terminal. Поэтому реальный admission — пересечение availability локальных parent slots, outstanding byte budgets, server quota/credits и per-camera temporal gates; pending old remote jobs продолжают занимать remote credits после local slot release. При неизвестной terminal occupancy автоматический бесконечный resume не допускается.

**W2-04-F11 [INFERENCE].** Для каскада считать не detector frames только. Пусть `q_j` — calls stage j на parent frame, bounded by explicit `q_j_max`; `L_rj` — residency remote credit одного такого job. Necessary mean remote occupancy:

`sum_i f_i * E[sum_over_jobs_per_parent(L_rj)] <= K_remote`.

Не заменять ожидание произведения `E[q_j*L_rj]` произведением средних при crowd-dependent latency без проверки. Это occupancy, а compute CPU/model/upload/downlink capacity считаются отдельно. Для однородных камер при установленном среднем per-parent residency `A_r` remote term `N <= K_remote/(f_req*A_r)`. Для server-side batched jobs считать quota в **фактических единицах контракта**, не воображаемых frame credits.

Локально caps: parent frames/camera `p_i`, primary/secondary job counts, ROI/frame `q_max`, ROI/camera, aggregate inflight bytes, ready-result count/bytes, client postprocess queue. Parent completion должен быть определён: если для temporal observation нужны secondary results, parent не считается complete до их usable completion или explicit partial/error/gap. Если tracker питается primary раньше, secondary имеет свой sent-id/order/coverage и не может задним числом незаметно менять уже закрытый live rule state. Отсечённый ROI по quota — unknown secondary evidence, не отрицательный PPE result. Worst crowd fanout/correlation проверять E03; базовый detector резервировать от starvation.

## Реальный sent-id reorder и late-result policy

**W2-04-F12 [INFERENCE].** Минимум p=1 проще, но p>1 допустим только для stateless inference либо явно поддержанного stateful sequencing. Один camera actor применяет наблюдения. При send в ledger добавляется `(request_id,parent_frame_id,source_time,deadline,epoch,tracking_generation_at_admission)` в **реальном admission order**, согласованном с source presentation order. Source IDs sparse: при sampling25→5fps нормальная последовательность 100,105,110; ждать101 нельзя. Offload вне порядка допускается только если ledger заранее хранит source order selected requests.

Ready map ограничена count<=p_i и отдельными bytes; результат после validation correlation/version/epoch помещается в ready. Применять можно только head outstanding. Если head ready и ещё fresh — apply и advance; если expired/error — emit Gap с известными временем/reason, advance, tracking policy reset при необходимости. Готовый следующий result повторно проверяется на freshness после reorder wait; deadline не продлевается от его arrival. Если head hanging, actor должен получить timeout/wakeup независимо от arrival следующих replies. Новые admissions прекращаются при исчерпании parent/ready/remote caps: иначе bounded reorder queue превращается в скрытый backlog.

Local terminal Gap завершает ожидание **live state**, но remote ledger/credit освобождается только по W2_01 terminal/reconcile contract. Поздний ответ не снимает already persisted Gap и не продолжает прежний dwell. Он может быть сохранён в отдельную offline ветку, если разрешены storage/evidence policy и correlation; live replay истории не производится. Старый epoch/model/duplicate/watermark rejection причины логируются отдельно. Reset/tracking_generation на missing head влияет на дальнейший apply: будущий ready result не следует отвергать лишь потому, что его admission был до локального reset; wrapper должен явно переадресовать пригодный source observation в новую generation после gap, сохранив trace. Старый source epoch при этом по-прежнему отвергается.

## Передача violation_methods / evaluation

**W2-04-F13 [INFERENCE].** Передать не одно число «FPS», а versioned temporal contract каждого метода: `min_unique_observation_fps`, измерительное окно/coverage denominator, `target_sample_period`, cadence tolerance, `max_media_gap_s`, `max_live_result_age_s`, warmup, dwell semantics, reset/unknown/partial/interrupted rules, ID continuity requirement, timestamp uncertainty и допустимость missing PTS. Mean5fps не исключает burst10frames+пауза2s; max gap и coverage обязательны. Критерий fresh-result FPS указывать и по applied source coverage, и по wall-time обслуживания; одинаковая средняя rate не даёт одинаковую оперативность.

Четыре разных величины: source/decode FPS; sampler admitted unique frames/s; completed valid RPC frames/s; **fresh ordered applied observations/s**. Secondary ROI/model calls — отдельная rate. Два тайминга: delta source time соседних accepted observations для физической временной модели и wall inter-application/result age для доступности/оперативности. Arrival jitter не превращается в motion dt, а source gap не скрывается ранним buffered delivery. Без true source clock mapping это не sensor-to-operator SLA; использовать ingest-relative age с явным timestamp_source.
