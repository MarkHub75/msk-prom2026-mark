# Видеоархитектура сервиса промышленной безопасности с удалённым LinQ

Авторский черновик для последующей редакции. Основания собраны 23 октября 2026 года, Europe/Moscow (UTC+3). Полный кейс, выданные команде SDK и права доступа, образец результата LinQ и измерения работающего конвейера отсутствуют. Здесь предлагается инженерный маршрут, который команда сможет принять или отклонить по ранним проверкам. Его сборка за 45 часов пока не доказана. Пять участников, 45 часов и названия критериев жюри — исходный контекст подготовки; официальные материалы прочитаны в пределах, указанных в [F023](../RAW_FACTS.md#f023) и [F024](../RAW_FACTS.md#f024).

Исследование приводит к достаточно узкому выбору: одно модульное приложение с последовательным владельцем состояния каждой камеры, общим ограниченным планировщиком запросов, адаптером фактически выданного LinQ, одной локальной БД событий и очередью доставки. MediaMTX обслуживает медиапотоки отдельным готовым процессом. Для экрана с аналитикой предпочтителен кадр, который действительно анализировался, вместе с его результатом. Запись точного клипа допускается только после доказательства связи временных шкал; при неудаче ранней проверки остаётся анализированный снимок и явный статус недоступного клипа. Такой минимум уменьшает число одновременно неизвестных механизмов, но не делает любой режим удалённого доступа пригодным для live. GUI без пригодного результата и очередь с неприемлемой задержкой могут означать, что live-интеграция пока не поддержана. [F070](../RAW_FACTS.md#f070), [F172](../RAW_FACTS.md#f172), [F204](../RAW_FACTS.md#f204), [K010 после W2](../CRITIC.md#k010-w2).

## Сначала установить, что именно выдали

Публичные материалы LinQ позволяют понять предмет разговора с постановщиком, но не выбрать сетевую топологию. Производитель предлагает демонстрацию и тестовую среду, описывает преобразование модели и вычисления int8. В разделе HPS отдельно указаны опциональные платы видеокодирования H.264/H.265, а в HX возможности декодирования относятся к CPU-блоку RK3588 рядом с LinQ H. Это не обещание decoder на любой плате LinQ и не описание выданного удалённого сервиса. Упоминание Python 3.8 API для quantize/compile также не устанавливает версию runtime хакатона. Скачать ПО можно после регистрации и верификации; команда этот доступ в рамках исследования не получала. [LinQ technology](https://lin-q.ru/tech), [HPS/HX и ПО](https://lin-q.ru/sol), [F005–F007](../RAW_FACTS.md#f005).

Из соседних исследований реально прочитан пакет `linq_platform`. Он тоже сообщает отсутствие matched proprietary SDK/native/driver/firmware и device access; его CPU и fake-native проверки не были исполнением на LinQ. Наличие иных законченных соседних отчётов здесь не предполагается. Поэтому первый технический результат команды должен состоять в коротком подтверждённом запуске на устройстве и сохранённом контракте доступа. Отдельное поле `backend=linq` в нашем JSON этого не доказывает. [S001](../SOURCES.md#s001), [F001](../RAW_FACTS.md#f001), [F215](../RAW_FACTS.md#f215).

| Наблюдаемый режим | Где разумно оставить приложение | Что должно подтвердиться до выбора |
|---|---|---|
| API изображения или тензора | Приём, decode, sampling, временное состояние, БД, доказательства и UI у команды; NN и только документированные pre/post на удалённой стороне | Формат входа и выхода, собственная модель или достаточный каталог, обновление версии, лимиты bytes/batch/concurrency, lifecycle и принятое доказательство исполнения |
| Shell с правом собственного постоянного процесса, доступным видеовходом и разрешёнными CPU/codec/storage/ports | Можно разместить рядом с decoder весь app data plane: планировщик, состояние, БД, recorder и проекцию для браузера; proprietary worker остаётся отдельной единицей поставки | Постоянство процесса и файлов, права на сеть, пакеты, backup и приватность. SSH сам по себе не даёт root, Docker или входящие порты |
| Shell только для временного NN worker | Основное приложение остаётся у команды, удалённый worker тонкий и использует supplied environment | Что переживает разрыв сессии, можно ли корректно завершить/повторно найти работу; нельзя переносить туда БД по факту одного успешного SSH |
| Job API или общая очередь | У команды persistent ledger, collector и fair/latest scheduler; submit, poll, fetch и postprocess входят в полный цикл | Получение пригодного результата, terminal/cancel/TTL, квоты, turnaround и частота свежих наблюдений каждой камеры. При провале — bounded stop, degraded или offline |
| GUI/manual либо job без пригодного результата и turnaround | Подтверждённый ручной/offline запуск LinQ; продуктовый поток отдельно воспроизводится с честной маркировкой replay/mock | Это `unsupported-live`, пока нет поддержанного пути интеграции. Автоматизация кликов не создаёт real-time контракт |

Общая очередь может существовать в любой строке; VPN определяет достижимость сети, а не права исполнения. Managed-video endpoint, принимающий RTSP и возвращающий события, был бы отдельным вариантом, но его наличие не установлено. Для него всё равно нужны свои классы, версия модели, timestamps и понятная граница ответственности за правила. Матрица — наше предложение по [F208](../RAW_FACTS.md#f208), уточнённое [F204](../RAW_FACTS.md#f204).

В первый час стоит пройти одну цепочку. Зафиксировать выданные endpoint, tenant/quota scope, runtime и права; получить минимальные input/output примеры и неизменяемую версию модели; выполнить golden input с подтверждаемым backend; сохранить результат, конфигурацию, hashes и platform witness; затем проверить двухкамерный полный цикл с реальной очередью. Отдельно выяснить направление разрешённых TCP-соединений: удалённый хост может не видеть RTSP URL из локальной сети команды. Публиковать камеры в интернет для обхода этой проблемы не требуется. Свои restart допустимы только в пределах выдачи; reset общего устройства не входит в этот план. [Q001](../OPEN_QUESTIONS.md#q001), [Q002](../OPEN_QUESTIONS.md#q002), [Q003](../OPEN_QUESTIONS.md#q003), [E001](../OPEN_QUESTIONS.md#e001).

Доказательный пакет запуска должен связывать неизменный вход и его hash, model/artifact/config/preprocess revisions, реальные request/job IDs и выданный платформой или согласованный с владельцем witness. Лог нашего клиента подтверждает отправку, а загрузка ускорителя — активность устройства; ни один из этих признаков отдельно не связывает конкретный результат с нашей NN. Где заканчивается обязательная NN-граница и допустимы ли CPU pre/post/cascade, решает фактическая выдача и полный кейс. RTX и CPU остаются полезными для отладки и сравнения, а их результаты получают соответствующую подпись. [F003](../RAW_FACTS.md#f003), [F215](../RAW_FACTS.md#f215), [Q025](../OPEN_QUESTIONS.md#q025).

## Сквозной путь и границы модулей

Приложение принимает поток, непрерывно декодирует его и выбирает кадры для анализа. Оно не заставляет decoder ждать удалённый инференс. На камеру достаточно одного логического actor: это единственный владелец временного состояния, accepted watermark, health и кандидатов событий. Actor может быть coroutine или объектом внутри worker, а не отдельным ОС-процессом на каждую из 500 камер. Изоляция зависающего native decoder или supplied SDK отдельным процессом — самостоятельная граница отказа. Приложение остаётся модульным и при нескольких worker processes. [F082](../RAW_FACTS.md#f082), [F094](../RAW_FACTS.md#f094), [F095](../RAW_FACTS.md#f095).

```text
camera / явно обозначенный looped_file
    → MediaMTX relay → demux/decode owner → latest frame
                         └→ indexed remux: только после E009
latest → bounded fair scheduler → actual LinQ adapter
                              ← validated result / explicit Gap
    → camera actor → event + outbox + evidence intent в одной БД
    → own-frame JPEG + metadata → bounded browser projection
    → dispatcher → optional внешнее уведомление
```

Это предлагаемый data flow. В API-варианте decoder и app plane находятся у команды. Перенос decoder к LinQ меняет и обратный путь: если отрисовка результата остаётся локальной, нужно вернуть сам анализированный кадр. Compact boxes без изображения не позволяют получить совпадающий processed view. Другой вариант — разместить проекцию рядом с decoder и передавать выбранные tiles непосредственно оттуда, но тогда этому месту нужны подтверждённые daemon/ports/persistence/DB/evidence/backup permissions. [F149](../RAW_FACTS.md#f149), [F200](../RAW_FACTS.md#f200), [F204](../RAW_FACTS.md#f204).

Модули связываются небольшими контрактами: источник выдаёт `FrameEnvelope` или `StreamStatus`; адаптер принимает неизменный запрос и возвращает коррелируемый результат; camera state получает упорядоченное наблюдение, `Gap` либо reset; repository подтверждает durable commit; media store возвращает ссылку на доказательство вместе со статусом покрытия. Крупные кадры и клипы не становятся durable event bus. На границах процессов передаются ссылки на ограниченный пул либо явные immutable copies; срок владения сохраняется до окончания реального потребления. `asyncio.to_thread` помогает освободить event loop от blocking call, но не доказывает параллелизм CPU-кода или thread safety LinQ. [F082](../RAW_FACTS.md#f082), [F094](../RAW_FACTS.md#f094), [F095](../RAW_FACTS.md#f095).

Предлагаемый frame/result contract задаёт `schema_version`, стабильный `camera_id`, новый UUID `stream_epoch`, возрастающий внутри epoch `frame_id`, исходные integer `pts` и rational `time_base`, nullable нормализованный `media_time_ns`, `timestamp_source`, geometry и обратимые transforms. Номер кадра назначается на декодированном presentation frame до sampling, поэтому пропущенные номера нормальны. `captured_at_utc` заполняется только при доказанной привязке источника к UTC; `received_at_utc` и `ingest_monotonic_ns` не подменяют exposure time. Для monotonic записывается clock domain/run ID: значения разных хостов или перезапусков не вычитаются. [F035](../RAW_FACTS.md#f035), [F083](../RAW_FACTS.md#f083), [F126](../RAW_FACTS.md#f126).

Запрос дополнительно содержит `request_id`, model/preprocess/request-contract revisions, payload format, dtype/layout/color, размер и hash. Для crop нужны parent frame, ROI и transform к исходному кадру. Результат обязан повторить correlation IDs, сообщить фактически исполненную model revision, status/error, тип и систему координат выхода. Raw heads требуют names/count/shapes/dtype/endian/scales/zero-point и точной decode-head семантики. Compact detections требуют class-map revision, box format, confidence definition, thresholds, NMS config и implementation revision, top-K/max detections/truncation. NMS нельзя выполнять второй раз по привычке: у end-to-end detector его граница может быть другой. Masks, embeddings и keypoints считаются отдельным payload. [F147](../RAW_FACTS.md#f147), [F215](../RAW_FACTS.md#f215).

Событие получает собственный неизменный `event_id` и возрастающий `event_revision`; повтор доставки сохраняет тот же ID. В нём нужны camera/source epoch, rule revision, observed source interval, evidence frames, coverage/gaps, model/run provenance и раздельные состояния snapshot/clip/delivery. Subject при трекинге идентифицируется как `(camera_id, stream_epoch, tracking_generation, local_track_id)`: tracker может сброситься без reconnect источника. Предложенная схема и пример единиц сохранены в [F096](../RAW_FACTS.md#f096); это контракт разработки, а не извлечённый API LinQ. Семантическая дедупликация одного эпизода согласуется с `violation_methods` отдельно от дедупликации транспорта.

## Приём и декодирование: свежесть начинается до нейросети

Для минимального маршрута выбран MediaMTX как relay и PyAV как кандидат decoder с доступом к packet/frame PTS. Альтернатива GStreamer разумна при уверенном опыте команды с bus/state machine и нужном аппаратном pipeline. OpenCV удобен для обработки массивов и smoke test, но настройка `CAP_PROP_BUFFERSIZE=1` не является обоснованным средством управления RTSP+FFmpeg. В коде OpenCV 4.13.0 `CvCapture_FFMPEG::setProperty` этот параметр не обрабатывает; timeout и hardware acceleration относятся к open-only свойствам и зависят от backend/build. [F025](../RAW_FACTS.md#f025), [OpenCV 4.13.0 code](https://github.com/opencv/opencv/blob/fe38fc608f6acb8b68953438a62305d8318f4fcd/modules/videoio/src/cap_ffmpeg_impl.hpp), [F032](../RAW_FACTS.md#f032), [F033](../RAW_FACTS.md#f033).

Непрерывное чтение и latest slot нужны потому, что редкий `read()` способен отставать от потока в upstream buffers. При этом latest slot не ограничивает decoder DPB, socket, RPC, WS и browser queues; у каждого слоя свой предел. Для FFmpeg n8.0 наружный RTSP AVOption называется `timeout`, а внутреннее поле — `stimeout`; сохранённая таблица не поддерживает старый внешний `-stimeout`. RTSP `timeout` и общий `rw_timeout` выражены в микросекундах, `listen_timeout` — в секундах и относится к listen mode, `reorder_queue_size` — в пакетах, socket `buffer_size` — в bytes. Код n8.0 использует timeout также в UDP poll loop, что уточняет краткое описание документации как TCP I/O timeout. Ни один из этих параметров не выполняет reconnect и не задаёт полный возраст кадра. [FFmpeg protocols](https://ffmpeg.org/ffmpeg-protocols.html#rtsp), [F026](../RAW_FACTS.md#f026), [F027](../RAW_FACTS.md#f027).

В PyAV 16.0.1 `av.open(..., timeout=(open_s, read_s))` использует секунды и monotonic interrupt callback. Open и stream-info могут запускать таймер отдельно; `(5,3)` не доказывает общий open ≤5 s. Read timeout возобновляется на каждом `av_read_frame`, поэтому непрерывный поток старых кадров может никогда его не нарушить. Container закрывается явно при каждом reopen. Hardware decode в этой версии существует, но `allow_software_fallback=True` по умолчанию: запрос acceleration без запрета fallback и проверки реального backend не доказывает GPU decode. Установленный wheel, драйвер, host transfer и NumPy boundary требуют самостоятельной проверки. [PyAV 16.0.1](https://github.com/PyAV-Org/PyAV/tree/v16.0.1), [F034–F037](../RAW_FACTS.md#f034).

GStreamer особенно наглядно показывает независимость буферов. У `rtspsrc` default `latency=2000` ms, `drop-on-latency=false`, `tcp-timeout=20000000` µs; его `timeout` означает ожидание UDP до fallback на TCP. `queue` по умолчанию ограничивается первым из 200 buffers, 10 MB и 1 s. Для raw latest policy `leaky=downstream` выбрасывает старые buffers, а `upstream` — новые. После decoder можно предложить `max-size-buffers=1 max-size-bytes=0 max-size-time=0`; выбрасывание произвольных encoded buffers до decoder нарушает межкадровые зависимости. У appsink остаётся собственная очередь: `max-buffers=0` unlimited. Старый `drop=true` deprecated с 1.28 в пользу `leaky-type`, поэтому этот ключ нельзя переносить в 1.24. `tcp-timestamp=true`, backported в 1.24.10, помогает в определённом drift-сценарии, но может ухудшать burst-поток; это вариант soak test, не универсальный рецепт. [rtspsrc](https://gstreamer.freedesktop.org/documentation/rtsp/rtspsrc.html), [F028–F031](../RAW_FACTS.md#f028).

Sampling до 5 fps после decode уменьшает resize/encode/inference/WAN, но H.264 25 fps продолжает требовать reference-state decoding. `skip_frame="NONKEY"` даёт keyframe-only, а не произвольные 5 fps: условный GOP 50 при 25 fps оставляет около 0.5 кадра/с. Более низкий camera substream действительно меняет входную сеть и decode, но его пригодность для мелких СИЗ проверяется отдельно. Короткий GOP может ускорить восстановление random access ценой bitrate; I-frame и IDR нельзя считать взаимозаменяемыми. [F042–F044](../RAW_FACTS.md#f042).

Для демонстрации сохранён официальный путь file → FFmpeg publisher → MediaMTX. Пример ниже относится к FFmpeg n8.0 и MediaMTX 1.21.2, является предложением и здесь не запускался:

```sh
ffmpeg -re -stream_loop -1 -i demo_h264.mp4 -map 0:v:0 -an -c:v copy -rtsp_transport tcp -f rtsp rtsp://127.0.0.1:8554/cam1
```

В TCP-only конфигурации publisher и reader должны оба выбрать TCP. У MediaMTX `rtspTransports` задаёт transports сервера, а per-path `rtspTransport` — pull от upstream. Codec/profile файла проверяются заранее; повторное live re-encode смешало бы нагрузку publisher с нагрузкой decoder. Источник подписывается `looped_file`, loop/seek discontinuity не склеивается с прошлым проходом. Сходство повторяющихся изображений в таком источнике не означает неисправность камеры. ONVIF discovery остаётся необязательным control plane: для минимума нужен ввод RTSP URL вручную; доступный порт 554 не доказывает прохождение RTP media через firewall. [MediaMTX FFmpeg example](https://github.com/bluenviron/mediamtx/blob/914e39535ece709919ac325aaeed98d394ed9093/docs/3-publish/17-ffmpeg.md), [F038–F041](../RAW_FACTS.md#f038).

## Передача кадра и планировщик: ограничивать работу до её создания

Формат передачи выбирается по фактическому endpoint. Если он принимает JPEG, сначала измеряются bytes, encode CPU и качество детекций. Если он принимает tensor, клиент точно соблюдает dtype/layout/shape/scales, а не выбирает uint8 ради экономии канала. Если разрешён собственный worker и сжатый видеовход, перенос decode/preprocess к LinQ может убрать передачу raw tensors. Преимущество зависит от bitrate источника, а не от названия протокола. Binary HTTP с reused connection, async gRPC unary или готовый WS endpoint — допустимые границы; сравнительной скорости на одинаковом payload/RTT/TLS/concurrency в базе нет. [F068](../RAW_FACTS.md#f068), [F215](../RAW_FACTS.md#f215).

Из деталей транспорта следуют несколько практических ограничений. Base64 занимает `4×ceil(n/3)` bytes для n исходных bytes, примерно на треть больше, без JSON-обёртки. gRPC не задаёт deadline автоматически; переиспользование channel/stub полезно, но concurrent HTTP/2 stream limits способны создать скрытую клиентскую очередь. Возврат из streaming write подтверждает принятие framework, а не удалённый результат. WebSocket даёт framing и ordered TCP bytes, но не model schema, per-camera fairness, идемпотентность или freshness. Triton binary tensors показывают, что HTTP не требует JSON-массивов чисел, однако поддержку конкретной extension нельзя приписать LinQ. [RFC 4648](https://www.rfc-editor.org/rfc/rfc4648.txt), [gRPC deadlines](https://grpc.io/docs/guides/deadlines/), [F053](../RAW_FACTS.md#f053), [F055–F059](../RAW_FACTS.md#f055), [F067](../RAW_FACTS.md#f067).

JPEG нельзя выбирать по тому, насколько приятно выглядит картинка человеку. В исследовании Bhowmik et al. на FLIR thermal 640×512, Person/Bicycle/Car и Cascade R-CNN/FSAF/Deformable DETR мелкие объекты оказались особенно чувствительны к сжатию. У Cascade R-CNN с original training mAP, описанная авторами через IoU>0.5, составила 0.822/0.789/0.623/0.109 при Q95/Q50/Q15/Q5 против original 0.823; это не COCO mAP50:95 и не RGB СИЗ. Независимая работа Gandor и Nalepa на COCO val2017, 5000 images и девяти Detectron2 RetinaNet/Faster R-CNN вариантах показывает, что precision при Tc=0.5 могла оставаться относительно стабильной при падении recall, особенно AP small. Разные Q30/Q40 в её выводах относятся к разным метрикам, а не к универсальной безопасной границе. Поэтому здесь нет разрешённого JPEG Q для каски, респиратора или сигареты. [Bhowmik et al.](https://arxiv.org/html/2205.08002), [Gandor, Nalepa](https://doi.org/10.3390/s22031104), [F063](../RAW_FACTS.md#f063), [F064](../RAW_FACTS.md#f064), [E004](../OPEN_QUESTIONS.md#e004).

ROI помогает только при учёте всей цепочки. Для r crops/frame трафик равен `8Nf×E[Σ(Jcrop+h)] + Rdiscovery`; сначала нужно найти человека/объект, а overlapping crops могут повторно передавать пиксели. Если каждый crop resize-ится в одинаковый вход классификатора, меньшая площадь не означает меньше NN calls. Толпа увеличивает fan-out именно тогда, когда система уже занята. Поэтому primary detector получает защищённую долю ресурсов, а secondary stages — конечные ROI/frame, jobs/camera и bytes caps. Отсечённый crop означает неизвестное secondary evidence, а не отрицательную классификацию СИЗ. [F065](../RAW_FACTS.md#f065), [F066](../RAW_FACTS.md#f066), [F068](../RAW_FACTS.md#f068), [F182](../RAW_FACTS.md#f182).

Планировщик хранит один ещё не отправленный latest frame на камеру и выбирает eligible камеры round-robin по `next_due` или token bucket с конечным burst. Он сначала получает ресурс допуска, затем забирает кадр; создание task на каждый входной frame, ожидающий semaphore вместе с полным payload, переносит неограниченную очередь в tasks. Глобально ограничиваются parent requests, input bytes, result bytes и pre/post jobs. Камера без кадров не задерживает остальные. Начальный режим — B=1 без намеренного batch wait и один parent frame в обработке на камеру. Совместимый batch допускается после измерения и только для одного model/version/input contract; исчезнувший источник не должен задерживать его заполнение. [F214](../RAW_FACTS.md#f214).

Batching расходует тот же freshness budget. Для равномерного потока λ и batch B первый кадр ждёт до `(B−1)/λ`; при 5 fps и B=8 это 1.4 s в идеальной детерминированной модели. Для Poisson arrival это уже ожидаемая величина без жёсткого верхнего предела. Partial batch требует поддержки модели/runtime; padding не создаёт новые наблюдения и учитывается отдельно. В Triton `max_queue_delay_microseconds` относится к формированию batch, а queue timeout/size — к другим механизмам. Stateful sequence model требует affinity/start/end/reset и допустимых gaps, поэтому её нельзя включить в stateless latest-drop по умолчанию. [Triton batchers](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/batcher.html), [F054](../RAW_FACTS.md#f054), [F069](../RAW_FACTS.md#f069).

У простой последовательной камеры есть собственный потолок. Обозначим `L_i` полным циклом от занятия её parent slot до возможности admit следующий: local preprocess/encode, сеть, remote queue, NN, return, client NMS, обязательный cascade и ordered apply. Необходимая средняя граница — `f_i ≤ p_i/E[L_i]`, где p_i число таких slots. При p_i=1 и L=300 ms потолок около 3.33 fps; глобальное K=100 эту камеру не исправляет. При L=160 ms потолок 6.25 fps, при 200 ms — 5 fps с нулевым запасом, при 500 ms — 2 fps, при 1 s — 1 fps. Это арифметические примеры, не LinQ measurements. Уменьшение числа камер не устраняет single-camera cycle; уменьшение требуемого FPS допустимо только в пределах метода. [F180](../RAW_FACTS.md#f180), [F181](../RAW_FACTS.md#f181).

Несколько inflight на камеру уместны лишь при подтверждённом stateless/concurrent endpoint либо поддержанном sequencing. Lower bound `p_min=ceil(f_target×L)` для постоянного L не обещает полезного выигрыша: очередь сервера может увеличить L. Little-law `Σf_i E[L_i]≤K_local` — проверка средних occupancy, не p95/p99 и не max-gap SLA. Для каскада remote occupancy считают как `Σ_i f_i E[Σ_jobs_per_parent L_rj]≤K_remote`; crowd-dependent число jobs и latency нельзя автоматически разнести в произведение средних. Единицы quota — jobs, frames, вес или иное — берутся из выдачи. [F069](../RAW_FACTS.md#f069), [F180–F182](../RAW_FACTS.md#f180).

### Отдельно учитывать удалённые обязанности

Локальный timeout завершает ожидание live-результата, но не доказывает освобождение удалённого job. Без этого различия bounded local semaphore может сосуществовать с бесконечно растущей удалённой работой: клиент после каждого timeout возвращает слот и отправляет новый кадр. Рестарт ещё ухудшает ситуацию, если теряются job IDs. Предлагаемый выход — persisted ledger и отдельные budgets для local submit/control/fetch calls и remote outstanding credits. [F143–F146](../RAW_FACTS.md#f143).

AWS Batch использован как один документированный контрпример, а не как описание LinQ. Его CancelJob может ответить HTTP200, продолжая STARTING/RUNNING; attempt timeout начинается после startedAt и не включает неограниченное ожидание RUNNABLE, а terminal history «не менее 7 дней» не является execution TTL. В SubmitJob не найдено документированного clientToken/dedup promise. Положительный поиск по уникальному jobName помогает восстановить ID, но пустой список не доказывает непринятие запроса. Этот пример объясняет, почему нам нужен фактический внешний lifecycle contract. [AWS CancelJob](https://docs.aws.amazon.com/batch/latest/APIReference/API_CancelJob.html), [AWS timeouts](https://docs.aws.amazon.com/batch/latest/userguide/job_timeouts.html), [F134–F140](../RAW_FACTS.md#f134).

| Наше состояние запроса | Что сохраняется и когда освобождается credit |
|---|---|
| `not_submitted` | Работа ещё не могла попасть в сеть. До send атомарно резервируются credit и immutable request intent |
| `submitting` | Intent успешно committed; отправка могла произойти, ack ещё не сохранён. Crash/timeout ведёт в `unknown` с удержанным credit |
| `accepted` / `running` | Сохраняются job ID, последняя remote observation и namespace. Local live deadline и reset камеры credit не возвращают |
| `unknown` | Есть возможная удалённая обязанность, которую пока нельзя разрешить. Poll/lookup/reconcile продолжаются в отдельном control budget |
| `terminal` | Доказана невозобновляемая финальность всего job или достоверный non-acceptance/not-sent. Evidence и release фиксируются одной транзакцией/CAS ровно один раз |

Ledger включает request UUID, camera/epoch/frame/crop, model/preprocess/contract revisions, payload hash/size, endpoint/tenant/quota scope, known job/attempt IDs, held weight, live disposition, terminal witness и отдельное состояние получения result artifact. Тот же request ID с другим hash отвергается до сети. Один submit owner владеет quota domain; смена токена или URL alias не создаёт свободный бюджет. При отсутствии server dedup один фактический network submit attempt означает одну возможную обязанность. Hidden SDK/proxy retries должны быть выключены либо явно покрыты credits; дедупликация результата не отменяет duplicate work. Минимум не делает автоматический повтор ambiguous submit. [F143](../RAW_FACTS.md#f143), [F144](../RAW_FACTS.md#f144).

При restart admission сначала закрыт: восстановить persisted held, превратить незавершённый submitting в unknown, reconcile known jobs и учесть старые leases/owners. Если часть credits доказанно свободна, продолжение возможно на этом остатке; ждать всех unknown необязательно. Если unknown заняли K_remote или сам ledger/namespace недостоверен, admission останавливается. Полученный ack при неуспешном DB commit не считается отсутствующей remote работой. Восстановленный старый backup ещё опаснее: он может не содержать jobs, принятых после cutoff. Пустая восстановленная таблица не разрешает held=0. [F145](../RAW_FACTS.md#f145), [F195](../RAW_FACTS.md#f195).

TTL освобождает обязанность только при документированной полной жизни job, включая queue/start/retry, и доказанном cutoff последнего возможного acceptance. RPC deadline, live frame age, attempt timeout, retention result и retention idempotency key — разные сроки. После expiry ключа same-key retry может создать новую работу. Без idempotent submit/lookup/полного TTL непрерывный auto-resume в общем случае не доказуем; bounded stop остаётся корректным конечным исходом. Borrowed native input buffer также удерживается до safe release по SDK, даже если view TTL уже закончился. [F146](../RAW_FACTS.md#f146), [F170](../RAW_FACTS.md#f170), [Q002](../OPEN_QUESTIONS.md#q002), [E007](../OPEN_QUESTIONS.md#e007).

## Временная логика: порядок результатов не заменяет время источника

Система различает presentation order после decoder reorder, порядок admitted запросов и порядок прихода ответов. При sampling 25→5 fps реальные отправленные IDs могут быть 100,105,110. Reorder buffer ждёт head из этого списка, а не несуществующий 101. Размер ready map ограничен count и bytes; независимый timer продвигает просроченный head даже при полном отсутствии новых ответов. Перед apply каждый результат повторно проходит freshness/version/epoch/geometry validation. Late response не переписывает уже применённую live-историю и не продолжает прежний dwell. [F084](../RAW_FACTS.md#f084), [F183](../RAW_FACTS.md#f183).

Например, ответы 110 и 105 пришли раньше 100. Они остаются ready до deadline head. После timeout 100 actor выдаёт `Gap`, сохраняет удалённую обязанность 100 и при необходимости сбрасывает tracker. Затем 105 и 110 применяются последовательно только если ещё fresh и пригодны как начало новой generation. Сам факт их раннего arrival не продлевает deadline. Поздний 100 разрешает remote lifecycle, но в live state не попадает. Если у 105 source delta оказалась 2 s вместо 0.2 s, ordered delivery всё равно не скрывает этот gap. Это проектный trace, который предстоит проверить в [E006](../OPEN_QUESTIONS.md#e006), а не выполненное наблюдение. [F183](../RAW_FACTS.md#f183).

`Gap(start,end,reason,known_count,duration_or_unknown)` — отсутствие наблюдения. Пустые валидные detections — наблюдение обработанного кадра без подходящих выходов detector. Эти ситуации имеют разные последствия: две секунды без результатов не доказывают две секунды отсутствия каски или безопасности. Dwell и coverage считают по source media time, при неизвестной шкале явно сообщают uncertainty. Длинный gap прерывает candidate; `closed/interrupted/unknown` выбираются по versioned domain contract, а не по желанию очистить карточку. После reconnect/seek/source replacement или недоказанной discontinuity создаётся новый epoch; обычный B-frame reorder сам по себе не является source reset. Decoder и recorder generations учитываются отдельно. [F085](../RAW_FACTS.md#f085), [F086](../RAW_FACTS.md#f086), [F158](../RAW_FACTS.md#f158).

Проверенный reference ByteTrack не получает elapsed seconds. В commit `d1bf0191adff59bc8fcfeaa0b33d3d1642552a99` KalmanFilter задаёт `dt=1`, а каждый `BYTETracker.update()` увеличивает frame_id на один. Constructor `frame_rate` меняет только `buffer_size=int(frame_rate/30.0×track_buffer)`. Поэтому PTS в нашем envelope не делает этот tracker variable-dt. Если update не вызывать минуту, predict/lost aging в этот промежуток не движутся; synthetic empty updates, напротив, меняют состояние tracks. Настоящий empty массив `(0,5)` может превратить unmatched confirmed tracks в Lost; `None`, shape `(0,)` и timeout ему не эквивалентны. [ByteTrack reference](https://github.com/ifzhang/ByteTrack/tree/d1bf0191adff59bc8fcfeaa0b33d3d1642552a99), [F173–F176](../RAW_FACTS.md#f173).

Отсюда tracker в минимуме необязателен. Его можно включить только при согласованном фиксированном source cadence, tolerance, max gap, coverage и reset policy. Пропущенный tick, unknown timestamps или cadence violation приводят к явному reset до следующего observation; новый instance и `tracking_generation` очищают локальное состояние, class-wide ID counter одной камеры не сбрасывается. Частые resets могут сделать ID-dependent метод непригодным: тогда он `degraded/unsupported`, а не автоматически заменён per-frame boxes. Более мягкое продолжение через gap требует проверки другой gap-aware реализации или корректной адаптации динамики и noise. Даже успешная интеграция wrapper ещё не доказывает ID/re-ID quality. [F172](../RAW_FACTS.md#f172), [F177–F179](../RAW_FACTS.md#f177), [Q021](../OPEN_QUESTIONS.md#q021).

До выбора FPS каждый метод должен сообщить `min_unique_observation_fps`, target period/cadence tolerance, max media gap, max live result age, coverage denominator, warmup, physical dwell semantics, ID continuity и правила unknown/reset/interruption. Средние 5 fps могут означать burst из десяти кадров и двухсекундную паузу. Поэтому нужны одновременно source deltas и wall inter-application gaps; arrival jitter не становится motion dt. Полного контракта сейчас нет, и 5 fps во всех расчётах ниже остаются допущением. [F184](../RAW_FACTS.md#f184), [Q005](../OPEN_QUESTIONS.md#q005).

## Событие сохраняется раньше, чем готов клип

Кадры допускают ограниченные потери ради свежести; подтверждённые event mutations требуют durable commit и повторяемой доставки. В минимуме это одна SQLite DB на локальной корректно поддерживаемой ФС и один writer с bounded queue. Event revision, dedup key, outbox rows, evidence intent/reservation и связанные refs фиксируются одной транзакцией. Remote submit intent с held также сохраняется до сети. Network await, hash/export или decode не держат эту транзакцию открытой. Только успешный `COMMIT` даёт право показать `event_committed` или `pin accepted`; принятый в RAM объект durable не является. [F087](../RAW_FACTS.md#f087), [F191](../RAW_FACTS.md#f191).

Этот выбор уменьшает интеграцию, но имеет границы. WAL допускает readers вместе с одним writer, требует одного host и не превращает network-mounted файл в общую БД между командой и LinQ. PostgreSQL становится обоснованным при multi-host writers или измеренной конкуренции операторских транзакций; `SKIP LOCKED` полезен для queue-like tables, но не гарантирует строгий FIFO. Новый Redis/NATS/Kafka для нескольких demo cameras добавил бы эксплуатационную задачу. Redis Streams требуют reclaim pending и retention, Core NATS ephemeral, JetStream — отдельный persistent режим, MQTT QoS2 и Kafka transactions не охватывают произвольный внешний HTTP effect. [SQLite WAL](https://sqlite.org/wal.html), [F088–F092](../RAW_FACTS.md#f088).

Dispatcher читает committed outbox, отправляет и сохраняет attempt/result/external message ID. Уникальный ключ включает event ID/revision/destination; один dispatcher достаточен для минимума. Crash после commit до send приводит к retry; crash после provider acceptance до delivered marker может дать duplicate. Exactly-once внешней доставки появляется лишь при реальном receiver idempotency/inbox contract. UI обновляет одну карточку по event_id/revision, а clip-ready становится новой revision этого события. Отправка не ждёт post-roll. Failed/poison сообщения получают конечную error/dead policy, не блокируют все тревоги и не удаляются бесследно. [F093](../RAW_FACTS.md#f093), [F119](../RAW_FACTS.md#f119).

Нужен исправленный фактический SQLite runtime. В primary WAL advisory описана corruption race диапазона 3.7.0–3.51.2; исправление 3.51.3 и backports 3.44.6/3.50.7. Один writer не заменяет патч при наличии других checkpoint/read/backup connections. Выбран provisional SQLite 3.51.3 с `SOURCE_ID 2026-03-13 10:38:09 737ae4a34738ffa0c3ff7f9bb18df914dd1cad163f28fd6b6e114a344fe6d618`. Это кандидат, не установленный движок; distro backport принимается по документированному vendor provenance и manifest amendment. Версия CPython и соседний `sqlite3` CLI не определяют библиотеку Python connection. [SQLite 3.51.3 release](https://sqlite.org/releaselog/3_51_3.html), [F186](../RAW_FACTS.md#f186), [E015](../OPEN_QUESTIONS.md#e015).

Предложенная настройка — WAL, `synchronous=FULL`, `foreign_keys=ON`, bounded busy timeout и короткие readers. Начальные `busy_timeout=1000` ms и `wal_autocheckpoint=1000` pages — параметры fixture, а не общий deadline SQL и не hard cap WAL. PRAGMA returned values/source_id/compile_options проверяются через actual connection; foreign_keys внутри уже открытой transaction не включатся. В Python 3.12 предлагается один явный transaction mode с explicit `BEGIN IMMEDIATE/COMMIT/ROLLBACK`, без смешения implicit modes и executescript. Dedicated writer владеет своей connection, sync SQLite calls не блокируют WS loop. [Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html), [F189](../RAW_FACTS.md#f189), [F190](../RAW_FACTS.md#f190).

FULL выбирается потому, что потерянный подтверждённый admission ledger способен разрешить лишнюю remote работу. Он требует честных sync/VFS/storage и не восстанавливает потерянный диск. COMMIT может вернуть BUSY с ещё активной transaction; FULL/IOERR способны оставить неоднозначный outcome. Error handler проверяет transaction state, bounded retry/rollback и затем recovery, но не объявляет success после catch. При неизвестном исходе caller ищет durable row по уникальному operation key. Long readers, например cursor на всё время browser streaming, мешают checkpoint и растят WAL. [F189–F191](../RAW_FACTS.md#f189).

### Почему готовая запись MediaMTX ещё не точное доказательство события

Запись encoded originals отделяется от анализа и не теряет кадры только потому, что scheduler выбросил inference frame. Stream copy сохраняет сжатый поток без decode/encode; встроенные рамки, blur, resize и frame-accurate trim требуют отдельного decoded/reencoded derivative. Оригиналом разумно считать покрывающие source segments плюс manifest с actual intervals и gaps; удобный клип для просмотра ссылается на эти originals. Copy может захватывать больше материала до/после, но нехватка окна должна называться partial. [FFmpeg streamcopy/seek](https://ffmpeg.org/ffmpeg.html), [F099](../RAW_FACTS.md#f099), [F100](../RAW_FACTS.md#f100).

Критический пробел — соответствие camera event time записанным bytes. В MediaMTX 1.21.2 fMP4 custom `mtxi` хранит StreamID (16 bytes), SegmentNumber uint64, DTS int64 ns и NTP UnixNano. StreamID создаётся recorder instance и не является source или decoder epoch. Hooks содержат path/segment path, а complete добавляет duration seconds; исходных PTS, decoder generation и source lineage там нет. Create hook вызывается до writeInit, complete hook не заменяет validation покрытия. Native playback `/list`/`get` использует filename start, при склейке учитывает recorder continuity, а export теряет mtxi UserData. HTTP200 и открывающийся MP4 не доказывают, что в файле есть нужный проход loop и полное окно. [MediaMTX 1.21.2 recorder](https://github.com/bluenviron/mediamtx/tree/914e39535ece709919ac325aaeed98d394ed9093/internal/recorder), [F152–F154](../RAW_FACTS.md#f152).

По умолчанию MediaMTX заменяет incoming absolute timestamps системным временем. `useAbsoluteTimestamp=true` требует source timestamps и всё равно не доказывает правильные часы камеры или совпадение независимых readers. RTCP NTP/RTP mapping, PTS и DTS — разные величины с session/reorder semantics. Нельзя выбрать доказательство по `camera_id + время в имени файла` и объявить его exposure-aligned. Анализ substream и запись main также требуют отдельной проверки FOV, clock offset/drift и uncertainty, а не только масштабирования координат. [MediaMTX absolute timestamps](https://github.com/bluenviron/mediamtx/blob/914e39535ece709919ac325aaeed98d394ed9093/docs/2-features/15-absolute-timestamps.md), [F155](../RAW_FACTS.md#f155).

Поэтому предпочтительный, но ещё не работающий route — один demux owner для одного H.264 video-only профиля. Те же encoded access units идут в decode и indexed remux; packet PTS/DTS/time_base/random-access/codec/extradata и sequence записываются до mux rebase. PyAV mux меняет packet timestamps/time_base, а B-frame delay/flush нарушают удобное предположение «один packet — один yielded frame». Нужны отдельные refs/copies и проверенное владение mutable Packet. Source, decoder и recorder generations различаются; decoder-only restart не обязан менять recorder generation и наоборот. Missing/duplicate timestamps сохраняют `mapping=unknown`, а не восстанавливаются из среднего FPS. [F150](../RAW_FACTS.md#f150), [PyAV remux example](https://github.com/PyAV-Org/PyAV/blob/v16.0.1/examples/basics/remux.py), [F158](../RAW_FACTS.md#f158).

Resolver выбирает segments по camera/profile/source generation и actual presentation coverage `[event_start−pre, event_end+post]`, учитывает random-access dependencies и внутренние holes, а не только min/max timestamps. После close independently decoded output сверяется с frame marker/PTS, фиксируются input/output time_bases, rescale/offset, hashes и mapping uncertainty. Успешный ранний [E009](../OPEN_QUESTIONS.md#e009) допускает этот recorder route; при fail custom recorder выключается, остаётся analyzed snapshot и при необходимости native archive с `mapping=unknown`. Два параллельных recorder в минимум не входят. Если полный кейс требует точных клипов, snapshot cut остаётся blocker обязательного требования. [F158](../RAW_FACTS.md#f158), [F226](../RAW_FACTS.md#f226), [F206](../RAW_FACTS.md#f206).

### Кольцо имеет конечную глубину, событие — конечные evidence jobs

Pre-roll невозможен для произвольно позднего результата при конечном диске. Срок evidence admission считается от самого раннего необходимого anchor; при длинном dwell onset старше последнего analyzed frame. При желании начало можно заранее pin-ить как provisional onset на конечный интервал, но нельзя бесконечно расширять один job. В проекте отделены live acceptance, evidence lookback, ожидание post-roll, close и общий job wall deadline. [F159](../RAW_FACTS.md#f159).

| Проектный bound для fixture | Значение и смысл |
|---|---|
| `A_live` | 2 s от local receipt; позднее — reject live, это не sensor latency |
| `L_evidence` | 20 s от earliest required anchor до durable pin request; превышение — late evidence unavailable/partial |
| Pre P / post Q | 5 s / 5 s, actual coverage обязательно проверяется |
| Segment target S / verified IDR gap G | 2 s / ≤1 s; без bounded G нет close guarantee |
| Close wait C / job deadline J | 4 s после target post-roll / 30 s wall; превышение даёт terminal partial/failed |
| Finite chunk / rollover | ≤10 s media на chunk; 60 s media на manifest child того же incident |
| Retained per incident | 10 min либо byte cap, что наступит раньше; затем coverage_truncated, metadata продолжаются |

Это сохранённые проектные числа [F159](../RAW_FACTS.md#f159), не требования кейса и не LinQ SLA. При bounded input progress, I/O, GOP и проверенной media↔receipt mapping формула `H ≥ P + L_evidence + S + G + C + maintenance_margin` даёт 5+20+2+1+4+3=35 s; H=40 s — выбранная fixture глубина. После durable admission persisted future pin range защищает post-roll, иначе Q/полный job envelope нужно добавить. В bytes кольцо считается по max bitrate, overshoot GOP, open parts и FS/index reserve, а не по среднему bitrate. Byte cap имеет приоритет над обещанием полного окна. [F160](../RAW_FACTS.md#f160).

Даже короткий native segment target — minimum. MediaMTX ждёт suitable next sync/IDR после целевого времени; `recordSegmentDuration: 2s` при длинном GOP или stalled source не даёт верхней границы 2 s. Default hour-long segment неудобен для малого кольца, а part 1 s не означает segment 1 s. `recordMaxPartSize` ограничивает part RAM, не весь диск. `recordDeleteAfter: 0s` допустим только с нашим работающим bounded janitor: native cleaner не знает incident pins и создаёт гонку с независимой pin DB. [F151](../RAW_FACTS.md#f151), [F157](../RAW_FACTS.md#f157).

Жизненный цикл evidence — `pending → waiting_postroll → waiting_close → validating → complete|partial|failed|unavailable`. Admission транзакционно сохраняет interval/generation/refs/future range/reserved bytes/deadline. Post-roll ждёт media progress и monotonic deadline, не бесконечного движения PTS. Retention и pin admission сериализуются одним owner: только closed validated, unpinned и неиспользуемый file может перейти в deleting. Manual и backup holds тоже имеют owner/expiry/cap, квота считает unique retained bytes. При low space сначала удаляются expired unpinned и failed temporary derivatives, затем отклоняются новые jobs/extensions; pinned originals не исчезают молча. Исчерпанный reserve останавливает recorder с `recording_unavailable:disk_full`; анализ может продолжаться, если его ресурсы доступны. [F161](../RAW_FACTS.md#f161), [F192](../RAW_FACTS.md#f192), [F196](../RAW_FACTS.md#f196).

DB и файловая система не имеют общей транзакции. Предлагается durable intent/reservation → temporary write → trailer/close → independent validation/hash → flush и supported FS metadata persistence → atomic rename в одной ФС → commit `closed_validated` и refs. Crash после rename до DB commit оставляет orphan для reconciliation. Удаление также проходит mark deleting → unlink → tombstone, с запретом новых pins на deleting. Rename/hash сами не доказывают power-loss durability. У native fMP4 recorder в прочитанных функциях нет явного File.Sync; documented loss последней part не является нашим испытанием питания. [F156](../RAW_FACTS.md#f156), [F196](../RAW_FACTS.md#f196).

### Backup и recovery входят в тот же проект

Обычный copy открытого `.db` не является выбранной процедурой backup: committed state может быть в WAL, а последовательное копирование `.db`/`-wal` при записи не даёт согласованного snapshot. Hot WAL не удаляют как мусор. Поддержанный primitive — `Connection.backup` в отдельном maintenance worker, с overall budget и проверкой завершённого destination. Его `sleep` не общий timeout. Backup БД не создаёт атомарный snapshot media и внешнего мира. [SQLite backup](https://sqlite.org/backup.html), [F193](../RAW_FACTS.md#f193).

Для минимума предлагается короткое maintenance window: остановить mutations/submissions/retention deletion, bounded drain writer, зафиксировать cutoff и unresolved remote obligations, собрать inventory immutable closed media с backup holds. Создать backup в новый temporary destination, проверить integrity_check и foreign_key_check отдельно, critical keys/refs и actual media size/hash. Только весь проверенный комплект публикуется с manifest/cutoff; pending tails остаются partial. При необходимости восстановления после disk loss копия должна лежать в другом failure domain. RPO — реальный cutoff последнего полного backup, RTO неизвестно до проверки; image tar этого не заменяет. [F194](../RAW_FACTS.md#f194).

Recovery начинает с fencing старых owners и нового boot/deployment generation, закрытого admission и retention. Исходный повреждённый комплект сохраняется для диагностики; restore выполняется отдельно, без подмешивания WAL другой DB generation. Затем проверяются runtime/schema/config, DB/FK, files/index, tail coverage и hashes. Missing refs становятся partial/unavailable, orphan не получает event provenance по filename. Pins/reservations пересчитываются из durable jobs/manifests/manual/backup holds до первого удаления. Старые monotonic leases не переносятся между boot. Наконец remote ledger сверяется с внешним состоянием, включая post-cutoff jobs; без надёжного reconcile LinQ admission остаётся STOPPED. Read UI может уже показывать recovering/stale. Process kill, OS/power crash и disk loss — разные классы проверки; ни один здесь не выполнен. [F195](../RAW_FACTS.md#f195), [F196](../RAW_FACTS.md#f196), [E016](../OPEN_QUESTIONS.md#e016).

## Экран с аналитикой: показать именно анализированный кадр

Самый простой честный вид для жюри — JPEG и boxes одного frame_id в одном binary message, отрисованные одним canvas pass. Он может иметь меньший FPS и бо́льшую задержку, чем original camera video, зато не выдаёт ответ на прошлый кадр за наблюдение текущего. Retained source representation сохраняется при admission, а после результата нельзя заново взять «текущий» кадр. Thumbnail допустим с transform и явным profile; он не называется original evidence. TTL view retention освобождает только view bytes, не ещё borrowed SDK input. Viewer ACK удерживает JPEG, а не raw ndarray камеры. [F116](../RAW_FACTS.md#f116), [F170](../RAW_FACTS.md#f170).

Для этого выбрана standalone `websockets.asyncio.server.serve` 17.0.1 и native WebSocket/Canvas в браузере. Она не требует добавлять ASGI/FastAPI/Starlette/Uvicorn ради одного view route. Один WSS `/view/v1`, bounded HELLO и camera authorization, один долгоживущий sender на connection. JPEG encode выполняется один раз на accepted frame и разделяется viewers, но каждый viewer всё равно создаёт NIC traffic. `broadcast()` без backpressure и task-per-frame для этого route не используются. [websockets pinned source](https://github.com/python-websockets/websockets/tree/fd3f16cc4f57ace08e323a7806f1432e957cb75e), [F162](../RAW_FACTS.md#f162), [F163](../RAW_FACTS.md#f163), [F166](../RAW_FACTS.md#f166).

Предел mailbox=1 недостаточен: send может быстро положить кадры в transport/TCP/browser queues. В 17.0.1 `send()` вызывает transport.write/drain, а drain ждёт paused transport; завершение send не означает render. `max_size`/`max_queue` относятся ко входящим control messages, write watermarks не ограничивают outgoing JPEG целиком. Browser `bufferedAmount` описывает browser→server send, а не очередь получаемых изображений. Поэтому нужен application credit: ровно одно ещё не подтверждённое изображение на connection, включая все его tiles. [F162–F165](../RAW_FACTS.md#f162).

Перед send owner атомарно занимает credit и сохраняет `(view_epoch, delivery_seq, nonce, camera_id, stream_epoch, frame_id)`. Он ждёт одновременно send completion и точный ACK после draw; early ACK в SENDING не разрешает следующий send до завершения первого. Duplicate/future/old/wrong-nonce ACK credit не создаёт. Timeout переводит connection в terminal CLOSING и инициирует close, а не возвращает READY. Active и closing connections продолжают занимать общий admission cap до cleanup. У выбранной библиотеки `close_timeout` по чтению кода не доказывает жёсткий wall bound всего teardown при blocked transport; этот вопрос остаётся в [E012](../OPEN_QUESTIONS.md#e012). Experimental transport.abort subclass не является public websockets API и в обязательный минимум не входит. [F164](../RAW_FACTS.md#f164), [F167](../RAW_FACTS.md#f167).

Предлагаемый wire format — `[u32 big-endian header_bytes][bounded UTF-8 JSON header][JPEG]`; header содержит length, dimensions, frame/model/geometry identity и boxes в объявленном пространстве. uint64 IDs передаются decimal strings из-за JS Number precision. Fixture profile: envelope≤512 KiB, metadata≤16 KiB, JPEG≤496 KiB, до 1280×720/921600 pixels, до 200 boxes, до четырёх tiles/page и трёх admitted connections. Send-progress deadline 1 s, overall render-ACK 2 s от send-start и close grace 2 s — проектные начальные значения для проверки. Если detail не помещается, меняются profile/FPS/tiles с quality gate либо показывается size_cap/unavailable; лимит не растёт бесконечно. [F166](../RAW_FACTS.md#f166), [F167](../RAW_FACTS.md#f167).

Browser ставит busy до первого await; async onmessage сам по себе не сериализует обработку. Допускается один createImageBitmap, один rAF/draw с image+boxes и bitmap.close в finally. Старый connection/source generation после decode повторно проверяется и не рисуется. Hidden tab инвалидирует generation и закрывает подписку; visible ждёт старый decode cleanup, открывает новый view_epoch и получает current latest. Incident history загружается отдельно, JPEG-пауза не replay-ится. Если renderer замёрз до close event, elapsed от последнего выданного local credit проверяется и при receive, и непосредственно перед draw: поздний TCP кадр не должен выглядеть новым. ACK после canvas draw — frontend telemetry, не доказательство physical scanout или прочтения человеком; злой клиент может лгать. Поэтому count/byte/rate caps нужны независимо от ACK. [F168](../RAW_FACTS.md#f168), [F169](../RAW_FACTS.md#f169).

App-owned payload bound можно описать как `(C+V)B` для C shared latest и V active+closing outstanding, плюс encoder slots и возможные V envelope copies. Он не равен total RSS: добавляются allocator, codec scratch, WS/TLS, kernel, browser bitmap/canvas/GPU. Номинальные canvas+bitmap RGBA8 при 1280×720 требуют около 7.37 MB, но это лишь два представления изображения. Отдельные metrics должны считать retained view и borrowed input, server sent/ACK, viewer skips/hidden/deadline и analytics drops. Пропуск показа одного viewer не является потерей inference или отсутствием violation. [F168](../RAW_FACTS.md#f168), [F170](../RAW_FACTS.md#f170).

Возраст тоже показывается с областью. Если ingest и sender в одном clock domain, `server_age_at_send=(send_mono−ingest_mono)` — время после нашего ingress, а не sensor→screen. Browser знает receive→draw и since-last-draw; server знает send→valid ACK, включающее обратный путь. Складывать server age и browser receive→draw как exact total нельзя: transit пропущен. Возможна консервативная upper estimate `server_age_at_send + (draw_local−credit_issued_local)` при подтверждённых duration clocks и общем ingest/sender domain, с запасом на drift; это может переотбрасывать кадры и не включает physical display. При unknown mapping поле total age остаётся unknown. [F171](../RAW_FACTS.md#f171).

Native original WebRTC — полезная опция после core. Для exact overlay понадобится source PTS/frame→RTP timestamp/SSRC/epoch→rVFC mapping, а не `Date.now()` ответа. rVFC best-effort, mediaTime для live может быть нулём, RTP field не произвольный camera ID. H.265 browser support ограничен; H.264 с B-frames непригоден в описанном MediaMTX WebRTC route. WHEP reader требует OPTIONS/POST201/Location/PATCH/DELETE/Link/CORS, ICE media живёт отдельно от HTTP proxy; STUN не заменяет TURN. WHEP на дату получения — active draft-ietf-wish-whep-05, не финальный RFC. LL-HLS default parts 200 ms и пример 3×200=600 ms не являются end-to-end benchmark. Пока mapping не доказана, original live показывается отдельно от analyzed view без якобы точных boxes. [F106–F115](../RAW_FACTS.md#f106), [E013](../OPEN_QUESTIONS.md#e013).

Преобразование координат хранится вместе с result: для letterbox используются фактические scale/padding, затем viewport contain/cover, crop/rotation/flip и DPR. Одинаковое соотношение размеров main/sub не доказывает одинаковый FOV. Разрешение Canvas и image profile ограничиваются вместе; UI resize не должен бесконтрольно увеличивать backing canvas. [F116](../RAW_FACTS.md#f116).

## Измерять три разных задержки

Время ответа NN, задержка processed video и время от физического начала нарушения до тревоги отвечают на разные вопросы. Определим `L_result` до пригодного actor observation, `L_video` до canvas draw собственного кадра и `L_alarm` до выбранной границы доставки тревоги. Physical display и operator acknowledgement измеряются отдельно. Миллисекунд LinQ в базе нет, поэтому бюджет сейчас задаётся формулами, местом часов и исходом при превышении. Это позволяет распределить будущий SLO без выдуманных измерений. [F132](../RAW_FACTS.md#f132), [F207](../RAW_FACTS.md#f207).

| Участок | Frame/tensor API | Shell с granted remote app plane | Job API | Часы, ограничение и failure |
|---|---|---|---|---|
| Exposure→ingress | Camera encode/network/relay | Camera encode/compressed WAN/relay | По выбранному input route | Sensor age unknown без calibration/optical test; read timeout его не ограничивает |
| Decode/pre/sample | Local decode/resize/encode/pack | Remote decode/pre | Local prep либо supplied video job | Same-host monotonic; source FPS decode, latest/count/bytes, no progress→stale |
| Admission | Local scheduler | Remote scheduler | Local ledger/submit | Локальная duration, per-camera/bytes/held caps; expiry→drop, credit остаётся |
| Отправка | Input WAN/RPC | Runtime IPC, compressed WAN уже учтён | Upload/submit ack | Client roundtrip доступен; one-way unknown; ambiguous→unknown ledger |
| Queue/NN | Opaque queue/remote NN | Own worker/shared-device contention/NN | Pending/start/run | Remote durations лишь если выданы; cap work не bound wait; no lifecycle→bounded stop |
| Return/post/apply | Download/raw-head post либо compact parse | Host post/IPC/state | Visibility/poll/fetch/post | Полный L включает NMS/cascade/reorder; late→Gap/history |
| Rules/commit | Local state/DB | Colocated state/DB | Local после collector | Dwell source time; commit local monotonic, error не success |
| Processed view | Retained image/encode/WS/browser | Remote selected images/WAN/browser | Только fresh result, иначе history | Одно credit/connection, browser clock отдельно; timeout/hide→close/stale |
| Тревога | Commit→UI projection/history | То же с WAN | После collector | Render ACK/optical отдельно от send; не ждёт clip |
| Clip ready | Pin/post-roll/close/validate/commit | На colocated recorder | Finite late acceptance | GOP/progress/I/O bounds; deadline→partial/unavailable |

Для одного trace, с возрастом до admission ровно один раз:

```text
L_result_API = ingress_age + decode/pre + local_admission + upload
             + remote_queue + NN + output_download + post + ordered_apply
L_result_shell = compressed_ingress_age + remote_decode/pre + remote_admission
               + shared_device_wait + NN + host_post + IPC_apply
L_result_job = input_prep + local_admission + upload/submit + job_queue/start
             + job_run + terminal_visibility + poll_detection + fetch
             + post + ordered_apply
```

Это проектная декомпозиция [F207](../RAW_FACTS.md#f207). Если state/projection остались у команды при remote decoder, shell formula дополняется serialized result и retained image return. Для GUI/manual поддержанного автоматического `L_result_live` нет. Completed job ещё не usable client result. Идеальное periodic polling даёт extra wait `[0,Δ)` и mean Δ/2 только при uniform phase/no outage; backoff и quota меняют это. `L_video_processed` добавляет к own-frame→usable-result projection/encode wait, send/transit и browser decode/draw. Native original video идёт иным путём без ожидания NN.

`L_alarm_onset` включает sampling/onset uncertainty, dwell qualification, обработку qualifying observation, commit и delivery. Для идеальных 5 fps период Δ=200 ms, первый hit ждёт `[0,200)` ms, mean 100 ms только при равномерной независимой фазе события. k последовательных positive observations добавляют `(k−1)Δ` лишь без drops и нерегулярного cadence. Physical dwell D секунд не равен completion count; отсчёт от onset и от первой положительной выборки даёт разное квантование. Событие короче Δ может не попасть sampler вообще. Поэтому сохраняются отдельно onset→alarm и rule-eligible→alarm, с misses и unknown intervals. [F132](../RAW_FACTS.md#f132).

Журнал каждого frame хранит входы/выходы ingest, decode, sample, pre/encode, local queue, send/receive, remote stage durations при их реальном наличии, post/rules, commit и UI receive/draw. Same-host durations измеряются monotonic_ns с host/run domain. UTC полезен для корреляции, но не доказывает синхронизацию. Если ошибки часов двух endpoints ограничены εA и εB, у timestamp difference uncertainty до εA+εB. Без этого нельзя написать «точность 1 ms». Для sensor→screen помогает оптический тест: меняющийся timestamp/LED и экран в общей высокочастотной записи; Axis loop-overlay при 25 fps уже имеет квантование до 40 ms. Он проверяет видео, а onset→alarm снимается отдельно. [Axis latency paper](https://www.axis.com/dam/public/4a/c9/b0/latency-in-live-network-video-surveillance-en-US-443172.pdf), [F125](../RAW_FACTS.md#f125), [F126](../RAW_FACTS.md#f126), [E017](../OPEN_QUESTIONS.md#e017).

На слайде нужны source/ingest FPS, decode FPS, admitted unique frames, completed valid RPC, fresh ordered applied observations, model invocations/crops и render FPS — каждый со своим denominator. Aggregate 250 fps может скрывать starvation одной камеры; рядом показываются per-camera service, max source gap, wall inter-result gap и age. В журнал попадают offered, sampled-out, queue-replaced, timeout, invalid/error, late/epoch reject, completed, undetected и session-ended pending. Timeout — failure либо `latency>deadline`, pending в конце — right-censoring, а не удалённая строка. При более 1% незавершённых нельзя заявлять unconditional p99 ниже deadline по успешному подмножеству. [F132](../RAW_FACTS.md#f132), [F184](../RAW_FACTS.md#f184).

p50/p95/p99 сопровождаются n, длительностью, warm-up, offered workload, backend/model/hash/precision/batch/input, OS/CPU/GPU/driver, network и queue caps. Нагрузка paced независимо от ответов, иначе медленная система сама уменьшает себе offered rate. Cold start, reconnect и downtime остаются в reliability denominator. Общий p95 получают из end-to-end traces или совместимых histograms; среднее worker p95 и сумма stage p95 не являются p95 системы. Prometheus/Grafana возможны позже; для минимума достаточно structured log, counters и простого metrics endpoint, если сохраняются эти определения. [Prometheus histograms](https://prometheus.io/docs/practices/histograms/), [F127](../RAW_FACTS.md#f127), [F132](../RAW_FACTS.md#f132).

## Отказ виден отдельно от отсутствия нарушения

Для каждой камеры нужны независимые `video_state`, `analysis_state`, `recording_state` и `delivery_state`. Иначе живой RTSP кадр скроет умерший LinQ, а работающая NN скроет потерю evidence. Последний image/overlay затемняется и получает age; отсутствие новых результатов не превращается в надпись «нарушений нет». CPU/RTX fallback получает явный backend badge, отдельные event/run counters и периоды unavailable для обязательного LinQ. Сохранённый witnessed run показывается как replay, а не текущий live. [F131](../RAW_FACTS.md#f131), [F204](../RAW_FACTS.md#f204).

| Сбой | Обнаружение и восстановление | Что видит пользователь |
|---|---|---|
| Камера/decoder EOF, control alive без media | Decoded progress/age, close container, bounded backoff+jitter/reopen; зависший own worker изолированно restart; новая session identity | Video unavailable/stale, interrupted analysis coverage |
| LinQ timeout/overload | Live deadline/last usable age, latest вместо backlog, limited half-open probe, persisted remote held/reconcile | Video может оставаться live; analysis unavailable или degraded |
| Late/old model/old epoch result | Correlation/version/deadline validation, reject live, завершение remote accounting отдельно | Нет старых boxes на новой сессии, reason в history/metrics |
| Один источник/cascade перегружен | Per-camera fairness, bounded ROI/bytes, admission limit, measured target | Реальный applied FPS/coverage; не общий зелёный aggregate |
| Writer stall/disk-full | Bounded writer queue, reserve, reject admission; reopen/reconcile после устранения | Event not committed либо evidence unavailable отдельно; никаких ложных acknowledgements |
| UI hidden/offline/slow | Render credit timeout, close/resync, history из DB по revision/cursor | Stale/disconnected view; committed incidents доступны после восстановления |
| Process/host recovery | Fenced owners, DB/media/pins/remote ledger reconcile | Recovering, missing/partial evidence и unresolved remote jobs явно |

Camera reader можно описать `CONNECTING→STREAMING→STALE/ERROR→BACKOFF→CONNECTING`. Backoff 0.5,1,2,4… до 10 s с jitter в ingress fixture либо другой конечный capped profile — проектные числа для проверки. Ошибка credentials/unsupported codec относится к configuration error, бесконечный reconnect её не исправляет. Watchdog смотрит progression decoded sequence, а не PID/socket alone. Docker HEALTHCHECK добавляет unhealthy status, restart policy действует на exited process; их сочетание само по себе не перезапускает живой unhealthy контейнер. Нужен own supervisor/action или безопасный self-exit; remote shared device reset не подразумевается. [F052](../RAW_FACTS.md#f052), [F128](../RAW_FACTS.md#f128), [F129](../RAW_FACTS.md#f129).

Минимальный camera health проверяет progress и age. Repeated pixels, black/underexposed, overexposed, blur и scene shift — optional `suspected_anomaly` с per-scene baseline/ROI, suitability и CPU budget. Новые timestamps при одинаковой картинке могут означать нормальную статичную сцену; темнота — lights-off, blur — движение/сжатие, shift — legitimate PTZ или перекрывший обзор погрузчик. Axis Image Health Analytics прямо описывает unsuitable detail-poor scenes и неоднозначность lighting/occlusion; простой dark-image detector не доказывает умышленное закрытие линзы. Overexposure heuristic здесь наша гипотеза, а не заявленная capability Axis. [Axis Image Health](https://help.axis.com/en-us/axis-image-health-analytics), [F201–F203](../RAW_FACTS.md#f201), [E019](../OPEN_QUESTIONS.md#e019).

Внешний messenger после core — дополнительный канал из outbox. По прочитанным текущим Telegram FAQ: избегать >1 message/s в один chat, groups ≤20/min, бесплатный broadcast примерно 30/s; sendVideo до 50 MB, success Message не означает read, retry_after в seconds. У MAX документы указывают `platform-api2.max.ru`, `Authorization: <access_token>` вместо query token и trust сертификату Минцифры; это не повод отключать TLS verification. POST messages — до 2/s на диалог/группу/канал, общий лимит здесь не установлен. У команды нет подтверждённых accounts/tokens/tests; private clip URL может быть недоступен recipient/provider. Ссылка на защищённую карточку и thumbnail часто проще полного upload, но доступ к ней проверяется. [Telegram FAQ](https://core.telegram.org/bots/faq), [MAX API](https://dev.max.ru/docs-api), [F120–F122](../RAW_FACTS.md#f120), [Q018](../OPEN_QUESTIONS.md#q018).

## Что действительно означают 50 и 500 камер

Сайзинг начинается с профиля, а не с TOPS. В едином сценарии ниже N=50/500, main 1920×1080 25 fps и 4 Mbit/s, optional sub 1280×720 25 fps и 1 Mbit/s, analysis 5 fps, JPEG 100000 B/frame. Это допущения: 720p не задаёт bitrate 1 Mbit/s, а 100 kB не гарантируют качество или размер actual JPEG. SI decimal: kB=1000 B, MB=10⁶ B, GB=10⁹ B, TB=10¹² B, Mbit/s=10⁶ bit/s. Для памяти отдельно указывается nominal 8-bit NV12 1.5 B/pixel/RGB 3 B/pixel без stride/copies. Все числа — локальная арифметика, не benchmark камеры или LinQ. [F068](../RAW_FACTS.md#f068), [F133](../RAW_FACTS.md#f133), [F200](../RAW_FACTS.md#f200).

| Величина и формула | 50 камер | 500 камер | Условие |
|---|---:|---:|---|
| Main camera→gateway `N×4 Mb/s` | 200 Mb/s | 2 Gb/s | Compressed ingest; 25/250 MB/s payload write |
| Main+sub `N×(4+1) Mb/s` | 250 Mb/s | 2.5 Gb/s | Если оба профиля приходят в узел |
| JPEG input uplink `8NfE[J]` | 200 Mb/s | 2 Gb/s | 100 kB×5 fps=4 Mb/s/camera |
| Tensor 640² RGB uint8 `8Nf×640×640×3` | 2.4576 Gb/s | 24.576 Gb/s | Только при actual uint8 contract |
| Тот же FP32, ×4 | 9.8304 Gb/s | 98.304 Gb/s | 4915200 B/frame, dtype не свободный выбор |
| Raw 1080p NV12 ×5 fps | 6.2208 Gb/s | 62.208 Gb/s | Nominal без stride/copies |
| Raw 1080p RGB ×5 fps | 12.4416 Gb/s | 124.416 Gb/s | 6220800 B/frame |
| Raw 720p NV12 / RGB ×5 fps | 2.7648 / 5.5296 Gb/s | 27.648 / 55.296 Gb/s | Даже меньший raw не становится маленьким WAN payload |
| Raw-head return `8Nf×2822400 B` | 5.6448 Gb/s | 56.448 Gb/s | Условный `[1,84,8400] FP32`, не выбранная модель |
| Compact return `8Nf×2404 B` | 4.808 Mb/s | 48.08 Mb/s | ≤100 packed detections, без envelope/JSON/masks |
| Remote decode→local analyzed JPEG return | +200 Mb/s | +2 Gb/s | Если каждый analyzed image возвращается команде |
| Selected view egress `8×3×4×2×100000` | 19.2 Mb/s | 19.2 Mb/s | Три viewers, четыре tiles, 2 fps/tile |

Input и output — разные направления. В этом сценарии JPEG uplink равен main compressed bitrate, поэтому от remote decode не возникает экономии uplink автоматически. Его выигрыш может состоять в локализации raw tensor/postprocess, но local processed view добавляет изображение в обратный канал. Colocated remote projection передаёт только выбранные tiles непосредственно браузеру. Camera LAN, gateway uplink/downlink, remote host traffic и app→browser нужно рисовать по фактическим границам: нельзя сложить всё как нагрузку одного full-duplex линка. Если проектно выбрать 70% utilization, полезные 2 Gb/s требуют хотя бы 2/0.7≈2.857 Gb/s measured available bandwidth до VBR/protocol запасов; это допущение, не стандарт. [F133](../RAW_FACTS.md#f133), [F200](../RAW_FACTS.md#f200).

Разница raw/compact return в примере обусловлена точной формой. Один head `[1,84,8400] FP32` содержит 2822400 B; compact M≤100 records по 4 FP32 coords, FP32 score и INT32 class — 24 B/record плюс count 4 B, максимум 2404 B. Это не actual LinQ output и не универсальная compression ratio. JSON numeric arrays считаются по wire bytes, FP16 cast не делается без разрешённого контракта. Postprocess CPU требует `NfE[cpu_seconds_post/frame] < available CPU seconds/s`; fetch/post queues и tensors имеют отдельные byte caps. [F147–F149](../RAW_FACTS.md#f147), [Q025](../OPEN_QUESTIONS.md#q025).

Control traffic считается отдельно. При J outstanding jobs, poll interval Δ и поддержанном batch query до b IDs грубая rate `q_poll≈ceil(J/b)/Δ`, а status traffic `8q_poll×E[request/response bytes]`. Условные J=50, Δ=0.5 s, b=1, 1 kB request/2 kB response дают 100 calls/s и 0.8/1.6 Mb/s вверх/вниз. Это не quota LinQ; batch query уменьшает calls, но крупнеет response, поэтому traffic не делится автоматически на b. Unknown jobs могут создавать control load уже после live stop; status, повторяющий полный output, особенно дорог. [F148](../RAW_FACTS.md#f148), [F149](../RAW_FACTS.md#f149).

View traffic определяется выбранными tiles, а не registered cameras. Для трёх viewers с четырьмя tiles выше одинаковые 19.2 Mb/s и при 50, и при 500 источниках; если каждому открыть все 500, арифметика дала бы 2.4 Gb/s, но minimum такой admission запрещает. При одном credit на connection четыре tiles по 2 fps требуют суммарно 8 rendered messages/s и идеального ACK cycle ≤125 ms. Четыре tiles не дают четыре credits. JPEG encode shared, NIC copies остаются; replay, seek, clip downloads и backup добавляются поверх live. [F199](../RAW_FACTS.md#f199).

Хранение определяется интегралом bitrate: `S=N×b×T/8`, при b в bit/s и T в s. Для суток `GB/day/camera=10.8×b_Mbit/s`. [F105](../RAW_FACTS.md#f105), [F133](../RAW_FACTS.md#f133).

| Хранение payload | 50 камер | 500 камер |
|---|---:|---:|
| Main 4 Mb/s за сутки | 2.16 TB | 21.6 TB |
| Main за 7 суток | 15.12 TB | 151.2 TB |
| Main за 30 суток | 64.8 TB | 648 TB |
| Sub 1 Mb/s за сутки | 0.54 TB | 5.4 TB |
| Все JPEG 100 kB×5 fps за сутки | 2.16 TB | 21.6 TB |
| Compressed ring 40 s при 4 Mb/s | 1 GB | 10 GB |
| Условные 20 events/day/camera×30 s×4 Mb/s | 15 GB/day | 150 GB/day |

Это без containers/FS/index/replication/backup/reserve и derivative duplication. Event fraction не равен доле кадров с violation: pre/post-roll, округление до GOP/segments и long incidents расширяют окно. Overlap может делить originals, но отдельные exports повторно занимают место. Для ring берётся max bitrate с overshoot/open parts/reserve; табличные 1/10 GB по среднему не являются hard cap. Main archive остаётся прежнего размера, даже если анализируется только маленький substream. [F104](../RAW_FACTS.md#f104), [F105](../RAW_FACTS.md#f105), [F160](../RAW_FACTS.md#f160).

Полный decode считается по source FPS: `Pdecode=NWHf_source`. Получается 2.592/25.92 GPixel/s для 50/500×1080p25 и 1.152/11.52 GPixel/s для 720p25. Требуемые уникальные analysis observations — 250/2500 в секунду; secondary crops прибавляются отдельно. Full-rate raw traffic в памяти при 1080p25 — nominal NV12 3.888/38.88 GB/s либо RGB 7.776/77.76 GB/s до повторных copies. Один latest 1080p slot требует NV12 155.52 MB/1.5552 GB, RGB 311.04 MB/3.1104 GB, но это не total RSS/VRAM. [F133](../RAW_FACTS.md#f133).

Рабочий memory inventory включает base processes/libs/contexts, demux/parser/jitter, decoder DPB/reorder/decode/output surfaces, latest pools, immutable admitted frames, native borrowed inputs, retained view, pre/post scratch, outputs, active+closing view connections, DB/index/cache и reserve. NVIDIA NVDECODE guide отдельно задаёт minimum decode surfaces и output mappings; забытый unmap исчерпывает ресурс, contexts имеют overhead. OS inventory добавляет processes/threads/stacks, FD/handles, upstream/relay/remote/control sockets, ports/TIME_WAIT/NAT, open segments/logs/DB/WAL и IPC. Пятьсот логических actors не требуют пятисот процессов, но sharding увеличивает область одного native hang. Коэффициенты bytes/stream и FD/stream неизвестны до измерения actual backend. [NVDEC guide](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-video-decoder-api-prog-guide/index.html), [F197](../RAW_FACTS.md#f197), [F198](../RAW_FACTS.md#f198).

Диск измеряется одновременно с append, concurrent replay/export, hash/validation, backup/checkpoint и derivative writes. Сумма 250 MB/s входного payload на 500 main streams не является доказанной Cwrite: random IO, cache misses и tail latency могут стать пределом раньше. Admission строится как минимум измеренных usable budgets inference/decode/preprocess/input/return/post CPU/network/storage/RAM/FD/sessions после per-camera temporal gate. Например, для однородного JPEG пути:

```text
Nmax ≤ floor(min(Cinf/f_a,
                 Cdec/(W×H×f_source), Cpre/f_a,
                 Cin/b_in, Cup/(8×f_a×E[J]), Cdown/(8×f_a×E[O]),
                 Cpost_cpu/(f_a×E[cpu_post]),
                 Cwrite/(b_record/8), Susable/((b_record/8)×T),
                 Musable/mcam, K_local/(f_a×E[L_local])))
```

Это necessary planning expression, а не финальная admission реализация: неиспользуемые terms убираются, quota/remote residency, variable fan-out, byte caps и per-camera p_i/gaps проверяются отдельно. Все C должны быть measured usable capacity нужной полной цепочки с reserve, а не peak. Cinf LinQ сейчас unknown. Гипотетически Cinf=300 fps и u=0.7 дают 210 effective и минимум ceil(250/210)=2 узла для 50, ceil(2500/210)=12 для 500. При Cinf=1000 — 1 и 4. Это демонстрация формулы, не LinQ numbers или рекомендация покупки; другие bottlenecks увеличат число. TOPS и ops/frame не устанавливают поддержанные operators, compilation, precision, copies, queue и service fairness. [F133](../RAW_FACTS.md#f133), [F181](../RAW_FACTS.md#f181), [F182](../RAW_FACTS.md#f182), [Q022](../OPEN_QUESTIONS.md#q022).

### Чужие benchmarks полезны как протокол, а не как обещание

NVDEC SDK 13.0 даёт indicative Ada per-engine показатели для 1920×1080 YUV420 на Windows 11, SDK 13.0, video clock 2160 MHz: H.264 903 fps, HEVC 1641, HEVC Main10 1520, AV1 1018. Это не measured full-service RTX 4070 команды: нет нашего bitstream/GOP/driver/transfers/resize/inference/UI/latency distribution. Capability matrix указывает RTX4070 Desktop/Laptop Ada, один NVDEC, но exact SKU/VRAM/drivers команды всё равно инвентаризируются. NVENC session cap нельзя использовать как NVDEC streams limit. [NVIDIA NVDEC 13.0](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-application-note/index.html), [F045](../RAW_FACTS.md#f045), [F046](../RAW_FACTS.md#f046).

В DeepStream 7.1 T4 NVIDIA опубликовала 45 H.265 и 31 H.264 streams 1080p30 с dual Xeon E5-2650 v4 2.20 GHz/48 threads, T4 clock 1513 MHz, Ubuntu 22.04, driver 535.161.08, CUDA 12.2, TensorRT 8.6.1.6. Memory literal источника сохранён как `360448Mb (22x16384) DDR42666, 2400MHz`; исправлять его по памяти нельзя. PGIE TrafficCamNet ResNet18 batch=N interval=0, IOU 960×544, две SGIE ResNet18 VehicleTypes/VehicleMake 224×224 batch32 async; tiler/render/OSD off. CPU/GPU указаны 51.81%/100% для H.265 и 2.72%/61.23% для H.264. Нет WAN, нашего RTSP/UI/alerts, p95/p99/duration или переноса на LinQ. [DeepStream 7.1 performance](https://archive.docs.nvidia.com/metropolis/deepstream/7.1/text/DS_Performance.html), [F123](../RAW_FACTS.md#f123).

Переносимого CPU/QuickSync decode-only «потоков на ядро» для неизвестного компьютера не найдено. QuickSync practitioner tables в рассмотренном материале измеряют encode/transcode, Smelter — decode+encode+composition; их FPS не подставлены в Cdec. Intel VPL сам по себе dispatcher, runtime implementation и доступный iGPU требуют проверки. На RTX GPU-resize до download может уменьшить copies, но граница CPU/API/WAN заканчивает zero-copy. Поэтому ближайшее действие — [E003](../OPEN_QUESTIONS.md#e003), а не вымышленный коэффициент CPU. [F047–F049](../RAW_FACTS.md#f047).

## Поставка и закрытый контур имеют конкретную область

Собственный app bundle и proprietary inference worker/client — две единицы развёртывания. При API client код приложения может работать в своей pinned среде; supplied LinQ native ABI не смешивается с ней. Offline комплект содержит app commit/config/migrations, selected wheels/native libraries/notices, static UI без CDN, разрешённые model artifacts/golden inputs, images с platform/digest, перечень secret files и runbook sample→event. DB/media backup передаётся отдельно: `docker image save/load` не содержит mounted data, host driver, Docker/Compose или сеть до LinQ. Команды `docker compose up -d --no-build --pull never` и platform filtering применимы только после проверки actual CLI; `--platform` у image save/load требует API 1.48+. [Docker save](https://docs.docker.com/reference/cli/docker/image/save/), [Docker load](https://docs.docker.com/reference/cli/docker/image/load/), [F012](../RAW_FACTS.md#f012), [F013](../RAW_FACTS.md#f013), [F209](../RAW_FACTS.md#f209).

Clean-target smoke проверяет отсутствие runtime pip/apt/model auto-download и CDN, но offline own client не означает offline обязательный remote LinQ. Windows workspace не задаёт target OS; x86-64 image не становится ARM HX image. Для Astra отдельно фиксируются edition/update/kernel/ISA, actual Docker/Compose, privilege/rootless, mandatory labels/mounts/cgroups/device permissions, supplied driver/runtime pairing и storage. Успех UI в container не подтверждает decoder или NN driver. Compose running не ready; depends_on service_healthy помогает при старте, но не выполняет runtime reconnect. File-backed Compose secrets — mounted files, не encrypted vault, `_FILE` лишь соглашение некоторых images. [F008–F016](../RAW_FACTS.md#f008), [E015](../OPEN_QUESTIONS.md#e015).

У заявлений Astra сохранён точный scope: релиз 13.11.2025 говорит об интеграции LinQ HP с Astra Linux Server, а тестирование всей линейки — план. Релиз 07.10.2026 описывает LinQ HX с Astra Linux Embedded; упоминание сертификатов относится к Embedded OS. Они не являются сертификатом нашего приложения, всех SKU, контейнера или удалённого соединения и не дают версий driver/kernel/runtime. Изменять mandatory security или reboot общего host для «починки Docker» этот проект не предлагает; нужна поддержанная конфигурация владельца. [Astra HP/Server](https://astra.ru/about/press-center/news/gruppa-astra-i-khaytek-obedinyayut-usiliya-dlya-razvitiya-otechestvennykh-ii-resheniy/), [Astra HX/Embedded](https://astra.ru/about/press-center/news/khaytek-i-gruppa-astra-razrabatyvayut-sovmestnoe-reshenie-na-osnove-rossiyskogo-ii-uskoritelya-dlya-/), [F017](../RAW_FACTS.md#f017), [F018](../RAW_FACTS.md#f018).

Сетевая схема для внедрения — camera segment/VLAN→ограниченный ingest gateway→application segment→разрешённый outbound LinQ channel. Browser получает authenticated HTTPS application path, не camera password/admin URL/LinQ token. Viewer/operator/admin проверяются на server endpoints клипов, событий, subscriptions и изменения rules; скрытая кнопка не authorization. Clips адресуются внутренними IDs, а не user-controlled filesystem paths. Секреты читают только соответствующие owners, не frontend/logs/image layers/git. Docker socket и privileged/all-devices не передаются UI ради restart. [Axis hardening](https://help.axis.com/en-us/axis-os-hardening-guide), [NIST SP 800-82r3](https://doi.org/10.6028/NIST.SP.800-82r3), [F019–F022](../RAW_FACTS.md#f019), [F210](../RAW_FACTS.md#f210).

HTTPS управления камерой и Digest authentication не означают шифрования RTSP media; безопасный transport проверяется у actual camera firmware и client/relay. Если локальный участок plaintext, защищённый gateway channel ограничивает его область, но не становится end-to-end encryption камеры. У remote owner отдельно выясняются tenant isolation, upload/result retention, logs и delete policy. NIST segmentation/MFA guidance здесь инженерная опора, не доказательство IEC 62443 compliance; правовые вопросы и КИИ передаются `market_deployment`. [F019](../RAW_FACTS.md#f019), [F020](../RAW_FACTS.md#f020), [Q019](../OPEN_QUESTIONS.md#q019).

## Работа пяти участников и порядок сокращения объёма

Смысл плана — как можно раньше получить цельный обязательный путь. 225 person-hours не взаимозаменяемы и не доказывают schedule feasibility. Сначала одна камера, одна модель, B=1, один профиль; затем две камеры для проверки isolation. Настоящий LinQ golden run важнее второго messenger или native live. Каждый owner интегрирует свои contracts, а не сдаёт изолированную ветку в последние часы. [F206](../RAW_FACTS.md#f206).

| Участник | Основная ответственность | Ранний совместный результат |
|---|---|---|
| 1, media | Source/relay/demux/decode, clocks/identity, index/validation | Frame lineage с 2/3; E009 recorder proof вместе с 5 |
| 2, LinQ/model | Issued contract, golden input/output/witness, model/pre/post parity, adapter | Реальный result для 3/4; lifecycle/bytes/ownership для 5 |
| 3, temporal | Scheduler/fairness/per-camera admission, gaps/rules/state, credits с 5 | Ordered observations и event revision/coverage |
| 4, product | HTTP/auth/history/UI, processed WS/render/ACK, degraded states | Same-frame view и история committed events |
| 5, storage/integration | One DB writer/recovery, ledger/pins/outbox, manifest/package, metrics/runbook | Единый trace, persistence failure boundary и воспроизводимая поставка |

| Время от публикации кейса | Gate | Решение при fail |
|---|---|---|
| 0–2 h | Case→required minimum, issued grant/model/network/quota/OS, real LinQ golden/witness, schemas и tiny positive/empty/error/late fixtures | Отсутствующий callable path локализовать; unsupported-live, tagged mock параллельно. Убрать optional |
| 2–6 h | Source→LinQ→own-frame view→event commit→history; geometry/backend/freshness trace, actual SQLite patch, ранний E009 | Remux fail→snapshot/clip unavailable. Tracker fail→ID methods degraded. Не добавлять вторую модель до slice |
| 6–18 h | Две камеры/stalled source; held через timeout/restart; epochs/gaps/no stale boxes, DB/outbox/pins reconcile; full cycle подходит методу | Сократить native live/messenger/cascade/extra tracking; profile/FPS менять только с quality gate |
| 18–32 h | Sustainable paced load, per-camera FPS/max gap/age, evidence outcomes, slow browser и storage/restart faults | Явный admission/degraded. Сокращение camera count не лечит single-camera p1 cycle |
| 32–40 h | Freeze model/stack, clean-target/offline client, verified restore и remote reconcile, репетиция в сети площадки | Только core/package/recovery fixes, optional cut; saved witness — replay при отсутствии current access |
| 40–45 h | Reproducible demo/runbook/submit assets и regression walkthrough | Feature freeze; replay не подменяет обязательный live полного кейса |

Все интервалы — проектный план [F206](../RAW_FACTS.md#f206), не подтверждённая трудоёмкость. Cuts применяются в явном порядке: optional native WebRTC, messenger без готового доступа, image-health heuristics, blur/reencode, object storage/broker, extra cascade/tracker, камеры сверх measured admission. Core сохраняет реальный LinQ, correlation/geometry, freshness/gaps, committed events/history и честные failure/evidence states. Если required method требует ID, неудачный tracking gate сохраняет blocker этого метода. Если required exact clip не сопоставляется, snapshot не закрывает требование. [Q024](../OPEN_QUESTIONS.md#q024), [E018](../OPEN_QUESTIONS.md#e018).

Путь роста следует из измеренного bottleneck. Для 50 камер кандидат — один ingest/recording host с выделенным adapter после ресурсного и temporal допуска; само число 50 не требует кластера. Для 500 — shards по площадкам, локальная main recording, measured WAN substream/JPEG или разрешённый colocated inference, централизованные compact events/control. `500=10×50` не убирает суммарную нагрузку центральных links. PostgreSQL, durable broker/object storage и более сложный placement вводятся при multi-host owners и измеренных требованиях, а не для сходства с enterprise diagram. N+1 требует spare capacity и проверенной reconnection/ownership, RAID не заменяет его. Edge LinQ HX остаётся условным placement до SDK/decode/memory/network проверки. [Milestone 2026r1 architecture](https://doc.milestonesys.com/xprotect/xprotect-system-architecture-guide/2026r1/en/overall-system-architecture), [F124](../RAW_FACTS.md#f124), [F133](../RAW_FACTS.md#f133), [F200](../RAW_FACTS.md#f200).

## Программа практической волны и оставшиеся вопросы

Все E ниже предложены и не выполнялись. Они переиспользуют общий corpus/hash/trace, но проверяют разные утверждения; media/mock success не становится LinQ proof. Подробные inputs, steps, metrics, outcomes и limits сохранены в [OPEN_QUESTIONS.md](../OPEN_QUESTIONS.md). Для disruptive faults используется собственный disposable testbed в пределах отдельно выданного допуска; этот отчёт не поручает kill/reset общего стенда или отправку сообщений реальным людям.

Первые проверки меняют топологию. [E001](../OPEN_QUESTIONS.md#e001) получает actual capability contract и один real golden с hashes/request/run/device witness; один success не доказывает capacity/TTL. [E018](../OPEN_QUESTIONS.md#e018) связывает source/frame→request/model→LinQ run→result→event revision→evidence status→draw, затем добавляет две камеры. В нём сразу принимается mode go/no-go. Одновременно [E009](../OPEN_QUESTIONS.md#e009) проверяет packet index до mutable mux, independent original decode, B0/B2, long GOP, loop/reset/wrap, missing PTS и decoder-only/recorder-only restart. Его критерий — ноль false complete; неудача меняет evidence scope до того, как в recorder вложены оставшиеся часы.

Следующая группа проверяет ограниченность и время. [E007](../OPEN_QUESTIONS.md#e007) на fake-job service вводит lost ack, crashes до/после send, cancel200 с продолжающейся работой, hidden retry и поздний acceptance; проверяет, что каждая возможная обязанность покрыта reservation и credit не освобождается дважды. Он не устанавливает LinQ semantics. [E006](../OPEN_QUESTIONS.md#e006) проверяет sparse IDs 100/105/110, reorder/timeout wakeup/late/epoch, valid empty против Gap и fixed-dt tracker/reset; затем отдельно domain ID quality. [E005](../OPEN_QUESTIONS.md#e005) строит paced saturation curve C/B/p_i, crowd cascade, fairness и полный resource inventory сначала mock, затем real LinQ. Прошедший aggregate peak без per-camera age/gaps не pass.

Media и качество проверяются раздельно. [E002](../OPEN_QUESTIONS.md#e002) сравнивает continuous reader/latest с naive sleep/read, TCP/UDP, media blackhole при живом control, slow/stalled source и soak: 10 min correctness, затем 2 h/ночь при доступности. [E003](../OPEN_QUESTIONS.md#e003) измеряет decode-only и decode→download/resize/color/pack на actual CPU/NVDEC/QSV, hardware fallback disabled, cold/warm и paced streams. [E004](../OPEN_QUESTIONS.md#e004) делает paired target RGB JPEG/resize/ROI/sampling grid с fixed model/preprocess и class/size recall/event misses вместе с bytes/CPU. Ни один чужой Q threshold или красивый кадр не заменяет это. [E008](../OPEN_QUESTIONS.md#e008) получает actual heads/quantization/classmap, parity raw/compact/NMS/geometry и фактические return/poll/fetch/postprocess bytes/CPU.

Evidence и persistence требуют собственных отказов. [E010](../OPEN_QUESTIONS.md#e010) вводит delays 1/19/21/120 s, long dwell/ongoing event, stalled post-roll/no IDR, low space и retention/export races; смотрит finite jobs/pins/reservations и partial/unavailable. [E016](../OPEN_QUESTIONS.md#e016) различает process crash, reboot/power/disk loss, проверяет COMMIT boundary, BUSY/IOERR/long-reader WAL, supported backup и post-cutoff remote obligations при restore. Критерии — никакого acknowledged success без recovered row в заявленном scope, никакого false complete и удаления до pin rebuild. Process kill не доказывает power-loss durability.

Показ результата допускается после [E011](../OPEN_QUESTIONS.md#e011): fast/decode3s/hidden60s viewers, ACK off/early/wrong nonce, old generation, reconnect до cleanup, near-cap images/DPR, source/input lifetimes. Проверяются outstanding≤1/connection и decode≤1/page через поколения. [E012](../OPEN_QUESTIONS.md#e012) отдельно блокирует transport и проверяет public close/closing cap/resource cleanup; нет новых sends сверх cap, hanging teardown — видимый failure, а не исключённая из счётчика connection. [E013](../OPEN_QUESTIONS.md#e013) optional проверяет actual WebRTC/LL-HLS network/codec/WHEP lifecycle/rVFC mapping, иначе overlay остаётся отключённым.

Для событий [E014](../OPEN_QUESTIONS.md#e014) моделирует provider accept без marker, 429/500/timeout, UI cursor replay и poison payload; реальные bot tests возможны только после отдельной авторизации и credentials. [E015](../OPEN_QUESTIONS.md#e015) фиксирует фактические artifacts/ABI/SQLite/PRAGMAs/licenses, clean-target/offline/Astra route и функциональные auth/TLS/secret-redaction проверки. Это не pentest или сертификат. [E017](../OPEN_QUESTIONS.md#e017) снимает physical onset/rule eligibility/commit/draw в optical или calibrated clocks, оставляет misses/timeouts/censoring в denominator. [E019](../OPEN_QUESTIONS.md#e019) optional проверяет image-health с positive/negative controls света, static scene, loop, truck/PTZ и synthetic blur/black/shift; неразличимые controls означают cut, а не новый универсальный threshold.

Ближайшие P0-вопросы должны уйти постановщику в конкретном виде: [Q001](../OPEN_QUESTIONS.md#q001) — issued mode/model update/accepted witness; [Q002](../OPEN_QUESTIONS.md#q002) — quota/lifecycle/idempotency/terminal/TTL/borrow release; [Q003](../OPEN_QUESTIONS.md#q003) — разрешённый placement/ports/persistence; [Q005](../OPEN_QUESTIONS.md#q005) — required temporal FPS/gaps/dwell/ID; [Q025](../OPEN_QUESTIONS.md#q025) — actual heads/NMS/return. После golden критичны [Q004](../OPEN_QUESTIONS.md#q004) source profile, [Q007](../OPEN_QUESTIONS.md#q007) full cycle, [Q010](../OPEN_QUESTIONS.md#q010) exact mapping/snapshot admissibility и [Q015](../OPEN_QUESTIONS.md#q015) installed bundle. Остальные Q не исчезают: quality, evidence/FS, browser/native media, licenses, event rate, channels/privacy, soak, tracker, capacity и optional image health имеют собственных owners и способ закрытия в реестре 25 вопросов.

## Адресная передача соседним исследованиям

`linq_platform` получает требования к actual grant, custom model/I/O/lifecycle/terminal/quota/borrow и accepted execution witness: [Q001–Q003](../OPEN_QUESTIONS.md#q001), [Q025](../OPEN_QUESTIONS.md#q025), [E001](../OPEN_QUESTIONS.md#e001), [E007](../OPEN_QUESTIONS.md#e007), [E008](../OPEN_QUESTIONS.md#e008). API может быть достаточен без SSH; HX/RK3588 decoder и HPS optional encoder нельзя переносить на выданный TPU.

`model_stack` нужны actual output schema/dtype/scales/classmap/NMS/coordinates/caps/parity, batch/stateful/ROI work и точная NN-граница. Raw return может превысить JPEG input в десятки раз, secondary fan-out меняет capacity; CPU postprocess не отменяет необходимость device witness. `datasets` и `training_strategy` вместе с ним должны дать целевой RGB corpus и лицензии weights/data; мы не предполагаем, что repo license их покрывает. [F147–F149](../RAW_FACTS.md#f147), [F182](../RAW_FACTS.md#f182), [Q008](../OPEN_QUESTIONS.md#q008), [Q009](../OPEN_QUESTIONS.md#q009), [Q016](../OPEN_QUESTIONS.md#q016).

`violation_methods` получает versioned temporal contract и fixed-dt ограничение: Gap не negative observation, ordered PTS не меняет ByteTrack dt, p1 full cycle ограничивает observation FPS. Нужны minFPS/maxgap/coverage/dwell/reset/ID semantics, иначе no-tracker route не закрывает ID-dependent метод. `evaluation` получает paired compression/sampling checks, два endpoint latency, полный denominator/onset/dwell/clock uncertainty и явные lost/late/censored outcomes. [F173–F184](../RAW_FACTS.md#f173), [F132](../RAW_FACTS.md#f132), [E004](../OPEN_QUESTIONS.md#e004), [E006](../OPEN_QUESTIONS.md#e006), [E017](../OPEN_QUESTIONS.md#e017).

`operator_product` получает независимые video/analysis/evidence/delivery states, pending/partial/unavailable clips и различие event committed/provider accepted/browser drawn/operator acknowledged. Требования пользователя должны определить допустимость snapshot, retained window и каналов; messenger пока optional. `market_deployment` получает directional50/500/VBR/retention/IO reserve, exact OS/Astra/privacy/security/license scopes; это не purchase capacity и не legal certification. [F119](../RAW_FACTS.md#f119), [F159–F161](../RAW_FACTS.md#f159), [F171](../RAW_FACTS.md#f171), [F187](../RAW_FACTS.md#f187), [F198–F200](../RAW_FACTS.md#f198).

`hackathon_strategy` получает real golden/core gates/cuts, распределение пяти owners и честные reserve modes. 45 часов — разность расписания, не guaranteed LinQ uptime. GUI/job без usable live path остаётся unsupported-live; replay/CPU/RTX обозначаются; failing mandatory exact clip остаётся blocker. На защите полезен единый trace backend→source/result→event/evidence→render с контролируемым failure/recovery и метриками полного denominator. [F023](../RAW_FACTS.md#f023), [F024](../RAW_FACTS.md#f024), [F204](../RAW_FACTS.md#f204), [F206](../RAW_FACTS.md#f206), [E018](../OPEN_QUESTIONS.md#e018).

Эти передачи — подготовленные связи между файлами, без запуска соседних исследований и внешних сообщений. Весь проектный маршрут остаётся условным до фактического grant, полного кейса и практической волны; сохранённая доказательная база позволяет закрывать неизвестное адресно, не начинать архитектуру заново.
