## Инженерный ответ

**Обещание доступа подтверждено; фактический интерфейс команды неизвестен.** На с.8 локального кейса отдельно названы VM с ускорителями и сервис инференса. Из этого нельзя вывести SSH, Docker, HTTP API, собственную модель, объём памяти или квоту. Публичная страница хакатона подтверждает обязательный инференс на LinQ и обещание онлайн-доступа. [W1-13-S01, S02]

Первая развилка выбора 2–3 сценариев — какие признаки может вернуть **действительно выданный** LinQ-путь. Если доступны bbox человека, пригодны условные ветви бега/неподвижности/зоны с временными правилами; если доступны человек и техника — исследовать сближение; если доступны pose keypoints — возможен дополнительный признак падения. Телефон, сигарета, страховочная привязь и груз требуют иных наблюдаемых классов/признаков. Это **проектный вывод**, а не подтверждение качества готового зоопарка. Одного перечисления YOLO в документах для выбора конкретного сценария недостаточно.

Не нужно ждать SSH, если сервис принимает нужную модель либо имеет достаточную модель каталога, выдаёт требуемые результаты и даёт принятую организаторами трассу выполнения на LinQ. Обратное также верно: рабочая VM-консоль без доступа к устройству/сервису не закрывает обязательное условие.

## Access decision tree — четыре условных режима

Все ветви ниже — **ANALYSIS**, архитектурные решения после ответа организаторов. Ни один режим не заявляется уже полученным.

```text
0. Получен официальный runbook/ответ с режимом и сроком доступа?
   НЕТ → запросить пакет Q1–Q5; продолжать CPU reference/видео/правила,
         LinQ readiness = UNAVAILABLE. Не объявлять CPU demo LinQ demo.
   ДА → проверить auth штатным способом и срок действия.
        Не удаётся → сохранить код ошибки/время, обращаться в поддержку.

1. Есть программно вызываемый путь с реальным LinQ исполнением?
   НЕТ → есть только витрина/записанный пример → ещё не выполнено;
         нужен доступ к запуску и принятый организаторами proof.
   ДА → какой контракт?

A. VM/shell/container с runtime И разрешённой компиляцией своих графов
   → сохранить version/target/permissions; baseline организатора;
     custom graph → import/PTQ/compile → `.tpu` → runtime → output parity.
   → Если компиляции нет, перейти B; если устройства нет — проверить service B/C.

B. Managed custom-model service либо VM с runtime-only
   → определить точку приёма: graph / `.qm` / `.tpu` / иной официальный artifact.
   → Graph service: разрешённый формат + calibration + compile log + model ID.
   → Runtime-only: получить matched compile service/оператора/образ;
     upload `.tpu` без доступной цепочки подготовки ещё не делает модель переносимой.
   → Версия модели, запрос, результат, backend trace доступны? Да → smoke-test.
     Нет → уточнить proof; никакой произвольный HTTP ответ не считать TPU proof.

C. Сервис только с фиксированным каталогом моделей
   → запросить точные классы/выходы/частоту/числовой эталон.
   → Хватает наблюдаемых признаков выбранным сценариям?
     Да → правила/трекер на host при разрешении; NN остаётся на LinQ.
     Нет → сменить сценарий или запросить расширение; CPU второй detector
           не маскирует отсутствующий обязательный LinQ-признак.

D. Managed video/UI/jobs без прямого tensor endpoint
   → есть машинный экспорт bbox/keypoints/frame timestamps/request IDs?
     Да → адаптер jobs/files/events; проверить ordering, polling, quota, latency.
     Нет → можно ли расширить UI/достать данные официально?
       Да → согласованный extension route и новый contract.
       Нет → live integrable MVP не подтверждён; запросить B/C.
```

Если одновременно выданы VM и сервис, выбирать первую ветвь, которая проходит **baseline → признаки → proof → задержка**, а не более привычный транспорт. VM может оказаться host для клиента сервиса, а не PCIe passthrough; это надо спросить, не определить по слову VM. При смене модели заморозить новый manifest и заново проверить контракт/числовую и событийную цепочку.

## Первый smoke-test после выдачи — не выполнен

Выделить одного ответственного за LinQ path и один согласованный baseline; остальным готовить reference/события/демо. Временные бюджеты ниже не задаются: время компиляции и очередь не измерены.

1. **Зафиксировать grant.** Сохранить runbook/version, разрешённый режим, environment/model manifest, окно доступа. Секреты хранить вне отчёта. Результат `ACCESS = PASS/FAIL/UNAVAILABLE`, полный первый error с временем без токенов.
2. **Штатная связность.** Выполнить только предусмотренный runbook вход/health/list-models/device-list. Для VM использовать штатный предоставленный пример диагностики. Не сканировать сеть, чужие устройства и не угадывать endpoints. `device visible` ещё не означает `inference complete`.
3. **Один baseline на одном входе.** Штатный model ID/program с hash, разрешённый input с hash и golden output. Сохранить preprocessing/config, request ID, model revision, timestamps, output. Требуется успешное завершение, не только принятие задания в очередь.
4. **Доказательство backend.** Связать request ID с job/program/model identity и device/backend completion. Для A — лог открытия назначенного device, загрузки нужной `.tpu`, завершения inference; для B/C/D — trace/экспорт сервиса, понятный организаторам. Utilization как дополнительный сигнал, не самостоятельное доказательство. Отдельно запросить compiler report/декларацию границ графа, если требуется вся NN на TPU.
5. **Контроли.** Positive: golden вход с ожидаемой видимой целью. Negative: разрешённый фон/без цели. Разные входы должны давать осмысленно разные выходы; повтор одного входа оценивает воспроизводимость. Неверное имя модели/shape проверять только если такая проверка предусмотрена runbook, чтобы подтвердить явную ошибку, а не тихий fallback. Проверить backend flag/журнал и отсутствие подмены cached output; политика кэша должна быть известна.
6. **Числовой контракт.** Сравнить baseline с официальным golden и затем свой экспорт с CPU reference на одинаковых подготовленных данных. Сохранять raw outputs до NMS, descriptor и mapping. Допуски согласовать под quantized модель; равенство top-1 одной картинки не подтверждает detection quality.
7. **Малый timing-run.** После прогрева один последовательный поток, затем лишь разрешённая concurrency; каждый запрос сопоставлен кадру. Отдельно wall-clock upload/queue/backend/download/pre/post/event, число успешных и ошибочных запросов, median/p95 при достаточном числе наблюдений. Cold-start и compile time не смешивать с steady-state. Числа не прогнозируются из TOPS/ResNet latency.
8. **Переход к своей NN/каталогу.** Минимум один положительный и один отрицательный ролик/набор кадров для каждого выбранного события. Обязательные artifacts: exact weights/export/compiled hash или immutable service version, классы, preprocessing, decoded schema, FPS input и фактический processed FPS, timestamps. Остановка на первой нарушенной границе с `FAIL` и воспроизводимым минимальным примером; следующая стадия `NOT_RUN`.
9. **Сквозная событийная проба.** Состояния `candidate → confirmed → active → cleared`, параметры подтверждения/очистки задокументированы; стабильные camera/track/stream_epoch. Один продолжающийся эпизод даёт одно событие; новый после подтверждённого завершения — новое. Запоздалый ответ после reconnect/model update не смешивать с новой последовательностью. Timeout не равен отрицательной детекции; пропуски выводить в наблюдаемость.
10. **Граница готовности.** Повторить сохранённый короткий demo input через фактический LinQ path, журнал/кадр/тип/камера/время и дедупликацию. CPU fallback при сбое можно использовать только как явно обозначенный режим, а этот запуск помечать `LINQ_UNAVAILABLE`, не аппаратным PASS.

### Что считается успехом на настоящем устройстве

Минимальный reviewable bundle: `grant/runbook version → backend/device identity → model/program identity → input hash → request/job ID → completion trace → output → event → timings`. Для управляемого сервиса отсутствие доступа к PCIe допустимо при принятом организаторами backend proof; одного UI badge недостаточно. Самостоятельный файл `.tpu`, успешно завершившаяся конверсия, TLM и CPU parity находятся до этого критерия.

Различать два вопроса: **(а)** завершился ли этот запрос на LinQ; **(б)** какая часть конкретного NN-графа там выполнялась. Первое не доказывает второе. Для финальной демонстрации нужны оба в той форме, которую согласует постановщик.

## Точные пробелы и передача соседям

- **Модельный стек:** не фиксировать detector по названию семейства. Запросить exact model artifact и contract выданного пути; затем определить, есть ли person/vehicle/pose/small-object признаки. Public supported-family list не заменяет executable artifact.
- **Видеоархитектура:** проектировать заменяемый adapter с `model_version/request_id/frame timestamp/backend status`; поддержать sync и job/file варианты условно. Не предполагать RTSP в сервисе или доступность камеры из VM. Таймеры правил считать по времени кадров, задержку сервиса измерять отдельно.
- **Оценка:** добавить измерения LinQ readiness по стадиям, сопоставление запросов, quiet negative controls, FP/FN события и повторов. Аппаратный журнал не доказывает точность сценария.
- **Оркестратор:** срочные неопределённости Q1–Q5 меняют feasible shortlist сильнее поиска ещё одной модели. Для person-only каталога честно рассматривать бег/неподвижность/пересечение заданной зоны с оговорками геометрии; для person+vehicle — сближение; для телефона/курения/привязи без соответствующих признаков сохранять no-go до нового evidence. Неподвижность не называется потерей сознания, bbox — нарушением, пиксельная дистанция — метрами.

**Итоговый статус:** documented access promise; actual organizer interface **UNKNOWN**; closed LinQ execution **NOT_RUN**. Следующее решение принимается после пакета Q1–Q5, а не после произвольной установки SDK.
