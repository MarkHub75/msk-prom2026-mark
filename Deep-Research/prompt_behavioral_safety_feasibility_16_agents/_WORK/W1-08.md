## Вопрос и польза для решения

Какие конкретные публичные артефакты можно быстро передать platform-track, какие выходы они действительно дают, и где название модели обещает больше содержимого файла? Кейс требует реального нейроинференса LinQ, быстрых сообщений и одного события на длящееся нарушение; каталог не подменяет этот эксперимент.

**Рекомендуемый короткий набор:** официальный `yolov8n.pt` или уже экспортированный `yolox_nano.onnx` для person/phone и геометрии; официальный `yolov8n-pose.pt` для падения+неподвижности; специализированный forklift/person `best.pt` при подходящем видео. Параллельный запасной pose-путь — **RTMPose-t с уже существующим ONNX**, у которого удалось проверить deployment JSON без скачивания всего архива. Smoking имеет готовый небольшой ONNX, но не готовое событие и слабый provenance. Fire имеет маленький checkpoint с установленными классами, однако без доказанного качества. Для привязи/подцепления готовый надёжный checkpoint **не установлен**: самый прямой найденный кандидат оказался с иными классами внутри весов.

**Изменение решения по сравнению с названием/карточкой:**

- W1-08-F01: Thalos scaffold/harness исключить из контрольного списка готовых моделей: реальные `names` в checkpoint не содержат scaffold/harness, см. S07.
- W1-08-F02: MeetCool smoking не только «есть семейство YOLO»: существует ONNX, и частично прочитанный бинарный граф даёт реальные I/O, opset19, классы и версию экспортёра, см. S05. Требование compiler opset19 может оказаться блокером.
- W1-08-F03: RTMPose-t не требует строить первый ONNX с нуля: в ZIP лежит экспорт с opset11 и deployment contract. Но это top-down вторая сеть и crop-wise стоимость, а не готовый multi-person event detector, см. S04.
- W1-08-F04: `raidavid/yolov8_fire_and_smoke` не выбирать по имени как зрелый detector: собственный `args.yaml` — `task: segment`, база `yolov8n-seg.pt`, `epochs: 1`, см. S10.
- W1-08-F05: отсутствие весов у `farhatullah0066/yolov8n-fire-smoke-detection`, встречающееся во вторичной выдаче, свежими первичными API/Range опровергнуто: файл и class map есть. Это не доказывает качество, см. S06.

**Предпочтительные bundles для2–3 сценариев:**

1. **Один общий detector + ByteTrack:** бег как calibrated/proxy fast movement, phone-observation+motion и ROI crossing. Самая общая инфраструктура; не выдавать последние два за полноценный phone-use и перелезание без дополнительных признаков.
2. **Одна pose-сеть + host rules:** падение+неподвижность и геометрически однозначное пересечение/низкая поза; бег можно добавить по person tracks. Экономит detector→pose crop-chain, но надо реально подтвердить pose head compiler.
3. **S03 forklift/person + один общий pose/detector:** более прямой person-machine сценарий, если footage и старый checkpoint проходят gates. Сигарета и harness не должны быть критическим путём.

Если platform уже даёт поддержанный exact YOLO checkpoint, выбирать его после проверки классов/I/O, а не переписывать стек ради названия из каталога. Если поддержан только detector, это не разрешение имитировать pose results на LinQ.

## Общая временная логика и дедупликация

Предложенный host state: `UNKNOWN → OBSERVING → CANDIDATE → ACTIVE → RECOVERY → CLOSED`; ACTIVE после нескольких качественных наблюдений/hold, выход после отдельного recovery/hysteresis. Значения hold/threshold **не установлены**, зависят от source PTS, камеры и controls. Слепое фиксированное число кадров при dropped frames не равно заданным секундам. Короткие пропуски приостанавливают evidence timer, а не подтверждают опасность; длительные/scene cut → unknown/reset.

Одна ACTIVE episode→один alert, последующие кадры обновляют evidence. Дедуп key `(camera,rule_version,subject/pair,zone,episode)`, для fire region отдельная spatial merge/state. Не один global cooldown, который подавляет второго работника. ID fragments связывать осторожно, иначе merge двух людей; repeated entry после закрытия — новое событие. Сохранять start observed/confirmed, track/pair IDs, camera/zone/calibration/rule versions, raw perception scores отдельно от event decision, кадр/фрагмент и reason/quality flags. Stationary image пригоден для object observation, не для motion/immobility event.

## Smoke-test план — НЕ выполнен

1. **Выбрать2–3 события и один основной exact perception checkpoint**, получить от LinQ устройство/runtime/compiler, принимаемые форматы, supported opset/layout/precision, operators и ограничения output tensors. Отдельно спросить pose/SimCC/Conv3D, не общее «YOLO поддерживается». Уточнить допустимость host preprocessing/tracking/postprocessing при реальном neural accelerator inference.
2. **Pin manifest:** code tag/SHA, package versions, checkpoint URL/revision/LFS oid/size, после разрешённого скачивания свой SHA256. Для S07 не скачивать87MB в надежде исправить class map. Для S05 сохранить embedded metadata и проверить opset19; для S04 JSON contract и выбранный preprocessing channel order. Зафиксировать права weights и разрешённого footage отдельно.
3. **CPU эталон на10–20 кадров:** реальные `model.names`, input/output dtypes/shapes, min/max, classes/bbox/keypoints, пустой и crowded frame. Веса `.pt` в изолированном доверенном runtime; статическое чтение данной ветки не является проверкой безопасности исполнения pickle. Не запускать arbitrary repo scripts ради каталога.
4. **Export/graph gate:** S01/S03/S06 static batch1/shape и agreed opset, nms false, FP32 сначала. S02/S05/S04 существующие graph проверить ONNX checker/operators/actual inputs/outputs; S04 dynamic batch при необходимости закрепить поддерживаемым способом. Не обещать, что повторный export S05 с opset11 обязательно пройдёт: нужен исходный PT/совместимая версия и numeric comparison.
5. **Parity:** одинаковые исходные кадры/preprocess/threshold/NMS; сравнить PyTorch/ONNX/compiled outputs с допусками, raw output и после decode. Проверить RGB/BGR, center-vs-top-left padding, letterbox inverse, class-specific NMS, keypoint scale, objectness handling. Неверный channel order или class map нельзя компенсировать event threshold.
6. **LinQ настоящий run:** compile log, exact hardware/compiler/runtime, precision, model/compiled hashes, warmup отдельно, p50/p95 latency/throughput, host time/decode/preprocess/transfer/postprocess/track/event/UI и total delay. Никаких FPS из чужой GPU-таблицы. Записать source FPS/PTS/processed FPS/dropped frames, число людей/crops и потоков.
7. **Temporal controls:** короткие positive/negative клипы из таблицы, размеченные event start/end, unknown intervals. Посчитать event precision/recall, misses, FP/hour, delay от первого наблюдаемого выполнения правила, duplicates/event и ошибочные merge. Проверить long ACTIVE даёт ровно1 запись, re-entry2-ю, другой человек рядом не подавляется cooldown. Малый smoke set не production validation.
8. **Stop/fallback:** если exact compiler path не проходит, перейти на уже поддержанный perception и честно сузить событие/показ; не выдавать precomputed/mock detections за infer LinQ. Не добавлять новый action backbone до работающего одного нейронного пути и журнала.
