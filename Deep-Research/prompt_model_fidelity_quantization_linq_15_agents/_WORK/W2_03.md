## Вывод, меняющий следующий шаг

1. Для LinQ подтверждается только документированное описание `percentile` через **веса** в guide2025. Формула, допустимая область чисел и фактическое поведение текущего `RegularModel.calibrate` остались UNKNOWN. Считать это activation-percentile sweep нельзя. Адресный поиск не нашёл version-matched реализации или официального sample, снимающего неизвестность.
2. Не найден доказанный LinQ consumer для ONNX QDQ, AIMET sidecar encodings, trained scales либо FP islands. Это **UNKNOWN поддержки**, а не доказательство её отсутствия. До GPU/QAT нужен один маленький proof сохранения численного контракта на целевом toolchain; успешный ONNX import недостаточен.
3. ORT-конфликт теперь существенно сужен: в **onnxconverter-common v1.16.0** существуют **два разных API**. ModelProto API жёстко использует CPU; отдельный model-path API принимает provider и проводит через него обе проверки. В **ORT v1.23.2** CPU FP16 model может обслуживаться механизмом вставки FP32 casts; это не доказательство нативного FP16 compute и не точная симуляция CUDA. Live docs с категорическим GPU requirement нельзя применять как описание обоих путей этого tag. Совместимость данной пары и конкретной модели не запускалась.
