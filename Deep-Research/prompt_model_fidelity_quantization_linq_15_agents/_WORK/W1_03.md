# W1-03 — безопасное преобразование ONNX-графа

Дата сетевого доступа: 2026-10-23, окно 19:14–19:20 UTC по clock (22:14–22:20 MSK). Исследователь первой волны; модели, конвертеры и тесты не запускались. Выполнялись HTTP-чтение первичной документации/кода/GitHub API и чтение входных материалов. Все expected checks ниже — предлагаемые проверки, без статуса PASS.

## Решение для команды

Сохранять исходный ONNX как самостоятельный эталон и создавать отдельный артефакт после каждого изменения: фиксации формы, simplification, замены операции, precision conversion, компиляции. До выдачи матрицы поддержки LinQ не выбирать opset и не переписывать операции «на всякий случай». Валидация структуры, численная эквивалентность и исполнение на нужном устройстве — разные доказательства.

Три наиболее полезные находки:

1. В onnx-simplifier v0.4.36 `simplify(check_n=0)` и CLI с нулём по умолчанию могут вернуть `check_ok=True` без единого сравнения inference. Даже ненулевой `check_n` проверяет случайные входы либо один переданный набор, а не покрытие реальных промышленных сцен [F03–F04].
2. Opset — часть семантики, а не число для подавления ошибки импортёра. Softmax-11 и Softmax-13 по-разному нормируют многомерный вход; Resize при совпадении размеров может выбирать другие координаты. Нельзя заменять Transpose на Reshape либо «переименовывать» layout [F05–F10].
3. Даже преобразования, объявленные семантически сохраняющими, требуют сравнения: имеются свежие первичные bug reports о потере FP16 результата при ConvAddFusion и об изменении формы при GatherToSliceFusion. Это сообщения авторов воспроизведений, а не наши измерения и не доказательство дефекта LinQ [F13–F14].

Уточнение контекста: первоначально PDF в текущей папке не было; во время исследования root сообщил о найденном полном кейсе. Прочитаны `_WORK/CASE_NOTES.md` и `_WORK/NEIGHBOR_LEADS.md`. Это переданное локальное наблюдение root, собственного чтения PDF здесь нет. Подробности декодирования/NMS и precision принадлежат W1-04/06, LinQ import/SDK — W1-13/14.

Следующие expected checks — методические выводы из фактов, а не опубликованные измерения.

|---|---|---|

Поэлементное совпадение после явного inverse permutation. |

Точные правила/допуски W1-04. |

Любая layout-трансформация должна перенести всю согласованную область: axis-aware операции, broadcast-константы, weights там, где изменён формат соответствующей операции, shape computation и boundary transposes. Нельзя просто изменить shape input с `[N,C,H,W]` на `[N,H,W,C]`, оставив стандартный Conv прежним. Если compiler сам перестраивает внутренний layout и контракт границ прежний, дополнительный ручной Transpose не нужен.

Замена unsupported op — отдельная математическая реализация. Примеры опасных сокращений: Slice вместо Gather без проверки индексов; Pad+Conv вместо Conv с auto_pad без проверки нечётных размеров; ручной Exp/ReduceSum вместо устойчивой Softmax без проверки overflow; clip вместо правильного padding; вынос NMS без воспроизведения его контракта. Совпадение на одном изображении не подтверждает общую эквивалентность.

## Пошаговая локализация расхождений

1. **Зафиксировать границы сравнения.** Вход — один и тот же сохранённый препроцессированный tensor с именем, dtype, shape, hash и параметрами preprocessing. Отдельно хранить real fixtures: промышленные кадры с мелкими СИЗ, дымом/бликами, окклюзиями, hard negatives, пустыми сценами. Синтетические индексные/ramp inputs диагностируют операции; representative fixtures проверяют применимость к задаче. Один набор не заменяет другой.
2. **Создать inventory до изменения.** SHA256 модели и external-data файлов; IR/opset domains; producer; input/output имена/типы/формы; последовательность узлов, domain/op_type/name; input/output edges; атрибуты; dtype/shape/hash initializers; subgraphs/functions. Порядок узлов/имена могут поменяться без изменения функции: графовый diff должен показывать и смысловые поля, не только текстовый protobuf diff.
3. **Минимальная структурная проверка.** `onnx.checker.check_model(model, full_check=True)`. Затем на копии `onnx.shape_inference.infer_shapes(model, check_type=True, strict_mode=True, data_prop=True)` и проверка полученных/неизвестных форм [S01–02]. Не отключать opset compatibility check ради «зелёного» результата. Ошибка custom domain может означать отсутствие схемы у checker, её нельзя автоматически объявить дефектом модели.
4. **Дешёвый контроль runtime без дополнительных optimizer passes.** Выполнить original и transformed ONNX в одной версии ORT на CPU с `ORT_DISABLE_ALL`, на идентичных feeds [S04/S15]. Сначала сравнить количество/имена/shape/dtype outputs, маски NaN/Inf; для indices/shape integers — точное равенство. Для float логировать max/quantile abs error, relative error с явным near-zero handling, координаты худших элементов и их исходные значения. Thresholds устанавливает команда по baseline/рискам, а не onnxsim.
5. **Если выходы различаются, найти первую границу.** Извлечь подмодели через `onnx.utils.extract_model(input_path, output_path, input_names, output_names)` [S19]. Сначала outputs backbone/neck/head; затем между соседними операциями проблемной ветви. Сравнивать одинаковые семантические точки, а не предполагаемый одинаковый порядковый номер слоя. При layout change применить документированное inverse permutation только для сравнения. При fusion сравнивать boundary fused block с unfused block; имена внутренних тензоров могли исчезнуть.
6. **Не путать накопление с источником.** Если входы блока уже расходятся, подать эталонный вход в обе реализации выделенного блока. Если после этого выход совпал — источник выше. Если нет — сохранить минимальный подграф, вход и атрибуты первого проблемного блока. Не разрезать If/Loop; получать необходимые промежуточные value_info, не угадывать shape/dtype.
7. **Отдельно включать runtime transformations.** На неизменном ONNX и тех же inputs пройти Disable→Basic→Extended→All. Сохранить каждый optimized graph через `SessionOptions.optimized_model_filepath`, сравнить inventory и outputs. Если первая потеря появляется на уровне Extended, не исправлять checkpoint до установления pass. `disabled_optimizers={"..."}` — внутренний API проверенной ORT версии, использовать только в закреплённом диагностическом окружении [S22]; для LinQ эта команда неприменима без его SDK.
8. **Проверить влияние инструментирования.** Дополнительный output может блокировать fusion, поэтому «ошибка исчезла после добавления debug outputs» не доказывает исправление. Повторить на неизменённом deployable graph и compare block boundaries; хранить оба артефакта.
9. **Вернуться к реальному выходу.** После raw tensors сравнить decode и геометрию детекций/keypoints; затем W1-12/11 проверяют event outcomes. Успешный CPU replay доказывает эквивалентность именно в этом runtime, не поддержку LinQ.

Короткий пример конфигурации контрольной ORT-сессии (предлагаемый, не выполнен):

```python
options = ort.SessionOptions()
options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_DISABLE_ALL
session = ort.InferenceSession(model_path, sess_options=options,
                               providers=["CPUExecutionProvider"])
outputs = session.run(None, feeds)  # feeds = сохранённые tensor inputs
```

Основание — S04/S15. Это не самостоятельный тест: необходимы обе модели, fixtures, сравнение output contract и отчёт о допусках. Shape helper S21 позволяет зафиксировать символическое измерение:

```text
python -m onnxruntime.tools.make_dynamic_shape_fixed --dim_param batch --dim_value 1 model.onnx model.fixed.onnx
```

Команда дословно соответствует документации; здесь `batch` — пример реального имени из модели документации, а не установленное имя нашего неизвестного ONNX. Выполнять только после inventory. Фиксация batch1 не означает разрешения менять разрешение/растягивать кадр. Никакие инструменты в ходе исследования не устанавливались.

## Допуск преобразования и решение «чинить или нет»

| Наблюдение при будущем тесте | Действие |
|---|---|
| Исходный ONNX и transformed совпадают; LinQ importer сообщает конкретную unsupported schema/shape | Уточнить версию/ограничение; минимальная адресная замена или специализация; снова сравнить. Правка оправдана подтверждённым ограничением. |
| Checker проходит, после simplification расходятся CPU raw outputs | Откатить; разнести folding/shape inference/optimizer passes; проверить check_n и input contract. Не переходить к INT8/QAT. |
| Изменились shape/axis/candidate order после Transpose/Reshape/Concat | Исправить layout/индексы и output adapter. Это структурно-семантическая ошибка. |
| Только optimizer-enabled runtime расходится | Установить первый плохой pass, сохранить reproducer; временно отключить pass при допустимой latency, закрепить версию. Переписывать модель необязательно. |
| Только FP16/fused реализация расходится, структура эквивалентна | Отдельная precision/fusion диагностика W1-06; не называть это автоматически INT8 calibration error. |
| Raw outputs совпадают, боксы/события нет | Передать decoder/preprocessing/tracking владельцам; graph surgery не обоснована. |
| ONNX shape inference оставил неизвестные промежуточные формы, а импортёр/исполнение поддерживают их | Оставить граф; отсутствие annotation не является доказанной ошибкой. |
| Нет фактического ограничения target, исходный граф проходит gate | Оставить исходник. Меньше обязательных преобразований — меньше незакрытых переходов в fidelity ladder. |

Каждый принятый патч сопровождается записью: причина и diagnostic evidence; model hashes до/после; script/tool commit; точные параметры; перечень изменённых узлов/атрибутов/констант; input contract; проверенные реальные/синтетические fixtures; raw и decoded differences; target placement/latency; решение и границы допуска. Случайный sanity PASS, representative-fixture PASS и target PASS отражать разными полями.

## Fallback и ограничения переноса на LinQ

ORT умеет разделять граф по EP capability; CPU fallback может помочь выделить unsupported часть [S20]. Но `get_providers()` показывает зарегистрированные провайдеры, не полный placement. Требуются логи/profiling; «модель запустилась с ускорителем в списке» не подтверждает обязательный inference на LinQ. Вынесение NMS/decoder на CPU — архитектурный кандидат после подтверждения правил и интерфейса, а не установленная возможность текущего сервера.

Уже optimized под конкретный ORT/CPU/GPU граф не считать универсальным входом импортёра LinQ. Сначала portable ONNX, затем только требуемые изменения target compiler. Изученные bugs ORT не переносятся на LinQ и не дают универсального запрета fusion. Их польза — конкретные тесты boundary cases и разделение структурной/численной проверки.

## Открытые вопросы и следующий шаг

- **Q-W1-03-01, blocking target choice:** какая версия импортёра LinQ, поддержанные IR/opsets/domains, dtype constraints и attributes для реального inventory? Нужны SDK/version manifest и compile report; передача W1-13/14. Общий список supported models ответа не даёт.
- **Q-W1-03-02:** требуются ли static B/H/W и какие разрешены значения? Поддерживается ли shape вычисление или только compile-time constants? После доступа — compile неизменённого baseline и минимальная специализация с parity test.
- **Q-W1-03-03:** можно ли получить raw/intermediate tensors до встроенного decoder/NMS, отключить fusion/quantization и сохранить compiled graph/report? Без этого layer-level target diagnosis может быть недоступна; остаются внешние границы и минимальные test graphs.
- **Q-W1-03-04:** какие узлы действительно выполняются на TPU, есть ли CPU partition/fallback и как оно отражается в логах? Не установлен факт поддержки fallback LinQ.
- **Q-W1-03-05:** какая конкретная модель/checkpoint и output contract будут выбраны? До появления файла нельзя назвать реально релевантный список unsupported ops или назначить единственный безопасный opset.

Следующее практическое действие: после получения checkpoint/ONNX и SDK снять inventory и один неизменённый compile log, затем прогнать original→specialized→simplified на одинаковых сохранённых inputs. До этого полезный результат — доказанный протокол и список точных неизвестных; запуск обучения/аренда GPU не нужны.
