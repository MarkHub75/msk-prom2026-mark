## Решение для команды

До сравнения FP32/FP16/INT8 заморозить **один и тот же frame ID → декодированный канонический кадр → входной тензор → геометрический ledger**. Затем отдельно сравнивать модель на готовых тензорах и полный путь от исходного файла. Иначе изменение backend может менять не только precision, но размер входа, padding, цвет, нормализацию и набор кадров. Удобный API `predict` сам по себе не фиксирует этот контракт.

Три наиболее существенных находки:

1. В Ultralytics v8.3.0 выбор минимального прямоугольного letterbox зависит от `model.pt` и одинаковости размеров изображений в batch. Для 853×481 при nominal 640 один режим даёт 640×384, другой 640×640. Это confound сравнения runtime даже при одинаковом `imgsz`.
2. В той же версии обратное преобразование боксов использует округлённый padding, а точек — дробный padding, восстановленный из размеров. На указанном odd fixture разница подходов составляет около 0.739 пикселя исходного кадра по y до округления боксов. Это арифметический вывод из кода, не измерение потери точности модели.
3. В torchvision detection преобразование уже находится внутри модели; RTMPose top-down использует crop/affine и bbox metadata. Универсальный внешний «RGB, /255, YOLO letterbox, scale_boxes» не переносится между этими семействами.

Кейс теперь доступен локально: `INPUT/CASE_LINQ.pdf`; использованы первичные заметки root `CASE_NOTES.md`, а не собственный повторный визуальный осмотр. С.5 требует учитывать мелкие СИЗ и условия видимости; с.13 — кадр/камера/время для уведомлений и inference на LinQ. Старое предположение «PDF нет» уточнено. `NEIGHBOR_LEADS.md` прочитан; чужие helper probes/измерения не присвоены. Интерфейс LinQ, weights, calibration/evaluation data и контракт серверного preprocessing неизвестны.

## Проверенные факты и практический смысл

**W1-05-F01 [S02, 122–132; code observation].** Для списка numpy кадров preprocess меняет BGR→RGB, BHWC→BCHW, делает contiguous, переводит в floating type и делит на 255. Для уже переданного torch tensor цвет/раскладка и `/255` в этой функции пропускаются. Условие: конкретный BasePredictor v8.3.0. Следствие: сравнение numpy и tensor API требует отдельно сформировать равный тензор; dtype float ещё не гарантирует правильный диапазон.

**W1-05-F02 [S02, 154–156; S01, 1563–1588; code observation].** Минимальный rectangle включается по сочетанию same_shapes и backend `.pt`; letterbox округляет resized dimensions и делит остаток padding, а `auto` берёт остаток по stride. `scaleFill` использует разные отношения по x/y, `scaleup=False` ограничивает увеличение. Следствие: записывать фактическую shape, настройки и все четыре паддинга; название `imgsz640` недостаточно.

**W1-05-F03 [S03, 88–123 и 749–760; S04, 50–52; code observation].** В этой версии pose boxes после scale_boxes ещё округляются; points проходят scale_coords. При отсутствии ratio_pad box pad восстанавливается через round(...−0.1), point pad — дробно. Следствие: отличать intended reference behavior от собственного «исправления»: изменение округления только в новом runtime разрушит parity. Также эти helpers используют один gain; для stretch/crop нельзя без проверки применять их как общий inverse.

**W1-05-F04 [S03, clip_boxes и xywh2xyxy; code observation].** В xywh2xyxy x/y — центр, ширина/высота делятся пополам; clipping допускает правую/нижнюю геометрическую границу W/H. Следствие: именовать формат `cxcywh`, `tlwh` или `xyxy`; bbox boundary W не равна индексу последнего pixel W−1. Тест 1×1 отличает соглашения площади с `+1` и без него. Не менять соглашения GT/decoder молча.

**W1-05-F05 [S05; code observation].** GeneralizedRCNNTransform требует floating images и применяет `(image−mean)/std`, resize min/max и bilinear align_corners=False; batch padding добавляется справа/снизу нулями уже в нормализованном пространстве. Postprocess возвращает боксы и keypoints к original sizes с отношениями каждой оси, а третий компонент keypoints не масштабирует. Условие: не все torchvision модели, именно использующие этот transform. Следствие: внешний mean/std/resize может задвоиться при экспорте полного wrapper; «нулевой padding» здесь не означает чёрный raw RGB.

**W1-05-F06 [S06; schema documentation].** Resize задаёт разные отображения центров пикселей: half_pixel `(u+0.5)/s−0.5`, asymmetric `u/s`, align_corners `u*(Nin−1)/(Nout−1)`, а pytorch_half_pixel отдельно обрабатывает длину выхода 1. Следствие: совпадающий размер и слово bilinear не устанавливают одинаковые пиксели. Проверять actual node attributes, scales/sizes, antialias и nearest rounding; значения и наличие атрибутов зависят от schema. Не переносить атрибут новой schema на старую модель.

**W1-05-F07 [S07; code observation].** OpenCV FFmpeg backend при включённой конверсии выбирает BGR24, хотя property называется CONVERT_RGB; rotation properties и обработка PTS зависят от backend/версии. Следствие: проверять реальный результат цветовым fixture, логировать backend/build information и возвращённые значения properties. Этот факт не гарантирует поведение GStreamer, камеры или сервиса LinQ.

**W1-05-F08 [S08; API documentation].** PTS — время презентации в единицах time_base; frame имеет sample aspect ratio и display matrix metadata. Следствие: frame index/FPS нельзя считать универсальным источником времени VFR; decoded raster и display orientation — отдельные сущности. Для потока фиксировать источник/единицы timestamp, эпоху reconnect и missing timestamps. API-комментарий time_base предупреждает о контекстных ограничениях; нельзя предполагать заполненность каждого поля каждым декодером.

**W1-05-F09 [S09; documentation].** FFmpeg CLI autorotate включён по умолчанию; cfr fps_mode дублирует/удаляет кадры, passthrough передаёт timestamps, muxer может их дополнительно менять. Следствие: повторное ручное вращение после autorotate — проверяемая гипотеза; выгрузка с `-r` не является нейтральным способом заморозить sample IDs. Это свойства CLI, не автоматическое обещание всех libav consumers.

**W1-05-F10 [S10, 85–135; S11, 150–156; code observation].** TopdownAffine меняет bbox aspect ratio, использует center/scale/rotation и UDP/non-UDP warp, сохраняет input metadata. TopdownPoseEstimator восстанавливает предсказанные точки через input_size/input_scale/input_center. Следствие: для RTMPose нужен отдельный ledger каждого actor crop; YOLO scale_coords не заменяет этот путь. Не применять простую формулу восстановления вне условий выбранной test pipeline, особенно при произвольном вращении.

## Геометрический ledger и два разных эталона

Для каждого кадра сохранять: source/stream/frame ID, source PTS и time_base, capture/receive time раздельно; coded size, decoded size, SAR, rotation/mirror, canonical size; crop origin/extent; фактические resized W/H; pad left/top/right/bottom; output shape/layout; dtype/channel order; последовательность normalization; affine и inverse; coordinate convention и единицы выходов. Для pose добавить actor ID, bbox center/scale, crop rotation, codec/input dimensions, confidence/visibility convention. Для batch — собственный ledger каждого изображения, а не первый scale на весь batch.

Для axis-aligned resize/crop/letterbox геометрия непрерывных bbox boundaries имеет вид `x' = sx*(x−crop_x)+left`, `y' = sy*(y−crop_y)+top`. Обратное — вычесть pad, разделить по соответствующей оси и вернуть crop offset. При rotate/mirror преобразовывать все углы бокса, затем брать envelope; точки сохраняют identity. Композицию преобразований выполнять в правильном порядке и обращать целиком. Clip — после перевода в нужную frame space; целочисленное округление — только на оговорённой границе отображения/индексации, если reference не требует иного.

**Граница:** этот общий геометрический ledger и **точная воспроизводимость существующего predictor — разные задачи**. Ultralytics ratio использует nominal scalar r, хотя растровая высота округляется. Не подменять reference r на `rounded_height/H` при восстановлении только одной ветки. Формула центров пикселей Resize также не является автоматически формулой перевода bbox boundaries. Нужны отдельные проверки pixel values и output geometry.

## End-to-end parity checklist и порядок допуска

1. **До модели:** сохранить исходные bytes/hash, decoder/backend/build/options; выбрать один orientation/SAR policy; сопоставить frame IDs/PTS; получить decoded canonical frames. Идентичные bytes входного файла не гарантируют идентичный кадр после разных decoder.
2. **Preprocess contract:** проверить H/W, RGB/BGR, layout/contiguity, dtype, диапазон; порядок `/255`, mean/std, quant input scaling; наличие Cast/Div/Sub/Resize/Pad/Transpose в exported graph и wrapper. Normalization должен иметь одного владельца. Для уже quantized input нельзя автоматически делить integer на255 — нужен выданный quantization contract. Возможности LinQ здесь неизвестны.
3. **Pixel parity:** uint8 стадии одной реализации — exact equality; тензоры одинакового dtype одной последовательности — exact where deterministic. При намеренной смене библиотек/precision сохранять max/mean absolute difference, map по каналам/границам; допуск выбирать по reference, не придумывать универсальный epsilon. Тест на mean/std считать из фактического config: `(channel/255−mean_c)/std_c` только если именно такой порядок установлен.
4. **Model-only:** один готовый тензор, одинаковая shape/batch, разные runtime; сырые выходы перед decoder/NMS/clip. Если интерфейс сервера принимает только JPEG/video, model-only parity недоступен без серверного debug dump — это локализованное препятствие, не автоматический FAIL модели.
5. **Output-only:** одинаковые fabricated boxes/keypoints/logits подать обоим decoder; freeze thresholds/class mapping/NMS отдельно с W1-04. Проверить координаты до/после inverse, clip и round. Это отделяет export/precision от геометрии.
6. **Full path:** только после предыдущих ступеней replay одной последовательности и общий decoder/tracker/rules. Проверить ROI entry, footpoint и overlay в canonical source frame, event time по source clock. Для физической floor geometry дальнейшая homography применима только к своей плоскости — соседний отчёт является зацепкой, количественные выводы не перенесены.

Симптомы: перестановка каналов меняет цветные patches; почти постоянный translation указывает на pad/crop; ошибка, растущая по координате — на scale/axis; зеркальная поза — rotation/mirror/left-right convention; drift только pose — crop/codec/inverse; разный recall коротких событий при похожих кадрах — сначала проверить sampling/PTS. Это диагностические гипотезы, не взаимно исключающие доказанные причины.

## Границы, контрпримеры и конкретные неизвестные

- Полностью совпавший preprocessing не доказывает совпадение модели или событий. Synthetic fixtures валидируют контракт, а не representativeness рабочего видео, видимость СИЗ или recall.
- На square640 fixture почти все перечисленные pad/axis ошибки скрыты; на чёрно-белом RGB=BGR. Поэтому минимум включает odd landscape+portrait и независимые цветовые/пространственные признаки.
- Равные post-NMS boxes не доказывают равенство raw outputs. И наоборот, исчезновение одного box при tiny score drift требует анализа decoder/NMS, а не правки resize.
- **Q05-01:** что принимает сервис LinQ: encoded media, RGB/BGR uint8 или готовый tensor? Shape/layout/dtype, встроенные нормализация и letterbox, rotation policy? Нужен опубликованный или выданный контракт плюс debug dump одного G01.
- **Q05-02:** включён ли preprocessing/postprocess в конкретный export и сервер? Нужны graph/input/output metadata и версии клиентского wrapper. Общие возможности ORT/OpenVINO не устанавливают это для LinQ.
- **Q05-03:** доступен ли original frame PTS и decoder transform ledger в ответе? Как reconnect/queue dropping меняют frame identity? Если нет — клиент должен замораживать кадры и manifest до передачи, но server-side decode всё ещё надо проверять.
- **Q05-04:** выбранные weights/config определяют mean/std, coordinate/pose codec и crop pipeline; они не получены. Torchvision/RTMPose примеры показывают необходимую развилку, а не готовый config для неизвестной модели.
- **Q05-05:** какие frame spaces используются для ручных зон/разметки/доказательного кадра? Надо договориться о canonical frame до настройки зон и о сохранении transform metadata вместе с уведомлением.

Следующее действие после получения доступа: запросить/прочитать input/output contract и прогнать G01–G04 на клиентском preprocess/postprocess без модели; затем получить server-side model-input dump G01 и только после совпадения выполнять paired model run. Root передать различие `.pt` auto, pad boxes/points и переносимость между модельными семействами.
