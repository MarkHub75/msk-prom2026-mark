## Практическое решение

Для каждой конкретной модели нужен версионированный output contract: что именно выходит из графа, какие преобразования уже выполнены и кто выполняет оставшиеся. Для первого fidelity-сравнения предпочтителен выход **после штатного head decode, до NMS**, если такой экспорт доступен: оба runtime пропускаются через один закреплённый decoder/NMS. Затем отдельно проверяется production-вариант, включая NMS в графе при его необходимости. Это диагностическая рекомендация, не подтверждение интерфейсов или CPU fallback LinQ.

Три сильные находки:

1. Pinned сторонний linq-cv-bench не является готовым custom decoder. `normalize_prediction_shape` принимает только каналы 84/85, отвергая обычный Ultralytics Detect nc=1/2/3 с C=5/6/7. В том же файле есть ошибочное имя `args.output_tensอร์_name` вместо `output_tensor_name`. Поддержка C=85 в normalizer сама по себе не даёт совместимости с YOLOv5: дальше вызывается современный Ultralytics NMS без явного objectness-contract [F01–F03].
2. У обычных YOLOv8/YOLO11 на проверенном Ultralytics v8.3.230 ONNX без NMS уже содержит DFL, box decode и class sigmoid; objectness-канала нет. У YOLOv5 v7.0 есть отдельный objectness и другое расположение осей. Pose/segmentation добавляют extra channels, которые нельзя считать классами [F04–F08].
3. Одинаковые raw-тензоры не гарантируют одинаковые детекции при разных NMS. Проверенный export NMS и Python NMS имеют разные ограничения: multi-label, предварительное усечение, лимит времени, padding; ONNX NMS вообще возвращает индексы, а не строки готовых боксов [F09–F13].

До применения PTQ/QAT сначала исключить эти ошибки. Переобучение не исправляет неверную интерпретацию каналов.

## Модель → выход → decoder → готовая детекция

Обозначения: B — batch, A — число пространственных кандидатов после конкатенации уровней, C — число классов, K×D — число keypoints × размерность, M — число mask coefficients, Q — queries. «Raw» без уточнения запрещён: различать **сырые conv/logits**, **декодированный выход до NMS** и **готовый post-NMS output**. Типовые размеры ниже выводятся из кода, не измерены на LinQ.

| Семейство/версия | Фактический выход на указанной границе | Остаточная интерпретация | Готовая запись и критическая граница |
|---|---|---|---|
| YOLOv8/YOLO11 Detect, Ultralytics 8.3.230, обычный не-end2end, export без NMS | B×(4+C)×A; первые 4 — decoded cx,cy,w,h в input-pixel coordinates при обычном `xyxy=False`; далее class probabilities | Транспонировать в B×A×(4+C) только согласно contract; cxcywh→xyxy один раз; best-class или multi-label; NMS | N×6: xyxy, score, class_idx. Нет дополнительного умножения на objectness и повторного sigmoid/DFL |
| Та же Detect до `_inference` | По уровням B×(4R+C)×Hᵢ×Wᵢ; R=16 в этой реализации | Для каждой стороны softmax по R bins, математическое ожидание расстояния; anchor points + stride → box; sigmoid классов | Это отдельный decoder, не совместимый с уже decoded 4+C. Одинаковое название модели не определяет место graph cut |
| Ultralytics Pose 8.3.230 без NMS | B×(4+C+K·D)×A; decoded keypoints; при D=3 третий компонент sigmoid | NMS получает явное C; extra channels переносятся с выбранным кандидатом; reshape K×D, затем обратная геометрия | N×(6+K·D). Keypoint confidence не заменяет detection confidence; K, D, порядок суставов и flip permutation — из конфигурации |
| Ultralytics Segment 8.3.230 без NMS | Два выхода: B×(4+C+M)×A и prototype tensor | C задаётся явно; mask coefficients не являются class scores; сохранить prototype и согласовать индексы кандидатов | N×(6+M) плюс prototypes → masks штатным mask decoder. Первый ndarray rank≥3 недостаточен для выбора output |
| YOLOv5 v7.0 Detect export | B×A×(5+C), уже decoded cxcywh и sigmoid objectness/classes | score_c=obj×class_c; затем cxcywh→xyxy, threshold, NMS | YOLOv8 decoder на этом выходе сдвигает классы и теряет семантику objectness. Для нестандартной головы проверять код отдельно |
| Ultralytics end2end/v10-style head 8.3.230 | B×min(max_det,A)×6 после head postprocess/top-k; xyxy задаётся веткой decode, хотя docstring postprocess описывает xywh | Это уже scores/class index, а не C-channel probabilities; generic NMS обходит подавление | Не выводить семантику только по последней размерности 6. Отключение дополнительного NMS здесь связано с конкретной one-to-one моделью, а не со всеми outputs такого shape |
| torchvision FasterRCNN 0.24.0, обычный eval | List[Dict] по изображениям: boxes, scores, labels, уже postprocessed | Внутри RoI: decode, softmax, удалить background 0, class-wise NMS, global detections_per_img; результат геометрически возвращается моделью | Повторное YOLO decode/NMS и вычитание единицы из labels без карты классов запрещены; собственный ONNX wrapper может менять flatten/signature |
| Оригинальный DETR, commit 29901c5 | Dict pred_logits B×Q×(C+1), pred_boxes B×Q×4 | Softmax по C+1; исключить последний no-object канал; normalized cxcywh→xyxy; масштабировать исходными W,H | Штатный PostProcess без NMS. Добавление NMS меняет baseline, даже если уменьшает дубликаты |
| Ultralytics RTDETRDecoder 8.3.230 | B×Q×(4+C): decoded normalized boxes + sigmoid class scores | Его predictor делает cxcywh→xyxy, best-class threshold, sort/max_det, ×original W/H, без NMS | Это не DETR softmax/no-object и не YOLO BCN input-pixel layout. Predictor использует scale_fill=True; чужой letterbox обратный transform даст другой результат |
| MMPose 1.3.2 SimCC codec, применимый к соответствующим RTMPose-конфигурациям | Два массива N×K×Wₓ и N×K×Wᵧ, а не детекции | `get_simcc_maximum`, опциональный DARK refinement, деление на simcc_split_ratio; отдельная опциональная visibility ветка | K×2 и keypoint scores в пространстве входного crop; возвращать в кадр по affine/crop metadata. Конкретный RTMPose checkpoint/config должен подтвердить этот codec |

Граница применимости: это точные реализации, а не универсальные свойства всех моделей с названием YOLO/DETR/RTMPose. Новые YOLO head variants, rotated boxes, TensorFlow Lite Detection_PostProcess и vendor custom plugin требуют собственного контракта; их совместимость здесь не подтверждена. OBB нельзя подавлять обычным axis-aligned IoU/NMS. ONNX/operator support сам по себе не доказывает наличие нужного host decoder в сервисе LinQ.

## Диагностические процедуры — предложены, НЕ ВЫПОЛНЕНЫ

Ниже не требуется обучать сеть или арендовать GPU. Часть тестов — синтетические fixtures для будущего decoder unit-check, часть требует предоставленного checkpoint/runtime. Никакие численные допуски качества LinQ здесь не назначены: exact expected используется только для дискретного контракта и простой арифметики; float tolerances согласуются с W1-06/12 по baseline repeatability.

### E-DEC01. Custom-class/layout negative controls

Создать по одному decoded candidate с фиксированным box=(cx=20,cy=30,w=10,h=20), score=.9 в заданном custom классе; C=1,2,3. Остальные кандидаты имеют score=0. Contract явно BCN для v8/11. Ожидание box xyxy=(15,20,25,40), один правильный class ID. Повторить с BNC contract через разрешённый adapter, batch=2 и перестановкой кадров. Для C=2 неправильный BNC→generic NMS должен быть выявлен как schema mismatch до вызова, а не принят эвристикой lastdim==6. Отдельно A=6,84,85 ловят collision эвристик. PASS: одинаковый canonical output, extras не стали классами, неизвестный layout отвергается. Основания F01/F04/F08.

### E-DEC02. Head-stage и score contract

Проверить три fixture types отдельными схемами: (а) v8 probability=.8 остаётся .8, (б) v5 obj=.5,class=.8 даёт .4, (в) DETR logits с C+1 используют softmax и no-object исключается. Для v8 4R+C fixture с R=16 выставить одинаковые logits во всех bins: expected distance=(R−1)/2=7.5 в каждой стороне до stride; либо reference DFL из закреплённой библиотеки. Сравнить с decode output и явно отвергать подачу уже 4+C на DFL. Не использовать произвольные каналы под видом logits, если граф уже выдаёт sigmoid. PASS: стадия и arithmetic совпадают, repeated sigmoid контроль выявляется. Основания F04/F07/F14.

### E-DEC03. Pose/segmentation association

Положить в два сильно перекрывающихся кандидата разные «водяные знаки» keypoint/mask extras и разные scores. После NMS должны сохраниться extras именно выбранного box; K×D и M от contract. Переключить nc=1/3, keypoints с xy>1 и low visibility; координаты не должны попадать в class scores. Для segmentation обязательны оба named outputs и совместимые prototype dimensions. Для SimCC отдельно два пика по осям и split_ratio из config; verify xy order, invalid scores и crop inverse transform. PASS: нет перестановки людей/суставов, visibility не подменяет detection score. Основания F05/F06/F16; обратная геометрия — W1-05.

### E-DEC04. NMS truth table

Сохранить один набор canonical boxes/scores/classes и ожидаемый keep set для каждой политики. Использовать box [0,0,10,10] и его дубликат, scores .9/.8; третий непересекающийся [20,20,30,30]. При IoU threshold<1 дубликаты одного класса подавляются, разных классов class-aware сохраняются, agnostic оставляет только более высокий score. При IoU threshold=1 и условии suppression `>` идентичные boxes остаются; проверять реальный runtime. Для score threshold t добавить scores t−ε,t,t+ε; проверить effective strictness. Для multi-label одна геометрия с двумя class scores выше t даёт две строки только в объявленной multi-label политике; NMSModel F10 — max-class. При точном score tie принимать только оговорённую tie policy, отдельно проверить перестановку входных кандидатов. PASS: count, class, membership, ordering соответствуют каждому manifest, ни один timeout не скрыт. Основания F09–F13.

### E-DEC05. Top-k/max-det/in-graph parity

Сначала сравнить graph NMS и внешний reference на одном pre-NMS output, не на двух независимо предобработанных изображениях. Подготовить >max_det разнесённых boxes и >pre-top-k кандидатов; один важный low-score кандидат помещать в отдельный класс. Проверить per-class cap против global cap, class filter до/после cap, global sorting, clipping, padded zeros и empty case. Контрпример max_det=1, два разнесённых boxes разных классов: ONNX NMS с max_output_boxes_per_class=1 может дать 2 индекса, внешний global max_det=1 — один box. Это математически заданный пример, не выполненное измерение. Для NMSModel segment сохранить prototypes; B=1, экспортный B, допустимый maximum и последний неполный batch. PASS: canonicalized valid rows соответствуют выбранной общей политике; если семантика намеренно различна — это изменение модели/pipeline, требующее отдельной оценки, не numeric tolerance. Основания F09–F11.

### E-DEC06. Named outputs/dtype fail-fast

На уровне adapter interface подать shuffled dictionary outputs (det/proto/aux), отсутствующий det-name, неправильный dtype, integer output без quantization metadata, C mismatch, NaN/Inf, отрицательные размеры. Нужны явные ошибки до tracker/events. Корректный output при перестановке dictionary keys должен давать тот же результат; missing preferred_name не должен молча переключаться на aux. PASS: схема валидируется независимо от порядка словаря; unknown outputs либо объявлены, либо отвергнуты. Это предложение замены небезопасной эвристики S01, не утверждение о возможностях LinQ SDK.

### E-DEC07. Причинная проверка downstream событий

Взять замороженные frame IDs/PTS и один pre-NMS tensor pack. Replay с одним decoder/NMS даёт контроль численной ветки; затем менять **один** policy parameter: agnostic, multi-label, max_det, score/IoU threshold или tie selection. Tracker/rules/config/state reset и входные timestamps идентичны. Раздельно логировать source candidate→final detection→track→event. Ожидаемые механизмы риска (inference, не измерение): agnostic может удалить пересекающийся телефон/СИЗ другого класса; best-class вместо multi-label может убрать класс нарушения; max_det теряет человека в толпе; смена winner на overlap/tie изменяет keypoints/ownership; неправильная mask/keypoint association создаёт false event; padding порождает фантомные tracks. Детектированные дубликаты не равны автоматически дубликатам уведомлений — это проверяет event engine. Оценивать отдельно detection/pose, event recall/precision, FP per camera-hour, duplicate/late/wrong-person events. PASS на tensor/decoder уровне не заменяет event-level gate. Связь с кейсом: root CASE_NOTES с.5/7/13.

## Ограничения, контрпримеры и следующий шаг

1. **NMS вне графа — не универсальное production-решение.** Нужны фактические API сервиса, доступ к decoded outputs и разрешённый host processing. Если сервис отдаёт только final detections, можно сравнить этот stage, но нельзя заявлять проверку pre-NMS parity. Нейросетевой inference всё равно на LinQ.
2. **Декодирование в head не всегда переносимо на произвольный graph cut.** Поддержка Sigmoid/Softmax/Gather/Reshape/NonMaxSuppression у LinQ и точная доступность выходов неизвестны. Если compiler требует вырезать decode, host implementation необходимо сверять с конкретным head и shape/stride, а не добавлять generic YOLO decoder.
3. **Equal-score tie — реальная граница exact gate.** Незначительная numeric perturbation может поменять выбранного overlapping человека при практически совпадающих тензорах. Либо общий фиксированный NMS, либо объявленный deterministic policy в обоих путях; добавление epsilon по индексу само меняет near-ties и требует явного согласования.
4. **Class offsets требуют диапазонных предпосылок.** В S04 offset max_wh=7680, а в exporter S07 — нормализация/offset по числу классов. Проверять реальные coordinates, negative/out-of-frame decoded boxes и допустимый размер входа: магическое offset не является общим доказательством отсутствия межклассового overlap.
5. **Прочитанный linq-cv-bench — сторонний исходный код.** Его дефекты не доказывают дефект SDK, отсутствие custom output support или провал реального запуска. Не переносить известные helper probes соседей на наше исследование. Дату pinned commit 2026-04-03 сообщил соседний материал; наша повторная GitHub API проверка даты получила HTTP 403 rate limit, поэтому дата не считается независимо подтверждённой здесь. Сам raw-код именно указанного hash получен и прочитан.

Открытые вопросы, необходимые перед практической работой:

- Q-DEC03: где NMS, какие per-class/global limits и valid-count protocol? Кто применяет inverse geometry? Можно ли сохранить pre-NMS output для golden pack?
- Q-DEC04: фиксирована ли зависимость Ultralytics в выбранном adapter; исправлены ли shape/class mapping/output-name defects до запуска модели?
- Q-DEC05: какой policy baseline принят для multi-label, tie-equivalence, confidence/IoU, crowd cases и event thresholds? Эти параметры не заданы кейсом.
