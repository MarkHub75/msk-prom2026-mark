## Решение для команды

Сначала получить отдельный FP32 ONNX без дополнительной simplification и без NMS, сравнить его с PyTorch на **сохранённых входных тензорах**, затем включать каждое преобразование отдельно. Для новой кастомной модели рассматривать `dynamo=True` как основной документированный путь PyTorch 2.9; для модели Ultralytics сначала использовать её версионно закреплённый exporter и проверить фактический backend. Это инженерная рекомендация, а не доказанная совместимость с LinQ.

Главный конкретный риск: обновление PyTorch не означает обновление пути Ultralytics. В проверенном Ultralytics **v8.3.230** функция `torch2onnx` явно передаёт `dynamo=False` при torch>=2.4. В PyTorch 2.9 собственный default уже `True`. Оба поведения корректно сосуществуют [W1-02-F01, F04]. Другой важный риск: `verify=True` — диагностическая проверка примера, а не обязательный gate по качеству: в прочитанном коде расхождение помечается в отчёте и warnings; требовать исключение при любом расхождении нельзя [F05].

Нельзя выбрать универсальный opset «для LinQ» до получения его версии импортёра и списка допустимых операторов. Версии opset, ONNX IR и версия пакета onnx — разные поля. Успех ONNX Runtime на CPU подтверждает только этот контрольный runtime и эту выборку, не исполнение на LinQ.

## Тихие поломки: признак → проверка → решение

Эта таблица — наши диагностические выводы из F01–F12, а не каталог измеренных инцидентов.

| Признак | Наиболее различающая проверка | Решение при подтверждении |
|---|---|---|
| Совпадает только пример экспорта | Другой знак/значение при той же форме; обе ветви if | Удалить зависимость от Python scalar; корректный torch.cond или версионно подтверждённый другой capture path |
| Совпадает 640×640, расходится прямоугольный вход | Одинаковые входные тензоры нескольких допустимых H/W; проверить output A и anchors | Зафиксировать форму либо исправить shape logic/cache; повторить весь pack |
| Только второй элемент batch неверен | Прогнать [a,b], [b,a], каждый отдельно, повтор a; compare per-image | Найти loop unroll/broadcast/cross-batch state; зафиксировать B=1 либо нужный максимум |
| Detector похож, pose систематически смещён | Раздельно boxes/classes/keypoint xy/keypoint confidence до NMS и обратной геометрии | Исправить signature/reshape/decode; не менять precision в качестве первого шага |
| До NMS совпадает, после различается | Один CPU decoder/NMS для обоих raw outputs; сравнить threshold boundary fixtures | Выравнять threshold, class-aware policy, max_det и padding; при допустимости оставить NMS вне графа |
| Ошибка появилась при simplify/смене opset | Повторить тот же pack на сохранённых before/after ONNX | Вернуть pass, локализовать operator rewrite; не обучать модель для маскировки ошибки |
| Export вернул объект/файл, лог содержит ❌ accuracy | Прочитать report и свой numeric gate | Считать артефакт недопущенным независимо от успешного return |

NMS вне графа — полезная диагностическая граница: меньше дискретных операций в первом сравнении. Это не утверждение, что CPU/NMS разрешены интерфейсом соревнования; нейросетевой inference всё равно должен быть на LinQ.

## Предлагаемые воспроизводимые мини-тесты — НЕ ВЫПОЛНЕНЫ

Предпосылки: выбранные checkpoint и архитектура, полный lockfile, CPU PyTorch и ONNX Runtime с явно закреплёнными версиями, одни и те же FP32 NCHW входы; отдельно заданный contract выходов. Дальнейшие шаги требуют практической волны. Значения допусков ниже не придуманы: универсальный atol/rtol намеренно **не назначен**; его нужно согласовать с W1-06/12 и измеренной повторяемостью baseline.

1. **E-EX01 — отрицательный контроль ветвления.** Собственный toy module: `forward(x): return x*2 if x.sum()>0 else -x`. Экспортировать на положительном x legacy (`dynamo=False`), выполнить положительный и отрицательный x одинаковой формы; математически ожидаемые результаты известны. Условие выявления проблемы: negative case не совпадает с eager при успешном файле. Для dynamo фиксировать ожидаемую ошибку capture, не переключаться молча на legacy. Затем отдельный module с `torch.cond(x.sum()>0, lambda t:t*2, lambda t:-t, (x,))`; повторить обе ветви. Основания: F03/F11. PASS для исправленного пути требует обеих ветвей; тест не доказывает поддержку всех control flow или LinQ.

2. **E-EX02 — tensor parity и форма.** На каждой допустимой форме сохранить x и eager outputs, затем ONNX outputs без high-level image wrapper. Проверить names/order/count/dtype/shape, finite values, отдельно абсолютные/относительные ошибки и долю нарушений собственного допуска. Для динамики взять B=1, B=2, целевой максимум; H/W: экспортный размер, прямоугольный и другой поддержанный размер, все с архитектурно допустимым stride. Для static проверять только заявленный shape; чужой shape должен отвергаться. Дополнительно [a,b]/[b,a]/[a]/[b] ловят межкадровое смешивание. Сохранять NPZ, JSON метрики по output/channel/sample, ONNX hash, export report/log, actual input/output signature. PASS не гарантирует event recall.

3. **E-EX03 — разделение подготовленной модели и перевода.** Сравнить eager исходной модели с её подготовленной eval/float/fused/export-mode версией; затем prepared PyTorch с ONNX. Для Ultralytics нельзя предполагать неизменный tuple; явно выбрать inference tensor. Все шаги FP32, fixed preprocessing; с одного и того же x. Если первый переход FAIL, чинить подготовку/head/fusion, если второй — exporter/operator translation. Нужен инструментальный доступ к подготовленной модели этой версии; API для её извлечения здесь не выдумывается.

4. **E-EX04 — контракт Detect/Pose и NMS.** Для custom nc и фактического kpt_shape проверить размер каналов, диапазон class scores, единицы координат, порядок xy/conf, candidate axis. Для обычного трёхуровневого head число A сверять с суммой размеров feature grids, не фиксировать 8400 вне конкретного 640/stride contract. Один и тот же внешний decoder/NMS применить к обоим outputs. Потом отдельно экспортировать embedded NMS: проверить пустой кадр, перекрывающиеся люди разных классов, почти равные scores, max_det saturation, padding, batch 1/maximum/maximum+1. Последний batch должен быть явно отвергнут или корректно доказан; частичный результат недопустим. Сохранять до-/после-NMS outputs. Основания F07–F09.

5. **E-EX05 — преобразование графа и числовые константы.** Экспортировать идентичный model/input с нужным target opset; сохранить unsimplified ONNX. Затем отдельный simplify/pass и, если требуется, другой opset — каждый как отдельный артефакт. Повторить E-EX02/04. Для Resize добавить ramp/impulse и граничные размеры; для Python bool/scale — проверить, объявлена ли переменная реальным Tensor input либо записана в contract как константа. Проверить `opset_import`, `ir_version`, domain/operator list, shape inference и checker; только затем runtime. Основания F02/F10/F12. PASS checker без parity недостаточен.

Пример **документированного вызова** для нового generic exporter в PyTorch 2.9 (не исполнен; `model`, `x` и `target_opset` должны быть заданы из зафиксированного контракта):

```python
model.eval()
program = torch.onnx.export(
    model, (x,), dynamo=True, opset_version=target_opset,
    input_names=["images"], report=True, verify=True,
    dump_exported_program=True, artifacts_dir="export_diagnostics",
)
program.save("model.onnx")
```

Синтаксис S01; это static пример. Для dynamo dynamic_shapes задаётся по сигнатуре forward/ограничениям конкретной модели; не подставлять legacy dynamic_axes механически. Значения target_opset, tolerance и LinQ commands здесь неизвестны. Для Ultralytics v8.3.230 обоснован отдельный первичный прогон `YOLO("best.pt").export(format="onnx", imgsz=640, batch=1, dynamic=False, half=False, simplify=False, nms=False, opset=target_opset)` — 640 здесь **выбранный экспериментальный размер**, не требование LinQ и не объявленный размер production.
