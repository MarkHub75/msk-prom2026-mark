## Краткая общая оценка первой волны

**Что получилось сильным.**
1. *Верхняя половина лестницы совместимости* (артефакт → загрузка → экспорт → граф → согласованность на CPU) для Ultralytics YOLOv8n/YOLO11n/YOLO26n/YOLOv5u и для оригинального YOLOv5s v7.0 доказана на уровне local_observation. Версия зафиксирована (`8.4.184` = `f7dd275e…`), веса сверены по sha256, выполнено 23 штатных и несколько cut-экспорта, получены инвентари операторов, CPU-декод сверен с графом (W1-10, W1-11, W1-15).
2. *Найдены и прочитаны первичные документы LinQ*: операторский мануал (API пути ONNX/TF → DNN Quant → компилятор → `.tpu` → `pytpu`), презентация 2026 с измерениями `yolo5s`/`yolov8n_pose`, исходники `pytpu` и `iva_applications`, сторонний стенд `linq-cv-bench`, MLPerf v0.7 (W1-01, W1-12). Именно это сдвинуло фокус на «что проходит конвертер», и это главный успех волны.
3. *Тонкие версионные ловушки* прослежены до тегов. Среди них: смена семантики `nms`/`end2end` в v8.4.142, флаг `legacy` у cls-ветви, `cls_remap` с v8.4.91, перестройка ширины cls для n-моделей, смена fitness, строгость проверок меток, rect-letterbox в `Model.predict` против квадрата в статическом ONNX (W1-02, W1-06, W1-07, W1-08, W1-11).
4. Механизм «склейка px+prob в одном выходе обнуляет scores при per-tensor int8» подтверждён сразу тремя путями: код Ultralytics, ORT-суррогат и синтетический fake-quant (W1-10-F18, W1-12-F27, W1-11-F34).
5. Дисциплина доказательств в целом соблюдена: inference/hypothesis/unknown помечены, ONNX/ORT нигде не выдаются за LinQ.

**Главные системные слабости.**
1. *Волна целиком мыслила «ONNX-первым» путём*, хотя по мануалу нативный вход квантователя — TF GraphDef, а ONNX лишь конвертируется. Не исследованы ни собственная сборка TF-графа (Ultralytics `pb`/`saved_model` через onnx2tf, Keras), ни окружение SDK (Python 3.11, TF 2.14, onnx 1.16). Если вендорский `onnx_to_tf` откажет, запасного пути нет (K001, K002).
2. *Нижняя половина лестницы (L7–L9) пуста у всех* (это ожидаемо). Но подготовка к первому часу с SDK разбросана по пяти файлам с разными определениями «raw-head», разными opset и без единого набора эталонных тензоров (K003, K004, K024).
3. *Количественные выводы по int8 сделаны на двух картинках*, где калибровка совпадала с оценкой, а успех разрезанной головы переинтерпретирован (K011).
4. *Ни одного реального обучения*, хотя GPU-окружение уже рабочее (W1-09-F31). Перенос весов проверен только на random-init источниках (K013).
5. *Перекрёстные связи между ячейками местами не замкнуты.* Широкие веса `objv1-150`/`oiv7` не связаны с `cls_remap` (K014). Предобучение YOLO26 на Objects365 не связано с лицензиями (K021). Вендорские измерения детекторов (W1-12) противоречат «0 измерений» в W1-14 (K007). Вендорские tiny_yolo3/ssd_mobilenet_v2 не рассмотрены как запасной путь, обучаемый под наши классы (K016).
6. *Малые объекты и бюджет хоста оценены только качественно.* Нет расчёта пикселей головы после letterbox, нет памяти активаций против 16 МБ on-chip, не измерена CPU-цена decode/NMS/кропов (K018, K027).

### Путь к LinQ: формат входа, окружение, первая проба SDK

**K001 — Нативный TF-путь не исследован: всё подготовлено только как ONNX.**
- **Проблема.** По мануалу `QuantizedModel.quantize` принимает `tf.compat.v1.GraphDef`, а ONNX лишь «предварительно конвертируется» вендорским `onnx_to_tf` (проверка 5). Вендорские примеры и единственная подтверждённая детекционная программа (tiny_yolo3, Keras-происхождения) — NHWC/TF. Ни одна ячейка не сделала собственный TF GraphDef для кандидатов, например через Ultralytics `export(format="pb")` или `saved_model` (onnx2tf, NHWC), и не проверила его загрузку в TF 2.14 / `tf.compat.v1`. W1-09-F03 упоминает extras `export-tensorflow`, но не развивает. W1-15-R5a отмечает TF-вход только для SSD.
- **Затронутые материалы.** W1-01-F01, F04; W1-12-F03; W1-15-R5a, C7; W1-10 (только ONNX); W1-09-F03; противоречие layout W1-11-C4 / W1-12 «Противоречия» п. 4.
- **Последствия.** Если `onnx_to_tf` не примет Ultralytics-ONNX (opset 18, Split, Resize-18, 5D-Reshape у v5), в первые часы хакатона не будет готовой альтернативы. При этом TF-граф сам по себе мог бы снять вопрос NHWC/NCHW.
- **Нужное доказательство.** Для yolov8n, yolo11n, yolov5s (v7.0 и/или master), pose-модели (K005) и mobilenet_v2: (а) TF GraphDef, полученный документированным экспортёром (с версиями `tensorflow`, `onnx2tf`/иного конвертера), с NHWC-входом; (б) список TF-операций графа; (в) численное сравнение с ONNX/PT на одном тензоре; (г) загрузка этого GraphDef в окружении, похожем на SDK (K002), через `tf.compat.v1.GraphDef().ParseFromString` и инференс `tf.compat.v1.Session`, как в примере мануала (стр. 349–367).
- **Задание второй волны (W2-C, OM).** Вопрос: можно ли для каждого кандидата заранее получить TF GraphDef, который загружается и исполняется в TF 2.14 и численно совпадает с ONNX, и как при этом меняются layout и набор операций? **OM**, потому что это согласование нескольких промежуточных форматов (PT → ONNX → TF) с разными раскладками и версиями — ровно класс задач, отнесённый пользователем к Opus medium. Материалы: мануал (`W1-12_files/Framework_manual_H1.txt`, стр. 131–169, 340–370, 521–540), W1-10 scripts/inventory, W1-09-F03, `linq-cv-bench/requirements.txt` (через W1-12-S07). Объединяется с K002.

**K002 — Окружение SDK ≠ окружение экспорта, рекомендованное W1-09.**
- **Проблема.** Мануал требует Ubuntu 20.04 и Python 3.11 (сайт говорит о Python 3.8, в логе мануала `python3.8`). Сторонний стенд использует `tensorflow==2.14.1`, `onnx~=1.16.0`, `onnxruntime~=1.18.0`, `numpy==1.26.4` (W1-12-S07, W1-15-F26). Матрица W1-09 строит все роли на Python 3.13 / onnx 1.23.2 / numpy 2.5 / ORT 1.31, а E5 (LinQ-SDK) оставлен пустым. Не проверено, открываются ли наши ONNX (IR 8, opset 18; raw-head opset 13) в onnx 1.16 / ORT 1.18. Не проверено и то, совместимы ли версии на одном хосте: в W1-09 нет TF, а numpy 2 конфликтует с TF 2.14.
- **Затронутые материалы.** W1-09 (матрица, F10–F13, «Открытые вопросы» 4); W1-12-F01, «Противоречия» п. 1; W1-15-F20, F26; W1-01 FLASH-1.

- **Нужное доказательство.** Воспроизводимый «LinQ-подобный» контейнер или venv: Ubuntu 20.04 (Docker или WSL2 есть, W1-09-F30), Python 3.11, TF 2.14.1, onnx 1.16.x, numpy 1.26.4. **K003 — Нет единого «набора первого часа» для SDK.**
- **Проблема.** Пять ячеек (W1-10 E1, W1-12 E2, W1-15 E1, W1-11 E2, W1-13 E6) предлагают первые пробы `onnx_to_tf → quantize → compile_` с разными кандидатами, opset, вариантами головы и калибровки, причём под два разных API (мануал 2025: `QuantizedModel.quantize`, DEFAULT/STAGING; стенд 2026: `RegularModel/calibrate/quantize(thresholds)`, O1/O5). При этом нет: скрипта интроспекции (`dir/help/inspect.signature`); двойной калибровки NHWC/NCHW; чтения `metadata.json` из `.tpu` (W1-12-F17); фиксированного порядка подачи графов; критериев «что считать отказом конвертера, а что — квантователя».
