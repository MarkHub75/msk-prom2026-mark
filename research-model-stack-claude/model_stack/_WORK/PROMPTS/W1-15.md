# W1-15 E2E_CHAINS — сквозные цепочки и места разрыва совместимости

Роль: исследователь первой волны, одна из самых сложных подтем. Модель: Claude Opus 5.5, effort medium. Почему Opus: нужно на основе собственной проверки первичных зацепок соединить компоненты (версия кода → config → веса → классы → loader → обучение → exporter → вход/выход → подготовка к LinQ) и найти межкомпонентные противоречия, которые теряются в отдельных обзорах.

Сначала полностью прочитай `ROOT\_WORK\CONTEXT.md`. Файл результата: `ROOT\_WORK\WAVE1\W1-15_E2E_CHAINS.md`.

## Главный вопрос и решение
Какие несколько полных маршрутов (кандидат + версия + веса + обучение + экспорт + граф + обработка + LinQ-шаг) можно собрать из реально существующих компонентов, где каждое соединение доказано, а где оно только предполагается? От ответа зависит, какие цепочки команда пойдёт проверять первыми после публикации кейса.

## Что сделать
1. Собери 3–6 маршрутов-кандидатов, например (уточняй сам, не назначай победителя заранее): (a) Ultralytics YOLO11n/s detect, fine-tune на PPE → ONNX; (b) Ultralytics YOLOv8n/s → ONNX (YOLOv8 явно в списке LinQ как `yolo8`); (c) YOLOv5s из ultralytics/yolov5 v7.0 (anchor-based, вероятное значение `yolo5s` в списке LinQ — проверить) → ONNX; (d) лицензионно-чистый вариант (YOLOX-s/tiny или иной Apache/MIT) → ONNX; (e) SSD-MobileNet (torchvision ssdlite или TF) — как «осторожный» путь по списку LinQ; (f) каскад person-детектор + классификатор вырезок (mobilenet/efficientnet в списке LinQ). Для каждого маршрута проследи каждый переход сам по первичным источникам (код с commit, release-файлы, документация), а не по пересказу.
2. Ищи межкомпонентные противоречия: checkpoint из другого fork/версии; `names` в весах ≠ `data.yaml`; exporter другой версии, чем training-код (например, обучено в 8.0.x, экспорт в 8.3.x — что меняется в head/графе?); `yolov5s.pt` (yolov5 repo) vs `yolov5su.pt` (ultralytics) — разные головы и выходы; head в export-режиме с другой семантикой выхода (xywh в пикселях vs нормированные); примеры runtime с NMS при графе без NMS; калибровка не того входного диапазона; torchvision SSD с label 0 = background и COCO-91 id.
3. Для каждого маршрута укажи переходы в виде лестницы: артефакт доступен → реализация загружается → обучение возможно → экспорт проходит → граф корректен → результаты согласованы → компилятор LinQ принимает граф → устройство исполняет → качество/скорость приемлемы — с уровнем основания для каждой ступени (по CONTEXT §3) и точным открытым звеном.
4. Можешь читать файлы соседей в `ROOT\_WORK\WAVE1\` по мере появления (особенно W1-02, W1-03, W1-06, W1-10) и использовать их наблюдения с указанием происхождения, но каждое ключевое соединение перепроверь сам. Клоны — `<SCRATCH>\repos\W1-15\`. Не дублируй локальный экспорт W1-10; если нужен иной небольшой эксперимент для доказательства конкретного перехода (например, проверить `names`/metadata в официальном весе) — свой venv `<SCRATCH>\venv-W1-15`.
