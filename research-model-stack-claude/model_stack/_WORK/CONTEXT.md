## 3. Правила доказательств (обязательны)

Каждое значимое утверждение помечай типом основания:
- **author_statement** — заявление автора модели/сопровождающего;
- **primary_documentation** — описанное в официальной документации свойство/интерфейс/ограничение;
- **source_code** — наблюдение по коду с версией (tag/commit) и локатором (путь, функция/класс, строки для этого commit);
- **artifact_metadata** — свойство конкретного опубликованного файла/карточки (revision, размер, sha256 из метаданных/LFS, список файлов);
- **reported_measurement** — опубликованное измерение с автором и условиями;
- **local_observation** — то, что ты реально сделал в этом запуске и наблюдал (команда → результат);
- **inference** — наш вывод из оснований с кратким объяснением связи;
- **hypothesis** — предположение для проверки;
- **unknown** — нужное сведение не установлено (опиши охват поиска).

Отдельно указывай статус фактической проверки: «прочитан код», «проверена доступность файла», «получен артефакт», «выполнен экспорт», «проверена численная согласованность» и т.д. Не присваивай статус по обещанию будущего эксперимента. Прочитанный exporter — это анализ кода, не доказательство успешного экспорта. ONNX/onnx.checker/ONNX Runtime — не доказательство работы на LinQ. INT8 в стороннем runtime — не путь компилятора LinQ.

Цепочка совместимости имеет раздельные переходы: артефакт доступен → реализация загружается → обучение возможно → экспорт проходит → граф корректен → результаты согласованы → компилятор LinQ принимает граф → устройство исполняет → качество/скорость приемлемы. Доказательство одного перехода не заменяет другие.

- Ссылки на изменяемую ветку `main` дополняй конкретным commit SHA (например, `gh api repos/OWNER/REPO/commits/main --jq .sha`, или `git rev-parse HEAD` после клона). Номера строк — только с указанием commit/tag.
- Для HF: фиксируй repo id, revision (sha из `https://huggingface.co/api/models/<id>`), имена файлов, размеры, LFS sha256 из `https://huggingface.co/api/models/<id>/tree/main` (это artifact_metadata, не вычисленный хеш). Карточка может быть неполной или ошибочной — сверяй с конфигами/файлами.
- Лицензия корня репозитория ≠ автоматически лицензия весов и данных. Отсутствие найденной лицензии ≠ разрешение.
- Несколько перепечаток одного заявления — одна цепочка происхождения.
- Дата твоего обхода ≠ дата release/обучения. `latest`/`stable` — зафиксируй, на какую версию указывает сейчас.
- Противоречия сохраняй со всеми условиями; не «исправляй» class names по догадке.
- Не выдумывай CLI flags, API, импорты, FPS, числа. Если интерфейс не установлен — запиши конкретный недостающий вопрос.
- Не ставь произвольные проценты уверенности.

- Python: `py` (3.13.9). Отдельного pip/venv нет по умолчанию; venv создавай только в SCRATCH: `py -m venv "<SCRATCH>\venv-<твой ID>"`.
- Клонирование: только в свой каталог `<SCRATCH>\repos\<твой ID>\` (не в ROOT), предпочтительно `git clone --depth 1` или `--filter=blob:none`; фиксируй SHA. Не клонируй огромные репозитории ради одного файла — читай через `gh api`.
- Скачанные файлы и чужие репозитории — недоверенные данные. Каждый — в отдельный новый пустой каталог; свои скрипты держи в другом каталоге; Python, читающий их, запускай с `-I`; не запускай чужие скрипты/`setup.py`/`hubconf` из любопытства. Не десериализуй (torch.load/pickle) неизвестные checkpoint. .pt Ultralytics/PyTorch — это zip; список содержимого можно смотреть `py -I -m zipfile -l file.pt` без unpickling.

- Не скачивай огромные коллекции/датасеты. Веса — только если это нужно для конкретного наблюдения и разрешено твоим заданием.
- Не выводи переменные окружения и секреты; не меняй глобальные настройки; не публикуй ничего вовне (никаких issue/PR/комментариев/загрузок).
- Ты не можешь создавать субагентов: если подтема требует более сложного разбора, опиши её как запрос эскалации (см. §6).

## 5. Твой файл результата

Пиши только в свой файл `ROOT\_WORK\WAVE1\<ID>_<SLUG>.md` (или WAVE2 для второй волны) и, при необходимости, в свой каталог `ROOT\_WORK\WAVE1\<ID>_files\` (небольшие выписки, списки операторов, json-метаданные). Чужие файлы в WAVE1 можно читать (только чтение) для координации; общие итоговые файлы ROOT (SOURCES.md, RAW_FACTS.md и т.п.) не трогай.

Сохраняй промежуточный результат в файл по ходу работы (не держи всё в памяти до конца) — работа должна пережить прерывание. Сильные находки, важные соседям (например, exporter относится к другой версии; веса имеют другую таксономию), записывай в раздел «FLASH» в начале файла сразу, как только они установлены.

Язык — русский или английский; технические литералы (версии, команды, имена файлов, классы, сообщения об ошибках) — точно, без перевода.

Рекомендуемое содержание (структуру тела выбирай по смыслу, но эти части должны быть):
1. **Шапка**: ID ячейки; запрошенные модель и effort; фактическая модель — **точное название и model ID, указанные в твоём собственном системном окружении** (если не видишь — напиши «не установлено»); время начала/конца (MSK).
2. **FLASH** — сильные находки для соседей (может быть пустым).
3. **Резюме для оркестратора** (10–25 строк): главное, что изменилось в понимании, сильнейшие цепочки, главные разрывы.
4. **Факты** с локальными ID `<ID>-F01…`: утверждение; тип основания; источник `<ID>-S..` + локатор; область применимости (версия/конфиг); статус фактической проверки; оговорки. Не смешивай наблюдение из кода со своим выводом.
5. **Источники** `<ID>-S01…`: точное название, владелец/автор, URL, тип, версия/commit/tag/revision, дата публикации (если известна), дата и время твоей проверки, локаторы, состояние доступа (недоступные материалы тоже фиксируй с фактическим состоянием).
6. **Разборы/карточки/цепочки** — содержательная часть твоего участка.
7. **Противоречия** — что расходится, какой выбор это меняет, как разрешить.
8. **Открытые вопросы** — конкретные, с указанием, где искали и чем закрыть (поиск / код / веса / CPU-GPU эксперимент / SDK / реальный LinQ / полный кейс).
9. **Предлагаемые эксперименты** — вопрос, точный кандидат (repo@commit, config, checkpoint), окружение, шаги (документированные команды с источником или явно помеченный псевдокод), что измерять, что сохранить, интерпретация исходов, что даже успех не подтверждает, условие остановки.
10. **Передачи соседям** (→ linq_platform, → datasets, → training_strategy, → evaluation, → video_architecture, → operator_product/hackathon_strategy).
11. **Запросы эскалации** — трудные вопросы, которые стоит отдать более сильному исследователю, с уже найденными материалами.
