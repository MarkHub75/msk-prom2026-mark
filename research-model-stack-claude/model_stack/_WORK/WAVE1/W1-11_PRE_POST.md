## FLASH
- **FLASH-1 (→ все, особенно linq_platform/evaluation).** Один и тот же `yolov8n/yolo11n/yolo26n` даёт РАЗНЫЕ детекции в `YOLO(pt).predict()` и `YOLO(onnx).predict()` на неквадратном кадре, даже при одинаковых весах: `Model.predict` принудительно ставит `rect=True` (`engine/model.py` L540), а `BasePredictor.pre_transform` включает `LetterBox(auto=True)` (минимальный прямоугольник) только для `format=="pt"` или динамических экспортов (`engine/predictor.py` L224–243). Статический ONNX всегда получает квадрат `imgsz×imgsz`. Воспроизведено локально на v8.4.184: до 18.9 px и 0.22 по conf на bus.jpg (1080×810) при `conf=0.25`. С `rect=False` PT и ONNX совпадают на выходе NMS (IoU 1.0, dconf 0.0). **Следствие: эталон для сравнения с LinQ — квадратный letterbox 114 (центр, `round(d∓0.1)`), а не результат `model.predict()` на PT без `rect=False`.**
- **FLASH-2.** Три официальных примера Ultralytics для ONNX используют три РАЗНЫХ пред-/постобработки (центр+114 / top-left+нули / квадратный холст+нули+stretch; NMS class-agnostic vs class-aware; усечение боксов до int без clip). Пример `YOLOv8-ONNXRuntime` даёт бит-в-бит тот же входной тензор, что `LetterBox(auto=False)` (локально), но NMS у него class-agnostic (`cv2.dnn.NMSBoxes`), порог 0.5/0.5, боксы усечены `int()` (до ~2 px). Примеры `cpp` и `OpenCV-ONNX-Python` дают другой вход (нули вместо 114, сдвиг в top-left) → другой conf (до 0.23) и боксы (до 20 px). Нельзя считать «любой пример = эталон».
- **FLASH-3 (→ linq_platform, W1-12).** Дефолтный выход Ultralytics-ONNX `[1,84,8400]` склеивает в одном тензоре боксы в пикселях входа (0…640) и вероятности классов (0…1). Если компилятор квантует выход одним масштабом (hypothesis, не установлено для LinQ), шаг int8 ≈ 2.5–5 px/уровень разрушит оценки классов; см. §6.6 (синтетический fake-quant, local_observation) и рекомендацию резать граф до concat/decode (W1-10 `rawhead_*` ONNX: раздельные `box_s*`/`cls_s*`).

- **FLASH-4 (→ linq_platform; ответ на FLASH оркестратора из W1-01).** Проверено по PDF `Framework_manual_H1.pdf` (sha256 `ebe0ab67…bb102a`) и `sherstpasha/linq-cv-bench@3ad1b7aa`: в вендорном примере вход TF-графа NHWC `(1,224,224,3)`, препроцесс (RGB, crop, resize, вычитание среднего, 0..255) выполняется на хосте и одинаков для калибровки и инференса; vendor `tiny_yolo3` — вход `(8,416,416,3)` NHWC float32 0..1, **decode+NMS на хосте** (якоря `10,14 23,27 37,58 81,82 135,169 344,319`, маски `3,4,5|0,1,2`); попытка YOLOv8s в стенде — NCHW `(1,3,640,640)`, NMS на хосте (`conf 0.001, iou 0.65`), успех запуска на LinQ в прочитанном не показан. ## Резюме для оркестратора
1. **Эталонный контракт зафиксирован** (Ultralytics v8.4.184, commit `f7dd275e…`): BGR→RGB, `LetterBox` центр, фон 114, `round`, `/255`, NCHW; на статическом ONNX — всегда полный квадрат `imgsz` (F01–F05, F30). Обратно: `scale_boxes` (центр, раздельные gain, clip), NMS class-aware через сдвиг 7680, `iou=0.7`, `conf=0.25` (val: 0.001 + multi_label) (F06–F09).
2. **Главный «подводный камень»:** `YOLO(pt).predict()` по умолчанию делает rect-letterbox (`rect=True`), статический ONNX — квадрат. Результаты разные (до 19 px / 0.22 conf; F31), при `rect=False` совпадают идентично. Эталон для LinQ = квадрат; подтверждено issue #26269 (maintainer: expected) и локально.
3. **Официальные примеры не взаимозаменяемы** (F16–F19, F31): совпадает с обучением только `YOLOv8-ONNXRuntime` (но class-agnostic NMS, `int()`-усечение, без clip, пороги 0.5/0.5); `cpp` и `OpenCV-ONNX-Python` — top-left + нулевой фон → Δconf до 0.23, Δbox до 20 px. Версия пакета важна (F13–F15).
4. **YOLOX:** BGR, 0..255, top-left, фон 114, `int()`; в ONNX — сырой `[B,N,85]`, decode на хосте; `/255` даёт 0 детекций (F24–F26, F35). **torchvision SSDLite:** stretch 320×320, RGB, [−1,1], 3234 anchors, weights (10,10,5,5) (F27, F37).
5. **Протокол сравнения** (6.5): S0 вход бит-в-бит → S1 сырой выход раздельно box/cls на «положительных» якорях → S2 единый эталонный decode/NMS → S3 пограничные → S4 fp16/int8 с нормировкой на шаг выходного квантователя → S5 матрица 2×2 {raw PT/LinQ}×{ref/product post}. Допуски fp32 обоснованы измерениями (box ≤5e-3 px, cls ≤5e-4; наблюдено 5.2e-4 px / 4.0e-5; F32, согласуется с #26269); «max по всем якорям» непригоден (F32, F33, #19991).
6. **Вынос decode из графа (по FLASH оркестратора):** контракты хоста для v8/v11 (DFL 16 бинов, порядок l,t,r,b, якоря +0.5, страйды 8/16/32), YOLO26 (reg_max=1), YOLOX, tiny_yolo3 (якоря/маски), SSDLite (default boxes) — в 6.3. Сторонний стенд держит NMS (а у tiny_yolo3 и decode) на хосте.
7. **Layout/диапазон входа на LinQ противоречат друг другу** (C4): вендорный пример и vendor tiny_yolo3 — NHWC, float32 0..1 (учебный resnet — 0..255 минус среднее); попытка YOLOv8s в стенде — NCHW; работает ли — не показано. PDF IVA H1 скачан, но кириллица недоступна (эскалация 1).
8. **Синтетическое fake-quant выхода** (не LinQ): склеенный `[1,84,8400]` (px + вероятности) одним масштабом → 0 детекций; раздельные тензоры → все детекции сохраняются (IoU 0.92–0.98) (F34). Это риск для первого теста на устройстве; мера — резать граф и делать decode на хосте.
9. **Реализация resize** — отдельный источник расхождений: допустимы только `INTER_LINEAR_EXACT`/torch bilinear без antialias (max 1/255); AREA/antialias/NEAREST — Δconf 0.007–0.07 (F36).
10. **Главные разрывы:** нет данных о layout/dtype/квантовании выходов LinQ и о поддержке неквадратных форм; допуски int8 не могут быть назначены без реального прогона; на промышленных кадрах кейса ничего не мерилось (COCO bus/zidane).

### 6.1 Эталонный конвейер Ultralytics (детектор, дефолтный ONNX `[1,84,8400]`) — контракт по шагам

Все параметры относятся к v8.4.184 (S01), проверены локально (F30, F31). Псевдокод — мой пересказ прочитанного кода, не вызов API.

```
# ПРЕД (хост)
img_bgr  = cv2.imread(...)                       # uint8 HxWx3, BGR
r        = min(Hin/h, Win/w)                     # Hin=Win=imgsz из метаданных экспорта (F04), scaleup=True
new_w,h  = max(round(w*r),1), max(round(h*r),1)  # Python round (банковское)
dw,dh    = Win-new_w, Hin-new_h                  # auto=False для статического ONNX (F02): паддинг до полного imgsz
top,bot  = round(dh/2-0.1), round(dh/2+0.1)      # то же left/right; лишний пиксель вниз/вправо
img      = cv2.resize(img,(new_w,new_h),INTER_LINEAR); copyMakeBorder(..., value=114)
x        = img[...,::-1].transpose(2,0,1)[None].astype(float32)/255   # RGB, CHW, 0..1; mean/std нет (F01)
# ГРАФ  → y: [1, 4+nc, A]; A=8400 при 640x640 (s8: 6400, s16: 1600, s32: 400); y[:4]=cx,cy,w,h в ПИКСЕЛЯХ входа, y[4:]=sigmoid-вероятности (F11)
# ПОСТ (хост)
cand     = y[4:].max(0) > conf                   # строго '>' ; conf=0.25 (predict) / 0.001 (val)
box      = xywh2xyxy(y[:4]); cls = argmax; score = max (без multi_label)
nms      = torchvision.ops.nms(box + cls*7680, score, iou)   # class-aware через сдвиг; iou=0.7 по умолчанию (F03,F07)
keep     = nms[:max_det]                         # 300
gain_x,y = round(w*g)/w , round(h*g)/h ; g=min(Hin/h, Win/w)
pad_x,y  = round((Win-round(w*g))/2-0.1), ...
box_orig = clip((box - pad)/gain, [0,w],[0,h])   # float, без усечения до int (F06)
```

Вывод: «letterbox 114 центр, RGB, /255» (Ultralytics) и «top-left, BGR 0..255» (YOLOX) — несовместимые контракты; ошибка одного флага (стёрт `/255`, BGR↔RGB, иной фон) не вызывает исключений, а лишь деградирует conf (F35: YOLOX с `/255` — 0 детекций).

Основание: вендорный путь ONNX→TF→квантование→компиляция (F28) и практика стороннего стенда держать NMS (и у tiny_yolo3 — decode) на хосте (F29). Ниже — контракты, прочитанные в коде (source_code), для кандидатов; «граф-резка» (где именно обрезать ONNX) — зона W1-10/W1-12.

|---|---|---|---|
| YOLOv8 / YOLO11 (reg_max=16) | на каждом уровне s8/s16/s32: `box` `[B,64,H,W]` (4 стороны × 16 бинов, **порядок каналов: сторона l,t,r,b → бин 0..15**) и `cls` `[B,80,H,W]` логиты (в экспериментальном ONNX W1-10 sigmoid включён — F38; в оригинальной голове sigmoid на `scores`, F11) | (1) приведение layout к CHW (если NHWC), (2) `softmax` по 16 бинам, математическое ожидание = расстояние в клетках, (3) якоря `(x+0.5, y+0.5)`, `x1y1 = a − (l,t)`, `x2y2 = a + (r,b)`, (4) `× stride (8/16/32)`, (5) sigmoid по cls (если не в графе), (6) конкатенация s8,s16,s32 (строка за строкой), (7) далее NMS/масштаб как в 6.1 | порядок уровней и страйды; `reg_max`; `+0.5`; sigmoid в/вне графа; layout |

### 6.4 Layout и масштаб входа на LinQ: что известно и чего нет

- Известно (F28, F29): в учебном примере вендора вход TF-графа NHWC `(1,224,224,3)`, калибровка теми же тензорами float32 NHWC, что и инференс; для vendor-программы tiny_yolo3 в стенде подтверждён вход `(8,416,416,3)` NHWC, `float32 0..1`, имя `input_1:0`. В попытке YOLOv8s тот же стенд подаёт NCHW `(1,3,640,640)` в `onnx_to_tf` и калибрует NCHW (`input_layout:"nchw"`); достоверных данных, что такой `.tpu` собран и запущен на устройстве, нет (нет результатов в прочитанном; не проверялось).
- Не установлено (unknown): сохраняет ли `onnx_to_tf` layout входа ONNX или переводит в NHWC; требует ли runtime float32 0..1 или допускает uint8 с внутренним масштабом (`--input-range` в стенде различает `unit_float|uint8`, но «подтверждён» только `unit_float`); где в цепочке происходит деление на 255 и вычитание среднего (в вендорном resnet-примере это делается на хосте в `preprocess`, значения 0..255 минус среднее — не 0..1); точность и тип выхода (float32 после `rescale`?); допускаются ли не-кратные 32 размеры; максимальный батч; семантика `anchors_mapping` в `RegularModel`. Эти вопросы → linq_platform.
- Вывод (inference): так как в вендорном примере препроцесс для калибровки и инференса — один и тот же код, а скейлы квантования определяются калибровкой по выходам `preprocess`, **контракт препроцесса (размещение, фон 114 vs 0, 0..1 vs 0..255, RGB/BGR, layout) должен быть заморожен до калибровки и совпадать побитно в калибровке и на хосте** — иначе тихий сдвиг масштабов. Это следует из вендорного шаблона (F28), но на LinQ H не проверялось.

### 6.5 Протокол численного сравнения (PyTorch ↔ ONNX Runtime ↔ LinQ)

Принцип: **разделить причины расхождения «кто изменил вход» → «кто изменил сырой тензор» → «кто изменил детекции»**; на каждом шаге менять ровно одну сторону. Все шаги выполнимы без LinQ (кроме L-шагов), и протокол сразу отрабатывается PT↔ORT (F30–F33).

**Артефакты на кадр** (имена фиксируем заранее): `in_ref_nchw_f32.npy` (после пред-обработки эталона), `in_ref_u8.npy` (HWC uint8 после letterbox, до `/255`), `meta.json` (`h,w,gain_x,gain_y,pad_x,pad_y,imgsz,preproc_version`), `raw_<ref>_<tensor>.npy` на каждый выход каждого рантайма, `dets_<runtime>_<post>.json`. Набор кадров: ≥1 кадр на сценарий кейса + принудительно разные пропорции (16:9, 4:3, портрет) + «пограничные» (малые объекты, ночь, пересвет) + пустой кадр; на кадрах кейса, не COCO.

| Шаг | Что сравниваем | Метрика | Допуск (и откуда) | Что значит нарушение |
|---|---|---|---|---|
| S0 | **вход**: хост-препроцесс продукта vs эталон (`in_ref_*`) на тех же кадрах | `max abs`, доля отличающихся элементов, равенство форм/layout | **0** при той же реализации (F30: бит-в-бит достижим для ORT-примера); при другой реализации resize — не более 1/255 (LINEAR_EXACT / torch bilinear, F36); AREA/antialias/NEAREST — недопустимо без повторной калибровки (Δconf до 0.07, F36) | ошибка препроцесса (фон, порядок каналов, округление, `scaleup`, rect/auto, resize), а не графа |
| S1 | эталонный вход → PT(fp32, fused) vs ORT(fp32), **сырой выход** | отдельно: box-каналы (px) и cls-каналы (prob) на **«положительных» якорях** (эталон `max cls prob > 0.05`), `max abs`; дополнительно по всем якорям — как справочная; косинус по box-каналам (чувствителен лишь к грубым ошибкам); косинус по class-каналам — только справочно | box ≤ **5e-3 px**, cls ≤ **5e-4** (≈10× от наблюдённого max 5.2e-4 px / 4.0e-5, F32; согласуется с F20: ≤0.02 px, ≤1e-4); *не* ставить допуск на «max по всем якорям»: хвост 3.3e-2 px на CPU (F32), 1.5 на CUDA↔CPU (F22) | экспорт изменил граф (W1-10) или другой opset/оптимизатор |
| S2 | те же сырые выходы + **единый эталонный decode/NMS** (Ultralytics `non_max_suppression`+`scale_boxes`, F07/F06) для PT и ORT | сопоставление детекций: greedy по conf, class-aware, IoU ≥ 0.5; в сопоставленных парах `min IoU`, `max |Δconf|`, `max |Δbox|`; число «лишних/пропавших» | fp32: 0 лишних/пропавших вне пограничного множества, `min IoU ≥ 0.999`, `|Δconf| ≤ 5e-4` (F31: 1.0/0.0 при одинаковом входе) | расхождение при корректном S1 → разные параметры NMS/порогов/класс-режим |
| S3 | **пограничные** детекции | множество `B = {d: |conf_d − conf_thr| ≤ ε_cls}` и `{d: ∃ другой бокс того же класса с IoU в пределах ±ε_iou от iou_thr}` | `ε_cls = max ошибки cls по S1/ожидаемой на целевом типе (fp16: 0.06, F33; int8: см. 6.6)`; детекции из `B` исключаются из строгого сравнения и учитываются отдельным счётчиком | различия внутри B — ожидаемый шум порога, а не ошибка |
| S4 | **fp16 / int8 / LinQ** : тот же `in_ref_*` в целевой рантайм; сырой выход сравнивается с ORT-fp32 по S1-метрикам | `max abs` на положительных якорях; **нормировать на шаг квантования выходного тензора `scale_out`**: `err/(scale_out/2)` | fp16 (справка, F33): box ≤ ~0.9 px, cls ≤ ~0.06 на 3 моделях; int8 — допуск *не задан*: оценивать по `err/(scale_out/2)` (≈1 → шумит только выходной квантователь, F34; ≫1 → внутренние слои/калибровка) | граф/квантование/компиляция (→ W1-12, linq_platform) |
| S5 | **матрица 2×2**: {сырой выход PT-эталон, сырой выход LinQ} × {эталонный пост, пост продукта} | совпадение детекций по S2 | см. S2; интерпретация ниже | где ошибка: графе, посте продукта, или в обоих |
| S6 | сквозной на кадрах кейса | то же S2 + метрика кейса | задаёт evaluation | приёмка |

Интерпретация S5 (4 клетки): (PT-raw, ref-post) = эталон. (PT-raw, product-post) ≠ эталон → ошибка поста продукта (NMS-режим, пороги, округление, pad, layout выхода) — графа тут нет. (LinQ-raw, ref-post) ≠ эталон при (PT-raw, product-post) = эталон → ошибка графа/квантования/компилятора/layout выхода. Обе клетки плохи → ищем раздельно по S0/S1.

Дополнительные проверки, дешёвые и выявляющие частые ошибки: (а) **синтетический «единичный» вход**: кадр, где letterbox-фон и объект дают предсказуемый отклик, и квадратный кадр без паддинга (устраняет вопрос rect/auto); (б) **симметрия**: зеркальный кадр должен давать зеркальные боксы (ловит перепутанные оси/NHWC↔NCHW); (в) **транспонирование выхода**: проверить, что `y[4:]` выходит в диапазон [0,1] и `y[:4]` в диапазон `[0, imgsz]` (иначе перепутаны тензоры); (г) **счётчик якорей**: `A = Σ (imgsz/s)²` = 8400 для 640 (s=8,16,32), 5040 для 384×640 — быстрый тест неверного размера; (д) **батч-паддинг**: для статического батча N на выход приходят строки паддинга — отбросить (Ultralytics дублирует нулями, стенд — повтором последнего кадра, F10, F29).

Форматы сравнения со степенями свободы, которые нельзя оставлять неявными: единицы (px входа vs норм.), порядок осей `[B,C,A]` vs `[B,A,C]`, наличие sigmoid, dtype (fp16/fp32/int8+scale), порядок уровней, `conf >` против `>=`. Для детекций сравнивать **после** одинакового округления (оба float или оба `int`, F16/F18 усекают).

### 6.6 Что показало синтетическое квантование выхода (F34) и что отсюда следует

- Дефолтный выход Ultralytics объединяет величины разного масштаба (0…~640 px и 0…1). При квантовании этого тензора **одним** масштабом (лучший случай — по max самого тензора) вероятности классов теряются целиком: 0 детекций на 6 из 6 пар (F34). Если выход разделён на `box` и `cls` (или box нормализован на размер входа), квантователь шага ≈1/255 сохраняет все эталонные детекции (IoU min 0.92–0.98, Δconf ≤ 0.002). Это не утверждение о поведении компилятора LinQ (способ квантования выходов LinQ не опубликован — unknown), а **риск, который надо проверить в первом же эксперименте на устройстве**; независимо от LinQ дешёвая мера — экспортировать и подавать на квантование усечённый граф (раздельные `box_s*`/`cls_s*`, как в экспериментальных ONNX W1-10, F38) и делать decode на хосте.
- Диапазон box-каналов нельзя брать из размера входа: у yolo26n значения выходят за [0,640] (клиппинг давал ошибку 18.6–28.8 px, F34) — калибровать по данным.
- Нижняя граница ошибки: выходной квантователь с шагом `s` вносит ошибку до `s/2` (наблюдено); при `s≈2.5–5 px` box-ошибка 1.25–2.5 px только от последнего округления, поэтому абсолютный допуск по боксам на int8 нельзя назначать меньше этого значения; сравнивать надо с `s/2`.

## Предлагаемые эксперименты

Общее условие остановки: если шаг S0 не проходит (вход не бит-в-бит), дальнейшие шаги не интерпретировать.

**E1. Golden-вектор препроцесса (без LinQ, 1 час).** Вопрос: даёт ли продуктовый препроцесс те же байты, что эталон? Кандидат: Ultralytics v8.4.184 `LetterBox(auto=False)` (+ при выборе YOLOX/SSD — их функции). Окружение: venv как мой (`W1-11_files\venv_freeze.txt`). Шаги: взять `W1-11_files\scripts\w11lib.py::pre_ultra_square` как эталон; сохранить `in_ref_u8.npy`, `in_ref_nchw_f32.npy`, `meta.json` для 20 кадров (разные пропорции); сравнить с хост-реализацией продукта (в т.ч. на другом языке/ресайзе). Измерять: max abs, доля отличий. Интерпретация: 0 — OK; 1/255 — допустим; >1/255 — менять реализацию resize/pad (F36). Не подтверждает: работу на LinQ. Остановка: все 20 кадров 0 или явная причина.

**E2. Первый запуск на LinQ: «2×2» (нужен доступ).** Вопрос: ошибка в графе/квантовании или в посте? Кандидат: любая принятая компилятором модель с известным эталоном (первый кандидат — vendor tiny_yolo3, т.к. runtime-контракт «подтверждён» в стороннем источнике, F29; затем YOLOv8n/11n). Шаги: подать `in_ref` (в нужном layout/диапазоне), сохранить сырой выход каждого тензора (`.npy`), прогнать эталонный пост и пост продукта по S5. Измерять: S1-метрики на положительных якорях, `err/(scale_out/2)`, S2. Интерпретация — см. 6.5. Не подтверждает: качество на кейсе. Остановка: клетка (LinQ-raw, ref-post) совпала с эталоном по S2 (с учётом пограничных).

**E3. Гранулярность выходного квантования (CPU, аналогия).** Вопрос: насколько дефолтный склеенный выход хуже раздельных `box`/`cls` при int8-квантовании? Кандидат: W1-10 `yolov8n_default` vs `rawhead_yolov8n`; сторонний int8 (ORT QDQ / либо fake-quant, как в F34). Шаги: калибровка 100–500 кадров домена; сравнить детекции с fp32 по S2. Не подтверждает: поведение компилятора LinQ (INT8 в стороннем runtime — не путь компилятора LinQ). Передать результат W1-12.

**E4. Квадрат vs прямоугольник на 16:9 (CPU).** Вопрос: как влияет статический квадрат 640×640 на recall малых объектов относительно 384×640 на реальных 16:9 кадрах? Кандидат: yolo11n/26n с экспортами W1-10 `*_384x640`. Шаги: прогнать оба с одним и тем же ref-постом на кадрах кейса (после 13:00 MSK), сравнить recall по S2/метрика кейса. Не подтверждает: поддержку формы на LinQ.

**E5. Устойчивость к реализации resize (CPU).** Расширение F36: задать реальное, что будет на потоках (декодер видео, ffmpeg swscale, GPU-ресайз); измерить Δconf на детекциях. Остановка: Δconf < выбранного ε_cls.

**E6. Декод вне графа (CPU).** Для каждого выбранного кандидата реализовать хост-декод из раздела 6.3 и сверить с дефолтным ONNX (повторение W1-10 `cpu_decode_vs_default_onnx` для остальных кандидатов: YOLOX, SSDLite с чекпоинтом); допуск S1.

- **→ W1-10 (export_onnx):** для «LinQ-friendly» экспортов предпочесть раздельные `box_s*`/`cls_s*` (F34, F38) и сохранять в `metadata_props` imgsz/stride/layout; не использовать `nms=True` для сравнения (F15); фиксировать версию Ultralytics, т.к. `nms`-семантика и `non_max_suppression` меняются (F14, F15).
- **→ W1-12 (quantization):** калибровочный препроцесс = продуктовый (6.4); диапазон box-канала калибровать, а не задавать из размера входа (F34); оценивать погрешность выхода через `err/(scale_out/2)` (6.5 S4).
