## Резюме для оркестратора

- Собрано 6 маршрутов: R1 YOLO11 (+R1b YOLO26), R2 YOLOv8, R3a оригинальный YOLOv5 v7.0 (+R3b `yolov5su` в ultralytics), R4 YOLOX (Apache-2.0), R5 SSD-MobileNet (R5a TF OD API / R5b torchvision ssdlite), R6 каскад «person-детектор + классификатор кропов». Для каждого — лестница переходов с уровнем основания.
- **Нижняя половина лестницы одинаково пуста у всех:** «компилятор LinQ принимает граф», «устройство исполняет», «качество/скорость» — unknown, есть только вендорские косвенные свидетельства: мануал (2025) называет протестированными `yolo5s`, `mobilenet_v2`, `yolo2/3`, `tiny_yolo2/3` (без версий/входов/точки отсечения); презентация 2026 — `yolo5s` b1 23,71 мс, `yolov8n_pose` 21,51 мс, `ssd_mobilenet_v2` 3,54 мс, `mobilenet_v2` 1,44 мс (TPU Framework 2026.8.43). Ни для одного маршрута не установлено, *какой* граф (до/после decode, с NMS или без) стоит за этими цифрами.
- **Верхняя половина** (артефакт → загрузка → обучение → экспорт → граф) доказана сильнее всего у R1/R2 (код 8.4.184 прочитан, веса получены и сверены по sha256, метаданные весов прочитаны мной, экспорт выполнен W1-10). R3a — артефакт и код есть, но окружение конфликтует с современным torch (FLASH 3). R4 — веса 2021 г., код ясен, экспорт локально не выполнялся. R5 — разрыв: torchvision-SSD (MobileNetV3) не в списке LinQ и не покрыт ONNX-тестами torchvision; TF-путь ближе к «родному» входу LinQ (GraphDef), но окружение TF OD API тяжёлое.
- **Межкомпонентные противоречия** (раздел «Противоречия», C1–C10): версия обучения официальных весов ≠ версия exporter; YOLO26 one2one/one2many по версии; `yolov5s.pt` ≠ `yolov5su.pt` (разные головы, выходы `(1,25200,85)` vs `(1,84,8400)`, разные loader-ы); метаданные v7.0-чекпойнта ≠ схема `train.py` v7.0; YOLOX — BGR 0..255 без нормализации и паддинг top-left; torchvision SSD — label 0 = `__background__`, 91 COCO-id с 10 `N/A`; калибровка LinQ по примеру мануала (NHWC, mean-subtract, 0..255) ≠ контракт YOLO (NCHW RGB /255); `rect=True` в predict; `cls_remap: True` в 8.4.x меняет инициализацию головы при fine-tune; MatMul/Softmax (C2PSA attention) есть в графах YOLO11/YOLO26 и отсутствуют в YOLOv8/YOLOv5.
- **Самое дешёвое закрытие главного разрыва** — не новая модель, а один прогон фреймворка LinQ (`onnx_to_tf` → `quantize` → `compile_` → TLM `model_execute`) на уже готовых графах W1-10 (yolov8n raw-head и full, yolo11n full, yolo26n e2e) + YOLOv5 v7.0 (full и raw-head). Это отделит «граф не принимается» от «принимается, но теряет качество». Нужен wheel `tpu_framework`/доступ — запрос организаторам (→ linq_platform, hackathon_strategy).
- Сторонний репозиторий `linq-cv-bench` (FLASH 7) — единственный найденный код полного LinQ-пути для YOLOv8 (ONNX NCHW, opset 13), но его автор на реальном железе для детекции перешёл на vendor `tiny_yolo3.tpu`; API там отличается от мануала (C11). Лицензионный контекст (Ultralytics: обученные модели под AGPL-3.0 по умолчанию, W1-04) делает R4 (YOLOX, Apache-2.0) единственным не-AGPL детектором с полной верхней лестницей — но с поломанным под torch ≥ 2.5 exporter-ом (FLASH 6).
- Победителя не объявляю; порядок проверки предложен в «Экспериментах» как программа.

## Маршруты (лестницы переходов)

Обозначения ступеней: **L1** артефакт доступен → **L2** реализация загружается → **L3** обучение возможно → **L4** экспорт проходит → **L5** граф корректен (checker/форма/семантика) → **L6** результаты согласованы (pt ↔ ONNX) → **L7** компилятор LinQ принимает граф (включая `onnx_to_tf` и `quantize`) → **L8** устройство исполняет → **L9** качество/скорость приемлемы. В ячейке — уровень основания по CONTEXT §3 и статус фактической проверки. «W1-10 LO» = local_observation, выполненное W1-10 (не мной), с моей перепроверкой кода.

Общий для всех маршрутов LinQ-хвост (L7–L8), по мануалу IV A H1 (S01, primary_documentation, стр. 7–21): fp32 модель (ONNX или TF GraphDef) → `onnx_to_tf(onnx.ModelProto)` → `QuantizedModel.quantize(original_graph_def, input_shapes={name: shape}, output_nodes=[...], calibration_dict={name: ndarray}, percentile=100.0)` → `quantized_model.as_graph(batch_size=1)` + `rescale()` (проверка int8-модели в TF на CPU) → `Network.from_quantized_model` → `compiler.compile_(TPU_128x128_PARAMS, network, DEFAULT|STAGING)` → `model_execute` (TLM-симулятор, даёт `execution_time_us`) → `TpuProgram.to_file('.tpu')` → `pytpu`: `Device.list_devices()/open()/load()/inference().sync(dict)`. Пример мануала — классификатор resnet50, вход NHWC `(1,224,224,3)`, preprocess = RGB, crop, resize, `tensor - [123.68,116.779,103.939]` (без /255), 2 калибровочных изображения (рекомендуется 100). Ничего о детекторах, NMS, многовыходных графах, opset, NCHW→NHWC в мануале нет (unknown).

### Наблюдение о латентности (inference по вендорским числам)

Презентация 2026 (через выписку W1-12, `2026_linq_presentation.txt` строки 62–81): resnet50 b1 2,99 мс; `yolo5s` b1 23,71 мс; `yolov8n_pose` b1 21,51 мс; `ssd_mobilenet_v2` 3,54 мс. По авторским таблицам FLOPs: YOLOv5s@640 = 16.5 GFLOPs (README v7.0 L295), YOLOv8n ≈ 8.9 GFLOPs (`yolov8.yaml` L11; pose чуть больше), ResNet-50@224 ≈ 4.1 GMAC (общеизвестно, не перепроверял). **`yolo5s` в ~2× тяжелее `yolov8n_pose` по FLOPs, но время почти одинаковое; и в ~8× медленнее resnet50 при ~2× FLOPs.** Значит время YOLO на LinQ, вероятно, определяется не MAC-ами: частью графа на CPU (decode/NMS?), операциями без эффективной реализации (SiLU, Resize, Concat, 5D reshape), обменом с хостом или иным входом. Это hypothesis, но она прямо влияет на выбор «n vs s» и точки отсечения → вопрос linq_platform: «что входит в 23,71 мс и какой граф (до/после decode) использован».

## Противоречия (межкомпонентные)

- **W1-15-C1 — версия обучения весов ≠ версия exporter; одно имя файла = разные файлы.** `yolov8n.pt`: v8.4.0-asset 6549796 B (сохранён 8.0.0.dev0) vs v0.0.0-asset и HF 6534387 B (W1-03). `yolo26n.pt` сохранён 8.3.222 из непубличной ветки. Меняет: какие числа mAP можно считать «базовыми», воспроизводимость стартовой точки fine-tune. Разрешение: фиксировать в экспериментах **sha256 файла, а не имя**; базовые метрики перемерять на 8.4.184 (`yolo val`) с тем же графом, что пойдёт на LinQ.
- **W1-15-C2 — YOLO26: один чекпойнт, две сети.** Дефолт `nms` (≥ v8.4.142) → one2many + внешний NMS; ≤ v8.4.141 → one2one NMS-free. Опубликованная/вшитая метрика 0.401 — неизвестно, какой головы. Меняет: «YOLO26 = NMS-free → проще для LinQ» верно только при `nms=False`, и тогда в графе TopK/GatherElements/Mod. Разрешение: E3.
- **W1-15-C3 — `yolov5s.pt` (yolov5 repo) ≠ `yolov5su.pt` (ultralytics).** Разные классы (`models.yolo.Model` vs `ultralytics.nn.tasks.DetectionModel`), разные головы (anchor-based 3×85 на ячейку, `no=85` vs anchor-free DFL `no=144`), разные выходы (`[1,25200,85]` с obj vs `[1,84,8400]` без obj), `names` list vs dict, взаимно не грузятся (pip-ultralytics явно отвергает v5-чекпойнт, `tasks.py` L1970–1980). Меняет: вендорское «`yolo5s` протестирован» к `yolov5su` не относится (если вендор имел в виду оригинал — не установлено). Разрешение: вопрос организаторам.
- **W1-15-C4 — `yolov5s.pt` v7.0 не соответствует `train.py` v7.0.** Код v7.0 (L372–381) пишет `opt`, `git`, `date`, `ema`, а файл содержит `wandb_id`, без `opt/git`, `ema=None`, `date 2022-02-08` — т.е. веса созданы кодом эпохи v6.1 и переложены в release v7.0 (README v7.0 L295 вообще ссылается на `v6.2/yolov5s.pt`). W1-03 описал ключи по коду, мой local_observation — по файлу. Меняет мало (архитектура v6.0+ совпадает: SPPF, 6×6 stem), но показывает: «метаданные по коду» ≠ «метаданные файла».
- **W1-15-C5 — YOLOX preprocessing.** С 0.1.1rc0 «We remove the normalization operation like -mean/std. This will make the old weights incompatible» (release notes, author_statement); `ValTransform(legacy=False)`: **BGR (cv2), 0..255 float, без mean/std**, паддинг 114 **в левый верхний угол** (`preproc`, `data_augment.py` L142–158), а не центрированный letterbox Ultralytics (RGB, /255, `center=True`, `augment.py` L1702–1711). Перепутанный препроцесс/постпроцесс (unletterbox) даёт сдвиг боксов без ошибок. Калибровка LinQ для R4 — на 0..255 BGR.
- **W1-15-C6 — torchvision SSD: label 0 = `__background__`, 91 категория с 10 `N/A`**; `person` = 1, а не 0 как в Ultralytics. Цикл постпроцесса `range(1, num_classes)` пропускает фон. Fine-tune с `num_classes = K+1`. Смешение с YOLO-индексами в общем пост-процессе/правилах — источник тихих ошибок.
- **W1-15-C7 — калибровка LinQ vs контракт модели.** Пример мануала: NHWC `(1,224,224,3)`, RGB, вычитание mean, без /255. YOLO Ultralytics: NCHW `(1,3,640,640)`, RGB, /255. YOLOX: NCHW, BGR, 0..255. Не установлено, переводит ли `onnx_to_tf` вход в NHWC и в какой раскладке ждёт `input_shapes`/`calibration_dict` для ONNX-модели. Меняет: неверный диапазон калибровки → неверные пороги int8 при формально успешной компиляции. Разрешение: E1 шаг «quantized vs fp32 на одном тензоре».
- **W1-15-C8 — `rect=True` в `predict()`** (`engine/model.py` L540) vs статический 640×640 ONNX; плюс `val` по умолчанию тоже rect-батчи. mAP из `yolo val` на `.pt` ≠ mAP того же графа 640×640. Разрешение: валидировать экспортированный граф/фиксированный letterbox.
- **W1-15-C9 — инициализация головы при fine-tune зависит от версии.** `cls_remap: True` (есть в v8.4.100+, нет в v8.4.0) копирует строки cls по совпадающему имени (`person`, `Person` — case-insensitive). Два «одинаковых» обучения на 8.4.0 и 8.4.184 стартуют по-разному. Разрешение: pin 8.4.184 и зафиксировать в логе обучения строку «Transferred N/M items».
- **W1-15-C10 — attention в YOLO11/YOLO26 vs список «CNN/RNN» на lin-q.ru/tech.** Графы YOLO11n/YOLO26n содержат `MatMul` и `Softmax` (C2PSA), YOLOv8n/yolov5su — нет (кроме DFL-Softmax) (W1-10 inventory). lin-q.ru/tech: «Расчёт (inference) свёрточных (CNN) и рекуррентных (RNN) нейронных сетей», при этом lin-q.ru/sol — «на CNN/Transformer моделях», а `yolo11` в списке «поддерживаемых». Меняет: R1/R1b несут дополнительный риск L7, отсутствующий у R2/R3. Разрешение: E1.

- **W1-15-C11 — API фреймворка LinQ: мануал (2025) ≠ сторонний код (2026-03/04).** Мануал: `QuantizedModel.quantize(original_graph_def, input_shapes, output_nodes, calibration_dict, percentile)`, пресеты DEFAULT/STAGING, `Network.from_quantized_model` → объект. `linq-cv-bench`: `RegularModel(...)` + `.calibrate` + `.quantize(thresholds)`, `anchors_mapping`, пресеты O1/O5 из `tpu_compiler`, `from_quantized_model` → кортеж, `set_batch`. Также пример мануала задаёт NHWC-вход (TF-resnet), сторонний код для ONNX-YOLOv8 — NCHW, vendor tiny_yolo3 — NHWC. Меняет: скрипты, написанные заранее по мануалу, могут не совпасть с выданной версией wheel. Разрешение: в первый час после доступа — `help()`/`dir()` по `tpu_framework`, `tpu_compiler`, и фиксация версии.
- **W1-15-C12 — названия в списке LinQ ↔ ONNX Model Zoo.** По W1-03 (передано оркестратором; не перепроверял): ONNX Model Zoo содержит ssd-mobilenetv1, tiny-yolov2/3, yolov2/3/4 — совпадающие с именами LinQ-списка, причём yolov3 там **с NMS в графе**. Сторонний бенч использует Model Zoo `tiny-yolov3-11.onnx` только как CPU/CUDA-эталон, а для TPU — vendor `.tpu` и отдельный «strict raw-head» экспорт из pjreddie cfg/weights. Inference: вендорские «поддерживаемые» имена, вероятно, означают конкретные сборки (часто raw-head без NMS), а не любые одноимённые ONNX.
