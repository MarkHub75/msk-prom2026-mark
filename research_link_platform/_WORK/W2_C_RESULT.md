# W2-C — ONNX frontend, versioned exporter и constraints кандидатов

Назначение: K004 (P0), K005 (P0), сопряжение K008 (P1). Вопрос: что передавать `model_stack`, какие варианты экспорта различают реальные гипотезы и что известно о lowering LinQ. Контекст подготовки — ночь 23.10.2026; фактическая новая сетевая проверка — 23.10.2026 примерно 04:49–04:55 MSK (UTC+3). Пофайловое время UTC — `W2_C/HTTP_LOG*.json`. Никакого SDK, экспорта, ONNX Runtime, квантования, компиляции, симуляции или устройства в этой ветке не запускалось. Просмотрены W2 prompt с K004/K005/K008, исходная постановка, CRITIC, W1-05/06, RUN_STATE и pinned exporter/build source. Новых model bytes от D/E нет; root подтвердил, что они исследуются следующей очередью.

## Решение

**Нельзя назначить opset13/static/noNMS официальными ограничениями LinQ.** Новый поиск не обнаружил versioned публичной матрицы `onnx_direct` / прямого ONNX frontend для Framework2026.8.43. Это локализованный неизвестный, а не результат «не поддерживается». Сайт LinQ снова успешно открыт через web, хотя Python requests получил TLS EOF; сайт подтверждает ONNX-интеграцию, но не даёт parser/opset/IR/attribute contract.

**Нужно исправить смысл raw-head в handoff.** У стандартного Ultralytics Detect из проверенной версии v8.3.0 `nms=False` не удаляет DFL и decode. Экспортируемый inference path уже возвращает декодированные boxes и class probabilities. Отдельная граница до DFL/anchor decode требует собственного export wrapper / выбора tensor boundary и отдельного подтверждения правильности. Это не запрещённый путь; он просто не равен найденному авторскому `nms=False`.

**Версия экспортёра — часть идентичности кандидата.** В v8.3.0 ONNX exporter вызывает обычную модель; в v8.3.200 ONNX exporter имеет явный `NMSModel` wrapper при `args.nms`. Общая запись «YOLOv8 ONNX» скрывает разные графы. Pinned `linq-cv-bench` не фиксирует версию ultralytics; upstream sources ниже показывают конкретные возможные пути, а не восстанавливают задним числом граф автора. Предпочтение YOLOv8s над YOLO5s/YOLO11 из этих фактов не следует.

## Подробные факты

- **W2-C-F01, S01, source intent.** Экспортёр автора выставляет по умолчанию `opset=13`, `batch_size=1`, `imgsz=640`, argparse-флаги `dynamic`/`simplify` по умолчанию false, а в `model.export` передаёт `nms=False`. Он сам допускает иной `--opset`, batch и dynamic. Это прямое опровержение прочтения «script доказывает только static13 разрешён LinQ»; успешный проход иных вариантов он тоже не доказывает.
- **W2-C-F02, S01, local source fact.** `force_static_onnx_input_shape` меняет только четыре dim_value выбранного `graph.input`, жёстко `(1,3,img_size,img_size)`. Он не посещает nodes, initializers, Constant attrs, graph.output или value_info. Поэтому вызов не является полноценной shape specialization / пересборкой head. Даже если protobuf удалит взаимоисключающий dim_param, остаются неизменёнными внутренние constants. Из этого не следует, что конкретный неизвестный ONNX испорчен: его bytes отсутствуют.
- **W2-C-F03, S02, source intent.** v8.3.0 создаёт dummy `(batch,3,H,W)`, задаёт Detect `dynamic/export/format`, делает два dry-run, затем `torch.onnx.export` с явным opset, constant folding, именами `images`/`output0` (для detection). При dynamic отмечены N,H,W и output anchor count. Это поддерживаемый путь экспортёра; не доказанная поддержка dynamic LinQ. Его `simplify=True` использует onnxslim0.1.34, исключение лишь логируется — флаг не гарантирует, что итог упрощён.
- **W2-C-F04, S03, source intent.** Для обычного, не end2end Detect, `forward` строит feature heads, а при inference вызывает `_inference`; export возвращает `y`. `_inference` включает flatten по batch, concat, split box/classes, DFL, decode, умножение stride и class sigmoid. Поэтому noNMS output — decoded pre-NMS predictions; термин «raw» допустим только с явным определением этой границы.
- **W2-C-F05, S04, source intent.** DFL v8.3.0 берёт `b,_,a`, reshape в `(b,4,c1,a)`, transpose(2,1), softmax(dim=1), фиксированную 1×1 convolution с индексными весами и reshape `(b,4,a)`. Это конкретная область для inventory и stagewise численного сравнения. Нет bytes → нет утверждения, что конкретный экспорт содержит именно ONNX Softmax/Conv с конкретными names/attrs: exporter и optimizers могут изменить представление.
- **W2-C-F06, S05, source intent + inference.** `make_anchors` зависит от feature h,w через arange/meshgrid, формирует coordinates и stride tensors; `dist2bbox` выполняет split/chunk и арифметику. Следовательно, смена только input dim у статического файла не доказывает обновления anchor/grid constants. Полноценный повторный экспорт на новом H/W с parity — различающий тест.
- **W2-C-F07, S06, source intent.** v8.3.200 ONNX exporter выбирает `NMSModel(self.model,self.args)` при `args.nms`; при dynamic удаляет anchor axis из dynamic output mapping для NMS. Это versioned отличие от v8.3.0 ONNX path. Не выводить из этого поддержку ONNX NMS LinQ или произвольных dynamic H/W: даже здесь output и input annotations надо проверять в фактическом файле.
- **W2-C-F08, S07, source intent.** YOLOv5 v7.0 detection экспорт имеет `(images,output0)`, dynamic input N/H/W, output dynamic N/anchors по axis1; Detect включает anchor/grid decode и conf/objectness channels. Конкретный v7.0 source не содержит DFL-путь v8 Detect. Это даёт иной кандидат для локализации head проблемы, но не доказывает, что vendor `yolo5s` benchmark использовал v7.0. v7.0 ONNX `simplify` использует onnx-simplifier≥0.4.1, а не onnxslim.
- **W2-C-F09, S08, standard semantics.** Для Resize13 важны не только `op_type`, но mode, coordinate_transformation_mode, nearest_mode, scales vs sizes и их dtype; schema имеет defaults nearest/half_pixel/round_prefer_floor. Softmax13 имеет axis default -1. Reshape allowzero отличает трактовку 0. Поэтому inventory должен сохранять отсутствующие/присутствующие attrs и effective schema version. Не приписывать эти default values реальному YOLO файлу до чтения bytes.
- **W2-C-F10, S10, source configuration.** В проверенных yaml YOLOv8 и YOLO11 v8.3.0 есть `nn.Upsample` nearest×2 и Concat axis1, затем Detect. Это привязывает проверку Resize/Concat к конкретной архитектурной конфигурации вместо общего списка NPU-рисков. YAML не является ONNX inventory и не доказывает attributes, rank или lowering.
- **W2-C-F11, S01, source intent.** Build использует `tpu_framework.onnx_to_tf` или fallback import `onnx_direct.onnx_to_tf`, пробует try_simplify True/False/без аргумента, затем RegularModel с GraphDef; это два Python namespace одного предполагаемого TF seam, а не доказательство нового ONNX-native frontend. Broad exceptions скрывают исходную причинность; журнал надо сохранять отдельно по попыткам. По batch автор создаёт отдельные программы через `network.set_batch` для 1/8; это не dynamic batch одного executable.
- **W2-C-F12, K008 boundary.** В этом build нет доказанного Q/DQ import path: исходный ONNX конвертируется в TF, затем собственный RegularModel calibrate/quantize. Ветвь `except TypeError: calibrate(...)` может изменить effective вызов; QDQ/готовый INT8 ONNX надо считать отдельным неустановленным frontend feature, не заменой calibration. Что именно означает percentile, W2-C не установил; это предмет W2-F. Нет оснований объявлять per-channel/asymmetric activation support.

## Конкретная передача model_stack

1. Передавать один immutable manifest на каждый файл: repository commit, weights hash, task/detection-vs-pose-vs-OBB, class count/order, versions ultralytics/torch/onnx/onnxslim или onnxsim, полный export call. Одних `opset=13` и имени YOLOv8s недостаточно.
2. Сохранить **реальные** `ir_version`, все `opset_import` (включая domain), producer metadata, graph input/output/value_info, node domain/op_type/attrs, initializer dimensions/dtypes/external locations, small shape constants, local functions. Отдельно names/layout/dtype и decode/NMS boundary. Сначала read-only inventory исходного файла, потом отдельно результаты simplification/shape inference; каждый новый файл hash-ить.
3. Сохранить identical FP32 preprocessed test inputs: одиночные разные изображения, batch разных изображений; PyTorch и ORT outputs до NMS, task metrics после согласованной постобработки. Использовать репрезентативные калибровочные tensors той же предобработки; 500 — настройка автора, не норма достаточности.
4. Первый test order: exact vendor sample на matched target → unchanged custom candidate → float frontend parity → vendor PTQ → compile DEFAULT → TLM/device. Только затем менять один фактор: export opset, simplify, batch, H/W или NMS. Не выполнять декартово произведение гипотез до первого error.

`W2_C/INVENTORY_ONNX.py` — подготовленный read-only helper, запускается `python INVENTORY_ONNX.py candidate.onnx --out INVENTORY.json`. Он не импортирует SDK, не переписывает файл и не делает shape inference. Проверен только Python AST; onnx/torch здесь отсутствуют и actual model не предоставлен, поэтому helper на ModelProto не запускался. Он сохраняет attrs, small constants, shapes, external-data refs и hashes; local functions и sparse initializers помечает количеством для дальнейшего расширенного осмотра, их тела не инлайнит. Это helper, а не готовая проверка compatibility.

По ним relevant parser repo не найден; оставшиеся страницы/приватный code index не проверялись. Это ограниченный targeted retrieval, не исчерпывающий GitHub code search.
- PyPI JSON `/pypi/onnx-direct/json` и `/pypi/tpu-framework/json`: HTTP404. Это только отсутствие этих точных публичных имён в PyPI на момент проверки; import modules могли поставляться в иначе названном wheel или закрытом индексе. Никакой SDK не устанавливался.

HTTP_LOG_3 содержит поздние дополнительные fetches; timestamps коротких GitHub tag follow-up запросов записаны после ответа, а не время начала.
- Direct ONNX-native hypothesis не опровергнута. Имя `onnx_direct` и alias `tpu_framework.onnx_to_tf` сами по себе не отвечают на неё. Нужен actual installed frontend class/signature/version или vendor source release notes. Вещи, которых нет в report: maximum opset/IR, поддержка symbolic N/H/W, runtime shape polymorphism, CPU partitioning, NMS/DFL lowering, готовый QDQ import. Их статус неизвестен.

## Что изменилось относительно W1 и handoff root

Уточнён термин raw-head: noNMS оставляет decode/DFL в конкретном стандартном upstream path.
