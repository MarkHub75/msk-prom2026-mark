# W2-D — modern detector route и custom-class adapter

**K005, K006, K018, K020.** Вопрос: есть ли более доказанный custom detector, чем сторонний YOLOv8s, и какой output/NMS contract нужен для произвольных классов? Исторический контекст — ночь23.10.2026; фактический новый поиск/получение источников —23.10.2026 примерно04:52–05:00 MSK (контроль часов:01:59:50 UTC). Точные UTC и hashes direct downloads сохранены в `_WORK/W2_D/*HTTP_LOG.json`. Прочитаны исходный task, RUN_STATE, релевантные CRITIC K, W1-08/10/11 и W2-C; SDK/устройство не предоставлены по RUN_STATE. Research, без разработки сдаваемого prototype.

**Решение:** публично замкнутую цепь custom detection weights→export→LinQ compiler→runtime→quality evidence установить не удалось. Нет оснований объявлять YOLOv8s победителем по совместимости. Для инженерного старта остаются три условных custom route: source-detailed YOLOv8n/s detection, exact vendor YOLO5s route при получении исходного export/sample, YOLO11 detection при получении exact matched sample. Их первые gates различны. Отдельный vendor TinyYOLO3 — более сильный author-reported smoke route, но не доказательство custom PPE weights. Новая история YOLOv5su не закрывает классический YOLO5s; новое чтение СПбПУ уточняет ограничение ранее приведённых YOLO11l OBB20FPS.

## Установленные факты

**W2-D-F01 — S01/S02, source/history.** Новая полная история default branch не обнаружила опубликованных `.onnx/.qm/.tpu` либо results в `models/artifacts/experiments`: targeted `git log --all -- ...` пуст. В текущем tree этих закрывающих artifacts нет; S01 releases/tags/issues пусты. Это существенно сильнее проверки одного shallow checkout, но не исключает чужой private server, удалённые ветки либо неопубликованные logs. Полный history mirror и GIT_HISTORY_INSPECTION.json сохранены. V8 exporter/build появляются в history commit `f91c66b...`12.03.2026; дальнейшая история просмотренных файлов не добавляет success logs. Отсутствие лога не доказывает невозможность модели.

**W2-D-F02 — S02/S04, author-reported status.** Current RUN_SCENARIO завершает detection на vendor tiny_yolo3 и отмечает done для HP1M/HPD1M. Более ранний commit17.03 прямо разделял valid quality и INVALID MLPerfqps400. Поэтому current фраза, что VALID ожидается приqps2000, не заменяет raw loadgen summary. Для custom YOLOv8 author-reported done в найденных status notes не установлено. Нет причины объявлять весь репозиторий нерабочим из-за незавершённого modern route, равно как нет причины приписывать modern route успех Tiny.

**W2-D-F03 — S03/S09, новая контрпроверка альтернативы v8.** Исторический `export_yolov5su_to_onnx.py` действительно default `yolov5su.pt`, `from ultralytics import YOLO`, imgsz640/opset13/dynamic false; передаёт format/опсет/dynamic/imgsz, но не pin версии и не явный nms flag. Quantize ведёт ONNX→onnx_to_tf→RegularModel.calibrate/quantize→qm; compile→Network→compiler.compile_→TpuProgram; runner импортирует modern `ultralytics.utils.nms`, принимает84/85 и COCO80. Это ещё один source skeleton того же автора, не classic5+N success evidence. Upstream называет v5u objectness-free. Exact old ONNX bytes отсутствуют: из имени нельзя доказать nodes/output, но путать его с classic vendor yolo5s недопустимо.

**W2-D-F04 — S05, новое уточнение независимой линии.** Университетская аннотация говорит о ранее записанных стендовых измерениях, повтор которых при подготовке работы ограничен недоступностью стенда. YOLO11l obb20FPS относится к этой линии; основная опубликованная quality evaluation — регрессия координат, не PPE detection. Точные weights/exporter/SKU/batch/input precision/runtime/timing boundary и raw protocol не доступны из metadata. Источник независим от repo по автору/публикации; независимость самого bench от vendor измерений неизвестна. Нельзя превращать его в custom YOLO11 horizontal-detection success или quality evidence. Это опровергает чрезмерный тезис «современный YOLO существует только в vendor family list», но не замыкает наш route.

**W2-D-F05 — S06/S07/S08, versioned source, K006.** Modern NMS v8.3.0 и8.3.200 предполагает BCN: `nc = nc or (prediction.shape[1]-4)`; split `(4,nc,extra)`, class max; objectness multiply отсутствует. Classic v5v7.0 предполагает BNC, `nc=shape[2]-nm-5`, candidate objectness, затем `x[:,5:] *= x[:,4:5]`. Поэтому modern NMS не распознаёт old85 как 5+80. Если transpose old85 в BCN и оставить nc0 — будет81 класс, objectness станет class0. Если передать nc80 — objectness всё ещё class0, исходные class0..78 сдвинутся, последний class79 попадёт в extra. Простой `nc=80` проблему не решает. При v8 с81 настоящим классом85 каналов корректны, то есть число85 само по себе не ошибка.

**W2-D-F06 — S02/S06/S07/S10, contract.** Для standard Detect v8.3.0 export/noNMS выход decoded `(B,4+nc,A)` с xywh в координатах padded input и class sigmoid, без отдельного objectness; DFL/decode/stride уже внутри. A зависит от фактических feature maps, не от nc, стандартный640 обычно8400. Не sigmoid повторно, не DFL/decode повторно. Противоположный raw-conv multihead export — другой manifest и отдельный decode. Pose/seg/OBB имеют extra и иной decoder; 4+nc правило только для plain detection.

**W2-D-F07 — S02, actual limited helper test.** SCHEMA_PROBE.py AST-извлекает именно normalizer из pinned source, подставляет shape-only object и выполняет стандартным Python. `(1,5/6/7,8400)` custom nc1/2/3 отвергнуты; `(1,85,8400)` принят; `(1,6,84)` ошибочно трансформирован в `(1,84,6)`, потому что84 распознано как channels. `(1,84,84)` неоднозначен и молча принят. Это выполненный probe Python helper без numpy, модели, NMS, SDK и устройства. Счётный counterexample old2: obj.1, cls[.9,.2] → корректный score.09/class0, modern interpretation → score.9/class1. При threshold.25 ошибка меняет и наличие detection. Числовая иллюстрация выведена из source, не исполнявшийся torch NMS test.

**W2-D-F08 — S06/S07, дополнительная граница.** Обе версии NMS имеют shortcut `prediction.shape[-1]==6` → готовые BNC detections. Для обычного full detector A велик, однако tiny synthetic probe сA6 попадёт в чужую ветку даже при правильном nc. Поэтому golden synthetic tensors для проверки этих функций должны иметь A≠6 или проверять этот shortcut отдельно. У v8.3.200 `end2end=False` не отключает shape[-1]==6 shortcut. Нельзя решить контракт только перестановкой осей. Результаты NMS могут изменяться на ties и max_nms/max_det/time limit; thresholds и package/backend нужно фиксировать.

**W2-D-F09 — S02/S06, adapter source.** Runner imports `ultralytics.utils.nms`, а v8.3.0 NMS расположен в utils.ops. Поэтому просто pin8.3.0 без изменения import не даёт working runner. `load_io_names` при любом override сразу возвращает пару overrides и теряет второй name из summary; malformed/missing JSON молча переводит в heuristic mode. `pick_output` выбирает первый rank≥3. На multihead/pose может быть выбран неверный tensor. На custom evaluation COCO80_TO_91 и range guard дают неверный category_id или отбрасывают cls≥80. Такие ошибки не ловит successful runtime call.

## Спецификация adapter и planned patch list

Один model manifest, владелец model_stack; host adapter обязан прочитать его до inference. Обязательные поля: task/variant, weights+ONNX+compiled hashes, exporter repo commit/package versions/export call, nc и упорядоченные names, train-id→evaluation-category-id, tensor names/dtypes/layout/shapes, output schema enum, bbox representation/units, decode/sigmoid/DFL/objectness/NMS boundary, quant output scale/zero point только по actual runtime contract, preprocess/color/range/resize/padding, compiled batch/target. Одних nc/name модели недостаточно.

1. Заменить84/85 heuristic на explicit `schema` и layout. Для `decoded_xywh_class_prob` принимать только channels4+nc, transpose только если manifest BNC. Для classic `decoded_xywh_obj_class_prob` принимать5+nc и использовать pinned v5 NMS либо явно проверенный conversion; не присваивать extra каналу смысл objectness автоматически. Post-NMS BNC6 — отдельный schema, не повторный NMS. Неоднозначная/неизвестная shape, неверный nc, лишние outputs — fail with descriptor dump.
2. Выбирать output по точному manifest name; summary имена проверять против actual tensor_descriptions, merge input/output overrides независимо. Не переходить молча к первому rank≥3 при отсутствии metadata. Для undecoded multiscale heads требовать все named tensors/anchors/strides и отдельный decoder.
3. Pin совместимый NMS source/package/import; передавать nc явно для modern plain detection, agnostic/multi_label/max_det/max_nms/conf/iou явно. Для v8.3.0 import изops; для v8.3.200 изnms. Это примеры проверенных вариантов, не требование именно этих пакетов. Проверить strict detection-only output `(k,6)` после NMS. Не добавлять sigmoid/objectness product в4+nc route; не терять objectness product в5+nc.
4. Убрать COCO80_TO_91 как default для custom; использовать manifest category map. Train class index0 может соответствовать category_id17 — mapping должен быть explicit. Метрики PPE определяются датасетом, не именами COCO. Хранить model_class_id, semantic label и evaluation_category_id отдельно.
5. Inverse letterbox использовать metadata именно каждого подготовленного frame; сначала xywh→xyxy в input pixels, затем remove pad/divide gain, agreed clipping, затем output format. Не умножать повторно stride. Не предполагать normalized coordinates по range values. Не менять текущий clipping/maximg-1 или small-box cutoff≤1 без согласования evaluator; эти параметры тоже могут влиять на AP.
6. Проверять batch count/order, finite values, dtype и actual output dequantization. Не угадывать масштабы uint8/int8. Пустой результат считать корректным только после этих checks; shape/API success не доказывают class correctness. Для parity clone output до NMS: проверенные NMS изменяют box coordinates in place.

Это спецификация изменений, не внесённый production patch. Unicode issue повторно не исследовалась; она не закрывает перечисленные contract defects.
