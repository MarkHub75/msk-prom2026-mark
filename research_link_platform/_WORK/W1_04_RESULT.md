# W1-04 — Окружение и установка LinQ

Проверка источников: 23.10.2026, примерно 04:20–04:25 Europe/Moscow (UTC+3). Контекст подготовки: хакатон 23–25.10.2026; выданного SDK, реквизитов и точной модели ускорителя нет. Исследовательская ветка, без установки ПО и аппаратных экспериментов.

## Главный вопрос и результат

Какое окружение можно обоснованно подготовить для квантования/компиляции и отдельно для инференса LinQ, не выдумывая зависимости?

Полностью воспроизводимое окружение по открытым источникам **пока не восстановлено**: есть официальная инструкция установки framework, но нет доступного нам wheel, lock-файла, совместимого комплекта runtime/драйвера и матрицы их версий. При этом установлены полезные опорные точки: Ubuntu 20.04 / Python 3.11 / RAM ≥32 ГБ в руководстве 2025 года; Ubuntu 24.04 / TPU Runtime 16.18.6 / TPU Framework 2026.8.43 в условиях опубликованного теста 2026 года; отдельный драйвер LinQ H1 для физической платы. Они относятся к разным контекстам и не образуют единую рекомендованную конфигурацию.

Архитектура документации позволяет отделить подготовку `.tpu` от загрузки программы на устройство. Поэтому компиляция без платы — обоснованный кандидат первого эксперимента, но её фактическое выполнение и отсутствие требования лицензии/устройства при импорте не проверены. Windows следует рассматривать как рабочую клиентскую машину для разрешённого удалённого доступа, пока поставщик не подтвердит Windows-сборку framework/runtime. Это инженерный маршрут, не установленный протокол хакатона.

## Как читать требования и противоречия

1. **Python 3.8 против 3.11.** Сайт `/sol` и историческая продуктовая страница FW_TPU_H говорят о 3.8, guide 2025 явно требует 3.11, а его лог сохранил 3.8. Причина не установлена. Вероятна разновременность обновления частей документации, но это гипотеза. Не устанавливать 3.8 только из рекламы и не переезжать на 3.11 поверх готового удалённого окружения без сверки поставки.
2. **Ubuntu20.04 против24.04.** Guide — нормативные условия программы конкретной редакции; презентация — окружение измерения новой версии. Не доказано ни прекращение поддержки20.04, ни поддержка24.04 старым wheel. Здесь нет установленного противоречия одной и той же сборки.
3. **`py3-none-any` против Linux/Intel.** Платформенно нейтральный тег framework может сосуществовать с платформенными транзитивными зависимостями или внешними native libraries. Отсутствие ABI-tag CPython не доказывает, что весь стек переносим на Windows/ARM. Сам факт соответствия реального wheel этому имени ещё не проверен.
4. **Неполный install recipe.** `python3 -m venv` в руководстве не выбирает 3.11 явно. Даже при точном повторении команд нужно заранее проверить `python3 --version`. Guide не объясняет установку Python3.11 на выбранную Ubuntu и не фиксирует pip. Команда обновления pip делает среду зависимой от времени исполнения. Это замечания к воспроизводимости, не установленные ошибки установки.
5. **`MIPS` в lspci.** Это текст класса/идентификации PCIe endpoint в hardware guide. Он не доказывает MIPS-архитектуру хостового CPU. Нельзя выбирать MIPS Linux по этой строке.

| Linux-хост с физической платой | PCIe enumeration, отдельный драйвер, SDK device API. | Поддержанные kernel/glibc, driver/runtime/firmware pairing, права на device nodes, udev, DKMS, reboot, контейнерный passthrough. |
| Выданное облачное окружение | Публично заявлен Cloud TPU и существует описание прототипа. | Что именно выдают участникам, кто компилирует, кто ставит драйвер, как доставляется `.tpu`, квоты, хранение, доступ к логам. |

**Можно ли компилировать без платы?** Основание положительного ожидания: требования framework не перечисляют плату; compiler получает целевые hardware parameters; в примере compilation/TLM и сохранение файла предшествуют device API. Тип вывода — inference, а не выполненная компиляция. Надёжный ответ для выданного релиза даст изолированный CPU-only smoke-test с поставленным комплектом. Не путать «без платы» с «без SDK» и «бесплатно»: компоненты, лицензия и права всё равно нужны.

**Драйверы и runtime.** Hardware guide прямо требует отдельный драйвер; framework guide не даёт его install-команды. `pip install tpu_framework...` не следует объявлять установкой драйвера. Не найдены допустимые команды `modprobe`, имена `.ko`/deb/rpm и device paths; не подставлять типичные имена NPU. Для выданного API-сервиса установка драйвера на Windows-клиенте может вообще не требоваться; это зависит от контракта доступа.

**Docker.** Публичного проверенного Dockerfile или container digest этой платформы в данной ветке не найдено. Вакансия — полезная зацепка, но не runnable artifact. Не собирать «официальный образ» из предположительных apt/pip зависимостей. Запросить готовый image digest/registry и правила доступа к TPU либо точный wheelhouse/lock с host driver requirements. Контейнер compiler и контейнер runtime могут иметь разные требования; сейчас это проектная возможность, не документированный продукт.

## Конкретные следующие проверки и handoff

**Приоритет0, до выбора окружения.** Запросить у LinQ: какой контур доступа выдан команде (shell/VM/container/API); точные OS/ISA/Python; перечень framework/runtime/driver/firmware с версиями и совместимостью; wheelhouse или image digest; инструкция CPU-only compilation; лицензия/права; официальный минимальный model→`.tpu`→TPU пример; полный installation guide. Вопрос должен разделять машину compiler и runtime host.

**E01 — паспорт предоставленного окружения (план, не выполнено).** На разрешённом Linux shell сохранить `uname -a`, `uname -m`, `/etc/os-release`, Python version, pip list/freeze, `pip check`, device list. Уточнить команды версий vendor tools по `--help`/документации вместо выдуманного CLI. Для физической платы добавить полный `lspci -nn` и журнал discovery SDK; строка MIPS из guide — сверка конкретного endpoint, не универсальная гарантия рабочего драйвера.

**E02 — инспекция поставки (план).** Сохранить SHA256 выданных файлов; прочитать wheel `*.dist-info/METADATA`, `WHEEL`, `Requires-Python`, `Requires-Dist`, теги бинарных зависимостей и их источники. Выяснить, какой дистрибутив даёт `tpu`, TLM и `onnx_direct`. Только затем выбирать Python. Сохранить lock и фактические версии системных библиотек; не фиксировать произвольные TF/ONNX/CUDA.

**E03 — compilation без платы (план).** В предоставленном совместимом CPU environment выполнить import, quantization эталонной модели, compilation и сохранение `.tpu` при недоступном TPU. Сохранить logs, exit codes, artifact hash, wall time и peak RAM. Отдельно проверить, что runtime bindings не требуют устройства уже на import. Это закроет главный inference этой ветки и даст бюджеты компиляции.

**E04 — runtime smoke-test (план).** На выданном LinQ host перечислить устройства, загрузить vendor `.tpu`, выполнить один inference и сравнить с эталонными входами/выходами. Сохранить model hash и используемый target. Сам импорт или наличие PCIe записи не считать подтверждением inference.

**E05 — перенос артефакта (план).** Проверить, может ли `.tpu`, скомпилированный выбранным framework, исполняться именно runtime выданного host. Релизные названия сами по себе не дают forward/backward совместимость; проверить целевой hardware parameters и build numbers.

Для исследования моделей: версии PyTorch/ONNX пока не зафиксированы платформенной веткой; число поддерживаемых семейств не заменяет compiler test. Для архитектуры: держать независимую границу compiler artifact / runtime host / client и не предполагать транспорт online доступа. Для доступности: закрытый download подтверждён только текстом сайта; guides публичны. Для второй волны: наиболее ценны визуальное чтение слайда6 и обнаружение installation/runtime reference либо реального wheel/образа из официальной выдачи.
