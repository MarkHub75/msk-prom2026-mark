# W1-07. Квантование, калибровка и сохранение качества LinQ

Дата исследования: 2026-10-23, примерно 04:20–04:30 Europe/Moscow (01:20–01:30 UTC). Главный вопрос: каким подтвержденным путем превратить обученную CV-модель в квантованную модель LinQ, как проверить сохранение качества малых СИЗ и какие параметры нельзя предполагать до получения SDK?

## Вывод для команды

Обнаружен документированный путь калибровки обученной модели без переобучения и открытый сторонний пример отдельного вызова калибровки. Это дает основание начинать с PTQ, но не основание считать любую заранее квантованную ONNX-модель совместимой с LinQ. Поддержка QAT, ONNX Q/DQ и QLinear-операторов в выданном SDK не установлена.

Ключевое практическое ограничение: проверенное чтение документов и исходников не является выполненной калибровкой, экспортом, компиляцией или запуском на устройстве. В этой ветке таких запусков не было; численной оценки потери AP/recall на СИЗ нет.

В руководстве 2025 года рекомендовано 100 калибровочных образцов; два изображения в демонстрации выбраны ради простоты. Код YOLOv8s по умолчанию берет 500. Ни одно из этих чисел не доказывает достаточности для мелких перчаток, очков, касок на удаленных людях. Нужны отдельные evaluation-данные и сравнение до/после квантизации.

Нельзя автоматически превращать внешние float32-входы в int8: внутренний формат вычислений и внешний контракт программы различаются. Для pinned YOLOv8 пример подает RGB NCHW float32 0..1, а для авторской vendor TinyYOLO3-программы заявлен RGB NHWC float32 0..1. Формат нужно фиксировать для конкретного `.tpu`.

## Факты и степень проверки

### W1-07-F01. Что подтверждено о разрядности

Тип: **vendor_statement**, источники S02, S10. Статус: страницы/извлечение прочитаны, аппаратно не проверено.

Производитель указывает int8 для вычислительного ядра и DNN Quant. В HPS datasheet fp16/bfloat16 отнесены к перспективе. Фраза о сохранении точности не сопровождается в этом разделе таблицей FP32→int8, датасетом или допустимой потерей качества. Из этих заявлений нельзя вывести разрядность каждого промежуточного тензора, accumulator, bias, конкретных входов/выходов программы или наличие mixed precision.

### W1-07-F02. Исторический API квантизации

Тип: **primary_documentation**, S03 §3.1. Статус: прочитан извлеченный документ; вызовы не выполнялись.

Документированный интерфейс: `dnn_quant.QuantizedModel.quantize(original_graph_def, input_shapes, output_nodes, calibration_dict, percentile=100.0, batch_axis=0, explicit_batch_value=None)`.

Калибровка задается словарем имен входных тензоров и ndarray. Получаются внутреннее представление, квантованные веса и граф с преобразованиями масштаба. Предусмотрены `.qm`, `as_graph(...)` и `rescale(data)`. Пример показывает выполнение исходного и квантованного TF-графов; вокруг квантованного TF-графа используются преобразования входов и выходов через `rescale`. Руководство объясняет это масштабированием и приведением типа; формула с zero-point, rounding rule и granularity не приведена.

Это **inference** о PTQ-пути: процедура принимает уже обученный frozen graph и калибровочные тензоры, не содержит optimizer/backprop/training. Само слово PTQ здесь не следует выдавать за точный vendor-термин. Прямого подтверждения QAT из описанного маршрута нет.

### W1-07-F03. Калибровочные данные в руководстве

Тип: **primary_documentation**, S03 с.15, 25. Статус: документ прочитан.

В терминах руководства калибровочный ndarray содержит N образцов обучающего набора с соответствующим предварительным преобразованием; рекомендация — 100. В примере взяты 2 изображения, объединенные по batch axis 0. Для демонстрационного ResNet50 использованы NHWC, RGB, crop/resize 224×224 и вычитание средних каналов. Это контракт демонстрационной модели, его нельзя переносить на YOLO или собственный exporter.

### W1-07-F04. API стороннего примера отличается

Тип: **source_code**, S05 L240–286. Статус: статический просмотр pinned файла; калибровка не запускалась.

Вместо единого вызова S03 код создает `RegularModel`, получает `thresholds = regular_model.calibrate(calibration_data=calibration_dict, percentile=args.percentile)` и вызывает `regular_model.quantize(thresholds)`. `.qm` сохраняется через `save(file_dir=..., file_name=...)`, а не старую сигнатуру `save(file_path)`.

Критический fallback L275–280: любой `TypeError` первого calibrate ловится и происходит повтор без `percentile`. **Inference:** успешное завершение скрипта не доказывает, что явно выбранный percentile применился. Причиной TypeError может быть и внутренний сбой; blanket fallback затрудняет диагностику. Не копировать этот прием молча в эксперимент по подбору threshold. S07 L308–312 и ResNet50 builder L340–348 используют аналогичный fallback.

### W1-07-F05. Тензоры калибровки YOLOv8s

Тип: **source_code**, S05 L19–95, L304–324; S06 L215–282. Статус: статический просмотр.

Defaults: 500 изображений, `img_size=640`, `percentile=100.0`, chunk 128. Изображения сортируются и ограничиваются первыми N. Калибровка: letterbox, BGR→RGB, NCHW float32 /255. Полный тензор `(N,3,H,W)` хранится через memmap. Runtime делает такое же внешнее преобразование и подает float32 в `run`/`sync`; явного `quantized_model.rescale` в runner нет. Выход направляется в host-side NMS.

**Inference:** это полезный образец согласованной предобработки, но не доказательство всех dtype/scale внутри программы. Chunk уменьшает рабочий объем подготовки, а не обязательно память самого calibrate: ему передается весь memmap. При 500×3×640×640×4 байт backing store равен 2 457 600 000 байт (~2.29 GiB); промежуточные активации и копии требуют дополнительной памяти. Это расчет, не измерение RSS.

### W1-07-F06. FCN использует другую нормализацию

Тип: **source_code**, S07. Статус: статический просмотр.

Defaults: все доступные calibration-изображения (`--num-calibration-images=0`), размер 520×520, chunk 64, percentile 100.0. RGB bilinear resize → /255 → ImageNet mean/std → CHW float32. Тензор `(N,3,520,520)` передается тому же раздельному API calibrate/quantize. **Inference:** модельный preprocessing нужно версионировать вместе с калибровкой; нельзя иметь универсальный «LinQ preprocess» для всех сетей.

### W1-07-F07. Разделение данных есть, стратификации нет

Тип: **source_code**, S08. Статус: только чтение.

Default calibration ratio 0.1 и seed 42. Список перемешивается, калибровочная и evaluation части разделены по image ID; COCO-аннотации фильтруются по выбранным изображениям. VOC берет исходный segmentation val split. В `split_items` не используются классы, площади объектов, камеры или сцены. **Inference:** это воспроизводимое случайное разбиение, но не гарантия покрытия редких/малых СИЗ и не защита от сходных соседних кадров одной камеры по обе стороны разделения.

### W1-07-F08. Внешний контракт зависит от артефакта

Тип: **source_code** и авторское заявление, S09. Статус: README и код просмотрены; `.tpu` не запускался.

Для `tiny_yolo3_b8_o5_128x128_asic.tpu` автор указывает `input_1:0`, `(8,416,416,3)`, NHWC, float32 0..1. Это отличается от YOLOv8s NCHW. Существование int8-ядра не является указанием подавать сырые int8-байты в Python runtime. Параметры `unit_float`/`uint8` runner — варианты внешней подготовки, их наличие само по себе не доказывает, что любой `.tpu` принимает оба диапазона.

### W1-07-F09. Что известно о качестве

Тип: **primary_documentation** для S03 §4; **source_code** для S06/S09; статус: прочитано, собственных измерений нет.

Пример руководства сохраняет top-1 класс одного изображения, но ранжирование остальных классов меняется между исходным, квантованным и TLM/TPU путями. Это проверка одного случая, не accuracy всего датасета. В репозитории есть COCOeval runner и отдельные ONNX-ветки; наличие скриптов означает доступный механизм будущего сравнения, не найденный численный результат FP32→int8. Отсутствие результатов в tracked файлах согласуется с S11, но не доказывает, что автор никогда их не получал.

### W1-07-F10. Современная презентация не закрывает численную семантику

Тип: **vendor_statement** / **reported_measurement**, S04 с.3–4; статус: извлечение прочитано.

Презентация 2026 сохраняет int8-позиционирование. В опубликованном performance-контексте названы Runtime 16.18.6 и Framework 2026.8.43, однако не опубликованы нужные нам результаты качества до/после quantization, scales/zero-point, состав calibration set и точная схема quantizer. Нет основания объявлять эти версии установленными на обещанном онлайн-сервере.

## Противоречия, которые нужно сохранить в отчете

1. **API:** руководство-2025 `QuantizedModel.quantize(... calibration_dict ...)` и `save(file_path)` против стороннего кода-2026 `RegularModel.calibrate` → `quantize(thresholds)` и `save(file_dir,file_name)`. Возможны разные версии; точная совместимость не установлена. Дата коммита не сообщает версию использованного wheel.
2. **percentile:** руководство называет параметр процентом весовых коэффициентов, ограничиваемых по величине; код передает его в calibrate. Ни одно из этих наблюдений не объясняет полностью, применяется ли percentile к весам, активациям или обоим. Не утверждать автоматически стандартный activation histogram percentile.
3. **Платформа as_graph:** в руководстве сигнатура содержит `platform='64x64_fpga'`, текст рядом говорит default `128x128_asic`. Проверять конкретную сигнатуру установленного пакета и явно задавать target, если API позволяет.
4. **Количество samples:** 2 в демонстрации, 100 в рекомендации, 500 в YOLO builder — разные цели и происхождение, а не доказанная новая обязательная норма.
5. **Окружение:** S01 Python3.8; руководство-2025 требует Python3.11, но содержит log python3.8; презентация-2026 указывает Ubuntu24.04 против Ubuntu20.04 guide. Причину этой смеси устанавливать по release/SDK, не выбирать удобную строку.
6. **rescale vs runtime:** руководство явно масштабирует для TF quantized graph, но подает исходный подготовленный тензор в hardware runtime; новый runner также подает float32. Нельзя добавлять ручной scale к runtime «на всякий случай»: можно получить двойное преобразование. Нужно прочесть metadata/SDK и сравнить фактический выход.

Предпосылка: доступен SDK. Сохранить версии wheel/runtime, target, Python/OS, `inspect.signature` доступных quant API, help/docstrings; не устанавливать случайный одноименный `dnn_quant` из публичного pip. Проверить на маленьком известном примере calibrate, quantize, save/load `.qm`, построение quant graph. Сохранить ошибки и эффективные параметры, не скрывая TypeError fallback. Успех доказывает работоспособность конкретного маршрута, еще не качество детектора СИЗ и не hardware execution.

### E07-2. Разделить импорт, квантизацию и исполнение

Одинаковые входные изображения и preprocessing: исходный PyTorch → float ONNX Runtime → преобразованный float TF (если доступен) → quant graph с документированным rescale → TPU. Сохранять raw outputs, имена, shape/dtype/range, checksum модели и изображений. Сначала raw output diff на совпадающих выходах, затем одинаковый decode/NMS. Это позволяет локализовать потерю на конкретной границе. Совпадение one-image top-1 или нескольких bbox не доказывает датасетное качество.

### E07-3. Проверить сохранение малых СИЗ

До SDK подготовить неизменяемый evaluation split, разделенный по камерам/сценам/времени, и независимый calibration manifest. В калибровку включить характерные реальные яркость, масштаб людей, плотность, частичные перекрытия и присутствие/отсутствие каждого СИЗ. Начать со 100 репрезентативных кадров как документированного ориентира, затем сравнить с 500 при приемлемом времени и памяти. Это инженерный дизайн опыта, не vendor-требование и не обещание достаточности.

Для каждого варианта измерить AP50/AP50:95 и recall отдельно по классам и размеру объектов; отдельно recall малого СИЗ и частоту ложных пропусков нарушений. Держать фиксированными score/NMS thresholds, resize, evaluation manifest и ground truth. Если доступно, сначала менять только calibration set/size; percentile изменять лишь после подтверждения его семантики. Порог допустимой потери задается целевыми критериями кейса, пока они неизвестны.

### E07-4. Отличить численную проблему от неверного контракта

До изменения quantizer проверить RGB/BGR, letterbox и обратные координаты, NCHW/NHWC, /255, mean/std, dtype, batch padding, выбранную голову, class mapping и runtime input range. Для одной программы сравнить запись/чтение `.qm` и неизменность effective parameters. QAT рассматривать только при подтвержденной поддержке и измеренной проблеме PTQ; стороннее ONNX quantization не является заменой этой проверки.

## Короткий handoff

- Для главного отчета: int8 заявлен официально; механика scales/zero-point, granularity и QAT пока неизвестны. Доступен конкретный PTQ-путь, но аппаратно нами не испытан.
- W1-06: новый quant API и молчаливый fallback percentile важны для воспроизводимости; полный compiler-анализ остается у соседней ветки.
- Runtime/preprocessing веткам: float32 0..1 с разными layout является контрактом конкретных примеров; ручной int8 cast или `rescale` для любой TPU-программы не обоснован.
- Качество: нет доказанной потери/сохранения AP малых СИЗ; README и runner не заменяют accuracy report. Требуется staged comparison на отдельном evaluation наборе.
