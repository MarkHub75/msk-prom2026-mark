## Решение и изменение относительно W1

**PTQ остаётся разумным первым кандидатом, но sweep percentile пока нельзя считать корректно определённым экспериментом.** Нового открытого описания `RegularModel.calibrate`, threshold schema или текущего численного контракта не найдено. Официальный актуально открытый `/docs` по-прежнему ссылается на руководство редакции 2025 `RU.РМДВ.04.06.014-03 34 01`. Дата доступа не делает содержащийся там API современным SDK. Свежий GitHub API подтверждает тот же HEAD стороннего репозитория, что был прочитан W1.

Что добавлено W2: (1) build summary не позволяет установить даже requested percentile и факт retry; (2) конкретный исторический scale/shift helper найден и ограничен старым FPGA-артефактом; (3) разделены RAW-формат `.tpu`, RAW mode и byte reinterpretation; (4) сформулирован факторный опыт против weights-only/activations/ignored и save/load drift; (5) предложен один протокол качества с явно принадлежащими стадиям потерями. Не изменилось: неизвестны signedness, zero-point, rounding/saturation, granularity и текущий QAT/QDQ support; нет измеренного AP/recall на LinQ.

## Факты и численная evidence matrix

**W2-F-F01 — data-dependent quantization установлена документально, scope percentile нет.** Тип primary_documentation, S02. Описание квантования отделяет чтение графа/весов от определения порога по calibration tensor; затем создаются SoftwareNetwork с quantization/rescale и квантованными весами, HardwareNetwork как TF-модель операций TPU. Одновременно описание аргумента percentile относится к весовым коэффициентам. Это не логическое доказательство ошибки текста: процедура в целом может быть data-dependent, а один параметр weights-only. Нельзя заменить это привычной интерпретацией percentile histogram activations. Точная формула, выбор абсолютных значений/знаков, denominator и смысл 100.0 неизвестны.

**W2-F-F02 — современный пример не сохраняет доказательство effective percentile.** Тип source_code + inference, S03/S04. В L275–278 любой TypeError от вызова с `percentile=args.percentile` приводит к повтору без параметра. Это ловит как unsupported keyword, так и TypeError внутри принятого вызова; первый проход мог уже менять состояние объекта. L304–326 summary сохраняет sample count, preprocess, shapes, `.qm` и compiled paths, но не requested/effective percentile, threshold dump, exception/retry flag или quantizer version. Наличие `.qm`/summary и успех всего builder не позволяют отличить применённый аргумент от default retry. Текущий HEAD не исправляет это. Нужны fail-closed вызов без blanket retry и запись фактического пути.

**W2-F-F03 — thresholds передаются отдельно, но публичной serialization schema нет.** Тип source_code/unknown, S03. `thresholds = regular_model.calibrate(...)` → `regular_model.quantize(thresholds)` → `quantized_model.save(file_dir=..., file_name=...)`. Пример не показывает dtype, shape, naming, содержимое thresholds, собственный save/load thresholds или повторную quantization после перезапуска. `.qm` в S02 содержит топологию и числовые данные для compiler, но это не обещание экспорта исходных calibration statistics или portability thresholds между версиями/графами. Старый guide `save(file_path)` и новый sample `save(file_dir,file_name)` нельзя механически смешивать. Схема `.qm`, version policy и effective parameter dump текущего SDK unknown.

**W2-F-F04 — существует точная историческая формула выходного helper, её область узкая.** Тип source_code, S06. `get_output_scale` читает `fpga_data.pickle`, фиксированный ключ `output_node_1`, берёт `pos_scale`, `pos_shift`, возвращает `scale * 2. ** shift`; `dequantize` возвращает `data * scale`. Docstrings называют int16 scale/int8 shift и float16 result, но код не проверяет фактический dtype, не округляет/клиппирует и не устанавливает granularity. У нас нет pickle, поэтому shape значений неизвестен. Это не общая формула нынешнего LinQ `.tpu`, не доказательство symmetric quantizer и не предписание добавить умножение к FULL output. Применение такого helper к уже user-format выходу способно повторить преобразование.

**W2-F-F05 — RAW file kind и ProcessingMode являются разными осями.** Тип source_code, S05. `_is_raw_program` открывает ZIP `metadata.json`; `_is_raw_metadata` эвристически считает отсутствующий `user_dtype` признаком raw и комментирует address/size-only metadata. Независимо `ProcessingMode` задаёт RAW=0, PRE_PROCESS=1, POST_PROCESS=2, FULL=3, а `_run` передаёт число native `tpu_run_inference`. `_program._is_raw` управляет размерами и reshape возврата; mode не переписывает этот флаг. Поэтому одно `mode=RAW` само не доказывает, что Python output будет int8 тензором правильной формы или что текущий nonraw артефакт допускает безопасную такую подачу. Сначала нужен native contract конкретного release.

**W2-F-F06 — Python output conversion не является численным dequantization.** Тип source_code/inference, S05. `_load_inference` передаёт адрес ndarray как `POINTER(c_uint8)`; это представление буфера, не `astype(uint8)` данных. Для nonraw `_get_inference` делает byte view в metadata `user_dtype` и reshape в `user_shape`; для raw — reshape по `ddr_word_len`. В Python-функции `view` нет scale multiplication, transpose или preprocessing. Где native/compiled artifact выполняет эти операции, этот слой не раскрывает. Из `POINTER(c_uint8)` нельзя выводить внешний uint8 contract. FULL — запрос режима к native API, не доказательство размещения всех операций на TPU.

**W2-F-F07 — float reference, quantized TF и runtime имеют разные документированные boundary adapters.** Тип primary_documentation/source_code, S02/S03/S05. Для TF quantized graph S02 использует `rescale` на входе и выходе; TLM получает исходные подготовленные данные с переименованием tensor→op, hardware example также использует исходную подготовку. Новый сторонний runner подаёт float32. Это согласуется с user/raw boundary processing, но не раскрывает современную численную формулу. Ошибку parity сначала локализовать на I/O: применять `rescale` к TF quantized graph там, где это требует конкретный API; не переносить его автоматически на FULL runtime. Формула native transform, host/device location и RAW↔FULL golden pairs unknown.

**W2-F-F08 — TLM полезен как отдельный численный checkpoint, не гарантированно доступен.** Тип primary_documentation/unknown, S02. Guide описывает HardwareNetwork и TLM execution, печатает estimated execution time, сравнивает вероятный класс. Это не текущая спецификация bit-exactness, не layerwise compare API и не валидация accuracy малых СИЗ. Актуальные export intermediate tensors, compare tool, численные допуски и TLM availability не найдены. Если текущего TLM нет, нельзя блокировать весь проект ожиданием этой стадии; пропуск фиксируется как невозможность разделить compiler/runtime error на два участка.

**W2-F-F09 — historical float16 flag не устанавливает QAT или mixed precision H1M.** Тип source_code/unknown, S07. MobileNet quantize script использует `quantize_graph ... --float16_capacity_control=true`. Это конкретная первичная зацепка об управляющем параметре старого FPGA toolchain; без help/source quantizer его функция не раскрыта. Он не является доказательством float16 arithmetic современного LinQ, current activation clipping или пути QAT/QDQ. Нового первичного QAT/QDQ примера/контракта не найдено, поэтому обширный поиск общих ONNX quantization tutorials не предпринимался.

## Различающие эксперименты после доступа

Это проект опытов, не выполненные SDK tests. Владельцы указаны как роли для общего K020 handoff; сборщик назначает имена один раз. Не нужны несколько конкурирующих model manifests.

### E-F1. Доказать или отвергнуть effective percentile и область действия (нужен SDK; владелец quantization)

Предпосылки: exact SDK wheel/native version+hash, target, совместимый минимальный float graph с доступными weights, подтверждённый preprocess; актуальные help/source/signature `RegularModel.calibrate`, quantize, .qm save/load. `inspect.signature` сам по себе недостаточен при `**kwargs`/native extension. Не запускать старый blanket fallback. Любое исключение сохранять полностью и считать конкретный вариант failed, без автоматического повторного вызова на том же potentially mutated объекте.

Дизайн 2×2×2, отдельный свежий объект на каждую ячейку: W0/W1 (фиксированные веса vs контролируемый редкий большой weight), C0/C1 (фиксированные calibration данные vs контролируемый редкий activation/input outlier), P0/P1 (два различающихся документированно допустимых percentile). Менять один фактор за раз и сохранять графы, входы, threshold object schema/values, отдельно quantized weight arrays и activation/input/output scale metadata там, где SDK их действительно предоставляет. Добавить default P и повтор одинаковой ячейки для оценки nondeterminism. Подобрать outlier так, чтобы два разрешённых percentile действительно различались в задуманном распределении; не предполагать заранее, что 99.9 против100 различит короткий тензор.

Ожидаемые различия: изменение P, локализованное в weight thresholds/weights при обоих C, поддерживает weights-only для испытанного графа; изменение activation thresholds при фиксированных W поддерживает activation scope; изменение обоих допускает joint scope. Различие calibration datasets при фиксированном P проверяет data-dependence независимо от percentile. Если все dumps/outputs равны, это **не доказательство игнорирования**: clipping мог не активироваться, optimizer убрать outlier, сеть быть нечувствительной или dump неполным. Тогда нужен проверенный surviving sensitive layer + документированный invalid parameter test/help/source. Unsupported keyword → percentile experiment unavailable для этого API, а не «P по умолчанию победил». Нужны effective-settings log или vendor clarification.

Артефакты: `QUANTIZER_MANIFEST.json`, `FACTORIAL_RUNS.jsonl`, `THRESHOLD_SCHEMA.json`, supported threshold/value dump, raw reference outputs, exact errors. Точные имена сериализации брать из установленного API; здесь не выдумываются вызовы. Успех не доказывает качество детектора, арифметику всего графа или current QAT support.

### E-F2. Отделить сохранение модели от повторной калибровки (нужен SDK; владелец quantization)

На одном завершённом E-F1 варианте: quantize → inference → save .qm → новый процесс → documented load → inference тех же golden tensors, без calibrate. Сравнить semantically normalized metadata/thresholds/quantized weights и raw outputs; byte hash файла может меняться из-за timestamps/order и сам по себе не является численным критерием. Если SDK умеет отдельно сохранять thresholds, независимо повторить их save/load и quantize того же float graph. Если такого API нет, отметить threshold reproducibility как непроверенную, не использовать произвольный pickle как обещанную portability. Зафиксировать graph hash: thresholds от другого graph/anchors/оптимизации нельзя переносить без контракта.

Успех .qm round-trip доказывает лишь сохранение результатов данного quantization в данной версии, а не экспорт первоначальных calibration statistics и не переносимость между SDK/targets.

### E-F3. Локализовать float/user/raw границу без двойного scale (SDK + LinQ; runtime owner совместно с quantization)

Одна модель и один shared golden input spec: canonical decoded image hash; готовый float tensor `.npy` с tensor name, shape, dtype, layout, min/max и checksum; exact float outputs до decoder. Получить metadata конкретной `.tpu`, user/raw sizes/dtypes/shapes и native definition FULL/RAW. Только при документированном adapter получить один корректный raw tensor и сопоставить `FULL(user_input)` с `POST(native RAW(raw_input))` либо доступным эквивалентом поставки. Не подавать искусственно cast int8 в unknown raw packing и не считать output byte view dequantization.

Параллельно quantized TF/reference с его собственным document-required rescale; optional TLM с тем же user input. Сохранить outputs до и после boundary adapter, max/mean abs error и расположение расхождений, saturation counts лишь при известном диапазоне. Без допуска поставщика не требовать FP32 bitwise equality. Round-trip input adapter может терять информацию из-за квантования, поэтому его неточное обращение само не является дефектом. Если FULL совпадает с reference, а дополнительный ручной rescale нарушает совпадение, это evidence против добавочного преобразования для данной программы; не универсальный контракт всех .tpu.

Успех не доказывает, что pre/post работают на TPU: размещение подтверждает native documentation/profiler/compiler execution evidence другой ветки. TLM skip допустим с явным объединением неопределённости compiler+runtime.

## Единый staged evaluation для малых СИЗ (K020)

### Общая спецификация и разделение данных

Data/evaluation owner ведёт **один** manifest с image hash, camera ID, source clip, timestamp/time block, scene/light conditions, split, annotations и классами. Calibration, tuning validation и финальный holdout разделять по камерам и/или цельным непересекающимся time/clip blocks, исключая соседние кадры и повторные изображения между split. Для фиксированной камеры оценивать также отдельный поздний временной блок; для переноса между камерами — held-out камеры. Нельзя обещать одновременно camera-held-out при единственной камере: фактическую доступность фиксировать. Не отбирать только яркие кадры с крупными людьми. В calibration покрыть малые/дальние предметы, перекрытия, контраст, пустые сцены, наличие и отсутствие relevant СИЗ; эти страты должны реально присутствовать в данных, а не быть выдуманными классами кейса.

Числа100/500 — кандидаты budget experiments, не норма достаточности. Для сравнения размеров использовать вложенные subsets с сохранением покрытия и hash списков. Отдельный validation для выбора calibration/percentile/score threshold; final holdout после выбора. Если данных мало и есть только calibration+eval, любые итерации по eval считать tuning и получить новый независимый holdout перед заявлением качества. Достаточность оценивать по стабильности критических метрик/стратифицированному покрытию при добавлении данных и доступному budget, без обещания универсального sample count.

Один `MODEL_MANIFEST` у export/compile owner: weights/export graph hashes, exporter/options/opset, names/layout/static shape, preprocess, class mapping, output/decoder definition, quantizer settings+threshold artifact, compile target/preset, `.qm`/`.tpu` hashes. В роли quantization owner записывается только соответствующая часть; новые конкурирующие manifests не создавать.

### Последовательность и права вывода

| Stage / владелец | Что сравнивать и gate | Состояние сейчас; результат и ограничение |
|---|---|---|
| A. Float/export / model owner | Исходная float модель → exported ONNX → imported float graph, где доступен. Одни input tensors и raw heads, затем один decoder/NMS | Exported reference доступен без LinQ; importer может требовать SDK. Если raw/head semantics не совпадают, исправлять экспорт, не percentile. Успех не подтверждает PTQ. |
| B. PTQ/reference / quantization owner | Imported float → quantized reference с правильным boundary rescale; E-F1/F2 до sweep | Нужен SDK. Изолирует PTQ loss только при сравнимом imported float. Если imported float недоступен, разность ONNX→quant reference включает import+PTQ и так называется. |
| C. Compile / compile owner | Quant reference → optional TLM, exact compile output | Нужен SDK/TLM. Если TLM отсутствует, фиксировать skip, переходить к device с общей неопределённостью. Не делать обязательным недоступный инструмент. |
| D. Runtime / runtime owner | Reference/TLM → LinQ FULL с проверенным user I/O, E-F3 | Нужен LinQ. Расхождение только здесь требует boundary/compiler/runtime диагностики до смены calibration. Успех parity не доказывает full graph TPU coverage. |
| E. Quality / evaluation owner | Для принятых A–D те же labels, decoder/NMS, frozen thresholds и eval IDs | Можно подготовить сейчас, аппаратные outputs позже. Raw parity и итоговые accuracy — разные gates. |

Для каждого stage сохранять исходы PASS / FAIL / UNAVAILABLE / NOT_RUN, actual elapsed wall time, exit/error, stage artifacts и входную spec. Нет жёсткой выдуманной длительности компиляции. Изменение исходного float graph означает новый artifact lineage и повтор только зависимых gates. Known-good vendor sample полезен для isolating environment, но не обязательная единственная точка старта: выданный compiler+custom minimal example с reference/golden outputs способен дать проверяемый первый маршрут. Без reference успешная compilation — лишь syntax/support milestone.

### Метрики, memory/time и решение

Фиксировать AP50, AP50:95 и recall по классам; отдельно размерную страту мелких СИЗ с **явным определением размеров**. COCO AP_small и маленький объект после resize — не тождественные понятия: дополнительно указать bbox width/height в source и network pixels. Сохранить support counts и случаи miss по каждому классу/страте/камере; если наблюдений мало, вывод нестабилен, нулевые ошибки не доказывают достаточность. Для нарушения «отсутствие СИЗ» нужны person↔PPE association/правила и отдельная violation-level false negative/false positive оценка с владельцем rules; object recall не равен качеству определения нарушения.

Общие preprocessing, decoding, score/NMS и labels зафиксировать для оценки численной потери. Обязательно проверить NMS **внутри самого ONNX**, output stage и anchor mask/order: одинаковые CLI flags не обеспечивают одинаковый cutoff или decoder, когда один граф уже обрезал кандидаты. Если raw heads недоступны, фиксировать стадию after-NMS и сравнивать с тем же встроенным NMS на другом пути; потерю кандидатов от embedded score cutoff не называть PTQ loss. Это особенно важно для мелких СИЗ с низким confidence. Если позже меняются score thresholds, сообщать отдельно: это tuning меняет рабочую точку, а не восстанавливает прежние raw outputs. Допуски AP/recall/нарушений согласовать по полному заданию; сейчас численный «приемлемый loss» не установлен. Не выбирать победителя только по overall mAP, скрывающему респиратор/очки на дальнем человеке.

Связанный handoff от root/W2-E получен 01:59 UTC: сообщено об embedded NMS и anchor mask discrepancy в конкретном tiny-yolov3-11. Его численные literals в этой ветке самостоятельно не проверены; подробное primary evidence принадлежит W2-E. Здесь он учтён как требование проверки artifact-level NMS/decoder, а не как новый W2-F установленный факт.

Регистрировать calibration wall time, max RSS **включая subprocess tree** выбранным средством ОС, peak accelerator/GPU memory если действительно используется, memmap size/disk free, sample count, shape/dtype, preprocessing time и quantization time раздельно. При500×3×640×640×4 backing file =2,457,600,000 bytes≈2.29GiB, при100≈0.458GiB; это расчёт backing storage, не peak RAM. Memmap не гарантирует streaming calibrate: SDK может копировать целый tensor и хранить intermediate activations. Сохранять resource log с timestamps, OOM/error и частичным результатом; не приписывать quantizer wall time подготовке изображений.

Decision tree: A failed → исправить model mapping; A passed/B failed → подтверждённая PTQ loss, после E-F1 менять calibration composition/size или документированный parameter по одному; B passed/D failed → сначала user/raw/layout/compile/runtime; A–D passed/E bad → исходная модель/data/rules или недостаточная task quality. Если E-F1 не установил scope/effective percentile, остановить percentile sweep, сохранить baseline default и продолжить независимые стадии. QAT начинать только при фактическом SDK path и measured PTQ bottleneck; generic QDQ export не является подтверждённым обходом. Срок переключения пути задаёт общий 45-hour budget команды и фактические логи, не выдуманное vendor compile время.

## Точный остаток unknown и handoff root

K008 локализован, не закрыт численной спецификацией: нужен current quantizer reference/source или SDK introspection + E-F1/F2; вопросы поставщику — scope percentile, supported range, effective settings, threshold object/schema/serialization, rounding/saturation/granularity, current QAT/QDQ import. Первый SDK шаг — сохранить package versions/help и выполнить fail-closed калибровку, не копировать retry.

K009 локализован: W2-F даёт различие форматов/режимов и старую helper formula; native FULL/RAW processing/placement текущего release остаётся владельцу runtime W2-G/J. Нужны `.tpu` metadata и user/raw golden pair. Не выдавать pointer uint8 или dtype view за quantization.

K020: готов staged протокол с одним shared input spec, model manifest, отдельными владельцами A–E, допустимым TLM skip и конкретными fail/unknown outcomes. Сейчас можно готовить data split, manifests, float reference и evaluation harness; численная calibration/reference требует SDK; FULL↔RAW/parity и аппаратные outputs требуют LinQ; business loss tolerance/mandatory classes требуют полного задания.

Новых SDK/compile/device результатов нет. Существенное W2 отличие для сборщика: **saved summary не доказывает percentile вообще; file RAW и mode RAW не синонимы; historical scale/shift helper не применять к FULL без контракта.**
