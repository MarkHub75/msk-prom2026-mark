# Исполняемый файловый MVP с LinQ

Используется существующий worker `ml.pipeline.cli`, детекторы/декодеры, BehaviorEngine, EventMutation v1 и SQLite outbox. Для файлового LinQ-режима добавлены устойчивый курсор и factory `ml.linq.video:create_runner`. Обучение, пересборка TPU и GPU fallback не выполняются.

## Запуск

Рабочее окружение: `/workspace/.venvs/linq-client/bin/python`; `PYTHONPATH=/workspace/linq-client:/workspace/project`. Официальный формат 0.0.1 уже предоставлен отдельно и проверяется по source manifest. В изолированное окружение добавлены OpenCV 4.10.0.84 и jsonschema 4.26.0; основной PyTorch не менялся. Зависимости CLI описаны extra `linq-video` в pyproject.toml; точную библиотеку LinQ нельзя подменять похожим пакетом.

Для реального файла:

```bash
bash /workspace/project/scripts/linq_video_mvp.sh \
  --source /path/to/industrial.mp4 \
  --state-dir /workspace/artifacts/video-mvp/camera-01 \
  --sample-fps 2 --local-test-sink
```

Для диагностического порога confidence 0.25 явно добавить `--demo-policy`; стандартный порог поведения 0.5 не изменён. Ключевые точки требуют 0.5, строгая привязка головы к человеку сохраняется. Изменение политики не означает подтверждённую точность. Можно задать окно `--start-ms`/`--end-ms` в исходных миллисекундах; `--max-frames` ограничивает текущую порцию и позволяет продолжить её той же командой.

Выполненная контрольная команда:

```bash
bash /workspace/project/scripts/linq_video_mvp.sh \
  --source /workspace/artifacts/integration/reference.avi \
  --source-kind repeated-image-fixture \
  --camera-id CONTROL-FIXTURE-NOT-INDUSTRIAL \
  --state-dir /workspace/artifacts/video-mvp/repeated-image-control-001 \
  --sample-fps 2 --end-ms 3200 --demo-policy --local-test-sink
```

Это существующий ролик из повторённой публичной фотографии, НЕ реальное промышленное видео. Нейросетевые вычисления при этом действительно выполнялись на LinQ; source_kind помечает искусственную временную последовательность в событиях и отчётах. Ту же команду повторно проверили после завершения: 0 новых запросов, 12 журналов до/после, неизменный events.jsonl, одно оповещение.

## Артефакты и восстановление

- `video-session.json`: SHA256 исходного файла, source FPS, окно, политика, манифесты и устойчивый stream_epoch.
- `requests/<UUID>/`: durable intent, numeric inputs/outputs и состояние AMQP. Секреты и URI не записываются.
- `rpc/<model_id>/<logical-hash>/`: связь логического кадра с тем же транспортным UUID, в том числе после сбоя.
- `events.sqlite`: наблюдения, курсор видео, checkpoint поведения и outbox в одной транзакции.
- `observations.jsonl`, `events.jsonl`: выгрузка committed строк без накопления дубликатов при повторе.
- `evidence/*.jpg` и JSON рядом: снимок, исходные frame_id/PTS, SHA256 источника/RGB/JPEG. Проверяется повторным чтением того же исходного кадра.
- `summary.json`, `integration-review.json`, `resume-review.json`: фактические задержки, функциональная проверка и повтор без новых задач. Время cache/recovery отделено от исходного инференса.
- `worker.stdout.jsonl`/`worker.stderr.log`: накопительные диагностические логи запусков; канонические события берутся из `events.jsonl`/SQLite.

Один файловый worker удерживает общий локальный lock; две модели исполняются последовательно. UNKNOWN другого модуля блокирует свежую отправку. При обрыве до ответа worker сохраняет pending-frame и выходит с кодом3, не двигая курсор. После восстановления VPN/моста повторить ту же команду: старый UUID только получает ответ, не публикуется повторно. NOT_SUBMITTED позволяет новую попытку с новым UUID и сохранённой историей. Контрактная ошибка сохраняет курсор и требует исправления; terminal service failure становится gap и не повторяет нейросетевую задачу.

Ошибки/пропуски наблюдений прерывают накопление подтверждения. Потеря наблюдений и EOF означают interrupted, не соблюдение правил. Политика max_gap_ms 750 сохраняется; запрос sample_fps 1 обычно недостаточен для подтверждения временных правил, даже при успешных кадрах. Offline PTS отличается от wall time ожидания LinQ.

Автоматический тайм-аут не отменяет удалённую задачу. Блокирующие Pika RPC/close могут превысить polling deadline до обнаружения потери heartbeat. Настройки VPN/NetworkManager/SSH с Vast не меняются. Recovery проверено отказными/перезапускными тестами; живой разрыв VPN специально не провоцировался.

## Команда backend/frontend

См. `docs/BACKEND_HANDOFF.md`: существующая schema, синтетический пример, времена, evidence, идемпотентный POST/COMMIT/ACK, настройка URL. Марку потребуется реальный endpoint и доступное хранилище evidence. Локальный EventSink подтверждает только тестовый HTTP-контракт; backend/frontend команды не объявляются подключёнными.

Использовать отдельный state-dir для настоящего backend. Уже ACK-нутые тестовым приёмником строки не переотправляются автоматически другому endpoint. Тестовый сервер обслуживает только 127.0.0.1 на время команды; после завершения его media URL не являются постоянным хостингом.

Следующий этап требует решения команды: положительный промышленный видеокейс/разметка и проверка применимости текущих моделей, затем реальный backend/evidence и проверка падения/лежания на подходящем видео. Никакое обучение или новая архитектура автоматически не запускаются.
