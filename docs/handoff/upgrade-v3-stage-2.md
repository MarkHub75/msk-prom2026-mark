## 2. Обязательные баги

### 2.1 Повторные тревоги на каждом круге

- **Воспроизведение.** Этап 1: за 180 с в одной WS-сессии 31 красное и 31 notification по камерам 9/10/11, то есть одинаковые эпизоды на новых циклах. На стенде до работы эфиры 9, 10, 12 имели `loop=true` (cycle 14, 17, 99).
- **Причина.** `broadcast.loop_default: true` в `config/default.yaml`. Им пользуются автостарт после импорта пакета (`services._autostart`) и `broadcast_start` без `loop`. Кроме того, во вкладке «Эфир» камеры (`BroadcastTab.tsx`) галочка «Повторять по кругу» стояла по умолчанию (`broadcast?.loop ?? true`). Сервер внутри одного показа уже идемпотентен: ключ `b<broadcast>:c<cycle>:e<episode>` хранится в БД, эскалация обновляет ту же строку, очередь доставок — `INSERT OR IGNORE` по `(event_id, kind)`.
- **Исправление.** `loop_default: false`, галочка по умолчанию снята. Явный `loop: true` остаётся рабочим opt-in (`test_loop_cycle_republishes` не менялся). Ручной перезапуск — новый broadcast, то есть новый показ с новыми событиями. Пользовательский `config/user.yaml` ключ `broadcast` не задаёт (проверено), override нет. «Проиграть один раз» в демо-пульте и раньше слал `loop: false`.
- **Проверка.** `tests/test_one_alarm.py`:
  - `test_default_show_alarms_once` (синтетика, `fake_clock`). Две камеры: жёлтое→красное и независимое красное, запуск без `loop`, 70 с всех фоновых циклов (эфир, эскалация, доставки), webhook — `respx`, звонок — заглушка. Ровно 2 события с `cycle=0`; у жёлтого→красного тот же id и `red_at` = момент эскалации. На событие ровно один takeover, одна сирена, одна передача мастеру, по одному `(event, channel, kind)`, два звонка `to_master`. После сброса процессных кэшей ещё 30 с — 0 записей и 0 уведомлений. Ручной новый показ даёт новое событие нового broadcast; старое событие и его журнал не меняются; один takeover только у нового.
  - `test_real_pack_one_alarm_per_episode` — настоящий кэш `argus-real-v2`, копия во `tmp`. Импорт → 4 задания из кэша (`start` в LinQ не вызывался) → автостарт с `loop=False` на всех 4 камерах. Событий ровно столько, сколько эпизодов у камеры; у фоновой 2.3 их 0. Оператор подтверждает 1.5, мастер принимает и решает, журнал показывает `resolved`. Остальные эскалируются по таймауту по одному разу. Ещё три длины роликов — новых событий нет, дублей takeover, сирены, передачи мастеру и доставок нет. Тест пропускается, если пакет не распакован (CI).
  - Мутация: при `loop_default: true` оба теста падают.
  - `tests/test_broadcast.py::test_start_stop_conflicts_and_messages` обновлён: дефолт `False`, явный `loop_default: True` даёт `True`.
- **Осталось.** Уже сохранённые на стенде broadcast с `loop=true` остановлены (этап 1); новые запуски идут однократно. Живой подсчёт тревог в минуту на обновлённом контейнере — раздел 5.

### 2.2 Мерцание и действия с первого нажатия

- **Исправление.** На время повторной загрузки того же события показывается прежняя карточка (`useApi` и так хранит данные того же запроса). Карточка другого id и ошибка по-прежнему не показываются. Дополнительно в `AppShell`: повтор уведомления с тем же `id` (повторная доставка) не включает сирену и навигацию снова. Очередь новых красных из PR #36 сохранена.
