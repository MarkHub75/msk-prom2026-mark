# Подключение ML-worker к backend Марка

Используется существующий EventMutation v1: `ml/contracts/schemas/event.schema.json`. Новый несовместимый формат не вводится. Пример `docs/examples/event.synthetic.json` явно синтетический: он показывает контракт и не подтверждает нарушение или запуск модели. Реальные события конкретного прогона сохраняются вне Git в `<state-dir>/events.jsonl`, наблюдения — в `observations.jsonl`.

## Получение и подтверждение

ML отправляет `POST /api/v1/ml/events`, полный URL задаётся параметром `--backend-url`. Тело — одно событие, `Content-Type: application/json`, заголовок `Idempotency-Key: <event_id>:<revision>`. При необходимости токен берётся только из `MOSPROM_BACKEND_TOKEN`. Для удалённого подключения с токеном нужен HTTPS; HTTP redirects запрещены. Секреты не передаются в аргументах команды или событиях.

Backend должен в одной транзакции сохранить неизменяемую пару `(event_id, revision)`, обновить состояние инцидента и создать оповещение только при первом открытии этого `event_id`. Повтор той же пары с тем же телом возвращает прежний ACK. Другое тело для той же пары — ошибка. Поздние старые ревизии не должны откатывать более новое состояние. Следующие ревизии обновляют журнал; это не новые оповещения.

После COMMIT вернуть HTTP 200 и:

```json
{"committed": true, "event_id": "exact-event-id", "revision": 1}
```

Просто HTTP 200 недостаточно. Worker хранит SQLite outbox с повторной доставкой и ограниченным backoff. Если ACK потерян после COMMIT, он повторит ту же пару. Закрытие/прерывание эпизода также доставляется отдельной ревизией того же события. Отсутствие наблюдений не считается соблюдением правил.

## Поля и время

| Поле | Значение |
|---|---|
| `event_id`, `revision` | UUID эпизода и версия его состояния |
| `camera_id`, `stream_epoch` | Камера и устойчивый идентификатор данного запуска/источника; сохраняются при продолжении файла |
| `track_key` | Локальный трек, не личность человека и не идентификатор между камерами |
| `type` | `missing_helmet`, `suspected_fall`, `prolonged_lying` |
| `state` | `open`, `closed`, `interrupted`; interrupted означает потерю наблюдений, а не устранение нарушения |
| `start_media_ms` | Начало наблюдаемого эпизода по исходной шкале видео |
| `confirmed_media_ms` | PTS кадра, на котором правило подтвердилось |
| `end_media_ms` | Для последующей ревизии — окончание или граница наблюдения |
| `emitted_at` | UTC создания ревизии. Это отдельные часы, не время съёмки |
| `rule_version` | Применённая политика. `DEMO-confidence025` — диагностический порог, не подтверждённая точность |
| `model_ids`, `execution_backend` | Использованные модели и `linq`; CPU/GPU fallback отсутствует |
| `execution_records` | Корреляция логического кадра и модели, SHA256 программы, UUID/статус ответа TPU-сервиса |
| `evidence.frame_id`, `evidence.media_time_ms` | Номер исходного кадра и его PTS; остаются прежними при закрытии события |

Все значения `*_media_ms` — миллисекунды от начала исходного файла, даже если выбрано окно с ненулевого времени. Это не Unix timestamp. Исходный FPS сохраняется в наблюдениях и `video-session.json`; частота выборки задаётся отдельно. Время ожидания LinQ не добавляется к длительности эпизода в видео. При слишком редких наблюдениях правила воздерживаются от подтверждения падения/лежания.

## Кадр-доказательство

Worker атомарно сохраняет `<state-dir>/evidence/<uuid>.jpg` до фиксации события. Рядом находится JSON с исходными frame_id, PTS, SHA256 источника, RGB исходного кадра и JPEG. На JPEG нанесены детекции; координаты исходных наблюдений — xyxy в пикселях оригинального кадра. Ключевые точки — COCO-17 `[x,y,confidence]`.

Марк должен организовать доступ backend к этой папке: общий каталог либо отдельное хранилище с HTTPS. Параметр `--evidence-base-url` задаёт уже работающий URL-префикс, соответствующий `<state-dir>`. При доставке относительный `evidence/<uuid>.jpg` преобразуется в `<prefix>/evidence/<uuid>.jpg`. Публиковать нужно только `evidence/`, не SQLite, RPC-журналы или конфигурацию. Multipart-загрузка и авторизация отдельного media-сервиса этим MVP не реализованы. Пока префикс не настроен, готовые snapshots не считаются доступными backend, доставка остаётся pending.

Frontend получает события и media URL через backend, показывает одно оповещение на инцидент, затем обновляет состояние по ревизии. Подтверждение оператором хранится отдельно от `state` ML-эпизода. Для поиска: камера, тип, состояние, зона, UTC отправки и интервал видео. При просмотре evidence использовать его PTS, а не `emitted_at`.

`source_kind=repeated-image-fixture` явно обозначает искусственную временную последовательность. Даже при `execution_backend=linq` такие события нельзя показывать как подтверждённые промышленные нарушения. Их правило и источник — контроль интеграции.

## Команда подключения

```bash
bash /workspace/project/scripts/linq_video_mvp.sh \
  --source /path/to/industrial.mp4 \
  --state-dir /workspace/artifacts/video-mvp/camera-01 \
  --sample-fps 2 \
  --backend-url https://BACKEND/api/v1/ml/events \
  --evidence-base-url https://MEDIA/ml-artifacts
```

Заменить URL на фактические адреса команды. Для диагностического прогона явно добавить `--demo-policy`; штатный min_score остаётся 0.5. Для повторной доставки без новых TPU-задач:

```bash
python -m ml.pipeline.cli --state-dir /workspace/artifacts/video-mvp/camera-01 \
  --backend-url https://BACKEND/api/v1/ml/events \
  --evidence-base-url https://MEDIA/ml-artifacts dispatch
```

Состояние RPC и видео хранится вне Git. Повтор основной команды с тем же источником и настройками продолжает обработку с прежним stream_epoch и UUID запросов. При UNKNOWN worker останавливается с кодом 3; после восстановления связи повторить ту же команду. Она получает ответ прежнего запроса, а не отправляет TPU-задачу заново. Для другого видео/политики нужен другой state-dir. Один worker владеет камерой и каталогом; запросы выполняются последовательно.

Для подключения настоящего backend используйте отдельный state-dir. ACK-нутые локальным тестовым приёмником строки остаются delivered и не рассылаются автоматически другому сервису.

## Что подтверждено локальным EventSink

`--local-test-sink` включает временный сервер только на 127.0.0.1, со своим SQLite, настоящими HTTP POST/ACK/GET, дедупликацией и счётчиком уведомлений. Это тестовый приёмник, не backend Марка. После команды он закрывается; снимки и квитанции остаются на диске, тестовые media URL доступны только пока он работает. Для команды нужен действующий media-сервис. Нельзя объявлять интеграцию с backend/frontend команды готовой по одному этому тесту.

Производительность оценивается по `summary.json`. Порядка 10–11 с на одну модель означает десятки секунд на пару моделей одного кадра; реальное время и пятисекундный SLA не заявляются.
