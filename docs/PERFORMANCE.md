## Предложения после подключения настоящего backend

1. **Переиспользовать AMQP connection/channel для последовательных задач.** Здесь setup+close = 4.936 с / 47.3%. Идеализированное полное устранение этих расходов даёт 5.493 с/вызов и верхнюю границу выигрыша около 1.90x для этого образца. Это арифметическая оценка, не реализованное ускорение. Нужен отдельный A/B-прогон с сохранением journal, UNKNOWN, retained queues и fence при reconnect.
2. **Исследовать передачу входа после согласования интерфейса.** Publish/confirm занимает 4.50 с. Возможный будущий вариант — preprocessing рядом с LinQ и передача сжатого исходного кадра по разрешённому интерфейсу. Сейчас такого интерфейса нет; нельзя просто сжимать protobuf или менять dtype/shape стандартного worker.
3. **Отделить медленную доставку от инференса.** Существующие outbox и `dispatch` позволяют отдельный управляемый dispatcher. Это не ускоряет TPU, но исключает влияние HTTP timeout на следующий кадр. Нужны endpoint, media hosting и согласованное владение SQLite; daemon без supervisor не запускался.
4. **Измерить экспорт JSONL на длинном файле.** Сейчас committed экспорт пересобирается каждый кадр. Это растущая стоимость; SQLite остаётся каноническим журналом. Для коротких прогонов это не выявленный главный расход, поэтому новая реализация не добавлялась.

Параллелизм, модели и правила подтверждения не менялись. Пропуски live-наблюдений сверх max_gap_ms750 означают недостаточность данных. Нельзя считать время видео временем доставки или объявлять realtime по контрольным 0.046 FPS.
