## Что меняет решение

**[INFERENCE]** Локальный semaphore не является счётчиком удалённой работы. Нужен persisted ledger: credit резервируется **до первого возможного submit** и удерживается через timeout/restart, пока не доказано освобождение удалённой обязанности. Отдельный control-plane poll/reconcile продолжает работу после закрытия live deadline. Gap/epoch reset освобождает temporal ожидание камеры, но не remote credit старого job. Это конкретизирует W1-03 scheduler пп.2/6/9 и W1-04-F16/F18.

**[DOC → INFERENCE]** Один изученный аналог — AWS Batch, а не рекомендуемый backend для кейса и не API LinQ. Его CancelJob может успешно ответить, не остановив уже запущенную работу; running timeout не покрывает очередь и STARTING. Поэтому «есть cancel и timeout» недостаточно для bounded automatic resume. Если интерфейс не позволяет разрешить ambiguous submit и terminal state, безопасный исход — удержать credit, исчерпать конечный бюджет и остановить admission с escalation. Не сбрасывать ledger при рестарте.

**[INFERENCE]** Raw outputs могут быть больше исходного JPEG. В явно условном примере `[1,84,8400] FP32` ответ — 2,822,400 B/frame; при 50×5 FPS обратный payload равен 5.6448 Gb/s. Перенос decode-head/filter/NMS на разрешённый host рядом с LinQ и возврат bounded compact boxes может быть решающим. Реальные shapes/dtypes/pre/post LinQ — UNKNOWN.

## Новые документированные факты, ограничения и попытка опровержения

**W2-01-F01 [DOC + INFERENCE, S01].** `POST /v1/submitjob` возвращает `jobId`, `jobArn`, `jobName`. В прочитанной полной схеме нет `clientToken`/idempotency key или заявленной гарантии deduplicate submit. `jobName` документирован как имя с ограничениями формата; считать его ключом идемпотентности нельзя. Это **отсутствие документированного обещания**, а не измеренное доказательство, что каждый повтор обязательно создаёт дубль. Практическое следствие: для этого аналога same-name retry нельзя считать безопасным восстановлением lost ack. `x-amzn-RequestId` из HTTP response — идентификатор вызова, не заявленная замена клиентскому idempotency key. Наш `request_id` сам по себе не меняет семантику внешнего сервера.

**W2-01-F02 [DOC, S02].** DescribeJobs принимает список до 100 job IDs и отдаёт список job details, в том числе статус. Операция требует известного ID; endpoint не описан как lookup по нашему request UUID. Метаданные job не являются тензорным inference result. Для аналогичного interface отдельно нужны location/format/retention артефакта результата. Нет выполненного poll и нет измеренного QPS/consistency bound.

**W2-01-F03 [DOC, S03].** CancelJob работает для SUBMITTED/PENDING/RUNNABLE; PENDING может ожидать завершения dependencies. Для STARTING/RUNNING cancellation не происходит, но операция всё равно может успешно ответить HTTP200. Следствие: cancel acknowledgement не terminal proof; race «status runnable → cancel → starting» должен разрешаться повторной проверкой. Наш ledger хранит `cancel_requested`, а credit остаётся занятым.

**W2-01-F04 [DOC, S04].** TerminateJob переводит STARTING/RUNNING в FAILED; более ранние состояния отменяет. HTTP200 имеет пустой body. Наш вывод: отправка terminate — намерение, terminal observation и его сохранение — отдельный шаг; documentation API call не даёт нам измеренной upper bound времени окончательного освобождения всех ресурсов.

**W2-01-F05 [DOC, S05].** По умолчанию job timeout отсутствует. `attemptDurationSeconds` ≥60 s применяется после `startedAt`; termination best effort, возможна дополнительная задержка. SIGTERM затем SIGKILL через 30 s — описанная последовательность, не жёсткий deadline облачного scheduler. Timeout-killed job не повторяется, иной failed attempt при разрешённых retries получает новый отсчёт. Поэтому этот механизм не является полным TTL от submit до освобождения.

**W2-01-F06 [DOC, S06].** RUNNABLE может оставаться неопределённо долго; STARTING не включён в timeout. RUNNING с оставшимися retry attempts может вернуться в RUNNABLE: failure попытки ещё не terminal job. Terminal SUCCEEDED/FAILED history хранится **не менее** 7 дней. Это минимальная retention истории, не верхняя execution TTL и не обещание удаления точно на 7-й день. Попытка заменить unknown обязательным release через «достаточно подождать timeout/7days» опровергается этими условиями.

**W2-01-F07 [DOC → INFERENCE, S07].** Полезный контраргумент к «lost job ID навсегда»: ListJobs имеет case-insensitive JOB_NAME filter и пагинацию; при filter jobStatus игнорируется и возвращаются все статусы. Без filter/status по умолчанию только RUNNING — такой scan пропустил бы очередь/terminal. Наш уникальный lowercase nonce в имени помогает положительно найти job и затем DescribeJobs. Однако документация здесь не даёт atomic create-if-absent, уникальности имени и finite visibility bound. Ноль найденных совпадений не доказывает, что submit не был принят; нельзя на этом основании release/re-submit. Несколько совпадений — reconcile всех, а не выбрать первый. List permissions/retention/page completeness — дополнительные prerequisites. Это ограниченный recovery aid, не доказанная замена идемпотентности.

**W2-01-F08 [DOC, S08].** Triton позволяет отдельно запросить output binary (`binary_data`, общий `binary_data_output`); size задаётся `binary_data_size`, metadata описывает shape/datatype. Binary blocks идут после JSON в порядке outputs; native-size little-endian row-major без padding. Пример `[3,2] FP32` имеет 24 B tensor body. В absence output binary flag данные могут возвращаться JSON; размер JSON numeric arrays нельзя считать как `numel*sizeof(dtype)`. Это конкретный протокол Triton, не обнаруженная возможность LinQ.

**W2-01-F09 [DOC, S09].** Triton ensemble описывает preprocessing→inference→postprocessing на сервере и уменьшение передачи intermediate tensors между client/server. Это первичный архитектурный пример возможности server-side postprocess. Он не подтверждает доступность Triton, Python backend, NMS operator или install permissions на стенде LinQ. Для нашего placement нужен actual contract; не переносить ensemble config как готовый рецепт.

## Persisted ledger — проект, а не API LinQ

**W2-01-F10 [INFERENCE, опирается на F01–F07 и W1-04-F25].** Минимум — один local durable DB writer и один scheduler/dispatcher owner на `(service_endpoint, tenant/quota_domain)`. Если несколько процессов могут отправлять jobs, они атомарно claim-ят строки/credits в общей подходящей БД либо только один процесс является submit owner. DB transaction не охватывает внешнюю сеть: намерение commit-ится до send, ack commit-ится после. Это предотвращает потерю обязанности, но само по себе не обеспечивает exactly-once submit. Durability/backup DB — W2-E/K008; ниже гарантии предполагают сохранность ledger commit, а не любой disk loss.

В row хранить:

- `request_id` — UUID, стабильный для одного неизменного logical request; full `(camera_id,stream_epoch,frame_id[,crop_id])`, `model_revision`, `preprocess_revision`, payload hash/size и `request_contract_revision`.
- `endpoint_id`, `tenant_id`, `quota_scope`, `state`, `state_version`; `remote_job_id` nullable и отдельные attempt records, если внешний backend допускает несколько actual jobs. `UNIQUE(endpoint,tenant,request_id)` и unique known job ID в его namespace. Повтор с тем же ID и другим hash запрещён до сети.
- `remote_credit_held`/weight, `submit_intent_committed_at_utc`, `first_possible_send_at_utc`, `last_attempt_at`, `live_deadline_utc` с clock-domain/uncertainty; monotonic deadlines лишь внутри текущего run. После restart не вычитать старый monotonic из нового run.
- `idempotency_scope`, key, contract validity window, `server_expiry_at` **только если документирован**, `last_remote_state`, `last_poll_at`, `next_reconcile_at`, `cancel_requested_at`, `unknown_reason`, `terminal_reason`, `terminal_evidence_ref`.
- `result_state` отдельно: `not_available/pending_fetch/fetched/invalid/expired/unavailable`, artifact locator/hash/bytes, `live_disposition=eligible/stale/epoch_mismatch/...`. `applied_to_camera`/dedup key нужен отдельно от credit. Не хранить многомегабайтные tensors в каждой event/outbox row; bounded fetch/spool policy.

Идентичность quota tenant/service сохранять даже при смене токена/URL alias. Нельзя «получить свободные credits», создав новый endpoint label для того же удалённого лимита.

### Состояния и разрешённые переходы

| Наше состояние | Что достоверно известно | Credit | Переход и граница |
|---|---|---:|---|
| `not_submitted` | Intent ещё не мог уйти в сеть | 0 | Атомарно проверить budget, claim owner, записать `submitting`+credit; commit успешен **до** network send. Просроченное удалить/закончить `terminal/not_sent` без send |
| `submitting` | Намерение сохранено; send мог произойти, ack ещё не сохранён | 1 | Valid ack+job ID → `accepted`; доказанный non-acceptance → `terminal/rejected`; ambiguous error/timeout/crash → `unknown`. Это резерв даже если crash фактически был до send |
| `accepted` | Job identity подтверждена и сохранена; backend принял обязанность | 1 | Status queued/starting остаётся accepted с detailed remote state; running → `running`; terminal proof → `terminal`; невозможность проверить → `unknown` |
| `running` | Последнее подтверждение исполнения, не обещание текущей активности | 1 | Может стать queued/accepted при backend retry; terminal → `terminal`; timeout/error status → `unknown`. Local result expiry не меняет credit |
| `unknown` | Мог быть принят/работать/завершиться; неизвестность причинно записана | 1 | Status/idempotent lookup/resolved owner evidence восстанавливают `accepted/running/terminal`; без доказательства credit удержать. Неизвестное новое status enum, пустой lookup/404/auth failure — не terminal |
| `terminal` | Доказана невозобновляемая финальность **всего job**, либо job точно не был принят/отправлен | 0 после commit | Сохранить evidence+release одной transaction/CAS ровно один раз. Успешный job может иметь потерянный результат; failed job может оставить diagnostic artifact. Terminal не переводится обратно по запоздалому nonterminal poll |

`terminal/not_sent` и `terminal/rejected` — локальные итоги без remote job, не выдуманные статусы провайдера. Rejection освобождает credit только при контракте «эта ошибка означает не принят», а не по произвольному HTTP400/500. Cancellation intent — поле/command, не отдельное доказательство terminal. Polls одного job сериализовать; late старый ответ не понижает уже доказанное terminal, конфликтующие terminal сведения сохранять для escalation.

### Инварианты двух независимых бюджетов

**W2-01-F11 [INFERENCE].** Пусть `K_remote` — наш консервативный cap разрешённых outstanding jobs/весов, не придуманная квота LinQ. Для одноэлементных jobs без array/fan-out:

`held = count(state in {submitting,accepted,running,unknown}) <= K_remote`.

`free_remote = K_remote - held`; атомарное резервирование необходимо до возможного send. При весах использовать сумму задокументированных worst-case weights; неизвестный неограниченный fan-out не укладывается в обещание bounded work. Для batch job credit может ограничивать jobs, но нужен ещё лимит frames/bytes/work внутри job. Наш cap ограничивает нашу порождённую работу, не чужие jobs и не время ожидания в shared queue.

`local_submit_calls <= K_submit_calls`, `local_control_calls <= K_control_calls`, `local_fetch_calls <= K_fetch_calls`; отдельные byte caps для input upload и result fetch/postprocess. Local slot возвращается после фактического прекращения клиентской операции/освобождения его ресурсов; истечение app deadline без завершения blocked native thread ещё не освобождает его память/socket. Удалённый credit при этом остаётся. При process crash local calls исчезают, persisted held не уменьшается.

Новые свежие frames отправлять только при обоих доступных ресурсах, fair camera admission и живом deadline. Для poll/cancel/reconcile выделить control capacity отдельно: занятые inference slots не должны лишать систему возможности освободить known credits. Bounded retries/backoff+jitter, rate cap и очередь control IDs, а не tensor payloads. Допустимо останавливаться с меньшим количеством доступных credits из-за unknown, но нельзя возвращать их «для прогресса» без основания.

Без доказанной idempotency один фактический network submit attempt — одна возможная remote обязанность. Скрытые SDK/proxy retries должны быть выключены/учтены; иначе один ledger credit может породить несколько jobs. Новая попытка без dedup должна сначала резервировать **ещё один** credit и отдельный attempt, что сохраняет bound, но не решает дубль/устаревший кадр; минимум45ч такую повторную отправку не делает. При подтверждённой idempotency несколько попыток одного immutable key в его действующей scope/window покрываются одной обязанностью, лишь если сервер гарантирует single job и lookup того же outcome. Результат дедуплицируется отдельно.

### Fault/restart traces

**W2-01-F12 [INFERENCE].** Примеры ниже — ожидаемый проектный trace, не log выполненного эксперимента.

| Сбой/гонка | Правильное восстановление | Запрещённое сокращение |
|---|---|---|
| Timeout до submit ack, ID неизвестен | `submitting → unknown`, held остаётся. Query по client key, если контракт есть. Same-key submit допустим только при действующей server dedup и ещё живом frame deadline; если request уже stale, query-only предпочтителен, чтобы не создать впервые устаревшую работу | Новый request ID сразу после timeout; reset semaphore = reset remote jobs |
| Server accepted, process crash до persist job ID | После restart row всё ещё submitting/unknown с прежним UUID/hash/credit. Lookup по ключу возвращает ID. Если лишь AWS-подобное имя — положительный paginated search помогает, zero match не разрешает release | Считать job непринятым, потому что в DB `job_id=null` |
| Crash после intent commit до send | Неотличим от предыдущего случая без provider evidence; консервативно unknown. При valid idempotency и свежести можно same-key retry; иначе hold/escalate | «Row submitting старше 5 s, значит send не было» |
| Retry того же request ID | Проверить hash/model/scope/key window; повторный ack того же job не увеличивает число obligations, terminal effect idempotent. При неизвестной idempotency не retry автоматически | Дедуплицировать только result, оставив дубли remote work |
| Job ID известен, local timeout/epoch reset | Live waiter получает Gap; старый result не идёт в tracker/UI. Collector по ID продолжает status/cancel до terminal | Возвращать remote credit при очистке reorder buffer/смене camera epoch |
| Cancel HTTP success, статус ещё running | Cancel intent записан; credit удержан; poll/поддержанный terminate по policy. Только documented terminal/полный expiry proof → release | Принять HTTP200 cancel за остановку kernel/job |
| Restart всех client processes | Admission закрыт при старте; проверить ledger/quota namespace, восстановить held, переclaim собственных leases, reconcile known IDs, submitting → unknown. Старые video epochs не восстанавливать как live; новые latest frames ждут free credits | Начинать с held=0, чистить «старые» rows или создавать второй scheduler owner |
| Job исчез/404/lookup empty; result TTL прошёл | `unknown`, reason и последняя надёжная remote observation. Оператор/owner resolution либо доказанный full TTL. Result unavailable и execution unknown — разные поля | 404=SUCCEEDED, отсутствие результата=FAILED, ошибка auth=job deleted |
| Terminal наблюдён, crash до local release commit | После restart status/reconcile повторяется; CAS/transaction записывает terminal и освобождение ровно один раз | Release в RAM до DB commit, затем повтор release после restart |
| DB commit error/disk full при полученном ack | Остановить новые submit; сохранить diagnostic где возможно. Предыдущий persisted submitting credit остаётся; не терять обязанность и не «продолжать без ledger» | Разрешить новую отправку, считая failed ack persistence будто remote не принял |

После startup reconciliation допустимо возобновить только на **доказанно свободном остатке** budget; не требуется ждать всех unknown при наличии free credits, но unresolved credits всегда учитываются. Если unknown возрастает до `K_remote`, admission=STOPPED. Если есть системный риск недостоверности ledger/namespace, stop сразу. UI: `analysis unavailable / remote jobs unresolved`, счётчик known/unknown и last fresh result age; live video может продолжаться. Escalation — подготовленный локальный incident packet, а не отправленное здесь сообщение владельцу.

### Когда TTL действительно позволяет release

**W2-01-F13 [INFERENCE, ограничено F05/F06].** Различать: (1) client RPC deadline; (2) frame live deadline; (3) execution-attempt timeout; (4) максимальную жизнь job от acceptance, включая queued/starting/retry; (5) retention status/results; (6) retention idempotency record. Только документированный полный job expiry/release contract может заменить terminal observation для remote accounting. Для unknown-before-ack нужен ещё bound последнего возможного acceptance: зависший proxy/запоздалый send не должен создать job после локального решения об expiry. Требуются серверный `not_after`/lease или эквивалентный доказанный acceptance cutoff, clock-error margin и запрет поздних retries. Client timestamp+длительность сами по себе этого не доказывают.

При key-retention expiry same-key retry может стать **новым** submit; не отправлять старый UUID после окна как средство reconciliation. Если terminal record может исчезнуть раньше восстановления, нужны собственный persisted terminal witness/поддержанный audit lookup; иначе UNKNOWN даже при известном ID. AWS-подобные running timeout и ≥7-day terminal history не дают такой полной гарантии. Следовательно bounded ресурсное состояние возможно ценой остановки; **bounded непрерывное автоматическое обслуживание и auto-resume без idempotent submit/lookup/полного TTL в общем случае не доказуемы**. Предпочтение для live — сервис с проверяемым request lifecycle либо разрешённый свой worker, который можно корректно ограничить; недоступный contract не исправляется частыми fresh submits.

## K006 return tensors, NMS и обратные каналы

**W2-01-F14 [INFERENCE, F08/F09 + W1-03-F16].** Обязательный output contract включает tensor names/count, per-batch/per-frame shapes, dtype/layout/endian, quantization scale/zero-point, decode-head semantics (logits/objectness/class scores/box encoding), batch/frame/crop correlation, coordinate space и inverse letterbox/ROI transform. Для compact detections нужны class mapping/version, box format, confidence definition, threshold/top-K, class-aware/agnostic NMS, IoU threshold, max detections, truncation flag, postprocess implementation/config revision. NMS может отсутствовать в end-to-end detector — не добавлять его дважды по привычке. Masks/keypoints/embeddings — отдельные размеры, а не «маленькие metadata».

| Actual output / access | Где decode-head/filter/NMS | Последствия и проверка |
|---|---|---|
| API отдаёт только raw heads, свой код на remote нельзя | На клиенте после binary download/dequantize | Downlink, CPU и RAM могут доминировать. Проверить все heads, scales и reference parity; cap result bytes до выделения памяти. Новый dtype без согласования запрещён |
| Разрешён свой remote wrapper + есть host CPU/runtime | Рядом с inference; вернуть compact boxes | Кандидат45ч: меньше WAN; серверные CPU/queue/permissions unknown. Принятый inference evidence отдельно от CPU postprocess. Golden comparison обоих placement при одинаковых thresholds |
| API уже возвращает boxes | По подтверждённому server contract | Не делать повторный NMS без причины. Проверить server truncation/coordinates/class mapping; если меняются thresholds, это смена config revision |
| API возвращает только events | Правила/tracking уже внутри сервиса | Не предполагать доступность per-frame detections/своего temporal state. Может не покрыть необходимые классы/клипы/processed view; route условный |

Ни одно placement не установлено для LinQ. Перенос NMS на клиент может упростить интеграцию, но требует сначала посчитать response size, затем проверить полезный FPS/age и качество. Перенос на remote без изменения NN может быть допустимым инженерно, но accepted обязательная NN-граница определяется выдачей/кейсом, не этим аналогом.

### Формулы, polling и memory bounds

**W2-01-F15 [INFERENCE].** Для уникальных completed frames rate `N*f`, raw tensor bytes/frame `O = Σ_t product(shape_t_per_frame)*bytes(dtype_t)`; при batch не умножать batch dimension дважды. Binary request response metadata `h_out` и wire overhead считать отдельно. Для переменного output считать **измеренное** `E[O]`, p95/p99/max и burst, а не только fixed average.

`R_return = 8*N*f*E[output_bytes]` bit/s — именно remote→client inference data. Для raw binary `output_bytes≈O+h_out`; JSON/base64 брать фактический wire size (base64 как W1-03-F15 добавляет около 1/3 к binary, JSON numeric arrays имеют другую надбавку). Retries/download repeats увеличивают фактический rate; f здесь не camera source FPS и не число повторных completions.

Для J наблюдаемых jobs, каждого с poll interval Δ и server-supported batch query до b IDs: грубая upper planning rate `q_poll≈ceil(J/b)/Δ` calls/s при полном обходе; exact variable scheduling считать суммой реальных poll rates. Status-response bytes зависят от количества jobs/attempts/fields. Добавить `R_status_down=8*q_poll*E[status_response_bytes]`, `R_status_up=8*q_poll*E[status_request_bytes]`, submit ack, cancel/control, result locator requests и фактические result downloads. Если status endpoint повторяет полный output, каждый такой poll заново вносит O: нельзя считать «poll metadata мало». Callback/webhook вместо polling требует authenticated delivery/dedup/reconcile и не отменяет ledger.

При идеальном periodic polling обнаружение уже завершённого job ждёт ещё [0,Δ), среднее Δ/2 **только** при равномерной независимой фазе; quota/backoff/outage разрушают bound. Δ относится ко времени результата клиента, не accelerator compute. Успешный poll latency не доказывает terminal visibility delay. Использовать status-only response по доступному контракту; fetch successful artifact один раз с bounded retry/dedup/hash. Дефицит result fetch capacity должен создавать bounded spool/drop/unavailable outcome, не бесконечные completed tensors.

Client postprocess требование: `N*f*E[cpu_seconds_post/frame] < available_post_cpu_seconds/s` с измеренными concurrency/copy costs. RAM: `M_output >= K_fetch*O_max + K_post*O_max + compact_results + decoder/copy overhead` — считать реальное владение буферами, переиспользуемые ссылки не суммировать дважды. NMS top-K/output cap ограничивает память, но меняет recall; выбирать совместно с evaluation. Лимиты payload/result bytes, parse timeout и tensor shape validation нужны до trust внешнему size; truncated output явно маркировать.

### Один условный shape/dtype пример — арифметика, НЕ модель LinQ

**W2-01-F16 [INFERENCE/LOCAL arithmetic].** Допустим один raw head `[1,84,8400]` FP32, batch1, 84 условно = 4 box components + 80 class scores. Это **не утверждение о выбранной модели**, не import из LinQ и не стандарт для любого detector. Binary body `1*84*8400*4=2,822,400 B/frame`. FP16 при **поддержанном** другом контракте дал бы 1,411,200 B; произвольный client cast меняет численность/качество, его не считаем разрешённым.

Альтернатива после postprocess: максимум100 detections, каждая 4×FP32 координаты + FP32 score + INT32 class =24 B; fixed packed records `[M,24 bytes]`, M≤100, плюс count INT32=4B: при M=100 это2404 B/frame. Это проектный binary формат **до** envelope/HTTP/TLS; не JSON объекты и не masks. Объявленные class count/max detections — допущения примера, не требования кейса.

| Только return tensor/packed payload, analysis5 FPS | 1 камера | 50 камер | 500 камер |
|---|---:|---:|---:|
| Raw head FP32 2,822,400B |112.896 Mb/s|5.6448 Gb/s|56.448 Gb/s|
| Compact M=100,2404B |0.09616 Mb/s|4.808 Mb/s|48.08 Mb/s|

Арифметика проверена небольшим локальным Python-расчётом; результаты сохранены в [ARITHMETIC.json](MATERIALS/W2_01/ARITHMETIC.json). Это не benchmark. SI decimal units. Отношение payload ≈1174.04× здесь обусловлено допущениями raw/compact, не универсальная compression ratio. Если input JPEG условно100kB из W1-06, raw return в этом примере в 28.224 раза больше input payload. При local→remote JPEG варианте uplink input и downlink output — разные направления; их нельзя выдать за одно симметричное требование. При remote decode эти tensors могут остаться в LAN/host и через WAN идут только compact metadata. Viewer fanout отдельно добавляет browser egress — это часть W2-F, не замена R_return.

Условный polling пример: J=50 известных jobs, Δ=0.5s, b=1 →100 polls/s; request1kB и status response2kB →0.8Mb/s вверх и1.6Mb/s вниз. Это допущения bytes/interval, не AWS/LinQ measured quota. При b=100 и таком контракте число calls меньше, но response на50jobs крупнее; нельзя делить traffic ровно на100. У poll interval0.5s идеальная дополнительная средняя задержка250ms, край <500ms только при указанных идеальных условиях. Не назначать этот Δ как готовый режим стенда.

## Proposed experiments и точные границы успеха

### W2-01-E01 — fake-job fault fixture (NOT EXECUTED)

**Решение:** проверить наш ledger/credit/state recovery независимо от LinQ, включая честный STOPPED исход.

**Входы:** собственный fake service, отдельный durable ledger store, deterministic virtual clock и журнал service-side active jobs; model payload — маленькие bytes+hash, не NN. Fixture конфигурирует: `idempotent_submit=true/false`; key scope/retention; acceptance before lost ack; status visibility delay; cancel success while work runs; finite full TTL либо no TTL; disappearing terminal history. `K_remote=2`, local submit cap1, control cap1 — **тестовые значения**, не LinQ quotas. No arrays/automatic server retries в базовом case; отдельный case добавляет attempt retry.

**Шаги:** (1) happy submit→accepted→running→terminal; (2) crash непосредственно до/после intent commit и до/после socket send; (3) accept, потерять ack, crash до job_id commit; (4) same UUID/hash и затем другой hash; (5) reset camera epoch/live timeout при running; (6) cancel200 с continuing job; (7) status404/unknown enum/expiry; (8) restart client со всеми2held; (9) вернуть terminal, duplicate callback/status; (10) отключить idempotency и full TTL и получить STOPPED вместо автоматических новых jobs; (11) скрытый submit retry моделировать как два actual attempts и показать failure одного-credit реализации; (12) DB commit error при ack/release.

**Метрики/артефакты:** полный ordered trace `intent_commit/send/accept/ack/persist/crash/restart/poll/terminal/release`, request/hash/job IDs, DB rows до/после, service active count/IDs, held credits, local calls/bytes, double releases, post-deadline new submit, stale camera applications; fixture seed/config/source revision. Виртуальные durations не выдавать за реальные runtime latency.

**Критерии:** на каждом шаге `0≤held≤2`; все возможно активные jobs нашей системы имеют сохранённую reservation, service active count≤held при выполненных fixture prerequisites; release ровно один на terminal obligation; ни один ambiguous submit не исчезает при restart; mismatch hash не уходит в сеть; old epoch не обновляет live state; duplicate terminal не создаёт free>2; stop admission воспроизводим при неизвестности без разрешающего контракта. Если сервис задним числом принимает send после локального TTL release, test должен выявить ошибку до добавления доказанного acceptance cutoff.

**Исходы:** valid dedup+lookup → bounded automatic reconcile; no dedup/full TTL → bounded stop; duplicate service jobs → исправить hidden retries/credit model. Даже успешный fixture не подтверждает фактический LinQ lifecycle, DB power-loss durability или performance/качество NN.

### W2-01-E02 — issued lifecycle golden path (NOT EXECUTED)

**Входы:** официальный выданный manual/schema и именной grant, tiny allowed golden input/model, permission на обычные submit/status/cancel; fault actions только на собственном клиенте и допустимые владельцем, без reset/kill/нагрузки shared service. Сначала зафиксировать idempotency scope/window, actual status list, permissions lookup/list, acceptance/release/TTL semantics, hidden client retry policy.

**Шаги:** один normal submit и result; наблюдение известного job до terminal; повтор key только если explicitly supported; локальный client restart с сохранённым ledger; безопасно отсоединить client wait/проверить late completion если разрешено; cancel в разрешённых состояниях, затем status. Если duplicate/TTL эксперименты запрещены или contract opaque — оставить соответствующий UNKNOWN, не «проверить силой». Сохранить redacted request/response, timestamps/clock domain, artifact/model hashes, job ID, terminal evidence, реальные quotas из manual отдельно от измерений.

**Критерий выбора:** есть machine-readable result и корреляция, доказан remote-release accounting либо ограниченная stop policy; measured job cycle с polling укладывается в agreed freshness и per-camera FPS (связь W2-D/K005). Иначе это offline/job demo, live route unsupported. Успех одного run подтверждает ровно этот supported path/config, не p99, fairness всех команд, TTL в часах или глобальную надёжность.

### W2-01-E03 — output contract/placement/return budget (NOT EXECUTED)

**Входы:** actual serialized result и schema каждой output head, golden input/model/preprocess/precision, dequantization/postprocess reference, небольшой целевой размеченный набор для проверки cap/NMS с evaluation. При remote wrapper permission сравнить два placement с тем же NN; иначе только фактический доступный route.

**Шаги:** сохранить один raw response+metadata (без секретов); проверить bytes против shape/dtype, batch/frame mapping и coordinates; декодировать raw reference, затем compact output; проверить пустые/максимальные/oversize/invalid shape, crowded scene и truncation. Измерить actual wire bytes mean/p95/max, result fetch duration, poll bytes/QPS, local/remote postprocess durations локальными clocks, peak live buffers/RSS, fresh FPS/age. Небольшой correctness test сначала; sustained load — отдельная разрешённая практика, не выполнен здесь.

**Успех:** parity с reference в заранее объявленной tolerance/coordinate semantics, один postprocess revision, bounded output parse/fetch/post queues, расчёт actual link отдельно input/output/control/view; chosen cap не даёт неприемлемого quality loss по evaluation. Из результата пересчитать50/500 символически или actual measured coefficients; не переносить golden one-frame CPU время как готовую capacity 500. Успех postprocess не доказывает обязательное LinQ execution; нужен platform witness.

| ID / приоритет | Точное неизвестное | Чем закрывается / решение |
