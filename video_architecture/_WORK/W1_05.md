## Главные решения для команды

1. Писать сжатый основной поток непрерывно короткими сегментами; инференс и просмотр могут использовать отдельную ветвь. При событии немедленно закреплять интервал до события, затем дождаться post-roll. Клип имеет состояние pending/complete/partial/failed. Одной настройки «5 секунд до и после» недостаточно: retention и сбой способны удалить часть окна.
2. `-c copy -segment_time 2` не гарантирует сегменты по 2 секунды. Границы зависят от ключевых кадров исходного потока. Для evidence сохранять покрывающие окно сегменты целиком; точную пользовательскую нарезку делать отдельной производной при необходимости.
3. Для минимального честного демо удобен обработанный JPEG/кадр с метаданными одним сообщением WebSocket либо серверная отрисовка рамок. Это упрощает совпадение результатов именно с анализируемым кадром. Оригинальный WebRTC live view полезен отдельно, но наложение на него «последнего результата» без timestamp mapping неверно.
4. MediaMTX + собственный `<video>` через `reader.js`/WHEP — хороший кандидат для живого оригинального видео. Встроенный iframe достаточен для просмотра, но неудобен для синхронизации canvas и передачи учётных данных. Для площадки обязателен тест прямого медиасоединения; доступный HTTPS endpoint сам по себе ничего не доказывает про ICE/media.
5. Событие в БД и задача уведомления должны создаваться одной транзакцией. SSE/WS показывают тревогу быстро, но durable outbox и повторная загрузка истории дают восстановление. Ответ API бота не доказывает, что человек увидел тревогу. Текстовая тревога может уходить сразу, клип — после закрытия post-roll.
6. В свежих MAX docs есть практически значимое изменение: домен `platform-api2.max.ru`, токен в `Authorization`, максимум 2 сообщения/с в один чат; старые примеры могут не работать. В Telegram бесплатные лимиты различаются по чату, группе и рассылке. Мессенджер — дополнительный канал, не единственный источник событий.

## Факты и проектные следствия: хранение

### W1-05-F01 — DOC: длительность сегмента связана с GOP

S01 §segment: новый сегмент обычно начинается ключевым кадром reference stream; если он не совпал с запрошенным временем, разбиение произойдёт на следующем. Segmenter лучше работает с одним CFR video. `segment_time_delta` допускает погрешность округления timestamps при force-keyframes. `reset_timestamps` сбрасывает начало сегмента близко к нулю, но документация оговаривает зависимость от muxer/codec. Эти параметры нельзя принять за гарантию точного окна или единой исходной шкалы времени.

### W1-05-F02 — CODE: обход keyframe меняет условие, не создаёт независимость кадров

S03 `seg_write_packet` проверяет reference stream, флаг keyframe (либо `break_non_keyframes`), число кадров и временное/кадровое условие; затем вызывает `segment_end` и `segment_start`. В таблице options `break_non_keyframes` по умолчанию 0. INFERENCE: переключение этого параметра не создаёт отсутствующий IDR и не устраняет межкадровые зависимости. Для доказательств нельзя считать любой маленький сегмент самостоятельно декодируемым только потому, что файл появился.

### W1-05-F03 — DOC: stream copy сохраняет компрессию, фильтры требуют raw frames

S02 §3.1–3.3: stream copy передаёт пакеты из demuxer в muxer без decode/encode; фильтрация выполняется на decoded frames. INFERENCE: запись оригинала `-c copy` экономит вычисления, не меняет изображение повторным сжатием; наложение рамок, blur лиц, resize и frame-accurate переработка требуют иной ветви с декодированием/кодированием. Не обещать одновременно оригинальный битстрим и встроенное размытие.

### W1-05-F04 — DOC/INFERENCE: два разных вида evidence export

S02 `-ss`: input seek находит близкую точку до target; с transcoding и default accurate_seek лишнее декодируется/отбрасывается; со stream copy сохраняется. S01 fragmentation: обычный MP4 часто зависит от корректного финального metadata; fragmented MP4 устроен иначе и может сохранять полезные fragments при прерывании. Это не гарантия дисковой сохранности после power loss.

Рекомендуемый оригинал: покрывающие target interval исходные segments + manifest, фактические start/end, gaps. Производный клип: отдельно reencode/trim для просмотра, linked original IDs и provenance. Нельзя молча подписывать clip «ровно 5 секунд до», если его первый usable frame позже. При copy допускается больше материала до/после, но не меньше без `partial`.

### W1-05-F05 — DOC: MediaMTX уже умеет запись, но retention не знает наших incident pin

S04 Usage: `recordFormat: fmp4` или `mpegts`, `recordPartDuration: 1s`, `recordMaxPartSize: 50M`, `recordSegmentDuration: 1h`, `recordDeleteAfter: 1d`; это пример конфигурации, не наши выбранные значения. Документ называет part duration RPO и пишет о потере последней part при сбое. INFERENCE: для очень простого демо можно брать готовую запись MediaMTX вместо собственного remuxer. Нужно отдельно подтвердить recovery на выбранном FS/ОС. Автоудаление по времени не выражает pin инцидента: либо экспортировать incident в независимую папку до expiry, либо отключить auto-delete и управлять удалением самим. Длинный часовой segment неудобен для небольшого кольца и быстрых копий; это изменяемая настройка, не обязательный архитектурный выбор.

### W1-05-F06 — DOC: hooks есть, но finished segment может прийти позднее тревоги

S05 tag v1.21.2 `runOnRecordSegmentCreate` / `runOnRecordSegmentComplete` позволяют внешней обработке реагировать на сегменты. `recordPartDuration` и `recordSegmentDuration` — разные сущности. INFERENCE: не ждать закрытия часового файла для первой тревоги. Сначала event + pending clip, после закрытия нужного interval — clip-ready update. Нельзя объявлять open file complete из одного факта появления имени.

### W1-05-F07 — DOC: Frigate даёт полезный контрпример «pre-roll настроен, но отсутствует»

S06: Frigate пишет исходный поток без reencode, временно складывает segments в cache, валидирует и переносит по retention policy. Экспорты сохраняются отдельно и не удаляются retention. `pre_capture`/`post_capture` относятся к временному окну, но при `mode: motion` сохраняются только подходящие по motion segments. Следовательно, отсутствие движения до события может вырезать часть pre-roll. Это документированное поведение конкретной current версии, не проверка нашего приложения. Для evidence completeness выбирать непрерывную запись/`all` в нужном окне и явно проверять покрытие.

### W1-05-F08 — INFERENCE: безопасный жизненный цикл кольца

Проект, а не найденная гарантия готового SDK:

* Recorder пишет immutable сегменты с уникальными именами `camera_id/stream_epoch/segment_seq`; не переиспользовать имя в кольце. Индекс содержит исходную шкалу PTS/time_base, фактический временной диапазон, stream profile, размер, decode/validation status. Файл сначала считается open, после финализации и проверки — closed/available. Временные имена/atomic rename полезны при одной ФС, но сохранность после питания требует отдельного теста fsync/FS.
* При событии с исходным временем `t_event` выбрать `[t_start-pre, t_end+post]`; для продолжающегося события `t_end` ещё изменяется. В одной согласованной операции добавить durable clip job и pins ссылок на существующие segments; pin относится также к будущему target interval. Сразу защищать pre-roll, не ждать post-roll.
* Возраст кольца должен превышать `pre + worst_case_event_arrival_delay + segment_close_delay + margin`, все в секундах. Если event-time пришёл с задержкой удалённого инференса больше глубины кольца, требуемый pre-roll уже утрачен. Буфер «10 секунд» недостаточен при 15-секундной задержке результата.
* Retention worker удаляет только closed, не pinned, не читаемый/не экспортируемый segment; pins и удаление координируются БД/одним owner. Одна проверка file existence перед экспортом не защищает от гонки удаления. Можно копировать в независимый immutable incident directory; hardlink подходит только с пониманием одной ФС и copy-on-delete semantics, не как универсальная инструкция.
* После post-roll собирается manifest доступных интервалов, выявляются gaps, отсутствующие boundary keyframes и decode failures. Clip status: pending → complete, либо partial с missing intervals/reason, либо failed. Полнота файла/временного окна и качество распознавания — отдельные свойства.
* При рестарте сверить индекс и ФС, open/truncated файлы отправить на validation/quarantine, восстановить незавершённые clip jobs; не проставлять complete всем .mp4. Pin должен жить на диске/в БД, не только в Python set.
* При исчерпании диска остановить/деградировать запись с явным storage fault; события и metadata сохранять по возможности. Не вытеснять pinned evidence молча. У pins отдельная квота/срок/ручное освобождение, иначе incident storm полностью заполняет диск.

Для 45 часов достаточно SQLite/PostgreSQL event table + segment index + одна очередь clip jobs и один retention owner; конкретный storage engine согласовать с владельцем V08. MinIO/S3 добавляет распределённость, но не решает lifecycle сам. Хэши и manifest доказывают неизменность сохранённого набора относительно хэшей, а не юридическую chain of custody и не отсутствие пропущенных кадров.

### W1-05-F09 — INFERENCE: объём хранения в decimal GB

При среднем суммарном video+audio bitrate `b` в Mbit/s (1 Mbit = 10^6 bit), непрерывной записи 86400 s/day:

`S_GB_per_day = b * 10^6 * 86400 / 8 / 10^9 = 10.8 * b`.

`S_total_GB = N * D_days * 10.8 * b * recording_fraction + derived_clips_GB + thumbnails_metadata_GB + reserve_GB`.

Это арифметическая оценка payload, без контейнеров, файловой системы, replication и эксплуатационного резерва. Для VBR измерить интеграл фактического размера за репрезентативное время, а не подставлять max bitrate как средний. Event fraction нельзя считать долей кадров с нарушениями: pre/post-roll и округление до segments расширяют запись; overlapping incidents могут делить исходные segments, но отдельные exports дублируют байты.

| Средний bitrate одной записи | 1 камера GB/day | 50 камер GB/day | 500 камер GB/day | 500 камер, 7 дней, decimal TB |
|---|---:|---:|---:|---:|
| 0.5 Mbit/s | 5.4 | 270 | 2700 | 18.9 |
| 1 Mbit/s | 10.8 | 540 | 5400 | 37.8 |
| 2 Mbit/s | 21.6 | 1080 | 10800 | 75.6 |
| 4 Mbit/s | 43.2 | 2160 | 21600 | 151.2 |
| 8 Mbit/s | 86.4 | 4320 | 43200 | 302.4 |

Пример-допущение: main 4 Mbit/s + substream 0.5 Mbit/s, если хранить оба, — 48.6 GB/day/camera; только main — 43.2. При 500 камерах main ingress 2 Gbit/s и payload write 250 MB/s, без overhead/резерва. Raw RGB ring 1920×1080×3 bytes ×25 frame/s ×10 s = 1,555,200,000 bytes ≈1.56 GB на камеру; compressed 4 Mbit/s ×10s /8 =5 MB. Поэтому кольцо evidence разумно держать encoded, а не весь raw frame history. Это расчёты, не измерение камеры или LinQ.

Main/substream экономят decode/network только на соответствующей ветви: substream для аналитики не уменьшает место main archive. Низкое разрешение может убрать мелкий респиратор/сигарету; это решение принимает evaluation/violation_methods. Между main и substream нельзя считать одинаковым frame_id или ROI alignment без проверки crop/FOV/clock.

## Факты и проектные следствия: браузер и синхронизация

### W1-05-F10 — DOC: кодек медиасервера не равен кодеку браузера

S07 предупреждает об ограниченной поддержке H265 браузерами и непригодности H264 с B-frames для WebRTC playback. Рекомендуется совместимый H264 без B-frames и Opus для звука. INFERENCE: для контролируемого демо выбрать и проверить один browser+OS+codec profile; если source несовместим — отдельная transcode ветвь для viewer. Перепаковка без reencode не исправляет B-frames. Не переносить способность RTX декодировать HEVC на browser другого ноутбука.

### W1-05-F11 — DOC: LL-HLS — полезный fallback с оговорками

S05 v1.21.2 HLS: default `hlsVariant: lowLatency`, minimum `hlsSegmentDuration: 1s`, `hlsPartDuration: 200ms`, `hlsSegmentCount: 7`. Документ пишет о player buffer обычно в 3 parts/segments, final segment duration зависит от IDR, count не управляет latency; TLS требуется для корректного LL-HLS на Apple devices. INFERENCE: 3×200ms=600ms — только иллюстрация part-buffer component из defaults, не end-to-end benchmark. Начало потока, GOP, decode, player и сеть добавляют задержку. Уменьшение count не является надёжной настройкой low latency.

### W1-05-F12 — DOC: iframe прост, собственный video нужен для синхронизации

S08: HLS обычно имеет большую задержку, но меньше connectivity проблем, чем WebRTC. WebRTC iframe имеет query controls/muted/autoplay/playsInline, но не даёт website передавать credentials и напрямую обращаться к video tag. Документ предлагает `reader.js` и собственный `<video>` для динамических действий и auth; пример endpoint `http://mediamtx-ip:8889/mystream/whep`. INFERENCE: overlay canvas поверх чужого iframe по независимому таймеру не становится синхронным. Same-origin/модификация player могут изменить ограничения, но это отдельная интеграция, не свойство готового embed URL.

### W1-05-F13 — CODE: прокси должен пропускать lifecycle WHEP, а ICE media живёт отдельно

S09 код reader: OPTIONS запрашивает ICE servers в `Link`; POST `application/sdp` ожидает 201 и получает session URL из Location; PATCH `application/trickle-ice-sdpfrag`, DELETE на session URL; `#authHeader` поддерживает Basic/Bearer для начальных запросов; создаётся RTCPeerConnection, track отдаётся в callback; есть закрытие/перезапуск при ошибке. Прочитан этот код, reconnect не испытан. INFERENCE: reverse proxy должен сохранять methods, Location/Link/CORS headers и корректный session path; обычный GET-only proxy route сломает setup или cleanup. Следить за относительными/абсолютными URL после subpath proxying. Не копировать HEAD reader к произвольной старой версии сервера без smoke test.

S07 отдельно: static UDP media port по умолчанию 8189; TCP media port включается `webrtcLocalTCPAddress`; public/LAN адреса — `webrtcAdditionalHosts`; STUN и TURN задаются через `webrtcICEServers2`. Сигналинг HTTP и peer connection разные. STUN помогает обнаружить внешний адрес/пробить подходящий NAT, TURN ретранслирует media. Если UDP закрыт, возможен TCP/relay, но затраты/задержка и доступность не измерены. На demo network проверять реальный selected candidate pair, а не только HTTP 200.

### W1-05-F14 — DOC/CLAIM: go2rtc как альтернатива и ограничения доверия README

S10 говорит, что go2rtc WebRTC media идут напрямую browser↔go2rtc, HTTP reverse proxies участвуют в установлении; default listener `:8555` TCP/UDP, кандидаты можно задавать вручную, TURN доступен. В config filters указано исключение Docker-like 172.16.0.0/12 candidates. README содержит «примерно 20% пользователей» с проблемой symmetric NAT — это CLAIM автора без методики/выборки, не пригодный коэффициент надёжности нашей сети. Там же есть широкое утверждение о непригодности UDP для 2K/4K через интернет — не принимать как универсальный технический запрет; конкретную потерю/bitrate проверять.

### W1-05-F15 — DOC: статус WHEP нельзя брать из случайного старого README

S10 называет старый WHEP заменённым WISH standard; это неточная формулировка, а WISH — рабочая группа/процесс. S21 на дату доступа показывает `draft-ietf-wish-whep-05`, active Internet-Draft, intended Proposed Standard. Использовать WHEP как реализованный media-server endpoint, привязанный к версии сервера/reader, не обещать полную совместимость с финальным RFC. Этот отрицательный результат меняет обещания в technical delivery, но не запрещает MediaMTX reader.

### W1-05-F16 — DOC: MJPEG требует MJPEG source или transcoding

S11: `/api/stream.mjpeg?src=...` и `/api/frame.jpeg?src=...` работают с MJPEG codec в source; H264/H265 нужно конвертировать через FFmpeg. INFERENCE: MJPEG не бесплатный wrapper над camera H264. Он прост для debug и server-burned boxes, но bandwidth proportional JPEG_bytes×FPS, нет эффективного межкадрового сжатия. Стандартный `<img src=...mjpeg>` не даёт приложению надёжного frame_id per displayed image; лучше собственный framed transport, если нужна точная связь metadata.

### W1-05-F17 — DOC: WebSocket transport может означать очень разные вещи

S12 `/api/ws?src=...`: WebRTC SDP/candidates через JSON, MSE через `type:mse` с codec list, HLS playlist message, MJPEG `type:mjpeg`. INFERENCE: «видео по WS» надо расшифровывать: signaling-only WebRTC, fMP4/MSE, JPEG frames — разные buffering, codecs и sync. Для нашего простого JPEG протокола не приписывать go2rtc автоматическую передачу custom `frame_id`/LinQ results: это наша работа.

| Вариант | Когда брать в 45 часов | Главная цена/риск | Что честно показывать |
|---|---|---|---|
| WebRTC + MediaMTX native video | Нужен плавный original live, есть проверенная сеть | ICE/codec + доказанная timestamp mapping для overlay | original video; delayed analytics отдельно, пока mapping не проверена |
| WebRTC + go2rtc | Команда уже знает go2rtc/Frigate | Похожие NAT ограничения, другие ports/API | Та же честность; не выбирать два медиасервера одновременно без причины |
| HLS/LL-HLS | WebRTC не проходит firewall/proxy, нужен HTTP-only route | Больше буферизации; версии player и codec compatibility | Явная live delay и timestamp |
| HTTP MJPEG с server boxes | Один-два небольших debug вида | JPEG encode/bandwidth; `<img>` sync limitations | Кадр уже содержит собственные результаты |
| WebSocket JPEG+metadata envelope | Нужна быстрая faithful analyzed view | Частота/размер ограничены, очередь может накапливаться | FPS и age анализируемых кадров, не «25 FPS inference» из camera FPS |
| Server annotated H264 | Нужны плавный поток и burned-in boxes | Encode и необходимость ждать результатов/сопоставлять кадры | Processed delayed video, original отдельно |

### W1-05-F18 — DOC: requestVideoFrameCallback помогает, но не создаёт frame correspondence

S13 §1/§2.2: callback при кадре, переданном compositor; best effort, иногда на один v-sync позднее, под нагрузкой кадры пропускаются. `mediaTime` — presentation timestamp в секундах media timeline, для live/WebRTC MAY быть нулём; `rtpTimestamp` SHOULD присутствовать для received WebRTC, не обязательно; `captureTime` — оценка с синхронизацией часов, не достоверные UTC часы камеры. `presentedFrames` даёт счётчик compositor frames, не camera frame ID. INFERENCE: нельзя использовать `Date.now()` результата как timestamp картинки или считать rVFC гарантией каждого кадра. Проверять feature/field availability на реальном браузере; callback обслуживать заново на каждый кадр. Не подменять mediaTime настенными миллисекундами.

### W1-05-F19 — DOC: relay может менять абсолютную шкалу времени

S14: MediaMTX принимает/выдаёт absolute timestamps для RTSP/HLS/WebRTC, но по умолчанию заменяет входные absolute timestamps системными; `useAbsoluteTimestamp` позволяет сохранить входные. HLS использует EXT-X-PROGRAM-DATE-TIME; RTSP/WebRTC — RTCP SR c reference NTP/RTP. Формула документа: `frame_abs = ref_ntp + (frame_rtp-ref_rtp)/clock_rate`, seconds. INFERENCE: RTP timestamp — относительный счётчик с wrap/session semantics; один timestamp без SSRC/epoch/clock rate недостаточен. Даже включение preserve absolute timestamp не доказывает точные камеры UTC и соответствие с кадрами другой decoder branch.

### W1-05-F20 — INFERENCE: минимальный контракт идентичности и геометрии

Рекомендуемый envelope (проект): `camera_id`, `source_stream_id`, `stream_epoch`, `frame_id`, `source_pts`, `source_time_base_num/den`, `source_capture_utc` nullable + provenance/uncertainty, `ingest_monotonic_ns` на конкретном host, `source_width/height`, crop/rotation/flip, resize scale и letterbox padding, модель/version, bbox coordinate space, `result_ready_monotonic_ns`, inference backend и trace/request ID. `frame_id` выдаёт ingest один раз; результаты сохраняют его неизменным; при reconnect новая epoch. Backend LinQ не подменяется другим незаметно.

Согласовано с полученной соседней ветвью: [W1_03.md](W1_03.md), W1-03-F05 и разделы scheduling/request metadata, прочитанные 2026-10-23. Её async adapter сохраняет ту же identity/transform и отдельный remaining freshness budget. Просроченный результат допустимо оставить для offline evidence с признаком stale, но нельзя применять как свежее состояние. Это локальное чтение работы соседа, не независимое сетевое подтверждение. Архивирование encoded source и пропуск inference frame разделены: latest-frame scheduling не должно уничтожать доказательство.

Точное совпадение:

* В JPEG+metadata WS один binary message содержит length/header + JPEG + detections того же `frame_id` (или пара сообщений с явным pair ID и bounded assembler). Рисовать image и boxes в один canvas pass после decode обоих; старый async JPEG decode не должен перезаписать более новый кадр. Бounded mailbox и drop policy избегают возрастающей задержки. Если нужно сохранить все inference results, сохранять их отдельно от live mailbox.
* В WebRTC original path нужно получить и проверить mapping source PTS/frame_id → outgoing RTP timestamp/SSRC/epoch → rVFC metadata. Mediator/reencode может сменить шкалу и frames. Совпадение «ближайшее время» допустимо только с объявленным max skew и метрикой; stale metadata скрывать/помечать. Результат, пришедший после показа source frame, нельзя наложить на уже прошедший кадр без задержки видео/повторного просмотра.
* Если camera 25 FPS, inference 5 FPS, не растягивать один box на все промежуточные кадры как measured result. Tracking/interpolation должны быть названы отдельно и иметь свой timestamp/age.

Геометрия: для letterbox `r=min(Wnet/Wsrc,Hnet/Hsrc)`, offsets `px,py` фактически применённого preprocess; `x_src=(x_net-px)/r`, `y_src=(y_net-py)/r`. Для viewport `object-fit:contain`, `s=min(Wcss/Wsrc,Hcss/Hsrc)`, `ox=(Wcss-sWsrc)/2`, `oy=(Hcss-sHsrc)/2`; `x_css=ox+s*x_src`, `y_css=oy+s*y_src`. Для `cover` вместо min — max, появляются обрезки. Crop offset, rotation, flips, pixel aspect ratio и DPR canvas учитывать явно; хранить применённую transform matrix и inverse, а не восстанавливать её из предположений. Формулы предполагают стандартные square pixels/отсутствие дополнительных transforms. Между sub/main одинаковое отношение размеров не гарантирует одинаковый FOV.

## Факты и проектные следствия: тревоги

### W1-05-F21 — DOC: SSE reconnect не равен durable replay

S15: EventSource получает UTF-8 `text/event-stream`; `id` задаёт last event ID, браузер передаёт Last-Event-ID при восстановлении; `retry` в ms меняет reconnect delay; heartbeat comment примерно каждые 15 s помогает против legacy proxy timeouts. INFERENCE: сервер обязан сам хранить последовательность событий и выполнить replay после cursor; одного EventSource недостаточно для гарантии. Держать одно multiplexed connection на страницу, history API для полного resync, конечный срок replay. Если cursor старше retention — вернуть/показать resync condition, а не молча потерять тревоги. EventSource constructor не предлагает произвольного Authorization header; same-origin cookie/session или другой обоснованный способ auth согласовать заранее.

### W1-05-F22 — DOC/INFERENCE: WS не хранит события после disconnect

S16 `bufferedAmount` описывает bytes, поставленные браузерным `send` в очередь и ещё не переданные сети; это не receiver ACK. Стандартный WS API не обеспечивает наш durable incident history/replay. Для server→browser смотреть очереди самого сервера, а не browser bufferedAmount, который относится к исходящему browser traffic. Проект: WS для двусторонних команд/частых обновлений, SSE для одностороннего event feed, REST для acknowledge и истории. Оба транспорта нуждаются в event_id, sequence/cursor, dedup и восстановлении состояния. Подтверждение UI renderer и подтверждение оператором — разные записи.

### W1-05-F23 — INFERENCE: durable outbox на границе event/уведомление

В одной DB transaction сохранить incident и outbox rows по нужным каналам; иначе crash между DB commit и `send()` теряет уведомление или создаёт «призрачную» тревогу. Ключ job `(event_id, channel, recipient, message_kind/version)` уникален; worker читает persisted pending/retry rows, ставит попытку/lease, записывает result/external message ID, backoff и next_attempt. На 429 учитывать provider retry hint, на временный timeout повторять с exponential backoff+jitter, permanent auth/recipient error выводить в failed/dead state. Отдельно ограничивать общую и per-recipient частоту.

Сетевой timeout после принятия сообщения провайдером даёт uncertain outcome. Если API не предоставляет idempotency key с доказанной семантикой, exactly-once не обещать: возможен дубликат. В тексте event_id/ссылка помогут человеку и приложению распознать его, но не создадут provider-side дедупликацию. UI может обновлять одну карточку по event_id. Failed outbox не удаляется без следа. Pending clip job и pending notification — разные state machines.

Метрики разнести: `event_decided`, `event_committed`, `outbox_attempted`, `provider_accepted`, `browser_rendered`, `operator_acknowledged`. Длительность между разными host clocks не вычитать без синхронизации/оценки погрешности. Вебсокет send и Telegram Message response не означают прочтение человеком.

### W1-05-F24 — DOC: Telegram бесплатные лимиты не единый «30/s»

S17 FAQ: избегать более 1 сообщения/с в один чат; группы — не более 20/мин; рассылка — примерно 30/с бесплатно. Упомянуты paid broadcasts с иными условиями; для MVP на них не рассчитывать. S18 `sendVideo`: video до 50 MB, поддерживаемый Telegram-клиентами MPEG4, on success возвращает Message; `ResponseParameters.retry_after` — секунды до повторения после flood control. Это текущие server docs, не измеренные гарантии latency. Ссылка на защищённую карточку + thumbnail обычно быстрее/проще отправки полного clip; приватный production URL не будет автоматически доступен получателю или Telegram fetcher. Не класть camera credentials в ссылку.

### W1-05-F25 — DOC: MAX изменил endpoint/auth

S19 Обзор: направлять запросы на `platform-api2.max.ru` вместо `platform-api.max.ru`; требуется доверие сертификату Минцифры по документации. Query token больше не поддерживается, нужен `Authorization: <access_token>`. Токен получают при создании бота на business platform/через указанный business workflow. Это не доказательство, что команда уже имеет право/аккаунт/работающий токен, и не основание отключать TLS verification. Проверка регистрации/доступа относится к первому часу, делать MAX обязательным единственным каналом до этого рискованно.

### W1-05-F26 — DOC: MAX send limit и attachments

S20 POST `/messages`: текст, image/video/audio/file и inline keyboard/share поддержаны документацией; лимит до 2 сообщений/с в один диалог, группу или канал; превышение требует очереди/задержки. Отдельный общий limit из прочитанных страниц не установлен. Нет достоверного p50/p95 времени доставки/доказательства read receipt. Не переносить лимиты Telegram на MAX. No messages sent; медиазагрузка не проверена.

## Неизвестные, отрицательные результаты и адресная передача

* **W1-05-Q01, P0, полный кейс/operator_product:** какое evidence окно и максимальная задержка требуются; хранится ли весь оригинал или только events; требования к unredacted evidence и срокам. Меняет ring depth, main/sub selection и storage. Правовые требования здесь не устанавливались.
* **W1-05-Q02, P0, камера/практика:** реальный codec/profile, B-frames, IDR/GOP, bitrate VBR, main/sub crop и timestamps. Источники объясняют механизмы, не параметры неизвестной камеры. Получить ffprobe и короткую recording sample. Меняет copy/reencode и exact transform.
* **W1-05-Q03, P0, LinQ integration/V04:** worst-case frame→result delay, пропуски/out-of-order, возможно ли вернуть исходный frame_id/PTS; есть ли собственный host код. Наш контракт не приписывает LinQ такую возможность; adapter должен сохранять correlation самостоятельно. Меняет pre-roll depth и view mode.
* **W1-05-Q04, P0, frontend/media:** сохраняется ли source PTS→outgoing RTP mapping для выбранной версии MediaMTX/go2rtc, и предоставляет ли target browser нужные rVFC fields. * **W1-05-Q05, P0, network/deploy:** есть ли разрешённый прямой TCP/UDP media port, TURN и сертификат/домен на площадке. STUN не решает все NAT; HTTPS proxy не туннелирует media автоматически. E03 закрывается только в реальной среде.
