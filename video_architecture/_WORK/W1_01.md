## Ответ, который меняет решение

**[INFERENCE]** Основной интерфейс приложения следует отделить от способа доступа: источник → decode/preprocess → ограниченный inference adapter → результаты с идентичностью кадра → tracking/rules → события/UI. Сегодня нельзя зафиксировать размещение decoder или Linux runtime. Для интерфейсного API оставляем video state у команды; для собственного процесса на выданном сервере можно перенести приём сжатого видео, decoder и inference worker к LinQ, но только при проверенных CPU/codec/reachability/lifecycle. На ноутбуке Windows может остаться весь клиентский контур без местной установки LinQ SDK. Это маршрут подготовки, а не утверждение о Windows-совместимости runtime.

**[DOC/UNKNOWN]** Публичный сайт LinQ предлагает демо-тестовую среду, но не раскрывает протокол выдачи, SSH, контейнеры, квоты или гарантированную доступность RTSP. `/sol` содержит gate регистрации и верификации для скачивания ПО; это не спецификация доступа к устройству. Нельзя проектировать общий сервер как уже выданный. Соседний `linq_platform` пришёл к тому же ограничению; новое чтение первичного сайта не устранило его.

**[INFERENCE]** Compose пригоден для наших обычных сервисов. Контейнер с proprietary runtime — отдельное условное развёртывание, а не обязательный контейнер всего проекта. Если поставщик дал рабочий процесс/venv/image, сначала сохранить его и интегрироваться через адаптер; не тратить первые часы на перепаковку драйверов. `healthcheck` и `restart` решают разные задачи: health status сам по себе не создаёт перезапуск зависшего inference worker. Offline image bundle позволяет поднять клиентский сервис без registry, но не делает удалённый обязательный LinQ доступным без сети.

## Новые факты и границы

### LinQ: проверка именно доступа и host/decode

**W1-01-F05 [CLAIM, S02/S03, прочитано]**. Homepage предлагает заказать демонстрацию и получить тестовую среду. `/tech` описывает преобразование модели/квантование/граф/TPU и вычислитель int8; это не описание сетевого сервиса. Ни это предложение, ни технологический список не устанавливают выданные команде протокол, CPU, codec, endpoint или способ загрузки модели. [LinQ](https://lin-q.ru/), [technology](https://lin-q.ru/tech).

**W1-01-F06 [CLAIM, S04, прочитано]**. В разделе HPS опциональны платы аппаратного **видеокодирования** H.264/H.265. В разделе HX вычислитель LinQ H соседствует с RK3588; перечисленные возможности decode находятся в блоке CPU, отдельно от TPU. Это не основание приписать decoder чипу LinQ H, любой PCIe-плате или удалённому стенду. Заявленные максимумы кодеков не измеряют наш многопоточный pipeline. [HPS/HX](https://lin-q.ru/sol).

**W1-01-F07 [DOC/CLAIM, S04, прочитано]**. ПО на `/sol` предоставляет Python 3.8 API и CLI для quantize/compile; download требует регистрации **и** верификации. Это не доказательство текущего Python runtime стенда и не grant на устройство. В этой ветке формы не отправлялись. [Software section](https://lin-q.ru/sol).

### Compose: конкретные эксплуатационные ловушки

**W1-01-F08 [DOC, S05, прочитано]**. `healthcheck` определяет состояние healthy; `restart` применяется при termination. `init: true` помогает передавать сигналы/reap процессов. `image` поддерживает digest. `pull_policy: never` требует локальный cache, иначе fail; `latest` может подтягиваться даже при missing. Для file-backed secrets `uid/gid/mode` в Compose игнорируются из-за bind mount. [Service reference](https://docs.docker.com/reference/compose-file/services/).

**W1-01-F09 [DOC, S06, прочитано]**. Обычный `depends_on` задаёт порядок, а running не означает ready. `condition: service_healthy` ждёт успешную проверку dependency при старте. Вложенное `depends_on: ... restart: true` относится к явной Compose операции над dependency, например `docker compose restart`, и не является универсальным наблюдателем её падений. Приложение всё равно должно переподключаться к БД/сервису самостоятельно. [Startup order](https://docs.docker.com/compose/how-tos/startup-order/).

**W1-01-F10 [DOC, S07, прочитано]**. `on-failure[:max-retries]` действует на ненулевой exit code и не восстанавливает контейнер только из-за рестарта daemon. `unless-stopped` сохраняет намеренное выключение. Документация отдельно описывает successful start минимум 10 секунд перед действием политики и поведение manual stop. Эти условия надо проверить на поставленной версии, а не считать policy лечением любого сбоя. [Restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/).

**W1-01-F11 [DOC + INFERENCE, S08/S05, прочитано]**. Compose предоставляет secrets только перечисленным сервисам как файлы `/run/secrets/<name>`; файловый bind mount поддерживается здесь для Linux containers. `_FILE` — соглашение конкретных образов, не автоматическая функция любого приложения. Отсюда наш выбор: camera password читает ingest, LinQ token — adapter, private TLS key — ingress; не общий `.env`, не image layer и не git. File-backed Compose secret не следует описывать как зашифрованное хранилище: исходный файл и резервные копии защищает host. [Secrets guide](https://docs.docker.com/compose/how-tos/use-secrets/).

**W1-01-F12 [DOC, S09/S10, прочитано]**. `docker image save -o images.tar IMAGE...` сохраняет image repository/layers/tags; `docker image load -i images.tar` восстанавливает images/tags, включая поддержанные сжатые архивы. Platform filtering требует Docker API 1.48+, а выбранная архитектура должна уже присутствовать в локальном image store/archive. Не переносить этот новый флаг на произвольную выданную Astra/Docker версию. [Save](https://docs.docker.com/reference/cli/docker/image/save/), [load](https://docs.docker.com/reference/cli/docker/image/load/).

**W1-01-F13 [DOC, S11, прочитано]**. Для запуска готовой поставки есть `docker compose up -d --no-build --pull never`; `--wait`/`--wait-timeout` ждут running/healthy и не доказывают правильность модели или LinQ execution. Все флаги сверять `--help` фактической версии. [Compose up](https://docs.docker.com/reference/cli/docker/compose/up/).

**W1-01-F14 [DOC, S12, прочитано]**. Документация ALSE 1.8 различает privileged и рекомендуемый rootless режим, при котором daemon/containers не получают host root. В таблице одновременно есть `docker-compose 1.29.2-3+b1` и `docker-compose-v2 25.0.5.astra2+ci3`; это **версии пакетов Astra**, не доказательство upstream Compose 25 или гарантии всех current Docker docs features. [Astra Docker](https://docs.astralinux.ru/latest/guide/virtual/docker/).

**W1-01-F15 [DOC, S13, прочитано]**. Страница Docker-compose-v2 рекомендует его начиная с обновления 1.8.3 и указывает пакет `docker-compose-v2`; предварительные шаги отличают старый `docker-compose`. Выбор v2 и реальный `docker compose version` важнее бездумного переноса `version: "3"` из примера. [Astra Compose v2](https://docs.astralinux.ru/latest/guide/virtual/docker/compose2/).

**W1-01-F16 [DOC, S14, прочитано]**. В Astra есть отдельная настройка Docker на пониженном уровне целостности; по документации она не включена по умолчанию. Для privileged Docker дан отдельный рецепт memory cgroups, изменяющий параметры загрузки и требующий reboot. Это инструкция для администратора конкретной ОС, **не наша команда на общем сервере**. Мандатные метки, mounts, cgroups и device permissions — самостоятельные integration gates. [Astra restrictions](https://docs.astralinux.ru/latest/guide/virtual/docker/restrictions/).

### Камеры и промышленная сеть

**W1-01-F19 [DOC, S17, July 2026]**. Axis рекомендует отдельную учётную запись клиента с ограниченными правами; HTTPS вместо незащищённого доступа, при его отсутствии Digest вместо Basic. Видеозащита рассматривается отдельно: SRTP/RTSPS поддерживается Axis начиная с AXIS OS 7.40 при поддержке VMS; administrative traffic должен защищаться HTTPS отдельно. Следствие: authentication/Digest не означает шифрования видео, HTTPS web interface не означает защищённый RTSP stream. Возможности Axis нельзя перенести на неизвестную камеру: проверяется camera firmware + client/relay. [Axis hardening](https://help.axis.com/en-us/axis-os-hardening-guide).

**W1-01-F20 [DOC, S18/S19, final r3 September 2023]**. NIST §6.2.1.3 предлагает разделение по функции/расположению физическими switches либо VLAN и разрешение явных необходимых потоков через gateways/firewalls после карты потоков. §6.2.1.4.4 рассматривает MFA как best practice удалённого доступа к OT с учётом возможностей компонентов. Это архитектурная рекомендация, не сертификат соответствия IEC 62443. На landing 21.09.2026 уже указана initial public draft Revision 4; использован final r3, а не присвоенный draft статус final. [NIST final](https://doi.org/10.6028/NIST.SP.800-82r3), [version status](https://csrc.nist.gov/pubs/sp/800/82/r3/final).

**W1-01-F21 [DOC/INFERENCE, S20]**. Docker volumes — самостоятельные persistent host stores с отдельными backup/restore процедурами. Вместе с F12 это означает: image tar не является полной резервной копией БД событий, clips, mounted models/config/secrets. Воспроизводимая поставка должна перечислять эти артефакты отдельно. [Volumes](https://docs.docker.com/engine/storage/volumes/).

**W1-01-F22 [DOC/INFERENCE, S21]**. Docker отмечает daemon attack surface и связь privileged management с host access; rootless помещает daemon и containers в user namespace. Для нашего UI/API нельзя пробрасывать Docker socket ради перезапуска worker. Предоставление `--privileged` или всех `/dev` не считать обычной частью переносимого приложения. ### Порядок выбора за первые минуты доступа

1. **Control plane**: что можно загрузить/скомпилировать/выбрать и как обновить собственную версию модели? Выданный endpoint готовых моделей не автоматически достаточен для PPE. Сохранить immutable model/artifact/config hashes и baseline golden input.
2. **Execution grant**: свой process/container либо managed call/job? Узнать allowed own restart и запрет на reset shared device. Не требовать SSH, если custom service всё покрывает.
3. **Payload + outputs**: encoded image/tensor/video, размер, dtype/layout/batch, pre/post responsibility, detections/raw outputs/events и geometry. Получить minimal request, result и один подтверждённый terminal success.
4. **Network**: из какого направления разрешены TCP-сессии; доступ к localhost worker через разрешённый tunnel; upload bandwidth/RTT; camera URL с remote host может быть недостижим. Не публиковать камеры в интернет для обхода NAT.
5. **Lifecycle/quota**: max payload/batch/inflight/QPS, lease/TTL/session, очередь между командами, cancellation semantics, disk persistence, CPU/RAM, compiler quota. Протокол подтверждён инструкцией/ответом владельца и коротким тестом, не рекламой продукта.
6. Измерить полезный двухкамерный маршрут с реальной очередью и затем выбрать decoder placement. Ни успешный `ssh`, ни `docker ps`, ни device utilization по отдельности не подтверждают inference нашей NN на LinQ.

### Бюджет, который можно считать до доступа

**[INFERENCE, арифметика; не benchmark]**: для tensor `[1,3,640,640]` float32 размер `1×3×640×640×4 = 4 915 200 B`; при 10 sampled frames/s это `49 152 000 B/s`, или `393.216 Mbit/s` без transport overhead **на одну камеру**. Для uint8 — `1 228 800 B/frame`, `98.304 Mbit/s` при 10 fps; uint8 допустим только по input contract. Значения не требования кейса. JPEG требует измерить размер на actual frames и качество; compressed video — codec/decoder/network support. Host/queue latency не выводится из LinQ TOPS или PCIe bandwidth.

Для последовательного single-inflight запроса throughput ограничен `1 / T_roundtrip` frame/s; при concurrency `C` верхняя арифметическая граница `C / T_roundtrip`, лишь если нет других bottleneck/quota. `T_roundtrip` в секундах включает очередь и payload, а не только accelerator time. Это помогает соседям V04/V05 сравнить network placement, но не разрешает повышать C без поддержанного runtime contract.

## Упаковка для 45-часового окна

**[INFERENCE]** Разделить два deployment units: собственный service bundle (ingest/backend/UI, event storage и media process по фактическому выбору соседних ячеек) и один inference adapter, который бывает remote client либо worker на supplied host. Изменение access mode не должно менять event schema, tracker или frontend. Broker/Kubernetes не нужен только ради remote LinQ: он не исправит внешнюю quota. Если соседняя V08 выберет модульный монолит, этот интерфейс остаётся межмодульным; IPC/network вводится там, где проходит actual host boundary.

Состав reviewable release bundle: исходный commit; `compose.yaml`/override для режима; Dockerfiles и lock dependencies; полный перечень image tags/IDs/digests и platform; model manifest/artifacts/golden samples; camera/source config без passwords; миграция/инициализация БД; каталог clips с retention; local TLS CA/public cert и отдельно выдаваемый private key; operator runbook с проверкой sample-to-event; перечень secret files; примеры ответов actual adapter. Это перечень будущей реализации, не созданный здесь готовый продукт/код до хакатона.

Офлайн процедура на отдельном тестовом хосте, **предлагаемая, не выполненная**:

```text
# После online подготовки на разрешённой машине с нужными images:
docker image save -o images.tar team/backend:release team/worker:release
# На целевом Linux host после проверки archive hash и наличия engine/compose:
docker image load -i images.tar
docker compose up -d --no-build --pull never
```

Имена images иллюстративны, команды основаны на S09–S11. Нужны все транзитивные сервисы, не только два примера. Bundle hash проверяет целостность передачи, а не происхождение/подлинность без доверенного канала. Digest pin и загруженный tar следует сверить на чистом target: `image ID` и `RepoDigest` не взаимозаменяемы, не обещать, что любой архив автоматически восстановит все registry metadata. Модели и manifests при bind mounts переносятся отдельно; volume/DB backup/restore отдельно. На запуске нет `pip install`, `apt`, model auto-download или frontend CDN. Engine/Compose/host driver тоже должны быть заранее разрешены и установлены из подходящей поставки, но их наличие не входит магически в image tar.

Windows development не определяет целевую ОС: Linux containers могут служить средой собственных сервисов; native LinQ compile/runtime/ISA остаются в supplied Linux environment до получения support matrix. Перенос x86-64 image на ARM HX нельзя считать рабочим без подходящих image/native artifacts и проверки. Образ не несёт kernel driver target host.

### Health/restart политика приложения

- **Liveness** проверяет, что наш процесс/event loop отвечает; **readiness** сообщает актуальную пригодность inference/model/зависимостей. Потеря remote LinQ делает inferencing unavailable, но не должна запускать бесконечный restart API/БД, которые могут продолжать показывать сохранённые события.
- **Progress** измеряет последний successful frame/result по каждой камере, age, inflight, pending jobs и quota backoff. Живой HTTP не доказывает продвижение pipeline. Health probe не должен загружать NN в общий слот или создавать бесконтрольные inference jobs.
- Worker остановить admission → дождаться documented terminal/drain → закрыть собственную session → завершиться. Срок app deadline не доказывает освобождение native buffers/job; shared reset только оператору владельца. Отдельный local process supervisor не следует смешивать с competing Docker supervisor над одним процессом.
- `restart: unless-stopped` — возможный выбор для собственных обычных сервисов; bounded `on-failure` может быть у экспериментального worker, если supported lifecycle позволяет. Отсутствие automatic restart на `unhealthy` необходимо компенсировать нашим watchdog/exit policy только для разрешённого safe failure, не сбросом общей платы.

### Astra integration gate

До обещания «развёртывается на Astra» зафиксировать edition/update, kernel, ISA, Docker/Compose фактические версии, privilege/rootless mode, мандатный профиль, permissions на models/clips/secrets/device и supplied driver/runtime pairing. Затем по отдельности: обычный web/container start; persistent event write/restart; camera decoder и codec; LinQ worker import/load/run; полный результат/geometry/event. Успех UI в Astra container не устанавливает driver support; успех HP на Server в новости не устанавливает HX/ARM, а успех Embedded не устанавливает наш x86 сервер. Не отключать мандатную защиту или reboot shared host как «починку Docker». Запросить согласованную конфигурацию владельца.

## Достаточная граница безопасности без выдуманной сертификации

**[INFERENCE, применение F19/F20/F22]** Целевая схема: camera VLAN/segment → ограниченный ingest/gateway → application segment → разрешённый outbound remote LinQ channel. Browser проходит через authenticated HTTPS application endpoint; не получает camera credentials, administrative URL или LinQ token. DB/queue/worker порты не публикуются наружу без необходимости. Management/VPN/jump host — отдельный административный путь с MFA там, где поддерживается; пользовательский и machine-to-machine доступ имеют разные credentials.

Список разрешённых потоков конкретизируется по inventory, а не правилом «любые порты внутри VPN»: ingest → camera только необходимые streaming/control protocols; backend → LinQ endpoint; backend → storage; ingress → backend; администратор → management. Port 554/TCP относится к типичному RTSP, RTP/UDP может использовать динамические порты; не открыть весь UDP «чтобы заработало». Если camera/client умеют безопасный stream transport, проверить его отдельно от HTTPS управления. Если не умеют, изолированный локальный участок и защищённый gateway-to-remote tunnel ограничивают область plaintext; это не end-to-end encryption камеры до worker.

В prototype достаточно явно реализовать защищённый единый вход; разграничить viewer/operator/admin так, чтобы viewer не мог менять camera/rules/config и выгружать произвольный файл. Проверять auth у clip/event endpoints и stream subscription, а не только скрывать кнопку UI. URLs камеры, пароли, bearer tokens и query strings не должны попадать в frontend payload/logs/trace. Для clip filenames использовать внутренние IDs и controlled lookup, не путь из запроса. Retention, файловые разрешения и server-side authorization защищают клипы; TLS защищает передачу, а шифрование host storage/ключей — отдельный механизм и отдельная проверка восстановления.

VPN/TLS не решают доверие к стороннему inference server, срок хранения upload или доступ других участников. Минимизировать передаваемые данные до нужного payload; спросить remote retention, tenant isolation, log contents и delete policy. Не хранить camera credentials на чужом server, если выбран tensor/frame API и ingest остаётся локальным. Этот принцип уменьшает последствия компрометации worker и упрощает demo setup. Никаких заявлений о соответствии IEC 62443 или сертифицированном ПАК без actual scope не делать.
