## Решение, которое можно принять сейчас

**INFERENCE W1-02-F01.** Для 45 часов принять базу: MediaMTX как общий RTSP ingress/разветвитель и имитатор камер; отдельный worker чтения/декодирования на камеру; внутри worker PyAV/FFmpeg с ограниченными timeout и непрерывным чтением, после decode — слот последнего кадра; LinQ adapter потребляет кадры с назначенной частотой. OpenCV оставить для обработки массивов и быстрого smoke test, не назначать его `CAP_PROP_BUFFERSIZE=1` механизмом надёжности. Основания: F02–F15. GStreamer предпочтителен, если в команде уже уверенно используют его bus/state machine и если нужен управляемый аппаратный pipeline; осваивать весь GStreamer впервые во время 45 часов — дополнительный интеграционный риск (наш вывод, не измерение).

Необязательно ставить decode рядом с LinQ. При API кадров decode остаётся на стороне команды. При SSH на хост и разрешённой установке пакетов/доступе к RTSP можно перенести весь ingress/decode туда и передавать сжатое видео; CPU/GPU/NPU на том хосте неизвестны. Наличие RTX 4070 у команды позволяет проверить NVDEC как локальный decode, но не доказывает CUDA на удалённом хосте и не заменяет обязательный inference на LinQ. При WAN передаче размер выходного изображения и формат согласуются с V04; нельзя декодировать в BGR и бессистемно отправлять весь исходный FPS.

## Факты и инженерные следствия

### FFmpeg: TCP, UDP, timeout и reorder

**W1-02-F02 — DOC, S01, прочитано.** RTSP demuxer умеет RTP через UDP и TCP interleaved; HTTP/HTTPS tunneling — отдельные варианты. `rtsp_transport tcp` задаёт TCP, `rtsp_flags prefer_tcp` лишь предпочитает его, когда доступен. `reorder_queue_size` измеряется пакетами; `buffer_size` — байтами socket buffer; `max_delay` — не тот же параметр. UDP reorder отключается при `max_delay=0`. Current docs задают RTSP `timeout` как TCP socket I/O timeout в микросекундах, `listen_timeout` как секунды ожидания входящего подключения (включает listen mode). Общий `rw_timeout` также µs. Следствие: timeout ограничивает операцию, не выполняет полноценный reconnect и не ограничивает end-to-end age кадра. TCP удобен в сети с неизвестным NAT/firewall, но транспорт сам не гарантирует свежесть; UDP допускает потери, поэтому минимальная буферизация меняет устойчивость картинки.

**W1-02-F03 — CODE, S02, не выполнено.** В n8.0 option `timeout` записывается во внутреннее поле `stimeout`, default0; внешнего AVOption `stimeout` в прочитанной таблице нет. `listen_timeout` default−1; `reorder_queue_size` default−1 (авто). TCP URL получает `?timeout=...`; `udp_read_packet` также использует stimeout в poll loop и возвращает ETIMEDOUT. Это важное уточнение к краткому тексту DOC, называющему timeout TCP: в конкретной n8.0 реализации он участвует и в UDP ожидании. Не переносить этот вывод на все версии/обёртки. В популярных старых ответах 2014 года встречается `-stimeout`; перед применением проверять **именно установленный** `ffmpeg -h demuxer=rtsp`. FFmpeg CLI версия может отличаться от встроенного FFmpeg в PyAV/OpenCV.

Предлагаемый начальный **smoke test**, FFmpeg n8.0, числа — проектные, не оптимальные:

```sh
ffmpeg -hide_banner -rtsp_transport tcp -timeout 5000000 -i rtsp://HOST:8554/cam1 -map 0:v:0 -an -f null -
```

Для сравнения UDP:

```sh
ffmpeg -hide_banner -rtsp_transport udp -timeout 5000000 -max_delay 100000 -reorder_queue_size 64 -i rtsp://HOST:8554/cam1 -map 0:v:0 -an -f null -
```

Здесь 5 000 000 µs=5s; 100 000 µs=100ms и 64 пакета — старт эксперимента. Сначала убедиться, что сеть/камера умеет выбранный транспорт; затем варьировать задержку, а не применять `nobuffer/low_delay/probesize=32/analyzeduration=0` пачкой без теста. Слишком малый probe может лишить декодер параметров потока. `-f null` всё ещё предполагает декодирование при выбранном стандартном output codec; это не тест одного demux.

### GStreamer: три независимых очереди, а не один latency

**W1-02-F04 — DOC, S03, прочитано.** rtspsrc сам поднимает RTP manager с reorder/jitter/RTCP. Default transport negotiation UDP unicast → UDP multicast → TCP; ограничивается `protocols`. `latency` — миллисекунды, default2000; `drop-on-latency` defaultfalse ограничивает jitterbuffer заданным latency. `tcp-timeout` — µs, default20 000 000; `timeout` — µs ожидания UDP до попытки TCP, а не общий read timeout. `GstRTSPSrcTimeout` в docs поддержан только для RTCP-triggered timeout. Нельзя полагаться только на это сообщение для обнаружения зависшей камеры: нужен watchdog поступления декодированных кадров и обработка bus ERROR/EOS.

**W1-02-F05 — DOC, S03+S06, прочитано.** Долгий TCP stream может накапливать задержку из-за drift RTP clock относительно client clock. `tcp-timestamp=true` timestamp-ит RTP по времени получения и обходит этот механизм drift; при burst-отправке сервером способен создать другие проблемы. GStreamer release1.24.10 (2024-12-03) содержит backport этой возможности; прочитанная текущая API-страница точно указывает since1.24.10 и defaultfalse. Это **режим для сравнения в soak test**, не универсальное включение. Проверить доступность `gst-inspect-1.0 rtspsrc` в установленной версии.

**W1-02-F06 — DOC, S04, прочитано.** `queue` создаёт отдельный поток. По умолчанию блокируется при первом из лимитов 200 buffers / 10MB / 1second. `leaky=downstream` (2) выбрасывает старые buffers; `upstream` (1) — новые. Для latest-frame аналитики после decode логичен downstream. Задать `max-size-buffers=1 max-size-bytes=0 max-size-time=0` — значит лимитировать кадрами и выключить другие лимиты, а не оставить тройной default. Dropping encoded buffers перед decoder может разрушать межкадровые зависимости: raw leaky queue ставить **после** decoder. Jitter drop до decode — другая, сознательная плата потерями изображения.

**W1-02-F07 — DOC, S05, прочитано.** `appsink` имеет собственную очередь даже после `queue`; `max-buffers=0` означает unlimited. Медленное извлечение raw samples способно съесть память. Старый интерфейс `max-buffers=1 drop=true` выбрасывает старые; с1.28 `drop` deprecated в пользу `leaky-type`, тоже since1.28. Нельзя скопировать `leaky-type` в старую GStreamer1.24 и считать pipeline переносимым. `try-pull-sample` даёт timeout; приложение должно освобождать GstSample/GstBuffer и корректно делать unmap.

Предлагаемый H.264 CPU pipeline для интеграции с appsink (набор элементов проверить через gst-inspect; **не запущен**):

```text
rtspsrc location=rtsp://HOST:8554/cam1 protocols=tcp latency=100 drop-on-latency=true tcp-timeout=5000000
 ! rtph264depay ! h264parse ! avdec_h264
 ! queue max-size-buffers=1 max-size-bytes=0 max-size-time=0 leaky=downstream
 ! videoconvert ! video/x-raw,format=BGR
 ! appsink max-buffers=1 drop=true sync=false
```

`latency=100` — гипотеза для теста. `sync=false` снимает ожидание sink clock; не устраняет encoder delay, jitter, decode reorder и накопление вне appsink. Для H.265 нужны h265 depay/parser/decoder; наличие plugin и поддержка профиля — отдельно. CPU videoconvert/BGR может стать дороже собственно аппаратного decode. Для production raw latest-frame pool лучше одной из нескольких очередей; callback appsink должен быстро передать владение/ссылку и вернуться.

### OpenCV: почему CAP_PROP_BUFFERSIZE не является настройкой RTSP

**W1-02-F08 — DOC, S07, прочитано.** `CAP_PROP_OPEN_TIMEOUT_MSEC` и `READ_TIMEOUT_MSEC` — **open-only**, применимы к FFmpeg/GStreamer backend; передаются params в constructor/open. `CAP_PROP_HW_ACCELERATION` тоже open-only и backend-specific. Работа свойства зависит от backend/драйвера/сборки. Практика `cap.set(READ_TIMEOUT...)` после open не равна настройке timeout. Нужно логировать `cv2.__version__`, `getBuildInformation`, `getBackendName`/CAP_PROP_BACKEND, а не просто версию pip пакета.

**W1-02-F09 — CODE, S08, прочитано.** `CvCapture_FFMPEG::setProperty` в4.13.0 обрабатывает POS_MSEC/FRAMES/AVI_RATIO, FORMAT и CONVERT_RGB; default возвращает false. **BUFFERSIZE не обработан.** Нет основания рекомендовать `cap.set(CAP_PROP_BUFFERSIZE,1)` для RTSP+FFmpeg как исправление задержки. Установленный другой backend может иметь другое поведение. `read`/`grabFrame` поддерживают decoder state и вызывают FFmpeg read/decode, поэтому цикл «sleep1s, read один кадр» отстаёт от live source, если чтение не продолжается независимо.

Проект smoke test на соответствующей сборке, **не исполнен**:

```python
cap = cv2.VideoCapture(url, cv2.CAP_FFMPEG,
    [cv2.CAP_PROP_OPEN_TIMEOUT_MSEC, 5000,
     cv2.CAP_PROP_READ_TIMEOUT_MSEC, 3000])
```

Это не обещание, что API вернётся ровно через3s в любом native состоянии; внешний watchdog процесса всё ещё полезен. Для демо отдельный reader постоянно забирает frames и перезаписывает latest slot. `grab` не считать бесплатным пропуском H.264 decode: реальная работа зависит от backend.

### PyAV: точные таймауты, PTS и границы контроля

**W1-02-F10 — CODE, S09, прочитано.** v16.0.1 `av.open(..., timeout=(open_s,read_s))` использует секунды, float/tuple, и interrupt callback с monotonic clock. Это **не µs FFmpeg AVOption**. `buffer_size` — байты Python I/O, действует при file-like object, не «сколько RTSP кадров копить». В input constructor timeout включается также вокруг `avformat_find_stream_info`; demux заново запускает read timeout перед каждым `av_read_frame`. Следствие: timestamp/age и watchdog — отдельные механизмы; поток, непрерывно выдающий старые кадры, не обязан нарушить read timeout.

**W1-02-F11 — INFERENCE на S09.** `timeout=(5,3)` не обязательно означает полное wall-clock open≤5s: `avformat_open_input` и find_stream_info имеют отдельные запуски таймера. Реконнект реализуется владельцем worker, который ловит EOF/error/timeout, закрывает container и создаёт новый. PyAV даёт доступ к Packet/Frame/PTS/time_base и поэтому удобнее raw pipe/OpenCV для непротиворечивого `camera_id,epoch,seq,source_pts,time_base,received_monotonic,decoded_monotonic`. PTS — временная шкала media, не автоматически UTC capture time.

**W1-02-F12 — DOC, S10, прочитано.** В v16.0.1 caveats предупреждают о reference cycles и позднем auto-close множества Containers: применять `with av.open(...)`/`Container.close()` при каждом reopen. Поддержка sub-interpreters неполная; C callbacks/логирование могут вызвать lockups. В **этой** версии документ говорит, что logging disabled by default; старые caveats могут описывать другую политику. Не запускать native decoder в произвольном WSGI sub-interpreter и не удерживать все ndarray кадры в истории.

**W1-02-F13 — CODE, S11, прочитано.** Утверждение «PyAV совсем не поддерживает hardware decoding» устарело для v16.0.1: HWAccel принимает cuda/qsv/vaapi/d3d11va и др.; поддерживается путь AV_CODEC_HW_CONFIG_METHOD_HW_DEVICE_CTX. `allow_software_fallback=True` — default. Поэтому запрос acceleration без проверки не доказывает фактический GPU decode; для эксперимента запретить fallback и логировать используемый stream/codec/hw config. Наличие кода не доказывает совместимость конкретного wheel, драйвера или zero-copy в NumPy. Decode/transfer/resize/цвет измерять отдельно.

Проект Python reader:

```python
# Основание интерфейсов: PyAV v16.0.1 S09; это пример, не выполненный код.
with av.open(url, timeout=(5.0, 3.0),
```

### MediaMTX и честная имитация RTSP камер

**W1-02-F14 — DOC/CODE, S12, прочитано.** Официальный пример v1.21.2 публикует бесконечный MP4 loop как RTSP: `ffmpeg -re -stream_loop -1 -i file.mp4 -c copy -f rtsp rtsp://localhost:8554/mystream`. Это клиент publisher, а не RTSP server внутри FFmpeg. `-re` ограничивает чтение примерно source rate; `-stream_loop -1` зацикливает файл; `-c copy` ремультиплексирует, сохраняя encoded stream. Проверять source codec/profile и timestamp continuity на границе loop. Повтор одинаковых изображений не означает stuck camera. Нужен в демо явный source_type=`looped_file`; это не live industrial camera.

**W1-02-F15 — CODE, S13, прочитано.** В config1.21.2 глобальные `rtspTransports` — список разрешённых transports server, per-path `rtspTransport` — транспорт pull от upstream; это разные ключи. Config имеет `runOnInit/runOnInitRestart`; допустим автоматический publisher. Server read/write timeouts default10s, они не определяют срок восстановления worker. Для нескольких потребителей MediaMTX может быть одним upstream connection к камере; actual fanout/limits проверить. Не утверждать, что MediaMTX автоматически транскодирует любой кодек ради браузера.

Рекомендуемый тестовый комплект (**проект**, FFmpeg n8.0 + MediaMTX1.21.2; media commands не запускались):

```yaml
# mediamtx.yml — минимальный fragment к полной конфигурации этой версии
rtspTransports: [tcp]
paths:
  cam1:
    source: publisher
```

```sh
ffmpeg -re -stream_loop -1 -i demo_h264.mp4 -map 0:v:0 -an -c:v copy -rtsp_transport tcp -f rtsp rtsp://127.0.0.1:8554/cam1
```

С TCP-only MediaMTX недостаточно убрать UDP только у reader: publisher тоже должен явно получить `-rtsp_transport tcp`. Для camera pull вместо publisher:

```yaml
paths:
  cam1:
    source: rtsp://CAMERA/PROFILE
    rtspTransport: tcp
```

Учётные данные и реальный URL задавать через секреты/локальную конфигурацию, не сохранять в публикуемые логи. Если исходный файл не подходит по кодеку/профилю, подготовить H.2648-bit yuv420p **один раз** до прогона, а потом loop+copy. Re-encode во время live теста смешивает нагрузку publisher и decoder. Не обещать одинаковую задержку MP4-loop и реальной камеры: у камеры отдельные sensor/encoder/GOP/buffering.

### ONVIF discovery не читает видеопоток

**W1-02-F16 — DOC, S14, прочитаны релевантные разделы PDF, не conformance test.** Discovery основан на WS-Discovery; его результат — device service address, после чего запрашивают capabilities/services. Это control plane. Non-discoverable mode допустим; отсутствие ответа discovery не доказывает отсутствие камеры. Для хакатона конфигурация RTSP URL вручную должна работать без discovery. Discovery через обычный интернет/NAT не следует считать гарантированным.

**W1-02-F17 — DOC, S15, прочитаны §4/5.1.1/5.2.1 и схема.** Media service получает URI выбранного profile (`GetStreamUri`), затем RTSP DESCRIBE/SETUP/PLAY открывают реальное media session; RTP/RTCP несут video/audio/metadata. RTSP control поверх TCP не означает, что RTP media тоже TCP: согласованный media transport может быть UDP. Это объясняет ситуацию «порт554 доступен, ONVIF видит устройство, а кадров нет» — проверять media negotiation, UDP/firewall/маршруты и credentials отдельными тестами. Документ17.12 старый, выбран ради стабильной схемы и не используется как перечень всех возможностей ONVIF2026.

### GOP и что на самом деле экономит sampling

**W1-02-F18 — DOC/CODE, S16, прочитано.** FFmpeg описывает streamcopy как путь без decode/encode, а фильтры fps/select получают **декодированные frames**. Уменьшение выдачи до5fps после decode не означает, что H.26425fps поток стоил как5fps. Межкадровый codec хранит reference state; FFmpeg H.264 skip logic различает non-reference NAL, а не позволяет произвольно пропустить9 из10 compressed packets без последствий. Конкретная экономия skip modes зависит от codec/profile/reference structure. `fps=5` экономит downstream conversion/inference/network, но не весь decoder input.

**W1-02-F19 — INFERENCE на S16/S17.** Полезны три разных регулятора: (a) camera substream с более низким resolution/FPS — снижает сеть и decode; (b) decoder `skip_frame` с учётом зависимостей — ограниченный компромисс; (c) sampling **после** decode — ограничивает inference, сохраняя decode continuity. Короткий GOP ускоряет доступ к независимо декодируемой точке после reconnect/loss, но может увеличить bitrate при том же качестве; B frames могут вносить reorder delay. Модель «максимальное ожидание следующей keyframe примерно G/f секунд» применима лишь при регулярных независимо доступных random-access точках с периодом G frames и source f fps; open GOP/I-frame не всегда эквивалент IDR. Это не точная latency guarantee.

**W1-02-F20 — DOC, S17, прочитано и сверено с новой веткой там, где указано.** Cookbook демонстрирует `stream.codec_context.skip_frame="NONKEY"`; предлагает использовать frame.pts, а не индекс output. Это даёт keyframe-only, а не произвольные5fps. Если GOP50 при25fps и равномерных keyframes, получится около0.5 keyframe/s (арифметика нашего примера), что может пропустить короткое нарушение. FRAME/AUTO threading увеличивает delay между packet input и frame output; SLICE threading работает внутри frame. Упоминание cookbook «примерно5× быстрее на машине автора» **не используется как benchmark**: нет полной аппаратной/медиаконфигурации, к тому же stable9.0.2. Измерять p95 age, а не только максимальный FPS.

### CPU, NVDEC, Quick Sync: что найдено количественно

**W1-02-F21 — MEASURED_BY_VENDOR + CLAIM, S18, не локально.** Table NVDEC Decoding Performance SDK13.0 даёт indicative **1920×1080, YUV4:2:0**, Windows11, SDK13.0; video clocks2160MHz для Ada: H.264903fps, HEVC1641fps, HEVC Main10 1520fps, AV1 1018fps. Это не benchmark полной видеоаналитики: нет конкретного SKU, bitstream/GOP, bitrate, CPU/driver, host transfer/resize/inference, stream count/latency distribution. Следовательно это полезная калибровка возможностей **архитектуры Ada**, а не обещание30 камер1080p30 на нашей RTX4070. Даже деление903/30=30.1 — только арифметический верхний ориентир по суммарному decode FPS при тех условиях, непригодный для SLA. NVIDIA указывает ограничение доступной памятью и производительностью; несколько decode contexts поддержаны. Число NVDEC engines может различаться между SKU, нельзя умножать табличный FPS на выдуманное количество.

**W1-02-F22 — DOC/CLAIM, S19, прочитано.** В **decode** таблице GeForce RTX4070 (Desktop) и RTX4070 Laptop перечислены Ada/5thGen, total NVDEC1. Для обычного H.2644:2:0 8bit и HEVC Main/Main10 поддержка есть; H.26410bit/4:2:2 не следует считать поддержанными по имени H.264. Таблица capability не говорит установленный VRAM. Нужно установить фактический SKU/driver/capabilities `nvidia-smi`, `ffmpeg -hwaccels`, `ffprobe` и пробным decode; драйверу/сборке требуется совместимость. NVENC concurrent-session limit из соседней **encode** таблицы не использовать как лимит NVDEC streams.

**W1-02-F23 — DOC, S20, прочитано.** NVIDIA guide рекомендует `-hwaccel cuda -hwaccel_output_format cuda` для удержания frames на GPU; `scale_cuda`/`scale_npp` позволяют resize без CPU download. Для сборки нужны nvcodec headers, minimum driver зависит от SDK; CUDA toolkit требуется для описанной сборки, но не для запуска готового binary. Это не означает, что любой pip OpenCV wheel использует CUDA. Путь decode→GPU-resize→download маленького image может снизить transfer; путь decode→download1080p→CPU BGR→resize добавляет копии. В данной системе итог передаётся LinQ, поэтому «zero-copy на RTX» заканчивается на границе передачи/CPU API; не называть всю систему zero-copy.

**W1-02-F24 — DOC/CODE, S21, прочитано.** Intel VPL — dispatcher/API для hardware decode/encode/processing; требуется отдельно runtime implementation. Intel перечисляет VPL GPU Runtime для IrisXe/newer и MediaSDK для legacy; таблица выбора зависит от поколения/OS/backend. Наличие Intel CPU само по себе не подтверждает доступный и включённый iGPU/QuickSync. Для ноутбука сначала инвентаризировать GPU, драйвер, Linux `/dev/dri` либо Windows API, codec profiles и поставку FFmpeg с qsv. `libvpl` на неизвестном LinQ host не предполагается.

**W1-02-F25 — UNKNOWN после поиска + отрицательные результаты.** Переносимое число «720p/1080p H.264/H.265 потоков на CPU-core» и decode-only QuickSync benchmark с полной конфигурацией для нашего неизвестного CPU **не установлены**. Искались official Intel sample_decode/oneVPL, FFmpeg benchmark decode и primary practitioner results. QuickSync Benchmarks авторов ironicbadger/cptmorgan показывает много чисел и CPU моделей, но About прямо определяет `h264_1080p_cpu` как CPU **encode**, а h264/hevc tests — hardware encode/transcode. Нельзя использовать его244fps i5-12400 как decode-only. Smelter приводит g4dn.xlarge4vCPU/T4 и g4dn.2xlarge8vCPU/T4, 720p24/1080p30 CPU/GPU stream count; это pipeline **decode+encode+composition**, а не per-core decode, без зафиксированной версии/bitstream здесь. Эти источники полезны для программы теста, их числа не используются в сайзинге. Не найденное число — не доказательство невозможности QuickSync; пробел закрывается локальным benchmark E02.

### Противоречия, эксплуатационные ловушки и статус доказательств

**W1-02-F26 — CLAIM пользователя issue / maintainer hypothesis, S24.** Issue#28638 открыт10марта2026: macOS Darwin25.2.0, OpenCV4.8.0+, Python3.9+, CAP_FFMPEG; автор сообщает silent corrupted frames спустя15–30s при MediaMTX-loop и медленном чтении, `read` возвращаетTrue. `BUFFERSIZE` вернулFalse. Contributor12марта просит сопоставимый FFmpeg тест и предполагает saturation buffer, если consumer не успевает. Это **не установленный bug всех версий и не наше воспроизведение**. Но это конкретный контрпример подходу «ret=True достаточно» и основание тестировать непрерывность, frame age/decoder errors и memory, а не периодически reopen без диагностики.

**W1-02-F27 — исторический CLAIM/CODE trace, S25+S09.** PyAV#584 от2019 описывает hanging open при камере с лимитом3clients и четвёртом соединении без media; PyAV7dev, Ubuntu18.04, libavformat57.83.100. Закрыт через#589. В v16.0.1 InputContainer timeout вокруг find_stream_info действительно присутствует. Нельзя повторять историческое «timeout PyAV сломан» как актуальную характеристику; сохраним конкретный failure injection — RTSP control отвечает, media не приходит. MediaMTX fanout может снизить число обращений к реальной камере, но лимит upstream отдельно проверить.

**W1-02-F28 — INFERENCE / проект восстановления.** Для отдельного camera worker использовать состояния CONNECTING→STREAMING→STALE/ERROR→BACKOFF→CONNECTING. Таймер отсутствия **нового decoded frame** отличается от network read timeout; дополнительно считать age выбранного кадра и никогда молча отправлять бесконечно прошлый frame. После error закрыть native container/pipeline; parent watchdog завершает зависший worker и перезапускает процесс. Backoff например0.5,1,2,4…до10s с jitter — проектные числа, не найденные оптимумы. Ошибку credentials/unsupported codec показывать как configuration error, не бесконечно маскировать reconnect. После восстановления увеличить `stream_epoch`, сбросить decoder state/latest-slot, уведомить tracker о gap; не склеивать одинаковые PTS из разных соединений/loops. PTS reset допустим, поэтому идентификатор кадра `(camera_id,epoch,seq)` надёжнее одного PTS.

Сохранять метрики по каждому stream: input/decode/selected FPS; last_frame_age_seconds; source PTS interval и reset count; reconnect count/reason; queue depth/drop count; worker RSS; CPU; для GPU decode utilization/memory/video clock. Отдельно source wallclock если он достоверно есть. Age=`now_monotonic−received_monotonic` — измеряет возраст **с момента приёма**, не sensor-to-alert latency. Использовать watermark/визуальные часы E01, чтобы обнаружить уже старые кадры на ingress.

### W1-02-E01: controlled RTSP и overload/failure/soak

Решение: оставить PyAV или перейти на GStreamer; TCP/UDP; лимиты/timeout/reconnect.

Вход: MediaMTX1.21.2, зафиксированный FFmpeg n8.0 binary+buildconf, H.2648-bit420 файлы720p/1080p25/30 с видимыми номером кадра/часами; отдельный H.265 образец, реальная камера при наличии. Не подменять этот тест произвольным YouTube видео без характеристик.

Шаги: loop publisher `-re -stream_loop -1 -c copy`; один reader без inference; потом медленный consumer (например200ms service time) при reader25fps; сравнить naive sleep-read, continuous-read/latest-slot и GStreamer bounded queues. Прервать publisher, закрыть MediaMTX, восстановить, заблокировать только media UDP, оставить control доступным; отдельно RTSP endpoint, отвечающий без frames. Для network impairment на Linux отдельный netem host/namespace, на Windows подходящий инструмент, способ зафиксировать. Продолжительность сначала10min, затем2h/ночь при выбранной конфигурации; локальная loop-нагрузка не заменяет реальные нестабильные камеры.

Измерять p50/p95/p99 frame age **по watermark**, RSS trend, decode/selected FPS, stale duration, reconnect recovery, wrong-epoch results, duration и число drops, ошибки decode. Сохранять команды, версии, configs, CSV trace, график RSS/age, лог transitions. Критерий команды задать перед тестом; пример SLO — после восстановления свежий кадр за timeout+backoff+GOP+startup с измеренными составляющими. ### W1-02-E02: decode-only и реальная цена получения input модели

Решение: CPU vs RTX NVDEC vs доступный QuickSync, сколько потоков разрешать и где resize.

Входы: фактические CPU/GPU/VRAM/OS/driver, power mode, cooling; ffmpeg version/buildconf, hwaccels/decoders, SDK/runtime; corpus H.264/H.265720p/1080p,25/30fps, профили8/10bit420, GOP и B frames. Не запускать одновременно publisher-transcode на том же CPU при изолированном decode benchmark. Использовать один и тот же corpus для всех backend, warmup, ≥3 повтора, без `-re` для максимального throughput.

Проект команд FFmpeg n8.0, перед запуском сверить поддержку в binary:

```sh
ffmpeg -hide_banner -benchmark -threads 1 -i input1080.mp4 -map 0:v:0 -an -fps_mode passthrough -f null -
ffmpeg -hide_banner -benchmark -hwaccel cuda -i input1080.mp4 -map 0:v:0 -an -fps_mode passthrough -f null -
```

Первая — software decode с одним decoder thread как отдельный baseline; дополнительно default/2/4 threads. Вторая не гарантирует чистый device-only path: этот режим может вернуть host frames и includes transfer; лог decoder/hw setup обязателен. Для полного GPU-resize path отдельный experiment `-hwaccel cuda -hwaccel_output_format cuda ... -vf scale_cuda=640:360,hwdownload,format=nv12` плюс нужная final conversion; это сохранение aspect ratio16:9 в примере, **не автоматически letterbox640×640**. Формат NV12 применим к выбранному8bit420, для10bit нужны соответствующие P010/совместимые форматы. QSV command подобрать по обнаруженному Intel поколению/runtime, не обещать один флаг для Windows/Linux всех лет.

Измерять frames/s, user/sys/real time, CPU seconds/frame, CPU saturation по ядрам, GPU decode/video clocks/memory, decode+download, decode+resize+conversion, bytes transferred/frame, RSS и p95 frame age при1/2/4/8 streams с real-time pacing. Считать `U_CPU = sum(cpu_seconds_decoder_i) / wall_seconds` в эквивалентных занятых ядрах, а не делить случайный FPS на число cores. Для capacity использовать число потоков, удерживающее нужный FPS и latency с резервом; не переносить isolated throughput линейно на500 камер. Успех доказывает только изученную конфигурацию файлов/сборки и не доказывает RTSP reliability или LinQ throughput.

### W1-02-E03: sampling/GOP как управляемая плата качеством

Решение: нуждается ли система в меньшем camera substream, допустим keyframe-only или нужно continuous full decode.

Сравнить один исходный25fps stream: full decode→select5fps; `skip_frame=NONKEY`; camera/publisher substream5fps; вариации GOP25/50/100, B0/обычный. Зафиксировать bitrate/quality и keyframe structure. Метрики CPU decode time, selected timestamp intervals, loss recovery, p95 age, доля пропущенных коротких контрольных действий. Передать одинаковые traces в violation_methods/evaluation. Успешное снижение CPU не доказывает сохранения detection recall; нужен анализ методами соседней темы.
