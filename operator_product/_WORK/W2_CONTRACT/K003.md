Новое DOC основание W2-CONTRACT-F01–F03 и источники с URL/версиями/локаторами — [SEARCH_LOG.md](SEARCH_LOG.md). Это авторская INF-модель MVP, не утверждение о рынке, действующем регламенте ХайТэк или запущенном ПО. Из W1 сохранены FindFace auto-ACK/overflow только в Alarm Monitor2.2.1, смысл Milestone ACK и различие исполнитель/проверяющий. ## Словарь [W2-CONTRACT-F05, INF]

Событие — кандидат наблюдения в определённом источнике/отрезке; это не юридически установленное нарушение. Мера — отдельное действие/задача, способная охватывать несколько событий. Одна мера не обязательна на каждый кадр или краткий эпизод. В карточке показывать небольшие независимые подписи, не одну шкалу «новый→закрыт».

| Поле | Значения и смысл | Источник изменения | Чего не означает |
|---|---|---|---|
| `review_result` | unreviewed; supported — наблюдение поддержано доступным материалом; false_detection; insufficient_evidence; rule_not_applicable; duplicate (с original_event_id) | Уполномоченный человек; каждая оценка имеет revision/origin/evidence | supported не юридический акт; false_detection не безопасный участок; duplicate не удаление |
| `delivery_attempt.state` | queued/sent/transport_accepted/failed/unknown; попыток и адресатов может быть несколько | Адаптер/system с сохранённым ответом, каналом, получателем | HTTP202 или отправка не human ACK и не прочтение |
| `acceptance` | unaccepted/accepted/declined/transferred_pending; отдельно текущий accountable_owner и intended_recipient | Только явное human действие, принятое сервером, либо запись ручного контакта с указанием регистратора и сообщившего | Машинный auto-ACK хранится как external_machine_ack, не устанавливает accepted |
| `hazard_observation` | unknown; observed_present; observed_absent; stale. Всегда as_of, scope, evidence/origin | Система или человек согласно источнику, без вывода о будущем | observed_absent в свежем кадре не устранение причины и не гарантия отсутствия вне кадра |
| `measure.execution` | proposed/open/in_progress/completion_reported/cancelled | Владелец меры/исполнитель; отчёт с действием и основанием | completion_reported не verification и не обучение модели |
| `measure.verification` | not_required/pending/accepted/rejected; policy+verifier+evidence | Человек с разрешением проверки, только если policy требует | not_required не «проверено», rejected не false_detection |

`supported` переводится в UI «наблюдение подтверждено проверяющим», `accepted` — «ответственность принята», `completion_reported` — «исполнитель сообщил о выполнении», `verification=accepted` — «выполнение проверено». Общего слова «подтверждено» без объекта нет. Завершение работы с карточкой — фильтр/резюме по политике, не пятый вид безопасности. Оно не должно скрыть открытые связанные меры.

Внешние vendor state/reaction сохраняются дословно в `external_status` с продуктом/версией и mapping_version. Из FindFace Completed допустимо вывести только «обработка оформлена комментарием»; из Milestone Closed — «тревога закрыта в VMS». Наши review/hazard/measure поля из них не вычисляются. Сменный пользователь должен иметь устойчивый local user/role ID; строка displayName из API не доказывает полномочие [F03].

## Минимальные сущности

`Event(event_id, source_ref, input_ref, observed_range, received_at, rule_id/version, model_ref, review_revision, hazard_observation, control_health, external_status)`; `ReviewDecision(decision_id,event_id,result,reason?,actor,evidence_ref,revision,supersedes?)`; `DeliveryAttempt(attempt_id,event_id|measure_id,recipient_ref,channel,state,times,external_ref,error?)`; `Acceptance(entity_id,owner_id,intended_recipient,accepted_by/at,server_revision)`; `Measure(measure_id,event_ids[],action,owner,execution,verification_policy,verification,evidence_ref)`; `Audit(change_id,entity,action,before/after,actor_origin,actor_id,recorded_at,asserted_at?,basis,revision,request_id)`. Это логическая схема, не предложение строить семь отдельных экранов/сервисов. Срок меры nullable, пока его не определил владелец; нормативный срок и таймер демо не придумываются.

`actor_origin` = human/system/external_system, origin системы не маскируется именем человека. Человеческая запись чужого устного сообщения сохраняет `recorded_by` и `reported_by`; она не представляется прямым кликом исполнителя. Role demo явно `demo`, без предположения действующего сотрудника предприятия. Каждое системное действие имеет rule/job/request reference. Исправления не стирают прежнее решение: новая revision с supersedes и причиной. При одновременном изменении сервер принимает одну revision, второму сообщает конфликт/нужду перечитать; это требование реализации, не найденная гарантия Milestone.

## Переходы и условия [W2-CONTRACT-F06, INF]

| Действие | Роль / допустимый вход | Результат и audit | Обязательность |
|---|---|---|---|
| Оценить материал | Reviewer, доступ к evidence; unreviewed либо новая revision | ReviewDecision human, result, refs, время, версия; insufficient разрешён без клипа | Не gate для всякого оперативного предупреждения |
| Послать предварительное предупреждение | System по согласованной policy; подходящий тип/health/freshness | DeliveryAttempt/локальное действие system; метка «предварительный сигнал», review без изменения | Только при разрешённом процессе, не защитный останов |
| Принять ответственность | Адресат с правом, актуальная серверная revision | human acceptance+owner; UI ждёт ответ сервера | Нет универсального auto-ACK; при offline «отправка принятия ожидает» |
| Отказаться / передать | Текущий owner или уполномоченный dispatcher; target известен | intended_recipient + transferred_pending, старый owner сохраняется до server accepted новой роли; decline с причиной возвращает явный unowned/dispatch-required | Не снимать ответственность молча при смене |
| Связать/создать меру | Уполномоченный владелец; action/owner и event refs | measure_id, execution open; review не переписывается | По потребности процесса; ложной тревоге мера может не требоваться |
| Сообщить выполнение | Исполнитель; open/in_progress | completion_reported, действие/основание, human origin | Не требует автоматического второго человека для мелких действий |
| Проверить меру | Verifier по policy; completion_reported и доступное основание | accepted либо rejected с причиной; rejected возвращает execution in_progress | Только для нужного класса; допустима policy not_required |
| Переоткрыть / исправить | Уполномоченный reviewer/owner; новая информация/повтор | Новая revision/event relation и audit; прошлый результат сохраняется; мера re-opened только при явном решении | Новое событие само не отменяет прошлую проверку |
| Изменить hazard/health | System/человек с evidence и scope | as_of/freshness; потеря наблюдения → unknown/stale, история сохраняется | Нельзя переводить absent только по таймауту без health |

Системная повторная отправка той же операции с request_id идемпотентна: это одна операция/попытка либо запись retry, а не новое независимое событие. Группировка новых реальных эпизодов — отдельная связь episode/group, не дедупликация по одному типу. По каким временным/track признакам эпизод заканчивается — ответ violation_methods, здесь не выдуман.

## Четыре отрицательных случая

| Сценарий CRITIC | Итог модели | Проверка непротиворечивости |
|---|---|---|
| False positive + auto-ACK | external_machine_ack=system, acceptance unaccepted; review=false_detection human; hazard unknown/отдельный факт; мера не обязательна | Нет human ACK и «устранено» из автоматики; неверное наблюдение сохранено |
| Два эпизода / одна системная мера | Два event_id с отдельными review/временами и одна measure.event_ids=[A,B]; при выполнении мера одна | Не удваивается число мер; новое C после меры — relation/review, не автоматическое доказательство провала или reopen |
| Смена при непринятой передаче | transfer_pending; старый owner/dispatch остаётся видим; новый не accepted до серверного действия; declined/ошибка канала не теряются | Assignment ≠ принятие. Если регламент автоматически передаёт сменную ответственность, audit system/policy, human ACK всё равно неизвестен |
| Новых событий нет из-за камеры | control_health unavailable; hazard stale/unknown; существующие review/меры прежние; missing interval отмечен | Ни «безопасно», ни «мера эффективна», ни закрытие по нулю тревог |

Поправка EXPERIENCE принята по [K007.md](../W2_EXPERIENCE/K007.md): W2-EXPERIENCE-S08/F12 (Intenseye Public APIv2) — документальное основание сохранять customer/vendor происхождение; F15 — авторский feedback contract. В нашей схеме `ReviewDecision` — отдельное исходное мнение с origin, не автоматический gold. `review_result` в оперативной карточке означает текущую принятую продуктовую оценку по policy и указывает decision_ref; при споре показывается disputed/unresolved, исходные мнения не затираются. Для curation отдельно `curated_review_result`, curator/basis/revision; это также проверяемая оценка, не безошибочная истина. `eligible_for_curation` и `approved_for_training` различны; ни одно не устанавливается кликом «ложная тревога». Такой словарь согласует оперативную карточку с dataset-процессом, не заставляя строить curation UI в минимуме.

W2-EXPERIENCE-F04 в [K005.md](../W2_EXPERIENCE/K005.md) ограничивает обязательность reviewer/свободного комментария каждого эпизода; F03 — ограниченные self-reports, не замер нагрузки и не visual audit. Поэтому обычная оценка может быть короткой, комментарий обязателен лишь по процедуре/спору. Review маскированного кадра при скрытом СИЗ может быть insufficient; original access/права проверяются отдельно по W2-EXPERIENCE-F11 [K006.md](../W2_EXPERIENCE/K006.md).

Терминология согласована с [PROCESS K011.md](../W2_PROCESS/K011.md), W2-PROCESS-F07 с его пределом нормативной проверки: UI «Эпизоды»/«Сигналы», «разбор завершён», «мера проверена». Техническое `incident_id` допускается только с внутренним смыслом. Видеонаблюдение — описание получения/просмотра изображения; оно само не означает производственный контроль, формальный инцидент, расследование или право вмешательства. Наблюдение/подтверждённый кадр не устанавливают вину, достаточность для взыскания или соблюдение российского регулируемого режима. Если кейс требует формального реестра/защитного контура, наша advisory-модель недостаточна и объём пересматривается.

## Что меняется и как опровергнуть

Убирается универсальная линейная карточка и обязательная проверка каждым вторым человеком. Достаточно отображать review+owner/acceptance+measure summary, остальные значения раскрывать по ситуации. Новая документация не доказывает пригодность этой модели для высокого потока; если walkthrough показывает лишнюю нагрузку, мера создаётся на группу/паттерн и отдельный verifier остаётся только по policy. Если регламент не требует индивидуальных acceptance для локального warning, поле остаётся not_used по маршруту, а не фиктивно accepted.

Открыто: роли и полномочия ХайТэк; какое внешнее состояние реально поставляется; hazard end/freshness semantics; требование двойного контроля/реоткрытия; серверная concurrency. Закрытие: получить конкретный пример payload+mapping и локальный регламент; предложенный tabletop/test — четыре строки выше плюс два одновременных изменения и offline ACK. Успех теста проверит контракт, не точность модели и не снижение травм.
