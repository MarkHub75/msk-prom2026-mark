## 3. H07: выбор объёма и порядок снятия рисков

### W1D-F08 — правило допуска функции [INFER/PROPOSED]

Основание: F01/F02/F04, соседние training_strategy:F282–F284, W1A:F08/F09. Сначала выделить обязательные требования и критерии, затем для каждого кандидата записать: пользовательский исход, проверяемый вход/выход, обязательность, владелец, внешние зависимости, статус данных/SDK, способ демонстрации, полный remaining path и последний полезный срок. Не пытаться угадать эффект функции по числу строк кода.

Кандидат допускается, если он закрывает обязательность/существенную проблему или добавляет понятное проверяемое улучшение, проходит наблюдаемость/данные/совместимость и ещё помещается во весь downstream путь. Если длительность неизвестна — сначала ограниченный диагностический прогон этого участка. Свободная GPU не заменяет времени инженера, который должен собрать и проверить результат.

Заимствованный символический тест: `now + CP_remaining <= D_useful`, где CP_remaining включает выбор/сохранение/чистую загрузку/экспорт/квантование/компиляцию/устройство/качество/ревью/интеграцию, а D_useful назначает принимающий владелец. Параллельные стадии нельзя суммировать дважды; очереди, переносы и возможный повтор нельзя забыть. Это правило управления, а не гарантия/измеренная продолжительность.

Необязательные расширения после работающего ядра: второе нарушение на той же сети/геометрии, минимальная версия настройки зоны, один ясный операторский фильтр. Дорогие расширения по умолчанию отложить до доказанного запаса: новая нейросеть, VLM/pose/re-ID каскад, переезд framework, распределённые сервисы, обучение с нуля, пользовательская авторизация нескольких ролей, полноценный промышленный SLA. Если полный кейс требует один из них, его нельзя тихо удалить: он становится основной веткой либо предметом согласования объёма.

Признаки к остановке: нет различимого сигнала на реальном входе; отсутствует разрешение/доступ; модель не проходит согласованный target-contract; изменение ухудшило обязательный endpoint; нет пригодной независимой проверки; оставшийся путь не помещается до D_useful. Исход остановки — сохранённый статус и восстановление полного предыдущего пакета, а не удаление следов неуспеха.

### W1D-F09 — минимальный сквозной срез [INFER/PROPOSED]

Основание F01/F04 и соседние video_architecture:F205/F215, evaluation:F014/F046, violation_methods:F102/F103. Минимум зависит от полного кейса; до него предлагается **одна разрешённая камера/видеозапись, один подтверждаемый обязательный сценарий, одна модель/цепочка LinQ, одно событие и одно действие оператора**. «Одна камера» — старт интеграции, не обещание выполнить заданную многопоточность.

Путь: выбранный видеоисточник → корректно декодированный кадр с происхождением/временем → согласованный preprocessor → фактический LinQ inference → декодированный ответ в исходной геометрии → одно явное правило события с неизвестным состоянием → журнал/карточка с доказательством и временем → понятный переход оператора к кадру/эпизоду. Для обязательного API последняя граница — проверяемый API response, для обязательного UI — реальный UI, для свободного интерфейса выбрать самое короткое понятное действие.

Есть два разных «готово». **Технический скелет** пересёк реальные внешние границы на простом разрешённом входе и имеет проверяемый запуск; он ещё не доказывает качество/полноту кейса. **Полезный вертикальный срез** даёт согласованный предметный результат и проверен хотя бы на разрешённых положительном/отрицательном/неопределённом случаях, с границами наблюдаемости и сохранённой lineage. Красивый UI на синтетических событиях может помочь независимой разработке, но не является ни предметным успехом, ни LinQ-доказательством.

Если разрешён только manual LinQ/job, минимальный путь может быть честно offline: загрузка короткого файла → LinQ job → события → просмотр. Это уже отличается от обещанного realtime; нужен ответ постановщика о допустимости и чёткий статус. CPU/RTX-only итог не закрывает обязательный LinQ.

У каждого принятого пакета должны совпадать веса, class-map, pre/postprocessing, правила, SDK/artifact revision и тестовые входы. Откат только `.pt` при старом decoder/новом class-map не восстанавливает принятую систему. Основание training_strategy:D15/F284.

### W1D-F10 — очередность снятия рисков [INFER/PROPOSED]

1. Право использовать данные/инструменты и формальные обязательности; точное значение «работает на LinQ» и требуемая семантика.
2. Доступ, достаточная наблюдаемость видео и контракт результата; параллельно, а не ждать всего SDK ради просмотра данных.
3. Один поддержанный целевой golden путь и сохранённое происхождение результата. Каталог/vendor sample может проверять доступ, но не доказывает совместимость нашего графа.
4. Сквозной пользовательский результат и негативный случай. Уточнить где ошибка: объект/владелец/правило/доставка; не отвечать новым обучением на любой дефект.
5. Только затем один ограниченный цикл улучшения данных/весов/порогов, пригодный к принятому full path.
6. Производительность/несколько камер в заданных условиях; оформление/переносимость и сдача идут с первого рабочего среза, а не начинаются после всей оптимизации.

Порядок зависит от фактического раннего барьера. Если выдана готовая модель, первый риск может быть decoder/пользовательский результат. Если нет метрики/смысла события, до больших обучений важнее постановщик. Не выполнять шесть пунктов как бюрократический последовательный waterfall.

### W1D-F13 — рабочий ритм и git [INFER/PROPOSED]

В первые2ч согласовать контракты/владельцев/первую границу интеграции. Далее короткая синхронизация примерно раз2–3ч бодрствования и при смене доступа: работающий результат, точный blocker, ближайшая передача, изменение объёма. Это ориентир, не обязательный ритуал и не исследованный оптимум. Во время активного инцидента созваниваются нужные два владельца; остальных не удерживать в общем звонке.

Небольшие ветки/коммиты на один переход, частый merge в общую рабочую ветку после короткого поведения smoke. Модель/данные и большие бинарники передавать manifest/hash/явным местом, не незаметным перезаписыванием файла. Подтягивание main без публикации своих изменений не даёт соседям интеграции. Смена schema/class order/preprocessor требует согласования всех потребителей и новой версии fixtures. Общий рабочий пакет помечать версией; экспериментальная ветка не заменяет его до принятия.

В первой дневной половине интеграционный запуск по ключевым границам важнее большой системы тестов. Достаточный smoke должен ловить реально дорогие ошибки: чистый запуск, положительный/пустой результат, правильный кадр/масштаб, ошибка платформы, отсутствие события, восстановление принятого пакета. Это не подтверждает статистическое качество или SLA.

Перед сном/сменой: текущая версия и статус, точная следующая команда/процедура из реального проекта, незавершённые jobs и их IDs, ограничение доступа, известная ошибка, сохранённый принятый пакет, кто вправе перезапустить. Не оставлять приватный доступ/единственный рабочий запуск только в памяти одного человека; секреты не выкладывать в публичный код.

## 5. Сон: что допустимо рекомендовать на основании источников

### W1D-F14 — отдых планируется как зависимость работы [INFER/PROPOSED]

F05/F06 поддерживают риск ухудшения когнитивной работы, но не оптимальную схему хакатона. Прямого сравнительного испытания ротаций пяти программистов на45ч не найдено. Ни «90-минутный цикл», ни «4ч хватит», ни «кофеин восстановит разработку» здесь не обоснованы. Лабораторное time in bed также не равно фактически полученному сну.

Практическая организационная политика: дать каждому нормальные непрерывные возможности сна обе ночи, согласованные с его привычным режимом и самочувствием; уменьшать объём, если он не помещается при отдыхе. Не строить основной план на работе без сна до защиты. Сложные необратимые действия/сдачу проверяют два бодрствующих участника. Если появились повторяющиеся пропуски шагов/потери контекста, передать критичный участок дублёру и пересмотреть ближайшую работу; не ставить диагноз.

**Пример ротации, а не научно доказанный/медицинский график:** при пригодном месте отдыха и выполненных ранних интеграционных точках P1/P3 используют окно23.10 23:00→24.10 07:00; P2/P4/P5 —24.10 01:00→09:00. Вторая ночь P1/P3 —24.10 21:00→25.10 05:00; P2/P4/P5 —24.10 23:00→25.10 07:00. Каждому выделено по8ч возможности сна на ночь; это иллюстрация ресурса, а не обещание полноценного восстановления.

Поздняя группа страхует раннюю до своего отхода, ранняя встречает её утром; overlap01:00–07:00 первой ночи и23:00–05:00 второй оставляется **без обязательного человеческого дежурства**. Такой план сознательно предполагает, что ночью можно остановить систему или оставить лишь согласованную безопасную автоматическую задачу. Не надо держать одного участника бессонным ради фиктивного24/7.

Если доступ к LinQ даётся единственным ночным слотом, поменять окно соответствующего владельца и дублёра, сохранив реальную возможность отдыха; при этом сократить дневные расширения. Если требуется постоянное присутствие/ручная очередь, этот пример неприменим: выяснить слот/очередь и назначить смены без последовательного удлинения бодрствования. Отдельно учесть дорогу, питание, бытовые паузы и защиту после10:00:45ч заканчиваются сдачей, а не ответственностью презентующего. Разница между окнами сна и фактическим отдыхом существенна; не вычитать225 человеко-часов как доступный coding budget.

Один ранний срез — порядок реализации, не самовольное исключение остальных|P5 немедленно согласует обязательность/градацию; P2/P1 ищут общее совместимое ядро, P3 не раздувает микросервисы|Отличать покрыто/частично/непроверено; нельзя назвать бинарный ответ полной типизацией. Если список не помещается — зафиксировать компромисс с постановщиком|
|B04 Есть свобода выбора нарушений|Выбрать наблюдаемый важный сценарий с доступными данными и минимальным новым NN-графом; второй только после acceptance первого|P2/P5 сравнивают важность/поддержку; P1/P3 делают одно ядро|Один законченный пользовательский исход с доказательствами; не заявлять поддержку всех примеров анонса|
|B05 LinQ стабилен, docs/sample доступны|Сразу пройти supported sample→наш golden→наш сценарий; после первого успеха сохранить lineage|P1 target, P2 contract/model, P3/P4 интегрируют согласованный выход|Фактический вывод+привязка к устройству+артефакту; наличие sample не доказывает нашу сеть|
|B06 Нет документации/ошибка импорта/доступ не выдан|Сузить neural route до минимального поддержанного варианта; запросить exact sample/versions/slot; остальное на fixtures|P1 ведёт один воспроизводимый blocker; P2/P3/P4 работают независимо, P5 эскалирует с формулировкой решения|Честный статус target-unverified; скрин ошибки/точный текст только в разрешённом порядке. CPU-only не становится LinQ fallback|
|B07 Доступ через очередь/jobs|Выяснить completion/result/лимиты/длину полного цикла; сделать один short offline путь до обещаний live|P1/P3 ведут request/job IDs и сбор результата; P5 согласует scope|Если цикл не поддерживает live cadence, показывать offline факт; не делать имитацию очереди доказательством real-time|
|B08 Есть native видео реального объекта|Сначала наблюдаемость/negative exposure/timebase/group split; выбрать видимые endpoints|P2/P5 label/GT, P3 decode/PTS/geometry, P4 кадр с доказательством|Результаты относятся к этим условиям; один объект/камера не устанавливает перенос на другие|
|B09 Нет реального видео / только donor images|Попросить разрешённые target clips/пример/стенд; не предполагать право самостоятельной съёмки|P5 решает доступ/разрешение, P2 выбирает лицензированный diagnostic материал, P3 делает разрешённый replay|Image demo подтверждает только соответствующий уровень; временные нарушения/FP-hour/реальный объект остаются неподтверждёнными. Генерация не заменяет независимую проверку|
|B10 Задан UI/API/интеграция|Первая проверка должна пройти заданную внешнюю границу и формат, даже с минимальным ответом|P4 ведёт UI либо contract-client, P3 обязательный API, P1 не меняет ответ отдельно|Запуск через требуемую границу, не произвольный красивый dashboard; внешний обязательный endpoint может стать самым ранним blocker|
|B11 Интерфейс свободен|Один путь «получить тревогу→увидеть доказательство/время/причину»; выбор простейшего доступного представления|P4 узкий интерфейс, P5 проверяет полезность/честность, освободившееся время — QA/переносимость|Без лишней авторизации/панелей; наличие UI не заменяет качество или доказательство LinQ|

**Правило композиции:** например B01+B03+B07+B08+B10 означает supplied scorer + все обязательные endpoints + job-service + реальные видео + обязательный API. Первое решение — точный API и совместимый baseline под scorer, параллельно измерить полный job-cycle; не выбирать произвольно только каску потому, что B04 был удобнее. Если B06+B09, главный результат первых2ч — не подготовленная демонстрация, а точный перечень недостающих входов/прав и подтверждённый план снятия каждого барьера.

## 8. Что остаётся неизвестным и что W2 действительно может закрыть

### W1D-Q01 [P0, ответ постановщика/полный кейс]

Какие endpoints и все ли NN-стадии обязательны на LinQ; допустим ли offline job, кто принимает доказательство фактического исполнения; как трактуется частичное покрытие длинного списка? Меняет B03/B05–B07, критический путь и размер ядра. Соседние linq_platform:Q005/Q021, violation_methods:Q001/Q005/Q006. Общий интернет не заменит текущий выданный контракт.

### W1D-Q02 [P0, организатор/ЛК]

Какие критерии/веса/формула действуют; что считается ненулевым CP; где именно CP2 черновики; точные слоты и формат финальных ссылок? Основание W1A-F05/F09–F13. Не обещать, что предложенные пакеты автоматически принимаются.

### W1D-Q03 [P0, организатор/постановщик]

Как разрешены screen recording LinQ-прогона, запись демо, публичные кадры/код, дополнительные target-съёмки, платные инструменты/облачные GPU и маркировка ИИ? Основание W1A-F14–F17. До ответа не превращать раннюю запись в обязательный шаг; использовать допустимый журнал и доступный прототип.

### W1D-Q04 [P0, actual access + диагностический прогон]

Сколько занимает полный useful-artifact path, какие реальные очереди/слоты/лимиты/права? Определяет D_useful и перемещение окон отдыха. Наши15:00/17:00/20:30 не являются платформенными нормативами. Закрыть малым первым прогоном с timestamps/статусами, без большого benchmark.

### W1D-Q05 [P1, команда после инвентаризации]

Какие реальные компетенции, место отдыха/дорога, личные режимы, роль презентующего и доступы? Определяет назначение P1–P5/дублёров и применимость приведённой ротации. Эти факты открытым поиском не получить; сейчас предложен адаптируемый пример, пользователь не опрашивался.

### Адресные задачи W2

1. **Если критик требует более сильный вывод о сне:** получить полный оригинал Van Dongen и/или Stepan из авторского/издательского источника, уточнить методы/возраст/группы/эффект и пределы; не искать «оптимальный45ч режим» по популярным блогам. Результат может усилить общий риск, но не легализует конкретную ротацию. Текущего abstract достаточно для осторожной организационной рекомендации; медицинская ветка не нужна.
2. **Проверить на опровержение границу «тонкого среза».** Есть ли в полном кейсе/официальном baseline обязательный end-to-end интерфейс, scorer, длинный перечень, multi-stream или on-device cascade, из-за которых выбранный один сценарий лишь этап, а не допустимый финал? Это важнее ещё десяти общих статей про MVP.
3. **Связать реальный доступ с адаптацией графика:** если в открытых материалах есть очередь/слот/длительность выдачи, получить первичный документ; иначе узко оставить Q04 постановщику. Не выводить точное время компиляции из рекламы FPS.
4. При необходимости получить оригинал PDF/визуально проверить спорные W1A пункты и границу записи; это задача W1A/W2 правил, не повтор всей темы D.

## 9. Адресные передачи

* **linq_platform:** нужен один документированный минимальный runnable path и две связи proof, достаточные для принятия заказчиком; deadline-часть определяется downstream, не обычной скоростью сети. Режимы B05–B07. Не просить команду останавливать общий accelerator вне выданных прав.
* **video_architecture:** P1–P4 нужны общие fixtures positive/empty/error/late-old-epoch и одинаковый кадр/геометрия; для недоступного LinQ frontend не должен блокироваться. Mock/replay получает явный статус. Не строить production topology ради слова «сквозной».
* **evaluation:** P5 должен принять объект/человека/эпизод/доставку отдельно; нехватка GT/timebase/negative exposure превращается в ограничение заявления, а не в красивый общий процент. Помочь выбрать smallest meaningful acceptance corpus, без выдуманного универсального размера.
* **datasets/violation_methods:** первые20мин intake должны обнаружить semantic trap «снятый» и реальные cue pixels; отсутствие обязательного сигнала немедленно меняет B03/B08/B09 и вопрос постановщику.
* **training_strategy/model_stack:** D_useful модели раньше feature freeze; принимает полный immutable bundle, не только checkpoint. Измерять время всех стадий и человеческих передач. Поздний новый граф, который нельзя проверить на LinQ, не вытесняет принятый вариант.
* **operator_product:** минимальный outcome оператора нужен для выбора интерфейса, но не должен придумывать обязательный workflow. Нужны роль/действие после тревоги и доказательство; реалистичность продукта не означает измеренную безопасность.
* **W1A/W1F:** график привязан к трёмCP и прожарке, но записи и платные инструменты условны. После10:00 есть защита, поэтому сон/репетиция не обрываются дедлайном кода.
