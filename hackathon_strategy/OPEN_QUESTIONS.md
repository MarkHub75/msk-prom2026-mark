После двух волн,23.10.2026 Europe/Moscow. Это подготовленный банк, вопросы внешним лицам не отправлялись, ответы не получены. Все E001–E010 **proposed / не выполнены**. ## Предлагаемые процедуры

<a id="e001"></a>
### E001 — Один завершённый mapped LinQ run

**Статус: proposed; не выполнено.**
**Вопрос/решение:** Получен ли связанный actual run и подтверждена ли его target-граница? Это первый access milestone, не качество или полнота кейса.


Сначала получить от постановщика границу обязательной NN-части и допустимый witness. Параллельно выполнить один безопасный доступный пример на выданном пути и сразу сохранить связанное свидетельство. Такой sample run проверяет доступ; если используется чужая catalog/sample model, он ещё не доказывает перенос собственной модели или выполнение полного кейса.

Минимальная запись одного запуска содержит четыре группы:

1. **Вход.** Сохранённый разрешённый input или стабильный ID+hash/версия; для видео — конкретный clip/frame/range, фактически поданный модели. Важно различить исходное видео и tensor после preprocessing. Если tensor недоступен, записать выданную preprocessing revision; не придумывать его bytes.
2. **Модель.** Exact доступная identity: свои weights/export/program hash либо server deployment/model revision/catalog version. Человеческое имя «YOLOv8» слишком широко. При opaque service запросить у платформы стабильную revision; пока её нет — отметить невозможность связать результат с версией.
3. **Завершение и выход.** Command/request/job ID, итоговый completion/status и сохранённый соответствующий output; время/контекст запуска. Submit/HTTP ACK/queued — не completion. При timeout outcome unknown до штатного status lookup; не считать его автоматически failure и не плодить слепые retries.
4. **Target mapping/witness.** Документированный серверный mapping конкретного запроса/задания/загруженной revision на LinQ, либо наблюдение уполномоченного инженера по согласованной с постановщиком процедуре. Записать автора/роль, дату, какие именно input/revision/run он удостоверяет, и какое заявление разрешено. Надпись `backend=LinQ` в нашем UI сама по себе это звено не создаёт.

| Выданный режим | Что реально сохранять первым | Что закрывает target mapping | Если недоступны внутренности |
|---|---|---|---|

При заявлении «вся NN исполняется на LinQ» отдельно нужен scope: какая NN-часть обязана быть на ускорителе, что происходит с decode/pre/post/NMS/tracking/вторичными сетями и fallback. Полная compiler coverage полезна, если доступна; она не требуется к первому connectivity smoke автоматически. Но без неё/документированного гаранта нельзя расширять утверждение «этот принятый target run» до «каждый узел всего приложения аппаратно доказан».

## Что не должно блокировать первую интеграцию

**По возможности**, а не как выдуманное правило конкурса: compiler/runtime version, target ID, compile report, loaded artifact hash, firmware, profiler trace, device timers, clock/temperature/power и no-fallback semantics. Запрашивать релевантный документ сразу, но не тратить остаток 45 часов на поля, которых managed interface конструктивно не выдаёт. Критическое обязательное по постановке — actual inference; способ его подтверждения пока отдельный P0unknown.

**Отдельная проверка качества**: known input и осмысленный output проверяют smoke correctness этого примера. Нужны labels/официальный evaluator или frozen diagnostic set, чтобы заявлять измеренное качество. Один run не даёт accuracy/recall.

**Отдельная проверка производительности**: latency/throughput/concurrency/camera load требуют серии completions, границ измерения, counts/errors/drops и версии. Первая минимальная запись не обязана включать p95, многокамерный stress или CPU/GPU comparison. У чужих опубликованных чисел другой target, workload и контекст.

После первого успеха сохранить snapshot доступным разрешённым способом. Собственная видеозапись/публичная публикация требуют разъяснения K003; сам по себе proof-протокол не разрешает снимать/публиковать чужие кадры. При сбое доступа сохранять действительную последнюю verified revision и статус. Если успешного LinQ run не было, local demo/negative report не переименовывать в выполнение обязательного условия.



Входы: выданный доступ, matching docs/sample, разрешённый input, точная model/deployment revision. Артефакт: один manifest/ledger с request/job ID, completion, output и mapping/witness. Submit/queued не успех; timeout остаётся unknown до status lookup. Успех каталожной модели проверяет только catalog path. Достаточность для зачёта определяет постановщик.
